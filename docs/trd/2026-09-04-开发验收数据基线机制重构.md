## 实现摘要

本设计选择以下结构：

1. 在大需求拆分能力中，条件性建立一个具有独立交付结果的“开发验收数据与交付恢复”正式需求，或识别已经完整承担该结果的既有正式需求；
2. 该正式需求进入现有 Backlog、需求注册表和逐需求开发生命周期，因此不会只因某次开发遗漏而完全消失；
3. 在开发执行能力中，负责实现、维护和真实验证当前项目的 Seed/fixture、数据库外必要持久化资源、交付开发账号和使用说明；
4. 基线正式建立后，后续新增或改变其必要数据的需求同步维护既有实现和文档；
5. 不新增独立 Seed Skill，不新增流程节点，不修改任何 completed、continue、blocked 条件、decision system prompt、Python verifier 或状态结构；
6. Seed 机制的最终设计净增量只保留本文、两个现有 Skills 及各自 eval 的必要修改；纠正提交同时撤销 `8c32365` 的其它内容，并保留 `83b13ef` 已建立的 README 稳定入口合同。Skill 正文不点名任何其它自定义 Skill。

该选择利用已有正式需求生命周期保证“这项工作一定存在”，再利用开发执行和项目自动化测试保证“这项工作真正完成”。它不依赖 Agent 使用固定回复格式，也不通过增加模型返工阀门换取表面确定性。

## 需求定位

### 要解决的问题

当前工作流对交付开发账号、Seed/reset 幂等、真实登录和开发数据已有要求，但真实产品仍出现：

- 不同业务需求各自创建局部数据，最终没有覆盖全产品主要任务的统一恢复入口；
- 有的需求更新 Seed，有的只在当前数据库手工留数据；
- 数据库记录依赖对象存储文件时，只恢复数据库，文件没有恢复；
- README 或账号文档没有清楚说明恢复、启动、登录和重新复位方式；
- Seed 命令存在，但没有从专用空环境或可重建环境实际验证完整产品；
- 数据脚本、当前数据库现场和交付文档互相漂移。

问题的本质不是缺少更多原则，而是缺少两个清楚责任：

1. **存在性责任**：谁保证完整基线工作一定进入正式开发范围；
2. **执行责任**：谁负责把恢复实现、数据、对象资源、文档和真实验收一起做完。

### 用户和使用场景

该能力直接服务：

- 接收目标产品源代码和开发资源后，需要自行启动、登录并验收产品的客户或接手者；
- 需要稳定恢复开发环境、复验功能和继续后续开发的维护者；
- 需要使用可复位数据执行真实浏览器任务的产品验收人员。

首次成功结果不是“Seed 脚本退出码为 0”，而是：

> 接手者按照受跟踪说明，在项目专用开发或验收环境中完成迁移和数据恢复，启动真实服务，使用交付开发账号从正常入口登录，并能看到、操作和复验主要已交付功能所需的代表性数据与对象资源。

### 真实产品证据

#### Tailisle

Tailisle 已形成独立的固定基线、版本化规格、受保护 reset、完整性检查和验收 runner。这证明复杂跨角色产品的完整数据恢复本身可以形成独立、可验收的交付结果，而不是分散附着于每个业务需求。

同时，其运行基线和部分 README 曾出现版本漂移，说明“存在脚本”不足以证明交付完成，必须把恢复入口、文档和实际执行一起验收。

#### MealFlow

MealFlow 具有范围较完整的非破坏 Seed、稳定 ownership、漂移拒绝、六类开发账号和真实浏览器验收；完整恢复采用重建专用数据库后迁移并重新 Seed，而不是原地清库。

其真实 MinIO 生命周期由动态验收创建，稳定 Seed 不恢复对象资产。这证明：

- 不应强制 destructive reset；
- 数据库恢复与对象存储恢复必须按产品需求显式判断；
- 有对象存储运行能力不等于已经具备对象资源基线。

#### MendMark

MendMark 目前存在首个管理员初始化、目录 Seed、账号说明和测试库保护，但尚未形成覆盖完整产品的统一恢复入口。媒体能力正在演进，也尚未形成稳定对象资源恢复合同。

这证明只让每个业务需求自行留下局部数据，不能自然收敛为完整交付基线。

## 方案比较与裁决

### 方案 A：只修改开发执行能力

做法：只增加一段 Seed、对象资源和 README 维护要求。

优点：

- 修改范围最小；
- 不改变流程和 Backlog；
- 不新增能力或协议。

缺点：

- 每次开发只处理当前需求，没有一个需求负责最终跨模块整合；
- 当前需求可能合理判断与 Seed 无关；
- 所有需求结束后仍可能只有若干局部数据和手工现场；
- 无法保证完整恢复、账号、对象资源和交付文档一定有人统一验收。

裁决：不采用。它可以承担执行责任，但不能承担存在性责任。

### 方案 B：修改多个现有 Skills 形成纵向合同

做法：在产品定义、需求拆分、TRD、开发、审计等多个能力中分别增加基线规则。

优点：

- 每个环节都能感知基线；
- 理论上覆盖完整流程。

缺点：

- 同一政策重复维护；
- 容易出现 Skill 间点名、隐含上游和职责耦合；
- 简单需求也会持续处理同一概念；
- 文本越多，漂移和模型误解越多；
- 已由 `8c32365` 证明改动规模和成本过高。

裁决：不采用。该方案缺少最小性，并违反独立性方向。

### 方案 C：新增独立 Seed/基线 Skill

做法：新增一个专门能力，负责发现、创建、恢复和验证完整基线。

优点：

- 领域职责集中；
- 可以单独处理数据库、对象存储和文档；
- 将来可发展为独立版本化和恢复工具。

缺点：

- 与现有开发执行能力在代码、测试、服务、浏览器和文档修改上高度重叠；
- 要稳定进入自动化流程，仍需新增调度节点或修改现有流程；
- 基线发生需求级变化时，需要在两个实现能力之间协调；
- 当前真实项目数量和复杂度尚不足以证明独立能力的维护收益高于成本。

裁决：当前不采用。只有达到本文“重新讨论条件”时再考虑。

### 方案 D：正式需求锚点 + 开发执行合同

做法：

- 大需求拆分时，在适用项目中创建或确认一个正式的完整基线需求；
- 该需求由现有生命周期确定性选择、开发和完成；
- 开发执行能力负责实现、测试、文档和真实验收；
- 基线完成后的相关增量由当前业务需求同步维护。

优点：

- 正式需求解决存在性责任；
- 开发执行解决实现责任；
- 复用现有需求注册表，不新增流程节点和状态；
- 不修改完成阀门，不要求固定 Agent 回复格式；
- 不新增与开发执行重复的能力；
- 只需修改两个 Skills 及其 eval；
- 与 Tailisle 和 MealFlow 已存在的独立基线需求实践一致。

代价：

- 适用性判断必须准确，避免给简单项目机械增加需求；
- 完整基线需求通常较靠后，早期开发仍需局部账号和数据支持；
- 基线完成后的新需求必须识别是否需要同步维护。

裁决：采用。

### 成本、耗时与保证边界

适用项目会新增或确认一个正式需求，并完整经历设计、实现、验证、提交和合并，因此会增加一次需求循环的模型与执行成本。这不是通过固定回复格式制造的重复返工，而是完成跨角色、跨模块、跨存储恢复和客户交接本身所需的真实工作；若没有这次统一收口，成本只会分散为后续手工补数据、排查文档漂移和重复验收。

成本控制方式：

- 无持久化、空态优先、单一角色且只有少量参考数据并已由现有需求完整覆盖，或其它已有需求已经完整覆盖的项目不新增需求；
- 早期业务需求只维护自身完成所需的最小数据，不重复执行全产品恢复；
- 完整恢复和主要任务验收集中在一个正式需求中；
- 基线建立后的普通需求不机械复验全量，只在确实使基线失效时同步维护；
- 不增加每个需求的 decision 轮次、固定报告格式或程序化完成阀门。

在当前架构下，本方案能保证的是：一旦大需求拆分按合同完成，适用的基线工作会作为正式需求进入需求注册表，并受现有 pending/active/completed 生命周期约束，不能在仍为 pending 时被正常阶段一完成跳过；项目级恢复实现、自动化测试和真实验收再证明结果。它不声称从数学上消除模型违反 Skill 的可能性，防线来自针对性 eval、正常设计审查和现有需求生命周期，而不是继续堆叠 system prompt 条件。

## 目标行为设计

### 1. 正式基线需求的适用性

满足以下任一情况时，Backlog 必须包含一个明确承担完整恢复和交付验收结果的正式需求；已有正式需求完整覆盖时复用，不重复创建：

- 产品使用持久化数据，且主要功能不能仅依靠一个用户从空态自然、低成本地建立全部必要状态；
- 存在多个需要交付和核验的产品内角色或权限范围；
- 核心体验依赖待处理、处理中、已完成、冲突、历史记录等难以临时手工构造的代表性状态；
- 多个业务模块的数据和关系需要同时成立，才能体验主要闭环；
- 数据库记录依赖对象存储、搜索索引或其它持久化介质中的必要内容；
- 接手者若没有预置或可恢复数据，就无法合理完成主要功能验收；
- 项目已有多套零散 Seed、fixture、脚本或账号说明，需要统一收口。

以下情况不机械创建：

- 无持久化数据的纯工具或库；
- 产品核心价值就是从明确、可用的空态创建首个对象，后续主要状态可由正常任务低成本产生；
- 只有单一角色、少量参考数据，且已有身份或基础需求已经完整覆盖初始化、文档和验收；
- 纯内部重构、依赖升级或不改变数据交付的增量范围。

不适用不等于不验证空态、首次身份和持久化，只表示无需额外建立跨需求完整基线需求。

### 2. 正式需求的产品结果

推荐使用业务可理解的标题，例如：

- 开发验收数据与交付恢复
- 可复位的完整产品验收环境
- 交付开发账号与完整体验数据

标题不固定，也不使用“写 Seed 脚本”“初始化数据库”“上传 MinIO 文件”等技术任务名称。

目标结果至少表达：

> 接手者可以依据受跟踪说明，在项目专用环境中建立或恢复完整验收状态，使用产品内开发账号从正常入口登录，查看必要的代表性数据和对象资源，并自主完成主要已交付功能。

### 3. 需求范围

正式需求按项目事实包含：

- 产品内交付开发账号、角色、权限关系和必要已有数据；
- 必要参考数据、代表性业务对象、关键状态和历史关系；
- 数据库之外为主要功能所必需的文件或其它持久化内容；
- 项目已有恢复、重建、初始化或核验入口的统一收口；
- README 或项目既有受跟踪交付文档；
- 重复执行、管理范围保护、失败恢复和数据一致性测试；
- 从专用空环境、可重建环境或明确受控现场执行的真实恢复；
- 逐角色登录、数据可见性、关键允许/拒绝行为和主要任务验收。

不包含：

- 生产数据、真实个人数据或生产发布准备；
- 外部系统访问凭据的公开交接；
- 为所有测试场景永久保留数据；
- 与产品主要功能无关的大量装饰性样例；
- 强制统一命令、目录、Manifest、数据库或对象存储技术；
- 默认提供破坏性清库能力。

### 4. 需求依赖和顺序

完整基线需求通常位于阶段一后段，并只依赖那些在开始本需求前确实必须完成、且会决定基线内容或恢复方式的正式需求，例如：

- 身份与权限；
- 主要业务对象和状态流转；
- 文件或媒体能力；
- 影响完整恢复的异步处理或治理能力。

不为顺序整齐机械依赖所有需求。纯 UI 文案、与基线无关的内部优化等不自动成为前置依赖。

若一个早期验证切片必须使用真实身份和少量数据，相关早期需求仍负责满足自身完成所需的最小初始化；这不等于提前完成全产品基线。

### 5. 早期数据与最终基线的关系

阶段一前中期允许存在：

- 隔离测试 fixture；
- 当前需求的临时测试数据；
- 为真实开发验收创建的少量账号和业务记录；
- 某个业务模块自己的初始化入口。

这些内容只有在完整基线需求中被明确选用、统一恢复、形成受跟踪说明并通过完整验证后，才成为最终交付基线的一部分。

完整基线需求应：

1. 读取并核对已有脚本、测试数据、开发账号、当前数据库和文档；
2. 选择一个项目内权威恢复入口，复用有效内容而不是另建平行实现；
3. 删除或停止依赖仅存在于个人环境、一次性命令或 Agent 上下文中的隐含步骤；
4. 补齐跨模块和跨持久化介质的一致性；
5. 从受控起点实际重建并执行主要任务。

### 6. 基线完成后的增量维护

完整基线已经建立后，后续需求出现以下变化时，当前需求同步维护既有基线和交付说明：

- 新增或改变需要交付的产品内角色和权限；
- 新增主要任务所需的参考数据、代表性对象、状态或关系；
- 新增必须随恢复建立的文件或其它持久化内容；
- 改变现有恢复命令、迁移顺序、启动入口或账号登录方式；
- 使现有代表性数据无法继续体验受影响主要任务；
- 使当前说明、账号或恢复测试失效。

以下变化通常不要求更新：

- 不影响数据语义和主要任务的纯视觉调整；
- 纯内部重构且现有恢复测试仍通过；
- 只服务当次测试、不会交付保留的临时状态；
- 可以通过现有代表性数据完整验收的新只读表现。

## 开发执行合同

开发执行能力在任何项目中独立判断当前需求和现有工程事实，不引用其它自定义 Skill 名称、固定上游、流程阶段或节点。

### 当前需求是完整基线需求时

应完成：

1. 识别项目已有迁移、Seed、fixture、账号、对象资源、启动说明和测试；
2. 依据完整产品范围确定必要的角色、参考数据、代表性对象、状态、关系和历史；
3. 选择并维护项目内单一权威恢复方式；
4. 对数据库和适用的其它持久化介质进行联合恢复和核验；
5. 形成接手者可执行的 README 或既有交付说明；
6. 实际从受控起点执行恢复；
7. 再次执行，验证幂等或等价重复执行保护；
8. 启动真实服务，从正常入口逐角色登录并完成代表性主要任务；
9. 通过刷新、重新进入、接口或数据状态确认持久化；
10. 运行与恢复、管理范围和跨存储一致性相关的自动化测试。

### 当前需求是后续数据增量时

若项目已有完整基线，并且当前需求改变其必要内容，应更新现有恢复实现、数据、对象资源、文档和测试。不得为当前需求创建另一套平行 Seed 或仅在当前数据库手工补数据。

### 当前需求不影响基线时

正常完成需求，不机械修改 Seed、README 或数据恢复测试，也不要求在最终回复中输出固定状态字段。

## 数据与持久化

### 1. 数据库

项目可以采用任意适合自身技术栈的初始化和恢复方式，但必须满足：

- 重复执行不产生无界重复数据；
- 不覆盖或删除管理范围外的数据；
- 使用稳定业务标识或等价方式关联必要记录；
- 迁移与数据恢复顺序清楚；
- 失败时不把部分完成误报为成功；
- 时间敏感数据在恢复后仍具有业务意义。

### 2. 数据库之外的持久化内容

只有主要功能确实依赖时才纳入，例如图片、附件、文档或派生索引。应验证：

- 内容真实存在并可由产品正常路径读取；
- 数据库记录与存储内容关联一致；
- 重复恢复不会无界创建副本；
- 清理和覆盖只作用于明确管理范围；
- 部分失败具有可恢复或可重新执行路径；
- 不把第三方临时 URL 当作长期依赖。

不规定具体对象存储产品、CLI、bucket 结构、对象 key 或内容清单格式。

### 3. 恢复模式

项目按事实选择一种或多种：

- 非破坏性补齐或初始化；
- 重建项目专用数据库或环境后重新初始化；
- 独立完整性核验；
- 对明确可丢弃环境执行受保护重置。

没有原地 destructive reset 不构成缺陷。存在破坏性能力时，必须具有环境、目标、范围和确认保护，但本文不统一具体实现。

## 交付文档合同

项目 README 或既有受跟踪交付文档至少使接手者能够确定：

- 适用的开发或验收环境；
- 需要先准备的数据库和其它服务；
- 迁移、恢复或重建入口；
- 恢复操作会创建、覆盖或删除什么；
- 产品内开发账号文档和登录入口；
- 已有代表性数据支持哪些主要任务；
- 如何判断恢复成功；
- 如何再次恢复或复验；
- 哪些外部凭据仍只存在于受保护配置中。

不要求固定章节标题、固定命令名称或固定文档路径。账号单独成文时，必须能从主要运行说明中找到。

## 接口与外部协作

本设计不新增程序接口、状态字段、结果 schema 或 Agent 回复格式。

已有模型裁决继续根据 Agent 的自然语言完整回复判断：

- Agent 明确报告未完成、失败或验证缺口时继续；
- Agent 明确报告不可替代外部条件缺失时阻塞；
- Agent 没有报告缺口时，信任其已经按照当前需求和开发能力完成。

稳定保证来自：

- 正式需求存在于需求注册表；
- 需求未完成时生命周期不会结束；
- 项目自身恢复实现和自动化测试；
- 实际开发环境与浏览器验收。

不来自固定四态、关键词解析或追加 system prompt 门槛。

## 权限、安全与异常处理

### 安全边界

- 只操作项目专用、已授权且范围清楚的开发或验收资源；
- 不伪造外部账号、服务或凭据；
- 不公开数据库、对象存储、SMTP、OAuth、API Key 或基础设施凭据；
- 产品内交付开发账号按项目现有规则进入受跟踪账号文档；
- 不使用生产数据或真实个人数据；
- 破坏性恢复必须失败关闭，不能根据模糊名称猜测目标；
- 不清理或覆盖未知数据和对象。

### 失败场景

| 场景 | 处理 |
|---|---|
| 只有测试 fixture，没有开发环境恢复入口 | 基线需求未完成，建立项目实际恢复方式并验证 |
| 数据库恢复成功，对象文件缺失 | 基线需求未完成，补齐联合恢复或明确该对象不属于交付范围 |
| README 命令失效 | 修正文档或实现，并从受控起点重新执行 |
| 重复执行产生重复数据 | 修复稳定标识、幂等或重建策略后重验 |
| 现有数据与预期冲突 | 不静默接管，报告冲突并采用项目安全策略 |
| 缺少不可替代外部资源 | 保留真实阻塞和解除条件，不用 Mock 冒充 |
| 产品本应验证空态 | 保留空态首个成功路径，不用丰富 Seed 遮蔽 |
| 后续需求使基线过期 | 当前需求同步更新既有基线和交付说明 |

## 风险与重新讨论条件

### 风险

1. **基线需求过大**：通过只覆盖主要任务所需代表性数据、避免永久保留全部状态来控制。
2. **简单项目被机械加需求**：通过明确无持久化、空态优先、单一角色且少量参考数据已由现有需求完整覆盖等不适用条件控制；单一角色但无法从空态合理验收或存在零散恢复资产时仍适用。
3. **基线需求过晚影响早期开发**：早期需求继续维护自身完成所需最小账号和数据，最终需求负责全量收口。
4. **后续需求忘记维护**：开发执行能力在已有基线时检查当前需求是否使其失效；同时由项目恢复和回归测试暴露漂移。
5. **对象存储增加复杂度**：只有主要功能确实依赖时纳入，不因服务存在就自动加入。
6. **没有程序化阀门是否不够可靠**：正式需求生命周期保证工作存在，项目自动化和真实验收保证结果；增加自然语言格式阀门只会提高返工成本，不能替代真实证据。

### 重新讨论条件

只有出现以下事实时，才重新评估新增独立基线 Skill 或流程节点：

- 多个项目都需要同一套复杂、跨数据库、对象存储、搜索索引和外部沙箱的恢复编排；
- 基线拥有独立版本、升级、回滚和兼容生命周期，已明显超出单个正式需求的上下文；
- 基线需要被开发、CI、预览环境、人工 QA 和客户验收以统一接口长期调用；
- 需求完成后频繁需要独立 reconciliation，放在开发执行能力中已造成重复或职责冲突；
- PCM 已实现明确的项目最终收口节点，并有真实证据证明从 Backlog 正式需求迁移到该节点能降低复杂度；
- 两个目标 Skills 无法在不互相点名的前提下可靠表达各自职责。

在这些条件出现前，不因单次质疑或偏好变化改换架构。
