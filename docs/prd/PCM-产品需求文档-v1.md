## 1. 产品是什么

PCM 是一个开源、本地运行的 AI 自动化产品开发工作台。用户通过对话提供想法和已有资料，PCM 将这些内容整理成最终 PRD；用户确认后发起自动开发，获得经过开发和验证的前后端项目代码与配套文档，并能通过后续反馈继续迭代。

| 标识 | 内容 |
|---|---|
| 品牌名 | PCM |
| 英文名称 | PCM（Project Customization & Management） |
| 功能副标题 | AI 自动化产品开发工作台 |
| 工程标识 | `pcm`，用于后续目标工作区命名，不代表已经创建仓库，也不决定前后端工程各自的仓库名 |
| 产品 ID | `PCM-20261010-012` |
| 首版运行环境 | macOS，本地启动，通过浏览器使用工作台 |
| 发布方向 | 开源，当前没有商业化计划 |
| 本次开发交付 | 工作台前端、业务与生产后端、配套文档与真实验证结果 |
| PCM 运行产出 | 所生成目标项目的代码、文档和真实验证结果 |

先定义 PCM 的能力和使用体验，再通过真实使用观察它吸引哪些人。独立开发者、小型团队中的产品经理和有产品想法的非技术使用者都是可能的使用者，不以其中一种身份预先裁剪产品。

产品价值是减少从想法、需求到可运行项目之间的人工调度，而不是增加需要用户操作的管理步骤。用户负责表达产品意图、提供必要资源与授权；PCM 负责组织设计、开发、验证和改进。

## 2. 首版组成与范围依据

### 2.1 两个独立工程

| 工程 | 技术约束 | 产品职责 |
|---|---|---|
| Web 工作台 | Next.js，独立前端项目 | 产品讨论、配置、项目管理、执行控制、进度与成果查看、反馈提交 |
| 业务与生产后端 | Python + FastAPI，独立后端项目 | 业务数据、配置与凭据处理、生产任务管理，以及现有 PCM 自动化能力的服务化接入 |

两个工程共同服务同一条用户使用路径，按工作区约定分别放在 `frontend/`、`backend/` 并作为独立 Git 仓库管理，根仓库管理文档与协作资料。当前能力仓库仍是生产工具与流程工作区，`pcm-demo` 是正式产品的实现基础，不等同于已经建成的正式后端。

上述技术栈约束针对 PCM 自身。PCM 生成的目标项目沿用现有流程依据需求和基础工程选择技术方案，不由 PCM 工作台自身的框架强行决定。

### 2.2 范围确定原则

首版以当前 `pcm-demo` 已有生产能力为核心，补齐通过 Web 工作台正常使用这些能力所必需的业务处理。新增的对话式 PRD 整理、配置界面、任务展示和已确认的执行控制围绕这一核心工作。

首版管理 PCM 创建的项目及其后续迭代。代码与文档交付到经过真实验证、可以按说明接手运行的程度；生产部署不属于本轮交付范围。

自动化是默认行为。用户可以选择暂停，但普通设计、开发和验证不增加常规人工审批。运行期间的需求修改与新增意见统一进入第三阶段反馈迭代；补齐当前执行缺少的外部资源或授权仍按阻塞恢复处理。

### 2.3 已有基础与正式产品新增部分

| 项目 | 核验到的 Demo 事实 | 正式产品要求 |
|---|---|---|
| 阶段衔接 | 默认执行第一阶段，已有参数可串联第二阶段 | 工作台的一次默认开发连续执行第一、第二阶段 |
| 配置入口 | 文件、环境变量和 CLI；部分必要路径和模型策略没有可用默认值 | 工作台承接全部必要配置，提供经核验的默认值与可用性检查 |
| 暂停与停止 | 已有单步执行及进程信号转发基础 | 新增真正的节点后暂停、暂停请求状态与工作台控制，不把单步执行冒充已完成的暂停能力 |
| 本地预览 | 已有产品运行端点与浏览器验收约定 | 在实际可用时提供入口并展示状态 |
| 反馈启动 | 来源需为符合完成条件的质量或反馈执行 | 依据真实条件开放第三阶段入口，不能跳过完成约束 |
| 远程同步 | 新产品默认启用 GitLab 同步，缺少相应授权会阻塞 | 本地交付即可完成；GitLab 同步由用户通过工作台配置并选择启用 |

**GitLab 远程同步是可选能力。** 本地 Git 的分支、提交和合并管理保持不变。未启用远程同步时，不要求 GitLab 账号、组地址、令牌或远程 SSH 权限，也不因缺少这些条件阻塞开发、质量改进、反馈迭代或本地交付。

用户选择启用 GitLab 同步后，工作台检查相应资源与权限，并沿用已有远程同步和失败恢复规则。同步失败必须如实展示，保留已完成的本地成果，不能静默降级为未启用或把失败显示为同步成功。

## 3. 完整使用过程

1. **启动与配置**：用户在 macOS 启动 PCM，打开工作台，填写必要信息并完成可用性检查。
2. **创建项目与讨论**：用户输入想法并提供已有 PRD 或其他资料，在同一对话中逐步明确产品。
3. **形成并确认 PRD**：PCM 整理当前有效的 PRD；用户通过讨论修正，并明确确认开发范围。
4. **检查开发条件**：PCM 核对当前项目所需的环境与资源。能自动处理的自行处理，需要用户提供的在工作台说明并收集。
5. **启动自动开发**：条件满足后，用户一次启动，默认连续执行第一阶段开发和第二阶段质量改进。
6. **按需控制执行**：用户可以预设暂停点、运行中请求暂停、继续或立即停止。
7. **取得本轮成果**：本轮正常完成后，用户查看代码位置、文档、真实验证结果和适用的本地预览入口。
8. **提交反馈继续迭代**：用户使用成果后提交一批反馈，发起第三阶段，在原项目上增量修改。

“一键开发”表示在需求与必要条件明确后，一次启动完整自动化流程，不表示可以忽略真实资源缺口或承诺任意输入都必然成功。

## 4. 工作台功能

### 4.1 使用配置

**硬性要求：用户不需要编辑任何代码或配置文件，仅通过工作台填写必要信息即可正常使用。** 程序可以生成和维护底层配置，但不能将修改 `.env`、JSON、TOML、Python 文件或运行状态文件作为正常操作步骤。

配置按用途出现：

- **全局必要信息**：模型服务、开发 Agent 执行所需的连接信息与凭据，以及本地工作区等现有运行条件。
- **可默认的信息**：已有执行策略、运行参数和合理的本地目录采用默认值；确有调整需要时提供工作台入口。
- **项目特有资源**：依据当前项目的真实需要检查和收集，不要求用户首次启动就准备所有潜在第三方服务。

普通模型调用与开发 Agent 执行在 Demo 中是不同通道，产品化时应解释用途并承接实际配置，不能把界面上的一个模型输入框误当作已满足全部执行条件。开发任务还依赖有效的模型策略，现有实现没有默认模型兜底；正式产品需提供与用户所配服务相容的策略准备和检查路径，不能要求用户手写模型策略文件，也不能用未经核验的模型名称伪造可用默认值。

默认开发资源的交付责任：

- **PCM 提供或自动准备**：流程、Skills、必要规则、默认基础工程及对应资源目录。用户无需自行编写模板目录或配置模板路径，就能开始第一个项目。
- **用户按需提供**：自己的模型服务连接信息与凭据，以及具体项目确实需要的外部资源。必要输入均通过工作台收集；已有执行策略和可默认的内部参数由产品处理。
- **资源分别管理**：工作区工具配置与生成产品自身的运行资源按用途区分。程序负责组织底层配置和资源清单，不把内部文件格式交给用户维护。
- **开源交付独立可用**：默认资源的获取与使用不依赖作者本机路径或私有环境；内部凭据和私有配置不随产品分发。

GitLab 为可选配置，仅在用户选择启用远程同步时检查其必需条件，具体规则见第 2.3 节。

必要行为：

1. 表单使用能理解的名称、用途说明和输入示例，不把环境变量名作为唯一解释。
2. 用户保存后能检查相关连接、权限或本地条件，区分保存成功与实际可用。
3. 检查失败时保留输入并说明具体缺口，允许修改后重新检查。
4. 配置在正常重启后保留，后续修改仍通过工作台完成。
5. 凭据按敏感信息保存与展示，不能进入生成项目的公开代码、普通日志或公开文档。
6. 缺少作者本机才有的目录、资源或配置时，工作台必须给出实际可执行的准备路径，不能以内部环境已经具备代替首次使用准备。

技术设计需明确配置修改对当前任务和后续任务的生效时机，避免正在执行的任务被无提示地切换连接或运行参数。

### 4.2 项目管理

项目是产品讨论、PRD、生成工作区和后续迭代的统一入口。一个项目下可以先后执行首次开发、质量改进和反馈迭代，不能把每轮执行都呈现成一个无关的新项目。

首版需要：

- 创建项目并进入讨论。
- 查看项目列表，识别项目名称、当前阶段和实际状态。
- 重新进入项目，查看当前 PRD、生产任务和成果。
- 沿用 Demo 的不同项目并发、同一项目互斥规则；重复点击或多个页面操作不能重复启动同一项目的冲突任务。
- 达到本机执行容量时，明确提示当前限制与可采取的操作，不静默丢弃启动请求。

项目列表服务于继续工作，不以虚构的业务量、完成率或预估进度填充界面。

### 4.3 对话与最终 PRD

创建项目后直接进入同一讨论过程，不强制用户先选择“只有想法”或“已有文档”模式。

用户可以描述目标、提供已有 PRD 和参考资料，并补充或修改产品方向。PCM 应吸收已经明确的信息，只针对影响产品成立或开发范围的重要缺口继续讨论。

建议的交互规则：

- 对话与当前 PRD 可以同时查看；用户不需要从聊天记录自行归纳最终结论。
- 整理形成一份当前有效的 PRD，将明确要求与尚未决定的事项区分开。
- 用户提出修改后，PCM 更新当前 PRD，并使用户能理解当前开发范围。
- 讨论与必要文档持久保存，重新打开项目后可以继续。
- 上传或读取资料失败时明确说明，不把未成功读取的材料当作已经纳入需求。
- 普通讨论不启动编码；用户明确确认当前 PRD 并发起开发后，才进入生产流程。

当前 PRD 是本次开发的输入依据。运行期间不通过聊天悄悄改变已启动的范围，后续产品意见按第三阶段处理。

首版的产品讨论、参考资料和第三阶段反馈统一采用以下输入范围：

| 内容 | 输入方式 |
|---|---|
| 想法、补充说明、反馈正文 | 直接输入或粘贴文本 |
| PRD、文字参考资料 | Markdown（`.md`）和纯文本（`.txt`）文件 |
| 界面参考、问题截图 | PNG、JPEG、WebP 图片 |

受支持的文字和图片应实际提供给 Agent 理解，而不只是保存附件。格式不支持、内容不可读或超出限制时明确提示，不将未成功读取的材料视为已理解。文件大小限制与实际读取方式由技术设计在上述范围内落实。

### 4.4 自动开发与质量改进

一次默认开发连续覆盖：

1. **第一阶段**：沿用现有产品定义、工程准备、设计、需求拆解、逐需求开发、验证及成果整理流程。
2. **第二阶段**：沿用现有产品质量检查、候选取舍、增量改进和相关回归流程。

工作台确认的 PRD 需与后续流程正确交接，避免用户已经确认的范围被当作新的空白构思重新定义。具体输入映射由技术设计依据现有流程落实。

第一阶段完成不代表本次“一键开发”已完成。第二阶段正常结束后，才能显示本轮开发完成；失败、阻塞或尚未完成的必要验证必须如实呈现。

质量阶段沿用 Demo 当前的处理边界，由现有规则形成并完成本批改进，不将连续执行解释为无休止的自动审计。

工作台默认展示：

- 当前阶段、流程环节和正在处理的需求。
- 已经完成的实际成果。
- 是否等待暂停、已经暂停，或因什么条件不能继续。
- 本轮真实执行输出、错误与适用的验证结果入口。

详细诊断按需查看。阶段与需求状态来自实际执行记录，不根据耗时臆造百分比；程序启动、模型返回或代码提交本身均不能替代开发完成判断。

### 4.5 暂停、继续与立即停止

| 操作或状态 | 产品语义 |
|---|---|
| 预设暂停点 | 用户在启动前选择完成哪些实际流程环节后暂停；运行中可调整尚未到达的暂停点 |
| 请求暂停 | 运行中提出请求，当前环节继续到约定边界后暂停；期间显示“正在执行，已收到暂停请求” |
| 已暂停 | 已到达暂停边界，后续环节未开始；展示当前位置和当前成果 |
| 继续 | 从已经确认的暂停位置继续原有流程，不重新创建项目或重复执行已完成内容 |
| 立即停止 | 请求终止当前执行，适用于必须尽快停止的情况；在执行确实停止前如实显示处理中状态 |
| 停止后恢复 | 检查真实现场，接入可用的恢复路径；不能承诺任何中断都能从原指令位置无损续接 |

可选暂停点对应真实流程环节，界面使用业务名称，不要求用户记内部步骤编号。正常暂停与立即停止是不同语义，不共用模糊的完成提示。

暂停只是执行控制，不代表用户必须验收，也不是编辑本轮需求的入口。开发验证责任仍由 PCM 承担。

控制操作只能影响当前项目中归属明确的执行及其子进程，不误停其他项目或用户自行启动的服务。

### 4.6 成果查看

成果页让用户知道得到了什么、在哪里、如何接手使用，至少提供：

- 当前产品 PRD 与实际生成的相关文档。
- 代码工作区和适用独立仓库的位置。
- 已完成内容、实际验证结果及仍存在的限制。
- 目标项目的本地运行说明。
- 已有可访问的本地页面或原型的入口。

本地预览入口应反映实际可用状态；服务未启动或已退出时说明原因，不把失效链接呈现为在线成果。预览不等同于生产部署。

文档可以在工作台阅读，代码仍保存在实际本地工作区。已有成果在失败或停止后仍应可辨认，但不能把局部产物标记为完整交付。

### 4.7 第三阶段反馈迭代

用户在既有流程允许的完成状态下提交一批反馈并发起第三阶段。输入可以包含问题描述、新增想法和辅助资料，格式遵循第 4.3 节的统一输入范围。

PCM 根据当前项目代码、文档和现场核验反馈，沿用既有候选处理、需求化、增量开发和验证规则。普通内部取舍由 AI 负责人处理，不再增加一轮常规人工审批。

本轮结果说明实际处理了哪些内容、哪些未纳入及必要原因，以及对应验证结果。未纳入的反馈不能被静默当作已经实现。

反馈迭代修改同一个项目，不通过重新生成一套项目替代增量开发。后续新反馈由用户再次发起，不常驻等待下一批输入。

## 5. 长任务与恢复体验

浏览器页面和生产任务具有不同生命周期。用户关闭页面或刷新，不应终止已经启动的后台开发；重新打开时应能查看真实状态。

PCM 退出、进程异常或电脑重启时，需要根据实际执行和持久化事实识别中断：

- 不能仅凭旧状态记录继续显示“运行中”。
- 保留已生成的工作区、文档和必要的运行事实。
- 依据现有恢复能力判断能从哪里继续，并通过工作台提供对应操作。
- 外部资源缺失与执行错误应分别说明；前者补齐条件，后者展示错误及适用恢复路径。
- 恢复入口所需的用户输入通过工作台接收，不能要求用户手动创建恢复指令文件或编辑内部状态。
- 无法继续时如实说明当前原因，不以重新建项目掩盖恢复失败。

这里要求的是准确的状态与可用恢复路径，不将浏览器重连、后台重启和任意命令断点续执行混为同一种能力。

## 6. 本地使用与安全要求

首版允许用户按说明在终端执行少量安装和启动命令。工作台启动后，配置、项目创建、开发控制、资源补齐和反馈迭代等正常操作全部通过界面完成。安装说明需明确必要依赖并经过真实验证，不能要求用户自行猜测路径或修改代码与配置文件才能启动。

- 首版按 macOS 本地使用交付：PCM 直接在本机启动，自动开发的 Agent、命令、Git 和浏览器均在本机原生执行，正常使用不依赖 Docker。执行采用与本机开发工具相同的信任边界，保留访问、凭据、项目权限、并发及归属管理，不承诺抵御任意脚本、派生进程、网络或插件主动绕过的操作系统级强沙箱。默认访问范围应与本机工作台一致，避免将具备命令执行能力的接口无保护地暴露给其他设备。
- 本地运行不等于离线运行。模型连接配置与相关使用说明应解释：调用远程服务时，相关输入、项目资料或执行内容可能发送给所配置的服务。
- 开源产品与模型服务的获取条件分别说明，不能暗示外部模型调用天然免费或无需账号。
- 外部凭据保持本地受保护存储，界面脱敏，不进入源码仓库、公开内容或普通执行输出。
- Agent 的文件读写、命令执行和资源使用遵循明确工作区及已有授权范围。自动化程度不扩大授权范围。
- 界面应让用户识别提交的是想法、PRD、外部资源还是第三阶段反馈，避免把普通资料误用为执行控制指令。
- 生产任务、成果目录和控制行为按项目隔离；并发情况下仍需保护同一项目免于冲突操作。

首版以本地使用者管理项目为使用基础，小型团队成员可以使用它，不据此引入独立的组织与成员协作流程。

## 7. 完整交付要求

本文全部功能共同构成工作台与生产后端的交付范围，开发完成应同时满足：

- 在 macOS 上按说明启动正式前后端，通过工作台完成必要配置，默认流程能力与基础工程可随附或自动准备。
- 从想法和资料形成 PRD，一次启动连续执行开发与质量改进，展示真实进展、异常、代码与文档成果。
- 完成暂停点、暂停请求、继续、立即停止、中断识别和适用恢复操作。
- 支持多个项目及已有并发与互斥规则，并在原项目上完成第三阶段反馈迭代。
- 配置修改、资源补齐和正常生产操作均通过工作台完成。
- 提供与实际实现一致的 macOS 安装、启动、配置和使用说明，并在新环境验证首次使用路径。
- 未配置 GitLab 时也能按本地交付标准完成；启用时验证真实同步与失败恢复。

完成标准是工作台、后端与实际生产流程的集成结果，不以页面可点击、接口返回成功或独立模块通过测试代替。验证应覆盖真实项目的首次开发、暂停恢复和反馈修改，不能把修复环境缺口或重复技术验收交给用户。

GitHub 是 PCM 自身开源仓库的候选发布平台，具体地址与项目自身的开源许可证在发布前确定。源码发布安排与用户生成项目的可选 GitLab 同步分别管理。

## 8. 首版验收场景

验收由开发 Agent 在真实环境完成，用户对产品意图和范围作决定，不承担重复技术验收职责。

| 场景 | 必须观察到的结果 |
|---|---|
| 首次使用 | 在声明支持的 macOS 环境中，按说明执行少量安装和启动命令即可打开工作台，之后仅通过界面完成必要配置与正常使用，全程不修改代码或配置文件 |
| 默认开发资源 | 新环境能取得随附或自动准备的流程能力与默认基础工程；用户不编写模板目录或配置模板路径，交付包不含内部凭据与私有配置 |
| 配置错误与修正 | 真实不可用连接或缺失权限得到可理解提示，修正并重新检查后能继续 |
| 想法与资料共同输入 | 已提供的信息被吸收，重要缺口通过对话澄清，形成可查看并确认的当前 PRD |
| 文字与图片资料 | Markdown、纯文本及 PNG、JPEG、WebP 图片内容实际交给 Agent 理解；不支持、不可读或超限时准确提示，反馈附件遵循同一规则 |
| 一次完整开发 | 一次启动连续完成第一、第二阶段，结束状态和代码、文档、验证结果一致 |
| 纯本地交付 | 未配置 GitLab 时，开发、质量改进和反馈迭代均能按本地交付标准完成，本地 Git 管理正常工作 |
| 可选 GitLab 同步 | 用户通过工作台配置并启用后能完成真实同步；权限缺失或推送失败得到准确提示，保留本地成果并能按已有规则恢复 |
| 页面关闭与重新进入 | 关闭页面不终止后台任务，重新进入能显示实际状态 |
| 节点后暂停 | 不设置暂停点时连续推进；设置后在对应环节结束时暂停，后续环节未提前执行 |
| 运行中请求暂停 | 请求后明确显示等待状态，到达边界后才显示已暂停，继续后正确接续 |
| 立即停止与现场核验 | 状态与进程真实一致，不误停其他项目；恢复前检查现场，不虚报无损续接 |
| 资源阻塞 | 能在工作台理解并补齐真实缺口，通过现有规则继续执行 |
| 后台异常中断 | 不以陈旧记录冒充正在运行或完成，提供实际可用的恢复说明和操作 |
| 多项目与重复启动 | 不同项目按实际容量运行，同项目冲突请求受到控制，不重复启动生产任务 |
| 反馈迭代 | 使用一批真实反馈在原项目上增量修改，结果说明处理范围并提供相关验证 |
| 成果接手 | 代码与文档真实存在，说明与实际运行方式一致，预览入口状态准确 |
| 凭据与本地访问 | 凭据保持脱敏和受保护存储，正常产物及普通日志中没有实际秘密，执行接口不意外开放 |
| 安装与使用说明 | 文档内容与真实能力一致，在新环境按说明完成安装启动和工作台配置，并能执行首次生产 |

涉及界面的场景使用真实浏览器检查操作、状态、内容理解和实际渲染；生产能力使用真实模型、运行环境及适用服务验证。局部模拟测试可以辅助排错，不能替代关键完整场景。

不在缺少代表性数据时承诺生成成功率或固定完成时长。当前首先判断完整路径是否成立、失败能否准确解释、已有成果是否可继续使用。

## 9. 后续设计需核验的具体条件

以下是落实已确认范围时需要完成的技术核验与发布准备，不重新开放功能范围。技术事项依据已有实现和真实验证落实；项目自身的开源许可证与实际发布地址在发布前确定。

| 事项 | 需要明确什么 |
|---|---|
| macOS 支持矩阵与安装验证 | 在已确认的终端安装启动方式下，明确实际支持的系统版本、芯片架构、必要依赖和具体命令；“支持 macOS”本身不能冒充所有组合均已验证 |
| 输入资料处理 | 在第 4.3 节已确认的格式范围内，明确文件大小限制、文字读取与图片传递方式、失败提示，并验证资料实际到达 Agent |
| 默认资源与配置接入 | 按第 4.1 节已确认的交付责任，落实默认资源清单、随附或自动准备方式、实际用户必填项与检查路径，并在新环境验证 |
| 长任务与执行控制 | 如何将现有流程接入后台任务，以及节点后暂停、立即停止、进程退出和真实恢复之间的合同 |
| 前后端工程接入 | 按根文档仓、`frontend/` 工作台仓和 `backend/` 后端仓落实目录、基础工程选型及 Demo 能力迁移 |
| 开源发布材料 | 确定项目自身的开源许可证、实际源码位置和不含私密配置的可用交付内容 |
