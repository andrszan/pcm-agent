### A.1 产品决策摘要

食序围绕“库存—菜单—采购—烹饪—复盘”构建闭环。用户不需要为了使用系统精确记录每一克食材，而是以适合日常生活的数量、状态和保质期信息管理家庭库存；在安排周菜单时，系统依据库存判断食材是否充足，并把缺少部分汇总成共享购物清单。完成采购或烹饪后，库存随业务动作更新，用户能够看到食材如何被消耗，也能逐渐沉淀家庭偏好。

首版不以营养诊断、自动生成完美菜单或连接智能冰箱为目标。产品特色来自三个可稳定实现的联动体验：临期食材优先利用、菜单与库存的即时核对、多人采购清单协作。没有外部 AI、支付、地图或硬件接入时，产品仍能完成全部核心流程。

### A.2 关键假设

- 一个账号可以创建一个家庭空间，也可以受邀加入其他家庭空间；用户每次操作都处于明确的当前家庭空间。
- 家庭食材数量允许使用“个、盒、袋、克、毫升”等常见单位；首版不强求跨单位自动换算。
- 菜谱用量用于判断“充足、可能不足、缺少”，结果是生活计划辅助，不代表精密计量。
- 公共菜谱由运营人员维护并允许用户复制为家庭菜谱；家庭菜谱默认仅家庭成员可见。
- 提醒以站内通知为基础，邮件为可选增强；不依赖短信和移动端推送。
- 产品使用自身业务数据、预置种子菜谱和合理模拟内容，不依赖外部菜谱平台。

## B. 产品概述

很多家庭同时存在三类信息断裂：冰箱里已有的食材没人说得清，一周菜单只停留在临时讨论，实际采购又分散在纸条和聊天消息中。结果是临时决定吃什么、重复购买、忘记使用临期食材，或买回原料后缺少完整搭配。

食序把这些动作放进同一个家庭空间。成员先用低负担方式记录现有食材，再从公共菜谱或家庭菜谱中选择本周餐食。系统核对每道菜的用料，把短缺项合并成共享购物清单；采购者在清单中勾选和登记入库，烹饪者完成菜品后确认消耗。整个过程保留清晰状态和操作记录，但不要求用户进行专业仓储式管理。

产品最吸引人的部分不是食材列表本身，而是跨页面联动：在菜谱详情中能立即看到“家里有多少、还缺什么”；把菜品加入周菜单后，采购清单随人数和份数变化；临期食材会出现在今日概览和适配菜谱入口中。用户完成一次周计划后，得到的是一份可执行菜单、一份可协作采购清单和更清楚的家庭库存。

## C. 用户与使用场景

### C.1 家庭创建者

家庭创建者通常是最先建立家庭空间的人，目标是邀请同住成员、设置基本偏好并建立可共同使用的库存。其主要任务包括创建空间、邀请或移除成员、设置成员权限、维护家庭标签与默认用餐人数，以及查看空间级操作记录。

典型场景是情侣、合租室友或家庭中的主要规划者在周末创建下周菜单，并把采购任务分给不同成员。家庭创建者不是系统管理员，不可查看其他家庭的数据。

### C.2 家庭成员

家庭成员是主要最终用户，目标是快速了解家中食材、参与菜单安排、领取采购项并完成烹饪记录。成员可以录入采购、更新食材数量、标记临期或耗尽、创建家庭菜谱、编辑周菜单、操作购物清单和确认烹饪消耗。

典型场景包括下班前查看购物清单、在超市勾选已购食材、回家后登记入库；做饭前查看某道菜是否缺料；发现牛奶即将过期时，通过临期入口寻找可使用它的菜谱。

### C.3 访客成员

访客成员适用于临时共同生活或只参与采购的人。访客可查看当前家庭的周菜单和共享购物清单，可领取和勾选采购项，但不能删除库存、管理成员或修改家庭设置。家庭创建者可以随时撤销其访问权。

### C.4 内容运营人员

内容运营人员维护公共食材分类、常用单位、公共菜谱、主题合集和举报处理，确保新用户打开产品时有足够内容可浏览。其不参与家庭内部业务，也不能查看家庭私有库存、菜单和购物明细。

### C.5 平台管理员

平台管理员负责账号异常处理、运营人员权限、公共配置、内容审核策略和必要的审计查询。平台管理员只在处理明确的安全或合规事件时接触受限业务信息，且操作需要留痕。

## D. 核心价值与业务闭环

### D.1 用户获得的具体结果

完成主流程后，家庭成员应获得四项明确结果：知道家中关键食材的状态；形成一份按日期和餐次安排的周菜单；得到去重合并、可分工的购物清单；在采购与烹饪后留下正确的新库存和家庭偏好记录。

### D.2 端到端主流程

1. 家庭创建者建立家庭空间，选择默认用餐人数，邀请至少一位成员，或选择单人使用。
2. 成员通过快速录入或从常用食材中添加库存，填写数量、单位、存放位置和可选保质期。
3. 成员浏览菜谱，在详情页查看现有食材覆盖情况，将菜品加入某天某餐，并确认份数。
4. 系统按周菜单汇总用料，扣除可用库存后生成短缺建议。用户确认后，短缺项进入共享购物清单。
5. 成员领取采购项、调整数量、勾选已购；完成采购时可将已购项批量登记入库。
6. 烹饪者打开当餐计划，确认实际制作的菜品和份数；系统展示预计扣减项，用户确认或修改后完成扣减。
7. 家庭概览更新库存、临期提醒、菜单完成状态和本周减少浪费的记录；用户可给菜品标记“常做、一般、不再推荐”。

### D.3 关键分支

- 库存不足但用户暂不采购：允许保留短缺提示，或把菜品替换为库存覆盖更高的候选菜谱。
- 同一食材在多个菜谱中使用：购物清单按标准食材合并，保留展开后的来源菜品。
- 用户实际采购数量与计划不同：以实际录入数量入库，清单记录计划量与实际量。
- 用户未按计划烹饪：餐次可标记“跳过”或“改期”，不会自动扣减库存。
- 食材没有精确数量：可使用“少量、约半份、充足”等模糊库存状态；此类食材只给出提示，不自动执行精确扣减。
- 临期食材已经处理但没有烹饪记录：允许标记为已用完、丢弃或信息有误，并记录原因。

### D.4 完成条件

一轮周计划在以下条件下视为形成闭环：至少一个餐次已安排菜品；相关短缺项已确认或明确忽略；至少一个采购项完成或被取消；至少一个餐次完成、跳过或改期；库存根据真实动作更新。系统不得仅凭日期到达自动判定食材已采购或已消耗。

## E. 产品范围

### E.1 当前必须实现

- 账号注册、登录、退出和基础个人资料。
- 家庭空间创建、切换、邀请、成员角色与访问撤销。
- 食材库存录入、编辑、批量处理、分类、位置、保质期和状态管理。
- 公共菜谱浏览、家庭菜谱创建、菜谱复制、用料和步骤维护。
- 一周菜单按日期与餐次安排、调整份数、复制餐次和状态管理。
- 菜谱用料与家庭库存覆盖核对。
- 从周菜单生成短缺建议并确认到购物清单。
- 购物清单合并、分组、领取、勾选、取消及批量入库。
- 烹饪完成确认、预计库存扣减、人工修正和操作记录。
- 临期提醒、低库存提示和基于规则的临期食材菜谱匹配。
- 站内通知、全局搜索中的必要范围、空状态与异常反馈。
- 公共内容、分类和举报处理所需的运营后台。
- 可直接演示的账号、公共菜谱、家庭库存、周菜单和历史记录种子数据。

### E.2 重要增强

- 家庭常购清单与历史采购模板。
- 菜谱收藏、家庭评分和“不再推荐”偏好。
- 邮件提醒开关与提醒摘要。
- 菜谱导入辅助：用户粘贴文本后识别候选标题、食材和步骤，必须由用户确认。
- 购物清单打印视图和简洁移动购物模式。
- 周菜单复制到下一周，以及按家庭偏好进行规则排序。

### E.3 未来扩展

- 多语言家庭与单位换算增强。
- 自愿记录的预算和价格趋势。
- 与合规智能家居设备进行库存同步。
- 更丰富的饮食偏好与营养信息展示。
- 可选的自然语言菜单草案辅助。

### E.4 明确不做

- 不接入真实支付、外卖下单或超市结算。
- 不提供医疗、疾病治疗、过敏诊断或个体营养处方。
- 不要求智能冰箱、电子秤、条码枪等特殊硬件。
- 不建设公开社交广场、即时群聊或陌生人交易。
- 不从受限平台批量抓取菜谱，不使用来源不明的图片和文字。
- 不在用户未确认的情况下自动扣减库存、自动替换菜单或自动创建采购订单。
- 不追求精密仓储、财务核算或供应链管理能力。

## F. 信息架构与页面地图

### F.1 家庭成员使用端

主导航采用“今日、食材、菜单、菜谱、采购”五个一级入口，家庭空间切换与通知位于全局区域，个人设置位于账号菜单。

| 页面 | 层级 | 主要职责 |
|---|---|---|
| 今日概览 | 核心 | 展示今日餐次、临期食材、待采购项、成员动态和快捷动作 |
| 家庭食材 | 核心 | 按位置、分类和状态查看库存，支持快速录入与批量处理 |
| 食材详情 | 核心详情 | 展示数量批次、保质期、使用记录、适配菜谱和编辑入口 |
| 周菜单 | 核心 | 按七天和餐次安排菜品、份数、负责人和完成状态 |
| 餐次详情 | 核心详情 | 查看菜品、用料覆盖、准备事项、短缺项和烹饪确认 |
| 菜谱库 | 核心 | 浏览公共与家庭菜谱，按时间、标签和库存覆盖筛选 |
| 菜谱详情 | 核心详情 | 展示成品、用料覆盖、步骤、份数调整和加入菜单入口 |
| 购物清单 | 核心 | 汇总短缺、分配采购、勾选、取消并批量登记入库 |
| 烹饪确认 | 关键流程 | 核对实际份数和库存扣减，处理缺失或替代食材 |
| 通知中心 | 辅助 | 查看邀请、任务、临期、菜单变化和异常提醒 |
| 家庭设置 | 辅助 | 管理成员、权限、默认人数、餐次和家庭偏好 |
| 个人设置 | 辅助 | 管理资料、通知偏好、常用单位和账号安全 |

### F.2 内容运营后台

后台主导航包括概览、公共菜谱、食材与单位、主题合集、举报与审核、用户异常和审计记录。后台不展示家庭私有业务看板，不以家庭消费行为作为运营排行榜。

## G. 功能需求

### G.1 家庭空间与成员协作

**用户目的：** 建立数据隔离清楚、成员职责明确的共同空间。

**角色：** 家庭创建者、家庭成员、访客成员。

**触发与前置条件：** 已登录用户首次进入时可创建家庭空间；收到有效邀请的用户可加入。一个邀请必须关联目标家庭、预设角色和有效期。

**输入：** 家庭名称、默认用餐人数、常用餐次、邀请对象、成员角色。

**业务规则：**

- 家庭创建者至少保留一人；转让创建者身份后方可退出。
- 普通成员可编辑业务数据但不可管理成员；访客只可查看菜单与操作购物清单。
- 邀请过期、撤销或达到预设使用次数后不可继续加入。
- 切换家庭空间后，页面数据、搜索范围和通知上下文必须同步切换。
- 移除成员不删除其历史操作记录，但其后续访问立即失效。

**输出与成功状态：** 用户进入家庭概览，看到当前家庭名称、角色、成员和初始化引导。

**空状态：** 新家庭展示三步引导：添加常用食材、选择菜谱、安排第一餐。

**异常状态：** 邀请无效时说明具体原因并提供返回入口；创建者转让失败时不得改变现有权限。

**数据变化：** 创建家庭、成员关系、邀请记录、角色变更和审计记录。

**验收标准：** 不同家庭之间数据完全隔离；角色变更即时生效；无权限用户无法通过页面入口或直接地址执行受限操作。

### G.2 食材库存管理

**用户目的：** 用足够轻量的方式知道家中有哪些食材、存在哪里、何时需要优先使用。

**角色：** 家庭创建者、家庭成员；访客只读。

**触发与前置条件：** 用户处于有效家庭空间。

**输入：** 食材名称或标准食材、数量、单位、模糊数量状态、存放位置、购入日期、保质日期、备注、图片。

**业务规则：**

- 同一标准食材可存在多个批次，批次按保质日期分别记录。
- 用户可选择精确数量或模糊状态，两者至少填写一种。
- 保质日期未知时允许留空，但不进入临期倒计时。
- 同食材、同单位、同位置且保质日期一致时，新增记录可提示合并，不强制合并。
- 数量减至零后状态变为“已用完”，记录保留在历史中；用户可撤销最近一次误操作。
- 删除仅适用于误录且未被菜单、采购或消耗记录引用的数据；已有引用时改为停用或归档。

**输出与成功状态：** 库存卡显示数量、位置、保质状态和最近变动；总览同步更新临期与低库存提示。

**空状态：** 根据厨房常见分类提供快速添加入口，不显示虚假库存统计。

**异常状态：** 非法数量、单位缺失、日期冲突或并发修改时给出字段级说明；并发冲突不得静默覆盖。

**数据变化：** 食材批次、库存汇总、库存流水和操作人记录。

**验收标准：** 新增、编辑、消耗、丢弃、撤销和归档均产生正确库存结果；批次顺序和临期状态可复核；无编辑权限的用户不能改变库存。

### G.3 菜谱与家庭内容

**用户目的：** 找到可执行的菜谱，并清楚判断家中是否有足够食材。

**角色：** 所有家庭成员可浏览；家庭创建者与成员可创建家庭菜谱；运营人员管理公共菜谱。

**输入：** 标题、封面、简介、预计用时、默认份数、食材及用量、步骤、标签、可选替代食材、可见范围。

**业务规则：**

- 公共菜谱只由运营人员发布；用户可复制后修改为家庭菜谱，原内容不被反向改变。
- 至少包含一道步骤和一种食材方可发布为可用菜谱。
- 调整份数时按比例显示建议用量，但允许用户逐项修正。
- 库存覆盖分为“充足、可能不足、缺少、无法判断”；无法判断通常由单位不兼容或模糊数量导致。
- 替代食材只作建议，加入菜单时需用户确认采用哪一种。
- 被周菜单引用的家庭菜谱允许继续编辑，但历史餐次保留当时快照，避免内容变化影响已完成记录。

**输出与成功状态：** 菜谱详情展示用料覆盖条、缺少项、步骤和加入菜单入口。

**空状态：** 无搜索结果时展示清除筛选、创建家庭菜谱和查看主题合集三个动作。

**异常状态：** 图片上传失败不阻止保存文本草稿；内容发布失败时保留未提交编辑内容。

**数据变化：** 菜谱、菜谱版本、食材用量、标签、收藏和家庭偏好。

**验收标准：** 份数调整、库存覆盖和历史快照结果正确；公共与家庭内容权限边界清楚；菜谱在无图片时仍可正常阅读。

### G.4 一周菜单

**用户目的：** 把想吃的菜安排到明确日期和餐次，并让全家看到同一计划。

**角色：** 家庭创建者与成员可编辑；访客可查看。

**触发与前置条件：** 家庭已设置餐次，至少存在一个可用菜谱。

**输入：** 日期、餐次、菜谱、份数、计划负责人、备注。

**业务规则：**

- 一份周菜单以家庭本地周起始日为边界，可查看历史周和未来周。
- 同一餐次可安排多道菜；每道菜拥有独立份数和状态。
- 状态包括“已计划、准备中、已完成、已跳过、已改期”。
- 调整菜品或份数后，系统重新计算短缺建议，但不得直接改变已确认购物项；需提示用户同步差异。
- 复制上一周时只复制计划，不复制完成状态、负责人和采购结果。
- 已完成餐次不能直接删除，需撤销完成后再编辑，确保库存流水可回滚。

**输出与成功状态：** 周菜单呈现每日餐次、菜品、份数、覆盖状态和负责人；改动形成家庭动态。

**空状态：** 提供“从菜谱加入”“复制上一周”和“按临期食材找菜”三种起点。

**异常状态：** 菜谱已停用时保留历史卡片并提示替换；多人同时编辑时提示刷新差异。

**数据变化：** 周计划、餐次、计划菜品、状态历史和菜谱快照。

**验收标准：** 增删改、份数调整、复制、改期和状态流转正确；菜单变化与短缺差异提示一致；历史周保持可查。

### G.5 短缺建议与购物清单

**用户目的：** 把菜单中真正缺少的食材整理成一份去重、可分工、能反馈入库的清单。

**角色：** 家庭创建者、家庭成员、访客成员。

**触发与前置条件：** 周菜单至少包含一项未完成菜品；菜谱拥有用料信息。

**输入：** 目标周、纳入的餐次、库存扣减假设、确认数量、采购负责人、分组与备注。

**业务规则：**

- 系统先按标准食材和兼容单位汇总需求，再与可用库存比较，输出短缺建议。
- 不兼容单位不得强行相减，标记为“需确认”。
- 用户确认后才创建购物项；每项保留来自哪些菜品的可展开来源。
- 相同食材的手工购物项与菜单短缺项可提示合并，用户决定是否合并。
- 购物项状态包括“待购买、已领取、已购买、已取消、已入库”。
- 一个待购买项同一时间最多由一名成员领取；领取人可释放任务。
- 标记已购买时允许填写实际数量、单位和保质日期；批量入库后状态改为已入库。
- 菜单变化产生差异时，已购买项不被删除，只提示需求变化。

**输出与成功状态：** 用户获得按分类分组的共享清单，能看到计划量、负责人、来源和完成进度。

**空状态：** 若库存已覆盖全部菜单，明确显示“本周计划暂时不缺食材”，并允许添加日用品式手工项，但不把它们纳入菜谱覆盖。

**异常状态：** 重复提交、领取冲突或入库失败时保持原状态并给出重试动作；不得出现清单已完成但库存未更新的半成功状态。

**数据变化：** 短缺计算快照、购物清单、购物项、领取记录、状态历史和入库流水。

**验收标准：** 多菜谱同食材正确合并；来源可追溯；领取冲突被阻止；已购物批量入库后库存与清单状态一致。

### G.6 烹饪确认与库存扣减

**用户目的：** 在真正做完一餐后，用可控方式更新库存，而不是依赖系统猜测。

**角色：** 家庭创建者、家庭成员。

**触发与前置条件：** 餐次处于已计划或准备中，至少有一道有效菜品。

**输入：** 实际制作菜品、实际份数、采用的替代食材、每项实际消耗、备注。

**业务规则：**

- 系统基于菜谱快照和份数生成预计扣减预览，用户确认后才执行。
- 有多个批次时默认优先建议扣减保质期更早的批次，用户可改选。
- 库存不足时允许将剩余数量扣至零，并记录未覆盖部分；不得产生负库存。
- 模糊库存只允许用户选择“减少一些、用完、不变”，不生成伪精确数值。
- 确认完成后，菜单状态与库存流水在同一业务结果中更新；任一失败均不得部分成功。
- 允许在规定时间内撤销最近一次完成，撤销会恢复库存并记录原因。

**输出与成功状态：** 餐次显示已完成，库存更新，今日概览和临期提醒重新计算。

**空状态：** 无可扣减库存时仍允许记录餐次完成，但明确标记“本次未更新库存”。

**异常状态：** 批次已被其他成员修改时，要求重新核对最新库存；撤销失败不得改变原流水。

**数据变化：** 消耗记录、库存流水、菜单状态、家庭偏好和操作历史。

**验收标准：** 预计扣减、实际修正、批次选择、零库存保护、完成与撤销均可复核；同一餐次不能重复扣减。

### G.7 今日概览与提醒

**用户目的：** 打开产品后快速知道今天要做什么，以及哪些食材需要优先处理。

**角色：** 所有家庭角色，内容按权限裁剪。

**输入：** 无主动输入；用户可完成快捷动作或调整提醒偏好。

**业务规则：**

- 今日概览优先级依次为：今日餐次、临期食材、待处理采购、成员变更和一般建议。
- 临期阈值按食材类别默认值与用户设置计算；标签必须显示具体剩余天数或日期。
- 低库存提示仅针对用户设定了常备阈值的食材，不对所有库存机械提醒。
- 同一事件在一个提醒周期内去重；已完成业务动作后相关提醒自动失效。

**输出与成功状态：** 用户可以从概览直接进入餐次、食材详情或购物清单完成下一步。

**空状态：** 无待办时展示本周菜单摘要和“添加一餐”入口，不使用空洞庆祝文案。

**异常状态：** 局部数据加载失败时保留其他模块，并在失败模块提供重试。

**数据变化：** 通知、已读状态、提醒偏好和快捷操作记录。

**验收标准：** 提醒与真实业务状态一致；已完成或取消事件不继续出现；不同角色看不到越权入口。

### G.8 搜索、筛选与收藏

**用户目的：** 快速找到食材、菜谱和家庭历史记录。

**角色：** 家庭成员；运营后台用户在独立范围内搜索公共内容。

**业务规则：** 用户端全局搜索只返回当前家庭可见的食材、家庭菜谱和公共菜谱；历史记录需从对应模块进入。菜谱筛选支持预计用时、标签、库存覆盖、临期食材匹配和收藏。搜索无结果时保留关键词并提供清除筛选。

**验收标准：** 搜索结果严格遵守空间权限；组合筛选可清晰撤销；收藏变化即时反映在菜谱列表和详情。

### G.9 内容举报与处理

**用户目的：** 对不当公共菜谱、图片或文字进行举报；运营人员完成可追踪处理。

**角色：** 登录用户、内容运营人员、平台管理员。

**业务规则：** 家庭私有内容不进入公共举报流；举报需选择原因并允许补充说明；同一用户对同一内容的未处理举报不重复创建；处理结果包括保留、下架、要求修改和升级复核。

**验收标准：** 被下架公共内容不再出现在新浏览入口，但已有家庭复制版不被自动删除；所有处理动作有操作者、时间和理由。

### H.3 通用规则

- 关键状态变化保留操作者、时间、前后值和可选原因；普通浏览不记录为业务审计。
- 有业务引用的数据优先归档，不做不可恢复的物理删除。
- 截止日期、周边界和提醒按家庭设置的时区解释，页面显示明确日期。
- 图片、备注和菜谱正文不得在通知中暴露给已离开家庭的用户。
- 当计算结果不确定时，使用“需确认”而不是给出看似精确的错误数值。

## I. 产品特色设计

### I.1 冰箱覆盖尺

冰箱覆盖尺是菜谱详情和餐次详情中的核心组件。它逐项对照菜谱用料与家庭库存，用“已有、差一点、缺少、需确认”四种语义呈现，并在菜谱标题附近给出总体覆盖摘要。用户调整份数或选择替代食材时，覆盖尺即时重新计算。

该能力解决“看起来能做，真正下厨才发现缺料”的麻烦。它不依赖 AI，以标准食材映射、兼容单位和明确规则实现；无法换算时主动要求确认。验收重点不是追求营养级精密，而是每个结论可展开解释来源。

### I.2 餐桌周历与采购联动

周菜单不是静态日历。每次增删菜品、改变份数或改期，系统都生成与当前购物清单的差异提示，例如“新增 2 项短缺”“已有 1 项不再需要”“已购买项目不受影响”。用户选择确认后才改变未购买项。

该设计使计划、采购和实际生活变化保持一致，同时避免系统擅自删除已经买到的东西。即使多人协作，任何变化都有来源和处理结果。

### I.3 临期先用

今日概览将临期食材组织为一条可操作的“先用队列”。用户进入某个临期食材详情后，可以查看用到该食材且库存覆盖较高的菜谱。排序优先考虑临期程度、用量匹配、预计用时和家庭偏好，但必须显示排序理由。

没有复杂推荐能力时，使用规则排序即可完成体验；数据不足时按临期程度和公共菜谱标签展示，不出现空白推荐区。该功能的价值是帮助用户决定下一餐，而不是宣称精确减少了多少浪费。

## J. 网站视觉风格与 UI 设计契约

### J.1 设计命题

**把一周的餐桌安排设计成一张会随着库存和采购自然流动的厨房操作台，而不是一套仓库管理表格。**

风格关键词：清爽家常、食材可辨、步骤有序、协作友好、轻量可信。

不应出现的气质：医疗营养仪表盘、企业仓储后台、复古食谱书、外卖促销页、泛科技霓虹感。

### J.2 标志性视觉母题

核心母题是“餐桌周历上的食材纸签”。周菜单的每个菜品像放在日期与餐次格中的窄纸签，纸签左侧带一条按库存覆盖变化的短边标记；从菜品展开时，食材纸签向下延伸成覆盖尺，再自然连接到购物清单。视觉上让用户感到菜单、库存和采购属于同一张工作台。

这个母题只用于周菜单、菜谱覆盖和采购来源等关键联动，不把所有卡片都做成便签，不使用仿纸纹、胶带、手写字体等装饰性拟物。

### J.3 核心色彩

| 语义名称 | 色值 | 用途 |
|---|---|---|
| 蒸米白 | `#F7F5EE` | 用户端主背景，降低厨房内容图片与标签之间的视觉噪声 |
| 海带墨 | `#24322D` | 主文字、主导航和高对比操作 |
| 青豆绿 | `#4F7A5A` | 可用库存、完成动作和主要按钮 |
| 南瓜黄 | `#E6A23C` | 临期、待确认、计划变化和需要关注的信息 |
| 紫苏红 | `#B9564F` | 缺少、过期、删除前警示和错误状态 |
| 搪瓷蓝 | `#557A95` | 采购协作、成员分配、信息链接与辅助选择 |

状态色必须同时搭配文字或图标，不能只依赖颜色。青豆绿仅表示可继续和已完成，不用于所有装饰；紫苏红只用于真实风险、缺少和破坏性动作。管理端可以将主背景调整为更中性的浅灰白，但保留同一状态语义。

### J.4 字体气质与字阶

中文展示文字采用具有适度人文感、笔画开口清楚的宋黑过渡气质字体，后备顺序为系统可用的中文标题字体、通用中文黑体、无衬线字体。只在入口页主标题、周日期和菜谱标题中使用，避免整页书刊化。

正文使用中性、屏幕阅读稳定的中文无衬线字体；数字、数量、单位和日期优先采用等宽数字特性，后备为系统无衬线字体。不要用手写字体表达“家常”，也不要使用极细字重。

- 页面主标题：32–36px，字重 650–700，行高 1.2。
- 模块标题：22–24px，字重 650，行高 1.3。
- 卡片标题：16–18px，字重 600，行高 1.4。
- 正文：15–16px，字重 400–450，行高 1.65。
- 标签与辅助信息：12–13px，字重 500，行高 1.45。
- 数量与日期重点：20–28px，字重 600，使用稳定的数字宽度。

### J.5 页面宽度与信息密度

桌面用户端内容最大宽度建议保持在 1280–1360px 的舒适区间，主导航固定但不占用过宽空间。今日概览和周菜单使用较宽画布；食材与菜谱详情控制正文行宽，使步骤和用料容易扫描。

用户端留白以“能快速看清一餐”为准，卡片之间保持清楚呼吸；管理端信息密度可提高一级，更多使用紧凑筛选、表格和批量操作。任何页面都不采用将所有数据塞入同一仪表盘的布局。

### J.6 导航与关键布局原则

- **入口页：** 首屏直接呈现一个有真实数据的餐桌周历片段，旁边用一句话解释库存、菜单和采购如何联动；不使用抽象渐变球或手机模型堆叠。
- **今日概览：** 第一屏先回答“今天吃什么”和“什么需要先处理”。今日餐次占主区域，临期队列和采购任务占次区域，统计信息退后。
- **周菜单：** 桌面采用七列日期与纵向餐次结构，允许横向聚焦而非缩小文字；菜品纸签显示封面缩略图、名称、份数和覆盖短边。移动端按日期纵向分组，只展开一天。
- **食材列表：** 默认按存放位置分区，以图像、名称、数量和日期为主；表格式密集视图作为切换选项，不作为默认。
- **菜谱详情：** 成品图与核心信息在上，库存覆盖尺紧随其后，步骤在下；“加入菜单”固定在用户自然决策区域，不悬浮遮挡内容。
- **购物清单：** 以采购动作优先，按生鲜、冷藏、常温等真实取货顺序分组；来源菜品折叠显示，避免一开始占据主体。
- **管理端概览：** 先显示待处理举报、待发布菜谱和异常任务，再显示趋势；不展示无决策价值的大数字。

### J.7 组件视觉语言

按钮采用清楚的实色主按钮、描边次按钮和文本级弱操作。主按钮每个操作区最多一个，名称使用“加入周菜单”“生成购物清单”“确认入库”等结果导向文案。

输入框边界清楚，数量与单位成组展示；日期、份数和位置选择使用用户熟悉的字段名称。验证信息紧贴字段，不用只显示红色边框。

卡片圆角保持中等且统一，避免所有容器漂浮。食材卡以内容图像和日期状态为主；纸签母题只用于可安排、可流转的对象。表格用于后台和历史流水，用户端默认不使用大量表格。

标签分为状态标签与内容标签：状态标签有稳定色义，内容标签使用低饱和中性色。弹窗只用于高风险确认和短任务；复杂编辑进入独立页面或侧边工作区。

空状态提供一个明确下一步，例如“添加第一批食材”；错误反馈说明发生了什么、哪些内容未保存、用户可以怎样修复。加载时保持结构稳定，不让周菜单列宽跳动。

### J.8 图片、图标与素材边界

食材图片采用自然散射光、单一食材近景、背景干净的摄影风格，保持真实颜色，不使用油亮广告质感。菜谱成品图可有生活化餐具和局部桌面，但构图应便于裁切，避免叠加文字水印。

图标采用圆端、略带器具轮廓感的线性图标；冰箱、锅、清单、餐盘等图标应减少细节，在 16px 下仍可辨认。插画仅用于新手引导和空状态，表现食材、餐盘和动作，不使用通用人物办公插画。

素材必须来自明确可用来源、内部制作或种子内容，不抓取带版权风险的第三方菜谱图片。图片缺失时使用按食材类别生成的简单色块与图标组合，不使用随机网络占位图。

### J.9 数据可视化规则

数据可视化仅用于有行动价值的信息：一周菜单完成情况、临期食材变化、采购任务进度和常做菜谱偏好。优先使用时间带、分段进度和小型趋势，不使用 3D 图、仪表盘、雷达图或纯装饰环图。

任何“减少浪费”指标若无法从真实业务动作直接计算，就改为展示“本周按时使用的临期食材数量”“已完成的库存消耗记录”等可解释事实，不做夸大推断。

### J.10 动效与反馈

主要动效时刻发生在用户确认“从菜单生成购物清单”时：周历中的缺料标记依次收拢到右侧清单分组，持续约 500–700ms，随后显示合并结果和需要确认的单位冲突。该动效帮助理解跨模块联动，只在用户主动触发时出现。

常规反馈使用 120–200ms 的颜色、边框和位置变化；购物项勾选后保持原位置短暂停留再归入已完成分组，避免用户失去上下文。支持减少动态效果设置时，使用即时状态替换，不依赖位移动画表达结果。

### J.11 响应式与可访问性

桌面端保留周历全局视野；平板端允许日期横向分页并固定餐次标签；移动端改为“今天优先”的纵向日卡，每次默认展开一天。购物清单在移动端进入大触控目标的单列模式，数量编辑和勾选不得过于靠近。

键盘焦点使用清晰的搪瓷蓝双层轮廓，不被卡片裁切；所有拖放操作必须提供键盘可完成的“移动到日期/餐次”替代方式。正文与背景达到可读对比，状态不用单色表达。触控目标不小于 44×44px，表单错误可被辅助技术定位并朗读。

### J.12 文案语气

界面使用具体、克制、像家庭协作备忘一样清楚的语气。按钮说“加入周菜单”，不说“开启美味之旅”；空页面说“还没有记录食材。先添加冰箱里常用的几样”，不说“这里空空如也”；错误说“这项采购已被另一位成员领取，刷新后再选择”，不说“操作失败”。

状态名称在全产品保持一致。系统不评价用户饮食是否“健康”，不使用羞辱、焦虑或道德化语言描述过期、丢弃与未完成计划。

### J.13 关键页面视觉重点

- **入口页：** 让访客在十秒内看懂三者联动，主演示内容是一份真实周菜单及其缺料流向。
- **今日概览：** 今日两餐与临期先用队列最突出，数据数字不得抢过任务。
- **周菜单：** 日期、餐次和菜品纸签形成稳定节奏，库存覆盖短边是最有辨识度的信息编码。
- **菜谱详情：** 冰箱覆盖尺与份数调整构成主交互，步骤内容保持清晰阅读。
- **购物清单：** 领取人、完成状态和入库动作一眼可扫，减少操作干扰。
- **管理端概览：** 待处理队列优先，内容质量状态比流量数据更重要。

### J.14 禁止使用的模板化做法

- 禁止以蓝紫渐变、发光图标和抽象网格营造与厨房场景无关的“科技感”。
- 禁止首页用四个大数字卡片代替今日餐次与临期任务。
- 禁止把所有内容做成同尺寸、同圆角、同阴影的悬浮卡片矩阵。
- 禁止滥用米白、陶土色、高对比衬线标题组成通用生活方式模板；本产品色彩必须围绕食材状态和协作动作服务。
- 禁止使用仿纸纹、胶带、手写体和餐具涂鸦堆叠成装饰性手账。
- 禁止在用户端默认采用仓储表格和复杂筛选侧栏，也禁止用拟真冰箱门遮挡信息。

## K. 数据与内容设计

### K.1 核心实体及关系

| 实体 | 关键字段 | 主要关系与生命周期 |
|---|---|---|
| 用户 | 名称、头像、联系方式、通知偏好、状态 | 可加入多个家庭；停用后保留必要历史署名 |
| 家庭空间 | 名称、时区、默认人数、周起始日、状态 | 拥有成员、库存、菜单、菜谱和清单 |
| 家庭成员关系 | 用户、家庭、角色、加入时间、状态 | 控制空间访问；移除后失效但保留历史 |
| 标准食材 | 名称、分类、常用单位、关键词、状态 | 被库存批次和菜谱用料引用；运营维护 |
| 食材批次 | 家庭、标准食材、数量、单位、模糊状态、位置、保质日期、状态 | 通过库存流水变化；耗尽后转历史 |
| 库存流水 | 批次、变动类型、变动前后、来源对象、操作者、时间 | 不直接修改；用于追溯和撤销 |
| 菜谱 | 所有者类型、标题、份数、步骤、可见性、状态、版本 | 公共或家庭私有；计划餐次保存快照 |
| 菜谱用料 | 菜谱、标准食材、数量、单位、可选替代项 | 用于覆盖和短缺计算 |
| 周菜单 | 家庭、周起始日期、状态 | 包含多个餐次和计划菜品 |
| 计划菜品 | 餐次、菜谱快照、份数、负责人、状态 | 可生成需求并产生消耗记录 |
| 短缺快照 | 目标周、需求、库存依据、计算时间 | 用户确认前只作建议；保留计算依据 |
| 购物清单 | 家庭、目标周、状态 | 包含手工项和菜单来源项 |
| 购物项 | 食材、计划量、实际量、来源、负责人、状态 | 已购买后可入库；状态完整留痕 |
| 消耗记录 | 计划菜品、批次、预计量、实际量、操作者 | 与库存流水和餐次完成关联 |
| 通知 | 接收人、家庭、类型、关联对象、已读状态、失效时间 | 业务完成后可失效，不泄露离开家庭后的内容 |
| 举报 | 举报人、公共内容、原因、状态、处理记录 | 仅适用于公共内容 |

### K.2 数据来源

标准食材、公共菜谱、主题合集和常用单位来自内部维护的种子内容。家庭库存、菜单、购物和烹饪记录由真实产品行为产生。公共菜谱应有原创或明确授权的文字与图片；如无法确认图片授权，则使用内部制作的示意图或无图版本。

### K.3 隐私边界

家庭库存、菜单、采购项、消费习惯和成员动态默认仅当前家庭成员可见。运营人员不得通过普通后台浏览家庭详情。用户导出或删除个人数据时，应区分个人资料与家庭共同业务记录；共同记录保留必要的匿名化操作者信息，避免破坏其他成员的库存与菜单历史。

### K.4 删除与保留

账号注销前提示用户处理其创建者身份。注销后，个人联系方式和头像进入删除流程；被家庭共同记录引用的操作署名改为匿名标识。家庭空间由最后一位创建者发起删除，并设置可撤销等待期；等待期结束后删除家庭私有内容及图片。公共内容的审核和举报记录按安全需要保留必要期限。

## L. 消息、搜索与通用体验

站内通知覆盖家庭邀请、成员变化、采购领取与冲突、菜单调整、临期提醒、举报处理结果。通知必须指向可访问对象；用户离开家庭后，对应通知不再展开私有内容。

产品不建设即时聊天。成员协作通过对象备注、负责人、状态和站内通知完成，避免把关键采购决定埋在聊天流中。对菜谱、食材和购物项的评论不进入首版。

搜索支持当前家庭食材、家庭菜谱和公共菜谱；筛选条件在返回列表后保留。用户收藏菜谱后可以从菜单添加流程直接访问。文件能力仅服务于食材和菜谱图片，不提供通用网盘。

所有关键业务页面必须包含加载、无数据、无结果、无权限、内容已停用、网络重试和并发冲突反馈。关键编辑内容在可行时保留草稿，避免上传图片失败导致全文丢失。

## M. 管理与运营后台

### M.1 真实职责

内容运营人员需要维护公共菜谱和食材基础数据，使新家庭能快速开始；处理公共内容举报，避免不当内容继续传播；维护主题合集与首页内容节奏。平台管理员需要管理运营人员权限、异常账号和审计记录。

### M.2 后台模块

- **待办概览：** 待审核菜谱、待处理举报、单位冲突反馈和异常任务。
- **公共菜谱：** 草稿、审核、发布、停用、版本与来源说明。
- **食材与单位：** 标准食材、别名、分类、兼容单位和停用规则。
- **主题合集：** 维护“30 分钟晚餐”“优先用掉牛奶”等人工策划集合。
- **举报中心：** 查看原因、证据、关联内容、处理结果和复核记录。
- **用户异常：** 只处理明确异常状态、封禁和申诉，不提供家庭行为画像。
- **审计记录：** 查看高权限操作、内容下架、权限变更和数据访问原因。

### M.3 有决策价值的运营信息

后台可展示公共菜谱被收藏、复制、加入菜单和被举报的数量，以及新用户完成首个家庭、首批库存和首周菜单的漏斗。不得展示没有行动意义的虚荣指标，也不得以家庭具体采购内容生成敏感排行榜。

## O. 种子数据与演示方案

### O.1 演示账号

- 家庭创建者“林禾”：拥有完整家庭管理与业务权限。
- 家庭成员“周晴”：可编辑库存、菜单和购物清单。
- 访客成员“陈野”：仅查看菜单并处理领取的采购项。
- 内容运营“顾宁”：进入独立后台管理公共菜谱与举报。

所有账号使用明显的演示标识和独立凭据，不能沿用生产默认密码。

### O.2 预置业务数据

预置一个“南窗小家”家庭空间，包含约 28 种库存食材、6 个存放位置或分类组合、5 个临期批次、2 个模糊数量记录和完整库存流水。公共菜谱不少于 24 个，覆盖快手主食、家常菜、早餐、烘焙与轻食等主题；家庭菜谱预置 4 个，并包含一条停用历史版本。

当前周菜单预置 8 个餐次、12 道计划菜品，其中包含库存完全覆盖、部分缺少、单位需确认和使用替代食材四类案例。购物清单包含待购买、已领取、已购买和已入库状态。历史周预置至少两次完成餐次和一次撤销记录。

### O.3 边界案例

- 牛奶有两个不同保质日期的批次，验证优先消耗建议。
- 面粉库存单位为克，某菜谱用量单位为杯，标记为需确认而非强行换算。
- 同一番茄需求来自三道菜，验证购物项合并与来源展开。
- 已购买鸡蛋后菜单减少一道菜，验证系统不自动删除已购买项。
- 访客尝试编辑库存，验证权限拦截。
- 公共菜谱被停用后，验证历史菜单快照仍可查看。

### O.4 5–8 分钟主演示路径

1. 以“林禾”进入今日概览，查看今晚餐次和两项临期食材。
2. 打开临期牛奶，进入“临期先用”菜谱列表，选择香蕉燕麦松饼。
3. 在菜谱详情将份数从 2 调整为 3，查看冰箱覆盖尺从“充足”变为缺少鸡蛋。
4. 把菜谱加入周六早餐，进入周菜单查看新增纸签和采购差异。
5. 生成短缺建议，确认鸡蛋与香蕉进入购物清单，并把鸡蛋分配给“周晴”。
6. 切换“周晴”账号，在移动式清单视图领取、勾选并填写实际购买数量，批量入库。
7. 回到餐次详情，确认烹饪完成，查看优先扣减临期牛奶和库存流水更新。
8. 打开历史记录，展示本次菜单、采购和消耗之间的完整来源关系。

### O.5 备用路径

若菜谱文本整理或邮件不可用，直接使用预置菜谱和站内邀请码。若图片服务不可用，演示切换为类别占位图，所有核心文本、覆盖判断、清单状态和库存扣减仍可完成。

## P. 产品验收

- 新用户能够创建家庭、邀请成员并完成至少一项库存录入，且不同家庭数据不可互见。
- 用户可从菜谱加入周菜单，调整份数后得到可解释的库存覆盖结果。
- 系统可从多个餐次生成去重短缺建议，用户确认后形成购物清单；单位不兼容时明确要求确认。
- 多名成员可领取和完成采购项，冲突不会产生双重领取；已购物项能批量入库。
- 烹饪完成必须经过扣减预览和用户确认；库存不产生负数，同一餐次不重复扣减。
- 临期提醒依据真实保质日期和家庭阈值生成，完成消耗、丢弃或纠错后提醒及时失效。
- 公共菜谱、家庭菜谱和历史快照具有正确的可见性和版本行为。
- 访客、普通成员、家庭创建者、运营人员和平台管理员的页面入口与操作权限符合矩阵。
- 关键页面具备可操作的空状态、错误状态、无权限状态和并发冲突反馈。
- 外部邮件、AI 辅助和图片处理不可用时，核心闭环仍可完成。
- 演示账号和种子数据打开即用，主演示路径可在 5–8 分钟内稳定完成。
- 桌面、平板和移动端的核心流程均可完成，周菜单与购物清单不会因重排丢失关键信息。

## Q. 测试与验收验证

### Q.1 核心流程测试

覆盖创建家庭、录入库存、添加菜谱、安排菜单、生成短缺、完成采购、登记入库、确认烹饪和库存扣减的完整路径。测试正常路径、跳过餐次、改期、撤销完成和已购物后菜单变化等分支。

### Q.2 功能与状态测试

逐项验证食材批次、菜谱、计划菜品、购物项、邀请和举报状态转换。非法转换必须被阻止并说明原因。对批量入库和烹饪确认执行原子性检查，确保不出现部分成功。

### Q.3 角色权限测试

使用所有角色验证页面可见性、按钮可用性、直接地址访问、空间切换和数据查询范围。重点检查离开家庭后的通知、历史链接和图片访问是否失效。

### Q.4 计算与规则样例测试

使用固定样例核对份数换算、同食材需求合并、兼容单位比较、模糊库存处理、临期阈值、批次优先扣减和零库存保护。每个结果应能回溯到输入和规则，不预设无法验证的效果结论。

### Q.5 异常与降级测试

模拟网络中断、图片上传失败、邮件失败、可选 AI 服务不可用、重复提交、并发领取、并发库存编辑和内容停用。确认草稿、状态和库存不会被静默丢失或重复修改。

### Q.6 空状态与可用性检查

验证新家庭、无库存、无菜谱结果、无购物项、无通知和后台无待办等状态。每个空状态应说明当前情况并提供一个合理下一步。邀请、添加食材、加入菜单和确认入库流程不应出现无法返回的死路。

### Q.7 响应式与可访问性检查

在常见桌面、平板和移动宽度检查周菜单、食材列表、菜谱详情与购物清单重排。验证键盘焦点、拖放替代操作、状态非单色表达、触控目标、表单标签、错误定位和减少动效设置。

### Q.8 演示复核

使用正式种子数据完整执行主演示与备用路径，记录每一步所需账号、前置状态和预期结果。演示结束后能够恢复或重置种子数据，确保下一次打开仍是完整可用状态。

## R. 风险与范围降级

| 风险 | 触发信号 | 主动处理与降级 |
|---|---|---|
| 数量与单位换算过度复杂 | 大量菜谱出现跨单位冲突，用户无法理解结果 | 首版仅支持明确兼容单位；其他情况标记需确认；允许模糊库存 |
| 用户录入负担过高 | 新家庭在首批库存录入前大量退出 | 提供常用食材快速添加、批量编辑和可选保质期；不强制精确批次 |
| 菜谱内容与图片不足 | 新用户进入菜谱库后缺少可用内容 | 准备高质量原创种子菜谱；无图可用；家庭菜谱可快速复制修改 |
| 联动规则导致意外更改 | 用户反映菜单变化后清单或库存被自动修改 | 所有跨模块变化先展示差异并由用户确认；已购买项绝不自动删除 |
| 多人协作冲突 | 重复领取、重复入库或库存被覆盖 | 使用状态校验、冲突提示和操作历史；关键动作保持原子性 |
| 提醒造成焦虑或疲劳 | 用户频繁关闭提醒或忽略临期通知 | 仅提醒可行动事项，支持家庭阈值和摘要；不用道德化文案 |
| 范围扩张到营养诊断与电商 | 需求开始依赖专业数据、支付或商业接口 | 保持生活计划定位；营养仅作普通信息，支付与真实下单明确不做 |
| 外部服务影响稳定性 | 邮件、AI 或图片服务不可用 | 站内流程、手工录入、预置结果和占位图保证核心闭环 |
| 私密家庭数据越权 | 后台或离开成员能看到家庭内容 | 空间级权限、受限审计、链接失效和隐私测试作为发布门槛 |

最低可行降级版本必须保留家庭空间、库存、家庭菜谱、周菜单、购物清单和烹饪确认。可依次移除邮件、AI 文本整理、图片上传、公共收藏与高级统计，但不得移除库存—菜单—采购—烹饪闭环。

## S. 母版资产与客户变体

### S.1 四层可复用资产

**通用 Web 骨架：** 账号、空间隔离、角色权限、邀请、通知、图片、搜索、状态历史、审计和基础配置。

**场景业务层：** 食材批次、菜谱用料、份数换算、周菜单、短缺快照、购物项、库存流水和烹饪消耗。

**产品特色层：** 冰箱覆盖尺、菜单与采购差异、临期先用规则、批次优先扣减和采购来源追溯。

**品牌主题层：** 食序与 MealFlow 命名、餐桌周历纸签、食材状态色、厨房操作台式页面组织、原创菜谱与南窗小家种子故事。

### S.2 自然客户变体

1. **健身备餐版：** 面向周期备餐用户，核心对象增加餐盒批次和训练日计划；主流程改为目标餐次—批量制作—分装—取用；特色加入重复备餐模板。视觉从家常餐桌转向分装网格。
2. **宿舍轻食版：** 面向设备有限的合住用户，核心规则加入可用电器与制作条件；菜谱突出无需明火、低步骤和共享购买；采购协作权重更高。
3. **亲子家庭版：** 核心对象增加家庭成员口味与儿童可选项；菜单协作加入“同菜不同处理”与学校日历式餐次；文案和视觉更亲和但不幼儿化。
4. **家庭烘焙版：** 核心对象改为原料、配方和制作批次；主流程为配方计划—原料核对—采购—制作—成品记录；特色加入配方比例和耗材预留。
5. **节日聚餐版：** 面向一次性多人聚餐，核心流程变为宾客确认—菜单组合—份量汇总—分工采购—出餐时间线；强调任务协作而非长期库存。

每个变体至少改变核心流程或产品特色，并同步改变主要对象、规则与演示故事，不能只替换品牌和颜色。

## U. 已知事实、假设与未来设想

### U.1 已确认的产品要求

- 产品名称为食序，英文品牌为 MealFlow，仓库名为 `mealflow`。
- 产品围绕家庭食材、周菜单、购物清单和烹饪消耗形成闭环。
- 用户端是主体；后台只承担公共内容、基础分类、举报与安全职责。
- 首版不依赖真实支付、特殊硬件、大规模模型训练或高成本第三方服务。
- 外部服务不可用时，核心演示和业务流程必须成立。

### U.2 合理默认假设

- 默认用户包括个人、情侣、合租室友和家庭成员。
- 食材数量既支持常见精确单位，也支持生活化模糊状态。
- 公共菜谱由内部原创或明确授权内容构成，家庭内容默认私有。
- 站内通知足以支撑核心协作，邮件仅作为增强。
- 首版以规则匹配临期食材和菜谱，不需要复杂推荐系统。

### U.3 待后续产品评审事项

- 一个账号同时加入多个家庭时，通知与默认空间的优先级。
- 家庭创建者是否可以进一步自定义访客的细粒度权限。
- 精确数量与模糊数量混用时，覆盖尺的最清楚展示方式。
- 历史周、归档菜谱和库存流水的默认保留期限。
- 公共菜谱是否开放用户投稿，以及投稿后的授权确认流程。

### U.4 未来商业化设想

未来可探索家庭高级模板、跨设备同步、更多公共菜谱主题和可选内容订阅，但这些设想不属于当前开发与验收范围。任何商业功能都不能改变家庭私有数据默认不公开的原则。
