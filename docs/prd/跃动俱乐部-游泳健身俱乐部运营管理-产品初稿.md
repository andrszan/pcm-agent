# 跃动俱乐部｜游泳健身俱乐部运营管理

> 产品初稿 · 2026-09-14
>
> 中文品牌：跃动俱乐部；英文品牌：Active Club；工程标识：`active-club`。
> 工程标识用于后续 Agent 工作区命名，不代表已创建仓库。

## 产品定位与确认边界

为一家独立经营、只有一个经营场馆的游泳健身俱乐部提供员工使用的 Web 运营后台。将会员与学员、入场权益、课程预约、实际到课、课时消耗和收退款连接起来，让前台能准确接待、教练能清楚授课、店长能依据业务记录安排经营。

**用户已确认：** 单店定位；自由游泳、游泳培训、健身私教和团课均包含；游泳培训包含少儿班；采用上述品牌名称与工程标识。泳池、泳道、健身区及团课教室是同一场馆内的资源，不是多个门店。

**当前设计提案：** 以下角色分工、业务规则、页面组织和统计能力用于后续深化，并非客户已逐项确认的运营制度。建议本轮形成完整的内部运营闭环，不预设额外分期。

**当前边界：** 不默认增加总部管理、门店切换、跨店通卡、多商户平台、会员小程序或独立 App。会员预约由员工代办。门禁与支付接口不是已知现有能力，人工核验和收款登记应可独立完成业务。

## 为什么需要它

俱乐部同时售卖入场资格和课程服务，容易出现三类脱节：前台只知道会员买过卡，不清楚今天能否入场；教练知道谁来上过课，但课时余额没有同步；店长看到收了多少钱，却看不清还有多少课程尚未提供。

产品应让员工在接待、授课和对账时看清同一笔业务：谁购买、谁使用、购买什么、预约哪节课、是否实际到场、扣了什么权益、是否有更正或退款。少儿业务中还要清楚区分付款和联系的监护人与实际上课的孩子。

## 谁使用，分别完成什么

- **前台／会籍顾问：** 查询和建立会员档案，办理会籍与课程订单，登记收款，代办预约，核验入场，跟进即将到期或需要续费的会员。一个员工可兼任多个职责。
- **教务／课程负责人：** 建班和排课，分配教练与场地，处理调课、停课、补课和预约冲突。
- **教练：** 查看自己的课程和学员名单，登记到课与缺席，补充必要的教学备注。默认不查看全店财务或无关会员资料。
- **财务／店长：** 对账、处理需要授权的退款和余额更正，查看经营统计；店长还负责产品规则、员工权限与异常处理。
- **场馆负责人：** 维护区域开放、泳道占用、设施维护及水质巡检记录。实际可由店长或当班人员兼任，不要求新增岗位。

监护人与学员在本提案中是被服务对象，不默认拥有后台登录账号。

## 一天的主要业务过程

### 办卡或报名

前台先查找已有档案，避免重复建人。成人可同时是会员、付款人和学员；少儿以孩子建立独立学员档案，关联监护人的姓名、联系渠道和关系。同一位监护人可关联多个孩子，同一孩子也可记录多个联系监护人并指定主要联系人。

选择适用的入场卡或课程包，确认使用人、适用项目、有效期、次数或课时、价格及实际优惠，形成订单并登记收款。付款人不因此成为课时使用人；兄弟姐妹不默认共用课程余额。

已售订单保留成交时的适用服务、有效期、次数或课时、价格与使用规则，后续修改在售产品不能改变既有会员权益。在售产品维护当前内容，不因保留订单成交条件而建立产品编辑版本库。未完成收款的订单应明确显示未支付或部分支付，是否允许启用权益需形成明确制度，不默认视为全额付款。

### 自由游泳与健身入场

前台通过姓名、手机号等线索定位会员，核对本人及当前权益。结果应直接说明：允许进入哪些区域、卡是否已生效或冻结、是否到期、剩余次数是否足够。

核验后登记入场，次数卡按适用规则扣次，期限卡留下使用记录而不虚构扣次。记录适用的卡及经办人。重复点击不能形成重复扣减；误登记可由获授权员工撤销并保留原因和关联记录。

无有效权益时，前台可办理适用产品后再次核验，不以任意修改余额代替销售。若实际销售单次入场票，可作为入场产品办理。离场登记可支持在场人数估算，但只有入场、离场记录足够完整时才展示该口径，不能把当日累计到店人数称为实时在场人数。

### 排课、预约与上课

游泳培训支持少儿固定班与相应课次；健身私教支持学员与教练约定时段；团课按名额组织预约。自由游泳主要通过区域开放及容量安排管理，不强行套用课程预约。

每个课次明确项目、教练、起止时间、使用资源、容量和名单。泳池可以按泳道安排培训与自由游泳，健身课程可使用私教区或团课教室。排课时检查教练和独占资源的时间冲突；同一学员不能预约重叠课程。资源是否允许共享，应根据真实场地安排定义容量，不能简单地把所有同时间泳池活动视为冲突或无限叠加。

固定班报名后关联具体课次名单，并校验名额与权益；临时预约同样检查课时、有效期和课程适用性。预约占用名额及相应可用课时额度，但不代表已消费。取消预约释放相应占用，避免余额已被其他预约占用时继续超额预约。

上课当天，教练按名单登记到课、请假或缺席，再根据已确定制度完成扣课。上课签到和入场登记互相关联但不能混为同一笔消耗：课程是否包含当天入场资格需明确标示，避免重复收费。

临时停课应同步处理预约与课时占用；补课需关联原课次和处理原因，并重新检查时间、名额与权益，不自动多扣一课。修改上课结果或撤销扣课需保留原记录、更正原因及操作人。

### 收款、退款与日终核对

订单说明卖了什么、给谁使用和应收金额，收款记录说明何时通过何种方式实际收到多少钱。现金、转账或外部收款终端的登记，不等于系统已经发起或核实第三方支付。

退款关联原订单，分别记录拟退款、实际退款和权益处理结果。执行前检查已使用服务与未来预约，明确剩余权益是否停用、预约是否取消；退款失败或尚未实际退付不能展示为已退款。更正不删除历史账目。

日终按业务日期及经办人核对实收、退款和净收款，展开到订单与收退款明细。售卡收款与课时消耗分别呈现，不把未上完课程的预收款直接称为已实现营业收入；本产品不替代完整会计核算系统。

### 场馆开放与异常处置

场馆负责人维护区域开放时段、培训泳道占用、包场和设施维护。水质巡检记录时间、检测项目、测量结果、记录人及处置情况；适用项目和阈值依据场馆实际制度确定，不在初稿中编造标准。

发现需要关闭区域的异常时，由有权限人员确认停用范围和时间，查看受影响课程及预约，安排通知、调课或取消。系统记录处理结果，但不冒充自动传感器或自动完成安全判定。

## 核心规则必须保持一致

### 入场权益与课程权益分开

期限卡、次数卡和课程包分别表达有效期、使用次数及课程服务，不使用一个模糊的“会员余额”承载全部业务。游泳、健身和通用入场权益区分适用区域，课程包区分适用项目、使用人及课时。

冻结与到期状态直接影响核验和预约。冻结是否顺延到期日、顺延多少、课程包能否冻结，应按确定规则计算并保留记录，不默认对所有产品采取同一制度。

预约时有效不代表授课时一定有效，需依据课次日期检查权益。对已经预约后发生的冻结、退款或到期调整，提示受影响课次并要求完成处理，避免留下无法正常核销的预约。

### 少儿档案和联系关系清晰

孩子的年龄信息用于班级适配，监护人信息用于报名与联系。手机号是查找线索，不宜直接作为每个孩子必须唯一持有的身份：一家多个孩子可能使用同一监护人号码。

只收集教学、联系与安全安排确有用途的信息。教练仅查看负责学员的必要信息；敏感教学或健康提醒限制可见范围，不默认收集证件影像、完整病史或生物识别数据。接送交接是否需要记录及其具体制度尚待明确，不把联系人名单自动视作接送授权。

### 金额与权益更正有据可查

重复操作不重复收款登记或扣减权益。订单、收退款、入场、到课与课时消耗是业务记录；发生撤销、退款或金额、课时、会籍有效期更正时，按职责授权，只保存核对原业务与更正结果所需的内容、原因、经办人和时间。记录在对应订单、会员权益或课次内查看，不扩展成所有操作的统一审计中心，也不提供任意历史状态回滚。

会员联系方式、教学备注、在售产品文案、普通场地设置维护当前内容，不保存逐次编辑的前后值或版本列表。涉及已售权益、既有预约或已发生收支的调整，仍须按相应业务规则处理，不能用普通资料编辑绕过。

取消、缺席、迟到和停课是不同业务结果，不能都当作“未到课”自动扣除。正式开发前应确定相应制度，界面明确显示本次处理的影响。

## 工作台与页面体验

采用适合前台和管理人员长时间使用的桌面优先 Web 后台。教练在较窄屏幕上仍应能阅读当日名单并操作签到，但不因此附加另一套移动产品。

建议导航按实际工作组织：**今日工作台、会员与学员、会籍与课程产品、课程与预约、入场记录、订单与收退款、场馆运营、经营分析、员工与设置**。最终页面拆分随需求深化调整，不提前固定技术组件。

- 今日工作台优先显示即将开课、待处理调课、区域停用和待核对事项，不堆满与当前角色无关的经营数字。
- 前台可快速查人，会员详情首先呈现有效权益、可用课程余额和即将参加的预约；已发生的入场、上课与订单记录按需查看，不混入资料编辑流水，避免接待时反复跨页拼接信息。
- 课程日历支持按教练、项目和资源筛选，冲突说明指出具体占用对象及时间，而不是只显示“预约失败”。
- 少儿学员详情清楚标示孩子姓名、监护人及主要联系人，付款人与使用人保持可区分。
- 扣课、退款、冻结等操作在确认前展示影响，完成后提供可查的记录。空数据、无权限、保存失败和冲突状态分别说明原因及可行操作。

视觉建议采用清爽、有运动感但克制的专业后台表达，以水蓝或青蓝作为品牌重点，搭配清晰表格与时间安排视图；异常状态不只靠颜色识别。后台主要价值来自准确的数据与操作，暂不增加装饰性泳池照片或宣传横幅；必要的会员头像、场地区域示意等应有明确用途。

## 经营分析：看完能采取行动

提供经营分析页，同时在课程和会员页面展示对应业务汇总。统计来自日常业务记录，不额外要求员工录入“报表数据”，不默认增加独立全屏监控大屏。

| 分析主题 | 业务来源与口径 | 使用者可以采取的行动 |
| --- | --- | --- |
| 收款与退款趋势 | 按实际收退款时间统计实收、退款和净收款，区分入场产品与课程产品 | 店长核对收款变化，进入订单查明大额退款或产品销售变化 |
| 到店时段与项目分布 | 有效入场记录；分别标注入场人次与去重人数，撤销记录不计入 | 调整前台值班及泳池、健身区开放安排 |
| 课程预约与实际到课 | 有效课次、容量、预约名单及签到；区分预约占用率、实际到课率，取消课次单列 | 调整低需求时段、增加紧张课程，查看缺席或取消原因 |
| 教练授课与课时消耗 | 已完成且未撤销的授课、签到和课时流水；按课程类型与时长区分 | 平衡排课工作量、核对未完成签到；不直接把不同课程的次数混成业绩排名 |
| 到期与低余额会员 | 当前会籍、课程余额及预约占用；可筛选未来一段时间到期对象 | 进入会员记录安排续费联系，避免向已续费对象重复催办 |
| 尚待履行的课程服务 | 已生效课程包的剩余、预约占用和已消耗课时，按项目或课时单位分组 | 判断未来授课负荷，调整招生与教练安排，而非将不同单位强行相加 |

趋势采用折线或分组柱状图，类别和时段比较采用条形或柱状图；待跟进对象保留可操作的名单。选择形式以问题为依据，不为覆盖图表种类而增加图表。

统计需显示时间范围、业务定义及更新时间，比较采用一致时长和口径。到课尚未登记时，呈现“待登记”数量，不能把缺失当作缺席；小样本显示人数或课次数，不只显示百分比。没有业务数据时展示空状态，不填入虚构经营业绩。图表和汇总均可进入对应筛选明细，并遵循原记录的权限。

## 当前建议开发的范围与运营条件

当前建议开发覆盖会员及监护人档案、入场产品和课程包、办卡购课及收退款记录、入场核验、固定班和预约排课、签到核销、调课补课、场馆开放与巡检、员工权限、必要的资金与权益更正及经营分析。这些能力共同构成内部运营闭环，不包含通用操作历史、资料版本对比或配置回看，也不以外部接口尚未确定为由省略核心业务。

真实上线时需要俱乐部提供有效的在售产品、存量会员权益、课程与场地信息、员工名单和业务制度。历史余额迁入需要明确截止日期与核对结果，不能将演示数据当作真实余额。

线上支付、退款通道、短信通知和门禁若需要对接，应另行明确供应商、接口及可用资源；未对接时如实采用人工登记与联系记录，不显示自动发送成功或设备已放行。对外运营还需落实备份、个人信息访问与保留制度。这些是上线条件，不是阻止初稿讨论或本轮内部功能开发的前置门槛。

## 重要未知与待细化事项

以下问题不改变已经确认的产品方向，但会影响具体业务规则，应在对应需求深化时确认：

- 在售卡种、课程包单位、有效期及定价；是否销售单次票、体验课或允许分次付款。
- 课程是否自带当天入场权益；游泳与健身通用卡的具体适用范围。
- 少儿班按年龄还是能力分班，是否有固定学期、固定课次和补课有效期。
- 预约取消时限、迟到和缺席处理、停课补偿，以及冻结和延期规则。
- 退款计算方式、审批职责和原有财务对账习惯；是否有教练提成需求，当前不擅自加入薪酬核算。
- 泳道、场地容量与共享规则，水质巡检项目、阈值和异常处理职责。
- 少儿接送是否纳入后台，以及实际需要保留的授权与交接信息。
- 是否已有会员及余额数据、门禁或收款系统，需要迁入或集成到什么程度。

## 如何判断核心结果成立

以下场景用于检验产品设计是否闭环，不替代后续详细测试规范：

1. 前台为同一监护人的两个孩子分别报名，能准确找到每个孩子的班级、预约和余额，付款关系清楚且不会串扣课时。
2. 持有效入场卡的会员可以完成核验和登记；过期、冻结或次数不足时能说明原因；误登记撤销后余额正确，原入场记录标示已撤销并可查明原因。
3. 教务安排游泳培训、私教和团课时，能发现教练、资源或学员时间冲突，固定班与临时预约均不超出容量和可用课时。
4. 从预约到到课扣课可以追溯，取消释放占用、补课关联原课次；重复签到不会重复扣课，入场与课程权益不会混扣。
5. 退款处理能同时说明实际退付、剩余权益及未来预约的结果，财务可从汇总回到原订单核对。
6. 泳道因异常停用时，能定位受影响课次和预约，记录调课、取消及后续恢复处理。
