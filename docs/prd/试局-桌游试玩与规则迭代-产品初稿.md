# 试局：原创桌游试玩与规则迭代

> 产品初稿 v0.1 · 2026-09-12
> 面向原创桌游创作者与俱乐部的实际使用需求；具体功能范围与命名仍为讨论方案。

**试局（Rulefolio）帮助原创桌游创作者组织测试、整理证据，并在下一版中验证修改是否有效。**

产品采用纯桌面 Web 形态，工程标识为 `rulefolio`。试玩本身可以在线下完成，产品不提供在线桌游对战，也不要求现场通过手机扫码、推送或逐回合录入才能使用。

## 一、我们真正提供什么服务

一款桌游从“能够玩起来”到“规则清楚、体验稳定”，通常需要反复尝试。产品围绕这个过程提出一个价值假设：当创作者持续组织试玩时，分散的规则文件、聊天意见和测试表格会让他们难以回答以下问题：

- 这条意见针对哪一版规则、哪一种人数和哪一场测试？
- 同一个问题出现过几次，是规则表达不清，还是机制本身需要调整？
- 上次决定修改的内容，是否真的在后续版本中得到验证？
- 下一场应该优先测什么，而不是再泛泛地玩一遍？

试局将作品版本、试玩场次、观察记录、反馈、问题和修改决定连接起来。它提供的是**可持续维护的试玩研究记录**，不是替创作者设计游戏，也不是用一个评分判断游戏好坏。

这个需求尚未经过真实用户访谈验证。本稿描述目标使用过程与待验证价值，不把推断写成行业普遍事实。

## 二、第一批用户

### 核心客户：已经在持续做原创桌游测试的人

优先服务三类相互接近的对象：

- 持续维护作品、定期组织试玩的独立创作者。
- 同时推进数款原创作品的小型桌游设计工作室。
- 有稳定创作成员、持续开展原创作品测试的桌游俱乐部。

第一阶段不面向所有桌游玩家，也不把普通桌游门店作为主要客户。门店约局、桌位预约和会员消费是另一类业务，容易重新变成以手机为主的服务。

### 谁使用，如何协作

创作者和测试组织者是高频使用者：维护材料、安排场次、整理反馈、决定修改。工作室负责人或俱乐部组织者负责协调成员与测试安排。

试玩成员参与测试并提供反馈。一个成员可以在自己的作品中担任创作者，在另一款作品中担任试玩者，不通过固定账号类型割裂这两种身份。

上述客户的共同特征应当是“有连续测试任务”，而不是仅仅“喜欢桌游”。如果一个人只想发布构思、找一次活动或收几个点赞，产品对其价值有限。

### 从已有创作小组开始

首版允许客户带自己的成员和试玩者进入。即使平台只有一个工作空间、一位创作者和他们熟悉的测试小组，也应能完成全部核心工作。

公开作品社区、陌生试玩者匹配和招募流量都不是产品成立前提。未来只有在已有用户确实需要扩大招募、且存在稳定供给时，才单独评估这些能力。

## 三、为什么坚持桌面 Web

创作者需要对照规则书、整理卡牌文件、归纳多份反馈、比较修改决定，这些是适合在电脑上集中处理的任务。组织者在试玩结束后整理记录，也无需停留在现场。

试玩者的桌面价值不能被高估：如果只是回答三道满意度题，专门打开电脑并不合理。因此产品不强迫每个参与者都在线填写完整问卷。

提供两条同等合法的记录路径：

- **直接反馈：** 愿意深入参与的成员在电脑上阅读对应版本资料，提交观察与意见。
- **组织者整理：** 对口头讨论、纸面记录和现场观察，组织者统一录入，并明确注明记录人及信息来源。未注册参与者可用场次内代号记录，不强迫所有人建立账号，也不把转述冒充本人提交。

组织者即使独自使用，也能获得版本化记录、问题整理和复测计划的价值。成员协作会增加价值，但不是启动条件。

首版围绕中文创作团队设计，采用桌面浏览器完成核心业务，不将移动端响应式体验、小程序或 App 纳入交付。活动提前安排，重要消息通过工作邮箱和站内待办触达，不依赖临时即时响应。

## 四、一次完整的服务过程

以虚构作品《夜市摊主》为例：3～5 人经营摊位，通过采购与交易获得收益。示例只用于解释产品，不代表已有客户或真实测试数据。

### 建立作品与可试玩版本

创作者在自己的工作空间建立作品，说明玩法、目标体验、人数范围及预计时长，上传规则书和打印材料。首版使用文本、PDF 和图片承载规则与参考材料，不提供卡牌设计器或专业排版工具。

创作者发布 0.2 版时，形成一个稳定版本。草稿可修改，已发布版本的规则与材料不被静默覆盖；发现错误后通过新版本纠正。不同文件可以组成同一版本的材料包。

### 设计一轮有目的的测试

创作者为 0.2 版制定测试计划，提出两个问题：新玩家是否理解采购顺序，以及先手是否可能获得明显优势。

一份计划可以包含若干场次。每场记录自己的时间、地点、人数上限、参与者和实际使用版本。客户通过邀请或限定范围的报名找人，系统不承诺提供试玩者。

测试目标可以很轻量，不强迫客户填写正式实验设计。产品给出“希望观察什么、用什么方式记录”的提示，而不是给所有作品套同一份长问卷。

### 线下试玩，随后整理证据

现场使用真实桌游材料，系统不介入回合推进。组织者事后补充实际人数、时长、是否完成、座次或阵营、得分及关键观察。

参与者可以直接反馈，也可以由组织者整理现场意见。每条记录保留其来源，以及作品版本和场次关联。缺失数据保留为未知，不能自动填零或从报名人数推断实际到场人数。

未开展的场次可以改期或取消。已经完成的场次不会因计划后续改期或发布新版而被重写。

### 将反馈整理成问题与决定

两名参与者都没理解采购顺序，组织者也记录了同样的中断。创作者将这些材料归入“采购顺序表述存在歧义”这一问题。

问题保留原始反馈，补充创作者的判断和处理决定。可选择修改、继续观察、不采纳或合并重复问题；不采纳不是删除，原始证据仍能查阅。

反馈多不等于必须修改。系统支持设计判断，但不以投票替代创作者。

### 发布修订，并安排复测

0.3 版增加采购示例。创作者在版本变更中关联该问题，标记为“已调整、待验证”。下一轮测试复用这个观察目标，邀请未玩过的新成员检查是否仍存在理解困难。

完成后，创作者可以写下“本轮三位新玩家未再提出该疑问，暂时关闭”的结论，也可以继续观察。系统不会因为没有新反馈就自动宣布问题解决。

至此，客户得到的不仅是活动记录，还能回看：问题从哪里来、为什么修改、哪一版采取了行动，以及后续观察到了什么。

## 五、首个可对外试用版本

真实产品的首版需要范围集中，但不能用“只是原型”回避私密数据、可靠性或文件可用性。

### 工作空间与作品

一个工作空间承载一个创作团队或独立创作者的工作。支持邀请成员、创建私有作品、指定作品维护者和管理参与范围。

作品包含简介、阶段、目标体验、人数及时长、版本和材料。首版不提供通用页面搭建器，也不要求给每张卡牌建数据库。

### 测试计划与场次

支持指定测试版本与目标、安排场次、邀请或限定报名、确定参与名单、记录实际参与及取消情况。容量已满后不允许悄悄超额确认；首版不做复杂候补队列、票务或场地资源调度。

受邀者应能用简短路径了解自己要做什么，不被引导浏览无关后台。

### 记录与反馈

提供基础场次记录，以及短文本、单选、数值等少量问题类型。创作者按本轮目标选择必要字段，不建设任意逻辑分支的问卷平台。

个人反馈可以先存草稿，再明确提交。已提交内容的更正留下修订痕迹。组织者汇总记录与个人反馈始终区分来源。

### 问题与版本迭代

支持多条反馈关联一个问题、记录处理决定、关联修订版本、设定复测目标，以及回看全部历史。

问题不因发布新版本自动关闭。问题合并保留来源关系，重新打开不丢失过去结论。

### 项目回顾与导出

查看按版本组织的场次数、时长、未决问题及复测情况。统计显示样本量与缺失情况，尽量允许回到原始记录。

支持导出作品的版本目录、测试记录、反馈和问题处理结果，附件保留可下载入口，便于用户备份与迁移资料。具体导出格式在工程设计时确定。

邮件邀请、关键提醒、权限控制与基础账户恢复也属于对外试用所需能力，而不是仅展示在界面上的占位按钮。

## 六、需要提前讲清楚的规则

### 历史材料与现场变化

一次测试绑定一个已发布版本。如果现场临时更改规则，组织者记录“本场临时变体”及内容，不冒充标准版本，也不回写原版本。回顾和统计时应能够识别、排除这类场次。

作品可以按自己的习惯给版本命名，不强制采用软件的语义化版本号；系统负责提供不混淆的内部身份和发布时间。

### 主观判断与事实分开

“某阵营本场获胜”是观察记录，“该阵营过强”是解释。系统分别保存，不将少量胜率、低评分或关键词自动转成设计结论。

测试人数、玩家经验和临时规则不同的场次不能不加说明地混成一个平衡性评分。首版不做算法判定，不宣称具备专业游戏平衡评估能力。

### 作品默认私有

未发布的设计资料可能具有商业敏感性。作品与材料默认私有，访问由工作空间和作品权限控制。受邀试玩者只接触被授权的测试资料，不默认看到全部内部问题、其他作品或成员信息。

个人反馈默认由本人及授权维护者查看。需要开展集体讨论时，维护者发布不暴露个人身份的整理结论。首版不支持对外匿名公开投诉或评价墙。

预览和下载同样执行权限检查。撤销访问可以阻止后续在线读取，但无法收回已经下载的材料，不能向客户承诺“绝对防泄漏”。公开分享不进入首版。

### 提醒不是业务成功的前提

版本发布、邀请发出、反馈提交等真实状态独立保存。邮件发送失败不能丢失反馈或回滚已发布版本；失败状态可见，并支持有界重试。

不对每次编辑发送邮件。提醒集中于邀请、场次调整、需要处理的反馈与复测安排，不承诺现场紧急通知。

## 七、产品界面应体现桌游创作，而不是行政管理

核心界面围绕作品展开：总览、版本材料、试玩、问题与迭代。进入作品后，先看清当前版本、即将发生的测试，以及仍待验证的问题，而不是看到一排缺乏行动意义的统计数字。

试玩整理页面把事实记录、原始反馈与问题归纳放在容易对照的位置。版本回顾以明确的变更和关联问题为中心，不承诺自动比较任意格式规则书。

视觉建议采用“桌面上的实验笔记与游戏组件”作为表达：冷纸白 `#F7F9FC`、墨蓝 `#24324B`、骰子蓝 `#3F61C8`、木件黄 `#D9A63A`、记录灰 `#66758A`。正文优先使用清晰的中文无衬线字体，标题用 Source Han Sans SC 的较重字重，正文用系统中文字体栈；版本、场次及数值使用等宽或等宽数字表现。纸卡结构、组件小图和版本标签服务信息区分，不把后台做成拟真的棋盘游戏。

作品封面、卡牌缩略图和棋盘照片有助于理解作品，属于有价值的媒体。后续界面设计阶段应提供可展示的演示作品素材，并支持客户上传自己的作品图。本次只形成文档，不获取或生成媒体，也不修改产品代码。

## 八、边界与上线底线

首版不做在线对战、游戏规则引擎、实时语音聊天、卡牌排版器、陌生人匹配、众筹商城、印刷供应链、AI 自动平衡分析或手机端应用。

对真实客户开放前，至少需要实际验证：

- 工作空间、作品和文件之间的权限隔离，包括直接访问下载地址的情况。
- 版本发布、重复提交、报名容量与历史关联的正确性，过期页面不会覆盖新的业务状态。
- 文件上传的类型、体积和数量限制，以及不可信附件的安全处理；不执行上传文件中的内容。
- 备份与恢复、资料导出，以及客户离开服务时的数据处理路径。
- 账号恢复、邀请失效与撤销、成员移除后的访问限制。
- 邮件实际投递、失败状态和提醒频率；不能仅用模拟通知宣称已经可触达。
- 明确的数据保留、删除和服务支持说明；平台维护访问客户私密资料应受控并留下记录。

这些是上线前的产品责任，不代表本稿已经完成工程设计或通过测试。实际部署地点、运营主体和用户范围确定后，再落实适用的隐私与数据保护要求。

## 九、怎样判断产品是否有用

一次完整试用应至少覆盖两个版本：创建作品并发布材料，组织实际测试，收集或整理反馈，形成修改决定，发布新版，再开展针对性复测。仅仅注册账号、发布封面或填满测试数据，不代表产品价值成立。

重点观察：

- 创作者能否比过去更容易解释一次修改的依据，回到原始版本与记录。
- 第一轮结束后，是否会主动用系统安排下一轮，而非只在团队陪同下体验一次。
- 组织者能否承受每场整理工作量；先记录时间基线，再与其原有方式比较，不预设夸张的效率提升。
- 参与者直接反馈与组织者代录各占多少；若大多数人不愿独立使用，核心价值是否仍然成立。

需要警惕的信号包括：只有一次性活动、没人做后续迭代、资料依旧全部留在外部且系统只是重复录入、客户真正想要的是玩家流量或在线游戏。遇到这些情况应调整客群或定位，不用堆功能掩盖。

## 十、仍待讨论与验证

本次没有开展竞品核验或用户访谈，以下事项保留为未知：

- 独立创作者、俱乐部与小型工作室中，哪类用户的测试最频繁，最需要持续整理记录。
- 他们现有文件、表格和群聊方式在哪个环节造成了重复劳动或资料混淆。
- 是否愿意上传未公开规则，邀请试用需要哪些保密安排。
- 不同类型桌游需要多大程度的记录定制，基础字段是否足够。
- 非现场录入能否保留足够可靠的观察，组织者是否会持续补录。

试局首先服务已有的创作小组，不依赖公开社区规模，不强迫线下试玩数字化，也不替代设计判断。用户应当能从每次修改找到对应的试玩记录，并据此安排后续验证。
