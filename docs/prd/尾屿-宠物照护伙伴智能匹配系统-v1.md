## 一、项目命名与推荐题目

### 产品名称

- **首选名称：尾屿**
- **备选名称：宠契**

“尾屿”用于系统界面、Logo、演示和答辩中的产品称呼，表达为宠物与照护伙伴提供一个温暖、安心的连接空间。由于名称本身不直接说明业务，首次出现时应搭配说明，例如“尾屿——宠物照护伙伴智能匹配系统”。“宠契”作为备选名称，更突出照护需求与伙伴之间的契合和智能匹配。

### 正式推荐题目

**《面向城市社区的宠物照护伙伴智能匹配系统设计与实现》**

该题目能够交代应用场景、核心业务和技术特色，同时避免在标题中堆砌框架或夸大创新性。免费互助与有偿照护并存属于业务模式，可在正文中重点说明，无须全部写入题目。

### 备选题目

1. 《融合需求理解与多约束匹配的宠物照护伙伴推荐系统设计与实现》
2. 《面向社区生活圈的宠物照护互助与服务撮合系统设计与实现》
3. 《宠物照护需求发布、伙伴匹配与服务管理系统设计与实现》

第一项更突出AI和匹配方法，第二项更突出生活服务与双模式业务，第三项更突出完整软件系统。若导师重视算法特色，可优先考虑第一项；若导师重视系统实现，建议保留正式推荐题目。

## 二、项目定位

本项目首先是一项以顺利完成本科毕业设计、论文撰写和答辩演示为目标的软件开发课题。系统设计优先保证核心业务闭环完整、技术风险可控、实验可以复现和现场演示稳定；商业化不是项目验收目标，也不要求在毕设期间获得真实用户、收入或上线运营。文档中提到的商业模式只用于说明应用价值和未来拓展性，不反向增加当前系统的功能范围。

本系统面向城市养宠用户，以社区生活圈为首期服务范围，同时支持免费互助和有偿照护信息撮合。用户可以通过自然语言快速发布宠物照护需求，系统提取时间、宠物特征、服务内容、免费或有偿偏好及禁忌条件，在满足硬性约束的基础上，结合照护经验、时间、区域、历史表现和文本语义相似度推荐合适伙伴。

系统的核心目标不是建设一个复杂的宠物商业交易平台，而是降低宠物主人寻找临时照护帮助的门槛，减少填写和筛选成本，提升需求与照护伙伴之间的匹配质量，并通过照护反馈和熟悉伙伴机制缓解宠物主人在临时离开宠物时的担忧。

产品坚持以下原则：

- 同时支持免费互助和有偿照护，但共用一套业务流程，避免系统重复建设。
- AI用于减少填写成本和辅助匹配，不代替用户作出最终决定。
- 时间、区域、宠物类型和禁忌等硬条件通过规则过滤，描述性偏好通过向量语义辅助。
- 系统只提供信息撮合、服务记录和后台治理，不处理真实支付与资金纠纷。
- 以本地或局域网稳定演示为目标，不承担生产级部署和真实商业运营。

## 三、研究背景与实际问题

城市养宠用户在出差、旅行、加班、身体不便或临时有事时，经常面临短期喂食、遛宠、陪伴、铲砂和上门查看等照护需求。现有解决方式通常依赖熟人求助、群聊询问或综合生活服务平台搜索，容易出现需求描述不完整、寻找效率低、照护经验不匹配、服务时间冲突、距离过远以及宠物特殊禁忌被忽略等问题。

宠物照护也不同于普通物品代取。宠物主人不仅关心服务任务是否完成，还会关心照护者是否理解宠物习惯、能否遵循特殊要求，以及能否及时反馈宠物状态。因此，这一场景同时包含服务效率、信任建立和情感安心三类需求。

另一方面，不同照护任务的复杂程度并不相同。短时喂食或顺路查看可以通过邻里免费互助解决，而多次上门、长时间陪伴或具有特殊要求的照护任务，可能需要有偿服务。系统因此采用免费互助与有偿照护并存的模式，让用户根据实际任务复杂程度选择合适的服务方式。

本项目拟解决的核心问题是：

> 如何从自然语言宠物照护需求中提取关键字段，并在满足时间、区域、宠物类型、服务模式和禁忌等硬性约束的前提下，融合照护经验、历史表现和文本语义相似度，为用户推荐更加合适的照护伙伴。

## 四、目标用户与使用场景

### 4.1 用户范围

产品面向城市普通养宠用户，首期以社区、商圈或行政区域组成的生活圈为基本撮合单元。用户不被限制在单个小区，但系统不公开精确住址，也不开发实时定位与路线导航。

### 4.2 用户角色

#### 宠物主人

宠物主人可以建立宠物档案、发布照护需求、确认AI提取结果、查看匹配推荐、向照护者发送邀请、确认服务约定、查看照护反馈并完成评价。

#### 照护服务者

照护服务者可以维护照护经验、可接受宠物类型、服务内容、可用时间、服务区域和服务模式。服务者可以选择接受免费互助、有偿照护或两种模式，并对收到的邀请进行接受或拒绝。

同一账号可以同时拥有宠物主人和照护者身份，不需要创建两个独立账号。

#### 平台管理员

管理员负责用户、宠物档案、照护需求、服务记录、评价举报、分类规则、AI提取记录、匹配参数和运营数据管理。

### 4.3 典型使用场景

用户计划周末外出，需要找一位附近、有猫咪照护经验，并能在指定时间上门喂食和铲砂的照护者。用户输入：

> 这周六下午要出门，想找附近的人帮忙喂猫和铲砂，大概来一次就行，免费互助最好，也可以接受30元以内的有偿帮助。猫比较怕生，家里有大型犬的暂时不考虑。

系统将需求提取为：

- 时间：本周六下午；
- 宠物类型：猫；
- 服务内容：喂食、铲砂；
- 服务次数：1次；
- 服务模式：免费互助与有偿照护均可；
- 预算上限：30元；
- 特殊情况：宠物怕生；
- 排除条件：不接受家中有大型犬的照护者。

用户确认或修改后发布。系统先过滤时间冲突、区域不符、服务类型不支持、服务模式不兼容或违反禁忌条件的候选人，再按照照护经验、时间契合度、区域、历史表现和语义相似度排序，最后展示推荐伙伴及推荐理由。

## 五、免费互助与有偿照护双模式

### 5.1 服务模式

需求发布时提供三种选择：

| 模式 | 说明 |
|---|---|
| 免费互助 | 不填写价格，优先匹配愿意提供免费互助的用户 |
| 有偿照护 | 填写参考报酬，可选择按次、按小时或面议 |
| 两者均可 | 免费互助优先，同时允许有偿服务者响应 |

服务者档案也提供“仅免费互助”“仅有偿照护”和“两者均接受”三种模式。匹配时需要先检查需求方和服务者的模式是否兼容。

| 需求模式 | 服务者模式 | 是否兼容 |
|---|---|---|
| 免费互助 | 仅免费互助 | 是 |
| 免费互助 | 仅有偿照护 | 否 |
| 有偿照护 | 仅有偿照护 | 是 |
| 有偿照护 | 仅免费互助 | 否 |
| 两者均可 | 免费互助或有偿照护 | 是 |

### 5.2 有偿模式边界

有偿模式只记录参考报酬、计价方式、双方确认的约定金额和服务状态。系统不接入微信或支付宝，不保存银行卡信息，不处理退款、佣金、保证金、电子合同和资金纠纷。

页面中应明确提示：

> 本平台仅提供信息匹配和服务记录，具体报酬与履约事项由双方自行确认。

### 5.3 免费互助边界

第一版不建立互助币、积分兑换或复杂等级制度，避免增加积分发放、作弊、冻结、过期和申诉等规则。系统只记录免费互助次数、服务完成率、好评率和被收藏次数。这些数据可以作为推荐解释和历史表现的一部分，但不作为虚拟货币。

## 六、项目边界

### 6.1 项目要做的内容

- 只开发B/S架构的响应式Web应用，不开发微信小程序、原生App或其他独立客户端。
- 普通用户端兼容桌面、平板和手机浏览器，并根据屏幕宽度调整导航、列表、表单和详情布局；管理后台以桌面浏览器为主要使用环境，同时保证基础响应式显示。
- 建立用户、宠物和照护服务者档案。
- 支持免费互助、有偿照护及两者均可三种服务模式。
- 支持自然语言快速发布和结构化表单发布。
- 使用AI提取需求字段，并由用户确认后正式发布。
- 使用硬约束过滤与软偏好排序进行伙伴匹配。
- 实现服务邀请、接受或拒绝、服务记录和照护反馈。
- 实现评价、收藏、举报和平台管理流程。
- 通过匹配实验和可用性实验验证特色模块。

### 6.2 项目明确不做的内容

- 不开发微信小程序、原生App或其他独立移动客户端；未来如有实际需要，可复用后端接口另行开发。
- 不接入真实支付、退款、抽佣和保证金。
- 不开发即时聊天，只保留邀请说明、预约备注、状态通知和照护反馈。
- 不开发实时定位、路线导航和精确住址公开。
- 不提供兽医诊断、用药建议或医疗决策。
- 不声称AI能够判断某人绝对可信或保障线下安全。
- 不从头训练大语言模型。
- 不使用微服务、消息队列或容器编排等非必要架构。
- 不以真实商业收入、大量真实用户或生产级运营作为完成标准。
- 不要求公网、云服务器、域名、HTTPS、高可用或自动扩缩容。

## 七、核心功能模块

### 7.1 用户、宠物与服务者档案

用户可以维护账号资料、角色状态和服务区域。宠物档案包括类型、年龄、体型、性格标签、日常习惯、照护注意事项和禁忌条件。服务者档案包括照护经验、可接受宠物类型、服务内容、可用时间、服务区域、服务模式和有偿参考价格。

### 7.2 需求快速发布与AI结构化

系统提供两种发布方式：

- 快速发布：用户输入自然语言，AI提取结构化字段；
- 普通发布：用户使用传统表单直接填写。

AI提取字段至少包括时间、区域、宠物类型、服务内容、服务次数、服务模式、预算和特殊禁忌。AI结果必须通过JSON Schema等方式校验，并在用户确认或修改后才能保存为正式需求。

### 7.3 多约束伙伴匹配

匹配分为硬性约束过滤和软性条件排序两个阶段。

硬性条件包括时间、区域、宠物类型、服务内容、服务模式、必要经验、禁忌条件和账号状态。不满足硬性条件的候选人不得进入推荐列表。

软性条件包括照护经验、时间契合程度、区域便利度、需求与服务者描述的语义相似度、历史评分、完成率和是否为熟悉伙伴。

### 7.4 服务邀请与约定

宠物主人向推荐对象发送邀请，服务者可以接受或拒绝。接受后，双方确认日期、照护内容、服务模式、参考报酬或约定金额以及备注，形成服务记录。

### 7.5 照护反馈与情感安心

照护者在服务期间或服务结束后提交文字、图片和任务完成情况。主人通过反馈了解宠物状态，并在结束后确认服务结果。该模块体现宠物照护区别于普通生活服务的信息和情感需求。

### 7.6 评价、收藏与举报

服务完成后，用户可以从守时、沟通、照护规范和反馈完整性等维度评价。用户可以收藏合适的照护伙伴，以后优先邀请。系统支持举报、黑名单和申诉状态管理，评价只能关联已完成的服务记录。

### 7.7 管理后台

后台包括用户管理、宠物档案管理、照护需求审核、服务记录管理、分类配置、评价与举报处理、AI提取记录、匹配参数配置和运营统计。

运营统计可展示需求数量、免费与有偿需求占比、匹配成功率、热门服务类型、宠物类型分布、平均匹配时间、服务完成率、举报数量和用户活跃趋势。

## 八、最小可行版本

最小可行版本必须保证以下闭环：

> 用户与宠物档案 → 服务者档案 → 快速或普通需求发布 → AI提取并确认 → 硬条件过滤 → 伙伴推荐 → 发出邀请 → 服务确认 → 照护反馈 → 评价 → 后台审核与统计。

第一优先级包括账号与权限、宠物档案、服务者档案、双模式需求发布、匹配推荐、邀请与服务记录、文字反馈、评价和基础后台。

第二优先级包括图片反馈、收藏伙伴、匹配参数可视化、复杂统计图表和更多推荐解释。如果进度紧张，可以推迟第二优先级，但不得破坏核心业务闭环。

## 九、技术架构

### 9.1 架构原则

项目暂定采用模块化单体架构。当前已确定前端以React生态实现响应式Web应用；后端、数据库和AI方案属于基于现有需求给出的推荐选型，可在不破坏核心业务、实验设计和进度目标的前提下，根据导师意见、开发环境和实际学习成本进行调整。技术栈的作用是支持项目完成，不作为为了展示框架数量而设置的硬性约束。

在当前推荐方案中，React负责普通用户端和管理后台，FastAPI承担业务接口与AI协调，PostgreSQL保存关系型业务数据，pgvector提供文本向量存储和相似度查询。

推荐架构如下：

```text
React + TypeScript
        ↓ REST API
Python + FastAPI
        ↓
PostgreSQL + pgvector
        ├── 关系型业务数据
        └── 文本Embedding向量

FastAPI
  ├── 调用低成本大模型API完成需求结构化
  └── 调用固定Embedding模型或API生成文本向量
```

### 9.2 核心数据流

```text
用户输入照护描述
        ↓
FastAPI接收并调用AI提取字段
        ↓
JSON Schema与业务规则校验
        ↓
用户确认或修改结构化结果
        ↓
PostgreSQL保存正式需求
        ↓
SQL执行硬性约束过滤
        ↓
pgvector计算文本语义相似度
        ↓
FastAPI融合各项分数并排序
        ↓
返回Top-K伙伴及推荐解释
        ↓
邀请、确认、照护反馈与评价
        ↓
管理后台审核和运营统计
```

### 9.3 当前推荐技术栈与可调整项

下表是现阶段的推荐组合，不代表全部组件已经被强制确定。React响应式Web是已确认的前端形态；其他工具应在系统设计或编码初期完成小范围验证后再最终锁定。

| 层次 | 当前建议 | 确定程度与调整原则 |
|---|---|---|
| 前端框架 | React + TypeScript，构建工具可选Vite | React生态已确认；TypeScript和构建工具可根据现有基础调整 |
| UI组件 | 从成熟的React UI生态中选择 | 尚未确定；可比较Ant Design、MUI、Mantine、shadcn/ui等，按响应式能力、开发效率和风格选择，不在立项阶段写死 |
| 路由 | React Router或同类成熟方案 | 暂定，可根据最终工程结构调整 |
| 接口请求 | 原生Fetch、Axios或TanStack Query | 暂定；只选择项目实际需要的最简单方案 |
| 状态管理 | React内置状态，必要时再选轻量状态库 | 不预先强制引入Redux、Zustand等库 |
| 图表 | ECharts或其他成熟React图表方案 | 暂定；以后台统计需求和开发效率为准 |
| 后端 | Python + FastAPI | 推荐方案；如无新的导师硬性要求，优先保持单一Python后端 |
| ORM与迁移 | SQLAlchemy + Alembic或同类方案 | 暂定；应选择与后端框架兼容且本人能够稳定使用的工具 |
| 数据库 | PostgreSQL | 推荐方案；适合统一承载业务数据与向量扩展 |
| 向量能力 | pgvector | 推荐方案；仅在语义匹配实际实施时启用，不为展示技术而强制使用索引 |
| AI需求理解 | 低成本大模型API＋结构校验 | 模型供应商和具体接口尚未确定，必须保留普通表单与规则降级 |
| 文本向量 | 固定的中文Embedding模型或API | 具体模型尚未确定，应结合向量维度、中文效果、成本和本地环境选择 |
| 图片存储 | 本地文件目录 | 满足毕设演示；不强制引入对象存储 |
| 测试 | 后端接口与匹配逻辑测试、关键前端流程测试 | 测试框架可按最终技术选型确定 |
| 运行方式 | 本地启动；Docker Compose可选 | 以稳定演示和易复现为目标，不做生产部署 |

技术组件最终确定前，应逐项检查它解决了什么需求、不使用它会有什么影响，以及引入收益是否大于学习、调试和答辩解释成本。

### 9.4 响应式Web前端说明

本项目只开发Web应用。普通用户端与管理后台可以共用一个React工程，也可以在同一代码仓库中拆分为两个前端子应用；具体组织方式在系统设计阶段根据页面数量和维护成本确定。

普通用户端需要采用响应式布局，兼容桌面、平板和手机浏览器，但它仍是同一套Web应用，而不是独立的手机H5、小程序或App。响应式适配不应只是按比例缩小页面，而应根据视口调整交互结构：手机端可以使用紧凑导航、单列卡片和分步表单，桌面端可以使用顶部导航、多列内容、筛选侧栏和详情面板。

管理后台以桌面端为主要环境，重点保证表格、审核工作台和数据图表的可用性，同时提供基础的窄屏兼容。除非导师后续提出硬性要求，不额外开发微信小程序、React Native或原生App。

这种设计既能满足毕设的开发与演示要求，也能通过前后端接口解耦，为未来可能的小程序或App扩展保留后端复用条件；但未来扩展不属于本次毕业设计的验收范围。

### 9.5 PostgreSQL与pgvector选型说明

PostgreSQL与pgvector可以在同一数据库中存储关系型业务数据和向量数据。pgvector支持余弦距离、欧氏距离和内积，并支持精确最近邻及HNSW、IVFFlat近似索引。

本项目预计只有数百到数千条测试数据，第一版可以直接采用精确向量查询，不必立即创建HNSW索引。如果后续进行性能实验，可以将HNSW作为扩展方案，比较精确检索与近似检索的响应时间和召回率。

示例表结构：

```sql
CREATE EXTENSION vector;

CREATE TABLE provider_profiles (
    id BIGSERIAL PRIMARY KEY,
    description TEXT NOT NULL,
    embedding VECTOR(768)
);
```

示例余弦相似度查询：

```sql
SELECT
    id,
    description,
    1 - (embedding <=> :query_vector) AS similarity
FROM provider_profiles
ORDER BY embedding <=> :query_vector
LIMIT 10;
```

MySQL也可以通过JSON、BLOB或序列化形式保存向量，并在Python层计算相似度；部分较新的MySQL产品或环境也提供向量相关能力。但是，为了减少组件、统一关系过滤与向量查询，并提高论文中的架构清晰度，本项目优先选择PostgreSQL＋pgvector，而不是MySQL＋额外向量计算方案。

### 9.6 不采用复杂架构的原因

- 不增加Spring Boot业务后端，因为FastAPI已经能够处理全部业务和AI功能。
- 不拆分微服务，因为个人本科项目不存在独立扩缩容和服务隔离需求。
- 不引入消息队列和Kubernetes，因为它们不解决项目核心问题。
- 不单独部署向量数据库，因为pgvector已经满足毕设规模的向量查询。
- 不从头训练大模型，论文贡献集中在需求结构化、多约束过滤、混合排序与实验验证。

## 十、匹配方法设计

### 10.1 硬约束过滤

以下条件必须先通过普通SQL和业务规则过滤：

- 服务时间存在完全冲突；
- 服务者不接受该宠物类型；
- 服务者无法提供需求指定的照护内容；
- 服务模式不兼容；
- 服务区域不覆盖需求区域；
- 缺少需求明确要求的必要经验；
- 违反宠物特殊禁忌；
- 服务者账号或服务资格已被停用。

任何硬性条件不满足，都不得进入推荐列表。

### 10.2 软偏好排序

通过硬约束过滤后，对候选人进行综合排序。初始评分公式可以设计为：

```text
综合匹配分 =
语义匹配度 × 25%
+ 照护经验匹配度 × 25%
+ 时间契合度 × 20%
+ 历史服务表现 × 15%
+ 区域便利度 × 10%
+ 熟悉伙伴加分 × 5%
```

该权重只是初始方案，不能直接宣称为最优。论文中应使用验证集或消融实验分析不同权重设置的影响。

### 10.3 向量的使用边界

向量只用于处理描述性的软偏好，例如需求描述、服务者自我介绍、擅长照护的宠物性格和历史经验描述。时间、区域、宠物类型、服务模式和禁忌等明确条件不能只依赖向量相似度判断。

### 10.4 推荐解释

系统应为推荐结果生成基于真实字段的解释，例如：

> 推荐理由：具有多次猫咪照护记录；周六下午时间可用；接受免费互助和有偿照护；服务区域一致；相关照护描述与本次需求较匹配。

系统不能生成“绝对安全”“完全可信”等无法验证的结论。

## 十一、特色与创新点

### 11.1 自然语言照护需求结构化

用户可以使用日常语言描述需求，系统自动提取时间、宠物、服务内容、服务模式、预算和禁忌等字段，并在用户确认后进入匹配流程。该功能直接降低表单填写成本，而不是为了使用大模型而增加AI模块。

可验证指标包括字段级准确率、精确率、召回率、信息完整率、任务发布时间和用户修改次数。

### 11.2 硬约束与语义偏好融合的伙伴匹配

系统先排除违反时间、区域、宠物类型、服务模式和禁忌条件的候选人，再融合照护经验、历史表现和文本语义相似度排序。该方法比仅按距离、仅按标签或仅按向量相似度更符合宠物照护需求。

可验证指标包括约束违反率、Precision@K、Recall@K、NDCG@K和响应时间。

### 11.3 免费互助与有偿照护统一撮合

系统使用单一业务流程支持免费互助、有偿照护和两者均可三种模式，使简单任务能够通过邻里互助解决，复杂任务也能通过有偿方式扩大候选范围。该设计强调低门槛和实际适配性，不构建复杂交易系统。

### 11.4 照护反馈与熟悉伙伴机制

照护者通过文字、图片和任务完成项反馈宠物状态，主人可以收藏合适的照护者并在未来优先邀请。该机制体现宠物照护中的长期信任和情感安心需求。

## 十四、论文研究问题与主线

### 14.1 研究问题

**RQ1：** AI需求理解能否准确地将自然语言宠物照护需求转换为结构化约束，并降低用户填写成本？

**RQ2：** “硬约束过滤＋多因素加权排序＋文本语义相似度”是否比简单条件筛选或单一标签匹配获得更好的伙伴推荐结果？

**RQ3：** 基于真实匹配字段生成的推荐解释，是否有助于用户理解和选择推荐伙伴？

### 14.2 论文章节建议

1. 绪论：研究背景、研究意义、相关应用和项目目标。
2. 相关技术：React、FastAPI、PostgreSQL、pgvector、自然语言结构化、文本向量和推荐排序。
3. 需求分析：用户角色、业务流程、功能需求、非功能需求和项目边界。
4. 系统总体设计：模块化单体架构、数据库、功能模块和核心数据流。
5. 需求理解与伙伴匹配方法：字段设计、规则校验、硬约束过滤、语义检索、评分公式和推荐解释。
6. 系统实现：用户端、服务者功能、管理后台和核心流程实现。
7. 系统测试与实验：功能测试、性能测试、需求发布可用性实验和匹配方法对比实验。
8. 总结与展望：成果、局限，以及在毕设完成后的可选扩展方向。商业化、真实支付、身份认证、小程序或App均只作为未来拓展性讨论，不属于当前成果要求。

## 十五、实验与评价方案

### 15.1 AI快速发布实验

比较传统表单和AI快速发布两种方式。

评价指标包括：

- 任务发布平均耗时；
- 用户填写或修改次数；
- 关键字段完整率；
- 字段提取准确率、精确率和召回率；
- 用户操作满意度。

实验应分析AI提取错误案例，例如时间表达歧义、预算与服务模式冲突、宠物禁忌遗漏等。

### 15.2 匹配方法对比

建议设置三组方法：

| 方法 | 说明 |
|---|---|
| 基线A | 仅按区域、宠物类型和服务模式筛选，再按历史评分排序 |
| 基线B | 硬约束过滤＋人工标签加权排序 |
| 推荐方法C | 硬约束过滤＋标签加权＋文本语义相似度 |

主要评价指标包括：

- 约束违反率：推荐结果违反明确硬性条件的比例；
- Precision@K：前K个推荐中被标注为合适的比例；
- Recall@K：合适候选人中被成功推荐的比例；
- NDCG@K：系统排序与人工兼容度排序的一致程度；
- 平均响应时间：完成一次过滤和排序所需时间；
- 推荐覆盖率：系统能够为多少需求返回有效候选人。

### 15.3 消融与性能实验

可以移除语义相似度、历史表现或熟悉伙伴加分，观察各项指标变化，从而说明每个模块的实际贡献。

性能测试只需面向毕设规模，例如在100、500、1000和5000条服务者数据下测试响应时间。数据量较小时使用pgvector精确查询即可；如果实现HNSW，可以比较精确检索和近似检索的速度与召回率，但HNSW不是必做项。

### 15.4 功能与可用性测试

功能测试覆盖账号权限、需求状态流转、服务模式兼容、邀请状态、评价条件、举报处理和AI失败降级。

如有测试用户，可采用简化任务完成率、1—5分满意度或SUS量表评估可用性。

## 十九、答辩演示流程

建议将演示控制在5—8分钟。

### 第1分钟：问题与定位

说明宠物主人临时外出时寻找照护帮助的痛点，介绍免费互助与有偿照护并存、城市定位和社区生活圈落地的产品模式。

### 第2分钟：宠物与服务者档案

展示宠物特点、照护禁忌、服务者经验、服务区域和接受的服务模式，说明这些字段如何参与匹配。

### 第3分钟：AI快速发布

输入一段自然语言需求，展示AI提取出的时间、宠物、照护内容、免费或有偿模式、预算和禁忌，再展示用户确认过程。

### 第4分钟：智能匹配

展示推荐列表、各项匹配分和推荐理由，同时展示某个候选人因时间冲突、模式不兼容或违反禁忌而被排除。

### 第5分钟：服务闭环

演示邀请、接受、服务约定、照护反馈和评价，突出反馈给宠物主人带来的安心感。

### 第6分钟：管理后台

展示需求审核、服务记录、举报处理、免费与有偿需求占比以及匹配成功率等运营统计。

### 第7分钟：实验结果

展示传统表单与AI快速发布对比，以及三种匹配方法的指标结果，说明系统在发布效率、约束违反率和Top-K推荐质量上的表现。

## 二十、与导师沟通时需要确认的问题

1. “智能匹配”是否满足学院对算法、特色模块或创新点的要求。
2. 导师更重视完整软件系统，还是需求理解和匹配算法实验。
3. 免费互助与有偿照护并存是否适合题目，是否需要在标题中体现。商业化只作为未来拓展性说明，不作为毕设验收内容。
4. 使用模拟用户数据与人工标注匹配数据是否可以接受。
5. 响应式Web是否满足终端形式要求；若无额外硬性要求，本项目不开发小程序或App。
6. 是否要求公网部署；若无硬性要求，建议采用本地或局域网演示。
7. 是否允许使用低成本大模型API和开源Embedding模型。
8. 学院对论文篇幅、代码量、测试用户数量和实验指标有何具体要求。
9. 是否允许在实现阶段根据开发效率调整React UI组件库、请求库、状态管理和图表工具，而不改变总体架构与功能目标。

## 二十一、最终判断

**立项建议：推荐立项。**

该题目具备明确的城市生活痛点和目标用户，用户端、服务者功能与管理后台能够形成完整的软件成果。免费互助与有偿照护并存提高了场景适配性，但通过“单一流程＋服务模式字段”控制了复杂度。AI需求理解直接降低发布门槛，混合匹配方法可以通过基线和量化指标进行验证，照护反馈和熟悉伙伴机制又体现了宠物照护中特有的情感安心需求。

项目的关键边界是：

> 做“低门槛的宠物照护需求理解与伙伴匹配系统”，不做包含真实支付、即时聊天、导航、医疗诊断和履约担保的综合宠物商业平台。

项目的关键技术原则是：

> 双模式、单流程；确定只做React生态的响应式Web应用；当前推荐FastAPI单后端与PostgreSQL＋pgvector方案；硬条件使用规则过滤，软偏好使用向量语义辅助；AI减少操作，不替用户作决定；具体UI组件库、请求库、图表工具和模型服务可在实现阶段调整；以本地稳定演示和可复现实验为完成目标。

在严格控制范围的前提下，本项目适合个人在3—4个月内完成，具有较好的论文可写性、软件完整度和答辩展示效果。未来商业化、小程序、App、真实支付和生产部署只作为可选拓展设想，用于答辩中的发展展望，不作为当前项目成功与否的判断标准。当前第一优先级是完成稳定的响应式Web系统、可解释的匹配方法、可复现的实验以及完整论文。
