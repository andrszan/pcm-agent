# PCM 官网产品需求文档 v1

> 2026-10-10｜PCM 开源项目官网的独立开发输入。
>
> 本文完整定义一个内容型 Next.js 官网项目。交给 PCM Demo 后应实现本文全部需求，以官网页面、内容、SEO 和独立前端工程作为交付结果。工作台成品是介绍素材和事实来源，官网在独立工作区实现。

## 1. 产品定位与工程身份

PCM 官网用于介绍 PCM 开源项目，让访问者理解它能做什么、看到真实界面与成果、了解本地使用条件，并通过快速开始、文档和源码入口获取与使用产品。

| 标识 | 内容 |
|---|---|
| 品牌 | PCM 官网 |
| 英文名称 | PCM Website |
| 功能副标题 | PCM 开源项目介绍与使用指南 |
| 工程标识 | `pcm-website`，用于本官网工作区命名，与 `pcm` 工作台工作区分别管理 |
| 产品 ID | `PCM-20261010-013` |
| 工程形态 | Next.js 独立前端项目，业务代码位于 `frontend/` 独立 Git 仓库，根仓管理文档与协作资料 |
| 内容语言 | 中文为默认语言，技术名称与代码标识保留原文 |
| 当前交付结果 | 官网前端代码、适用的内容与媒体资产、安装构建运行说明及验证结果 |

访问者是希望了解 PCM、判断它是否符合自身需要、获取源码或学习如何使用的人。不预设职业身份作为使用门槛。

## 2. 官网介绍的对象

PCM 是开源的 AI 自动化产品开发工作台，首版支持 macOS 本地运行。用户通过对话提供想法和已有资料，形成并确认 PRD 后，由 PCM 连续进行开发与质量改进，取得代码和文档，并能对已有成果提交反馈继续迭代。

产品体验包括工作台配置、自动开发进展、按需暂停与恢复、成果查看，以及反馈迭代。默认开发资源由产品提供或自动准备，用户主要填写模型服务信息和具体项目必需的外部资源。GitLab 远程同步为可选能力，本地交付可以独立完成。

以上信息用于形成官网的产品介绍内容。页面中的能力状态、使用命令、界面和案例应以届时真实的工作台交付结果为准，不能把尚未完成的能力宣传为已经可用。

GitHub 是 PCM 自身开源仓库的候选平台，具体地址尚未确定。它与产品内可选的 GitLab 同步是不同用途，介绍时应避免混淆。

## 3. 核心访问过程

1. 访问首页，理解 PCM 的用途及开源、本地运行的产品形态。
2. 阅读从想法到 PRD、自动开发、代码与文档交付、反馈迭代的说明。
3. 查看真实工作台界面或案例，判断实际成果是否符合自己的预期。
4. 了解 macOS、模型服务和必要资源等使用条件。
5. 进入快速开始、使用文档或实际源码仓库，继续获取并在本地使用 PCM。

导航和主要行动入口应与上述过程一致。页面可以按内容组织成栏目或独立页面，具体路由由设计确定，不为形式完整重复拆分相同内容。

## 4. 内容与页面需求

### 4.1 产品介绍

首页应直接说明产品名称、用途、开源与本地运行形态，以及用户最终能够取得的成果。

用通俗文字解释“对话形成 PRD，再自动开发”的过程，避免只罗列 Agent、SDK 或编排等内部术语。主要入口清楚引导访问者查看快速开始、文档和源码。

产品当前以代码、文档和实际验证结果为交付边界。页面承诺应与这一事实一致。

### 4.2 核心能力与使用流程

围绕真实使用过程介绍以下内容：

- 提供想法、已有文字资料和界面参考，整理当前 PRD。
- 在工作台配置必要信息，使用产品提供或自动准备的默认开发资源。
- 启动自动开发与质量改进，查看真实进展和成果。
- 按需要暂停、继续或停止任务，并处理实际资源缺口。
- 对生成项目提交反馈，在已有成果上继续迭代。

每项说明回答“用户能做什么、会得到什么”，不要把内部步骤编号当作访问者必须理解的概念。

### 4.3 真实界面与案例

使用正式工作台的代表性截图和实际生成成果展示产品。案例说明输入目标、实际完成的内容和可核验结果，不以虚构成功率、用户数量或固定开发时长制造宣传效果。

截图应展示有意义的状态与成果，裁剪和排版服务于内容理解，并检查其中是否含有凭据、个人信息或内部环境资料。正式文档配图与官网资产进入约定的受跟踪位置，临时验收截图遵循工作区截图规范。

媒体以真实产品截图和案例为主。若其他图像确有助于解释使用过程，可按工作区已有媒体能力获取并固化；开发工具私有配置与凭据不进入前端资源。

### 4.4 快速开始与使用条件

快速开始应帮助访问者理解最短的实际使用路径：

1. 获取源码并准备声明支持的 macOS 环境与必要依赖。
2. 按经过验证的说明执行安装和启动命令。
3. 打开工作台，填写模型服务等必要信息并检查可用性。
4. 创建第一个项目并进入产品讨论。

说明本地运行与调用远程模型的区别，模型服务需要的账号、凭据及可能产生的调用费用以真实使用条件为准。

完整安装、配置和故障处理说明以工作台项目的权威使用文档为准。官网提供最短路径摘要和明确链接，更新时检查二者一致，避免维护相互矛盾的两套操作说明。

### 4.5 文档与源码入口

提供实际可访问的使用文档和源码地址。入口文字应说明目标用途，不能将仓库页面、官网页面和本地工作台混为同一个地址。

真实地址尚未确定时保留准确的准备状态，不生成看似可用的虚假链接。正式交付中需要使用的文档与源码入口，应在资源明确后完成连通性核验。

## 5. 视觉与交互要求

官网使用清楚的内容层级、易读的中文排版和一致的品牌表达，让访问者快速找到产品说明、真实展示和使用入口。

- 首页的核心用途与主要入口明确，长内容具有可理解的导航。
- 产品截图能够辨认关键内容，不以装饰遮挡真实界面。
- 桌面和手机宽度下均能正常阅读、导航和使用链接，页面不产生无意义的横向滚动。
- 链接、按钮、焦点状态、文字对比与图片说明满足基本可访问性要求。
- 导航、返回和适用的页面状态在真实浏览器中验证，不以静态截图代替交互检查。

## 6. SEO 与内容可发现性

Next.js 页面应输出可索引的真实正文，而不只是一个需要用户操作后才出现内容的空壳。

需要落实：

- 每个公开页面具有与实际主题一致的标题和描述。
- 标题层级、内部链接和页面路径清楚、稳定。
- 依据真实站点地址配置规范 URL、适用的站点地图和抓取规则。
- 结构化数据只表达页面真实包含的内容。
- 搜索内容围绕已实现能力和实际使用问题组织，不堆砌关键词。
- 产品截图和页面资源的加载方式与体积适合内容阅读。

官网域名尚未确定时，区分可在本地验证的页面结构、正文和元信息，以及需要真实域名才能最终核验的 URL 项。不得以占位地址宣称发布配置已经通过验证。

## 7. 开发输入与资料依赖

官网在工作台核心体验稳定后开发，以获得准确的使用说明、界面截图和真实案例。

需要的资料包括：

- 工作台当前真实可用的功能说明与使用条件。
- 已验证的安装启动、配置和首次使用说明。
- 可公开展示的工作台截图与代表性成果。
- 实际文档入口、源码仓库地址，以及发布准备时确定的官网域名。

资料能从已有产品交付中核验和提取的，由开发 Agent 自行处理。实际外部地址或授权条件缺失时准确说明所缺内容，不伪造资料，也不要求用户重复整理已有事实。

官网可以独立安装、构建和本地运行。运行端点使用官网工作区自身的 `.pcm/runtime.json` 分配，不占用工作台项目的端口或改动其运行状态。
