# 白长桌：品牌设计审阅与成果交付

白长桌是为一家品牌设计公司及其企业客户提供的纯桌面 Web 协作应用。它以设计成果为中心，把资料准备、方案审阅、正式反馈、定稿确认与文件交付放在同一个项目空间中，让双方知道当前在讨论哪份设计、下一步由谁处理，以及最终应该使用哪些文件。

- 中文品牌名：白长桌。
- 功能副标题：品牌设计审阅与成果交付。
- 英文品牌名：暂不设置，目录中使用 `null`。
- 工程标识：`design-signoff`，用于后续 Agent 工作区及工程目录命名，不代表仓库已经创建。
- 文档性质：用于继续讨论和深化的产品初稿，不是详细技术设计或开发验收合同。

## 已确认的方向与设计提案

用户已确认选择品牌设计公司的客户协作与交付方向，采用纯 Web 形态；客户端必须具有值得打开电脑处理的任务，不依赖手机应用、小程序或客户随时响应。通知可以通过工作邮箱引导用户回到系统。

用户已接受“客户多人参与审稿，一位负责人统一提交反馈和确认定稿”的协作方式，并确认上述品牌、功能副标题及工程标识。

本文对项目结构、角色权限、页面、反馈规则、统计和交付方式的展开属于当前设计提案。此前讨论的功能构成本次建议范围，不把选定方向或名称解释为对全部细节的逐项确认。具体文件规模、客户组织方式和生产运行条件仍需依据真实业务确定。

## 为什么客户愿意打开电脑

企业客户审阅包装、菜单、海报等设计时，需要看清细节、比较方案、整理同事意见并作出正式确认。相关品牌资料和交付文件通常也在工作电脑上。这些任务天然适合大屏与文件操作，不是为了迁就技术选型而搬到 Web。

系统不要求客户每天登录维护进度。客户在收到方案、需要补资料、需要确认或成果已交付时进入，完成一次有明确结果的工作。设计团队负责维护内部推进信息，客户不需要替供应商更新任务状态。

产品希望减少三类具体问题：

- 反馈散落在聊天和附件中，双方不清楚哪些意见需要执行。
- 当前送审稿不明确，双方可能围绕不同内容反馈或确认。
- 交付文件缺少用途与对应定稿说明，客户在使用时拿错文件或找不到源文件。

## 服务对象与项目结构

本次面向一家设计公司，不建设多商家交易平台。设计公司可以服务多个企业客户，每个客户可以有多个项目；同一客户的成员也不默认有权查看该客户的全部项目，而是按项目邀请参与。

建议以“客户—项目—设计交付项”组织业务。项目说明合作范围、负责人、关键日期和公共资料；交付项是能够独立审阅、定稿及交付的成果，例如包装设计、门店菜单或宣传海报。

一个项目中的交付项可以处于不同阶段。包装已经定稿，不应迫使仍在修改的菜单同步完成。项目概况汇总各项实际情况，不用单一的完成百分比替代业务状态。

交付项可以展示多个备选方案。备选方案是并列的设计方向；送审时应明确当前请客户选择或确认的方案，避免把候选方向与后续修订混为一谈。

### 贯穿示例

一家咖啡品牌委托设计公司制作秋季新品包装、门店菜单和宣传海报。客户提交品牌标志、文案与尺寸要求，设计团队分项发布方案。

客户的市场同事和品牌负责人分别审阅，负责人整理成正式反馈。设计师处理后更新当前送审稿，客户查看处理说明和本轮正式反馈，再决定继续修改或定稿。设计公司按已确认内容整理印刷文件、线上图片和必要源文件，客户核对后确认交付。

该示例仅帮助理解业务，不构成真实客户、成交记录或已发生项目。

## 参与者如何协作

| 角色 | 主要职责 |
| --- | --- |
| 项目负责人 | 建立项目与交付项，明确范围和日期，邀请成员，安排工作，正式发布方案和交付内容，处理项目异常。 |
| 设计师 | 查看资料与工作要求，准备设计稿，处理反馈，上传修订和交付文件。 |
| 客户成员 | 查看获邀项目，提供资料，对具体方案提出意见，查看和下载有权访问的成果。 |
| 客户负责人 | 在成员权限基础上，汇总并正式提交反馈，选择方案，确认定稿及交付验收。 |
| 公司管理员 | 管理内部账号与客户资料，配置公司展示信息，维护项目负责人及必要的访问权限。 |

内部角色允许兼任，小团队不必为了角色划分增加人员。每个项目指定一位当前客户负责人；只有一位客户参与时，该成员可以直接承担负责人职责。

负责人变更需要由项目负责人明确处理并通知受影响成员。此前已经提交的正式反馈、定稿和交付确认仍保留原操作者，不能改记到新负责人名下；不另建完整的人员变更历史。

客户只能访问获邀项目中已发布的内容。设计团队的草稿、内部备注和任务讨论对客户不可见。上传文件不等于发布方案，发布是一项明确动作。

## 从准备资料到确认定稿

### 建立共同理解

项目负责人创建项目和交付项，说明成果用途、约定范围、预计审阅与交付日期，并邀请客户成员。

客户可以提交品牌资料、文案、参考图片和其他附件。缺少资料时，团队提出具体补充请求，客户能够看清缺少什么、影响哪个交付项，以及提交后是否已被接收。资料更新不提供逐次编辑日志；当前送审稿应标明采用的资料，避免资料变化后失去审阅上下文。

项目日期属于当前协作约定，不是自动生成的承诺；发生范围变化或延期时，由项目负责人更新当前范围、日期和说明，并通知相关成员，不保留逐次编辑流水。

### 发布可以审阅的方案

设计师上传预览与方案说明，内部确认后由有发布权限的成员正式送审。交付项的日常审阅只显示一份当前送审稿，明确包含哪些方案、需要客户作出的决定及送审时间。

正式送审前可直接修改内部草稿；正式送审后发现错误，则由发布者撤回并说明原因，再发布新的当前送审稿。被撤回内容不能再被确认；已经形成的正式反馈或确认仍绑定原内容，不提供通用版本浏览、并排比较、修订谱系或完整回滚。

### 提意见，但不把每条评论都变成指令

客户可以对整份当前送审稿发表意见，也可以在具体页面或画面位置添加批注。批注始终对应当时送审的内容与页面，放大或调整窗口后仍指向同一位置。

普通评论用于讨论。客户负责人将需要执行的意见整理为一轮正式反馈，可以选择已有评论并补充明确要求，避免重复抄写。相互矛盾的意见先在客户侧协调；负责人未采纳的评论保留为讨论记录，但不自动成为设计任务。

正式提交后保留当时的内容与提交人。后续补充单独标记，不直接改写已经提交的要求。客户成员仍可讨论，但新评论不会静默进入已提交的修改范围。

### 处理修改并检查结果

设计师逐项回应当前正式反馈，说明已处理、需要澄清或暂未处理及其原因。内部勾选“已处理”只表示团队完成了相应工作，不等于客户已经认可。

处理完成后发布新的当前送审稿，本轮正式反馈及处理说明仍可供客户核对。原批注不会自动移到新稿的相同页码或坐标；反馈引用的原送审内容可从该反馈只读查看，用于理解这项要求，不能再提交意见或确认。客户在当前稿上作出新的判断，不提供跨轮次的版本目录、新旧稿并排比较或页面配对。没有被正式反馈或确认引用的旧稿，不作为产品留存档案。

涉及新增设计项或明显超出约定范围的要求，由项目负责人提出范围调整并取得客户负责人明确确认。系统只展示当前有效范围、日期和确认结果，不维护范围与日期的编辑流水，也不自动计算合同效力、费用或免费修改次数。

### 正式定稿

“发表评论”“提交正式反馈”“确认定稿”是不同动作。定稿前清楚展示待确认的交付项、方案和当前送审稿；存在尚未澄清的正式要求时，应先处理或由负责人明确确认其不再阻碍定稿，不能自动忽略。

定稿记录只保存防止误认所必需的操作者、时间和确认内容。确认仅绑定当时的具体内容；后续更新必须重新送审和确认，不能覆盖已确认成果，也不能把旧确认继承给新内容。

## 交付不是上传附件就结束

设计定稿确认内容，交付验收确认文件交齐且可使用，两者分开。

设计团队为已定稿的交付项整理交付包，按实际用途提供文件，例如印刷使用文件、线上宣传图片、可编辑源文件和使用说明。分类按项目需要选择，不要求每项都具备所有类型。

每份文件说明所属交付项、对应定稿内容和用途，必要时注明尺寸、格式等使用信息。源文件及预览由团队建立明确对应关系，系统不冒充能够自动证明专业源文件与预览内容完全一致。

客户可以分项或整包下载，查看约定交付清单并反馈缺失、打不开或用途不明的问题。客户负责人确认交付验收；下载行为本身不算验收。

交付后发现文件错误或遗漏时，团队更新当前有效交付包并明确更正范围。影响设计内容的修改回到审阅与定稿流程，原定稿确认不能自动继承；仅补齐遗漏文件则重新确认交付结果。产品保留有效交付文件和必要确认记录，不提供全量交付包更正史或完整回滚。

所有交付项完成后，项目负责人可以归档项目。获授权客户仍能检索历史定稿和交付资料；归档不等于删除，也不自动撤销成员的既有访问权限。

## 页面与使用体验

### 客户工作台

首先展示等待审阅、待补资料、等待确认和可下载成果，并提供直达具体对象的入口。项目卡片使用真实方案缩略图帮助识别，不用内部工时、复杂任务列表或装饰性指标占据首页。

### 项目空间

展示项目目标、约定范围、交付项、双方负责人、关键日期和公共资料。每个交付项独立呈现当前阶段与下一步处理人，客户能判断正在等自己还是等设计团队。

### 方案审阅页

设计稿占据主要空间，侧栏展示批注和当前正式反馈。支持缩放、页面切换和定位批注；提交反馈与定稿入口明确区分。

预览加载失败时保留评论输入并允许重试，不能把未加载出来的稿件视作已审阅。被撤回或已更新的送审链接提示当前已不可操作并引导前往当前送审稿；确被正式反馈或确认引用的原内容仅供有权用户只读核对。

### 内部工作台

按待准备、待内部处理、等待客户、准备交付等业务情况汇总工作，突出临近日期和阻塞原因。内部安排与客户可见进度分开，不要求设计师每天维护估算百分比。

### 交付资料库

按客户、项目、交付项和用途查找成果，默认突出当前有效文件，能够回到相关定稿和交付记录。客户的检索范围严格限制在获授权内容内。

### 视觉与媒体

界面定位为安静、专业的线上项目室。日常页面以浅色中性色和清晰排版为主，强调色用于操作与状态；审稿区域提供中性背景，避免界面本身干扰作品观察。

展示公司名称、标志和负责人，让客户理解空间归属，但不将本次范围扩展为可配置主题平台。产品演示需要质量适当的包装、菜单和海报等示例成果，覆盖首稿、反馈、修订和交付，而非只做空页面或无关装饰配图。

示例数据与真实项目明确区分，不将示例作品或项目量冒充真实客户记录。后续设计实现阶段按演示需要准备和固化实际媒体素材。

## 统计怎样帮助推进项目

建议为项目负责人提供轻量分析入口，并在工作台展示相关摘要。只使用当前送审、正式反馈、约定日期和交付状态，不增加统计填报或为统计保存历次编辑。

- 当前等待客户的时长与分布：依据本次送审时间和是否已收到正式反馈或定稿确认，识别需要跟进的交付项。撤回送审后不再列入等待客户，重新送审按新的发送时间计算。
- 临近到期与逾期交付：比较当前约定日期和实际验收情况，帮助负责人安排跟进和调整工作。缺少约定日期的项目单独显示，不默认为准时。

使用当前等待时长条形图和临期清单，支持回到具体交付项处理。不做修改轮次统计、历次等待分析或集中监控大屏，不为这些分析维持修订链。无数据时显示空状态，不填充虚构业务量，也不据此生成员工绩效排名。

## 实现原则与本次范围

本次建议开发范围包含客户与项目管理、角色与项目访问、资料补充、交付项管理、内部草稿与当前送审、图片和 PDF 审阅、画面批注、正式反馈汇总、处理说明、定稿、交付包与验收、归档成果检索、邮件及站内待办、必要统计。

一个 Web 应用承载不同角色的工作界面，共享业务记录。资料访问和下载授权由服务端实际限制，不能只隐藏前端按钮。通知链接仍需检查登录身份和项目权限，不能凭链接直接公开客户稿件。

图片和 PDF 用于在线预览；AI、PSD 等专业源文件作为受权限保护的附件保存和下载，由设计师同时提供预览。不是在线设计编辑器，不承诺准确解析所有专业格式，也不将自动识别视觉差异作为成立条件。

以异步协作为主。关键送审、资料请求、正式反馈、定稿和交付事件形成站内待办，并通过工作邮箱提醒；普通评论不默认逐条发送邮件。站内记录是事实依据，邮件失败不应使业务操作失效或待办消失。邮件服务的接入细节在工程设计中确定。

不把在线设计、实时聊天、合同签署、财务开票、销售管理、员工考勤或多商家交易纳入当前建议范围。业务确认保留证据，但不宣称具有电子签章或法律合同的效力。

本文不固定技术栈、接口、数据库模型、图表库或工程拆分，也不预先安排削减范围的开发分期。

## 重要未知与实际运营条件

以下问题影响后续设计深度，不改变已选定的产品方向：

- 真实设计公司是否已有稳定的送审、范围变更和定稿习惯；如果正式意见仍完全留在聊天软件里，本系统的价值会明显下降。
- 常见交付格式、单文件大小、PDF 页数和文件保留年限，决定预览、存储、下载与备份方案，当前不虚构容量数字。
- 客户负责人是否能代表客户汇总意见，以及多人意见冲突时实际如何处理；本文采用指定一位负责人，不扩展为复杂审批链。
- 源文件与使用说明按什么约定交付，不能假设每个项目都包含全部源文件，也不让系统自行作出商业承诺。

开发验证可以使用明确标识的示例公司、客户和成果完成完整流程。面向真实客户运营时，需要实际公司资料、可用的成员身份及邮件发送配置、适当的文件存储与备份、明确的资料保留和访问管理方式。具体资源在对应准备阶段核验，不假定当前已配置，也不把所有上线条件变成本轮构思或开发的前置门槛。

## 怎样判断核心结果成立

以示例咖啡品牌项目贯穿验证，而不只检查页面是否存在：

1. 客户多人能查看同一份当前送审稿并准确批注；内部草稿和其他客户资料不可访问。
2. 普通成员的评论不会直接成为正式修改要求，指定负责人能够整理并提交一轮明确反馈。
3. 设计师能将处理说明与当前正式反馈关联，客户能围绕当前送审稿判断要求是否落实。
4. 客户负责人能确认明确内容；被撤回或后来更新的送审稿不能继续确认，新内容不会继承旧确认。
5. 设计定稿后仍需完成文件交付与验收，客户能按用途下载当前有效文件并报告缺失。
6. 定稿后更新、交付更正、负责人变更与项目归档不会覆盖必要的正式反馈、确认或有效成果，也不会引入通用历史中心。
7. 用户能够通过站内待办完成工作；不需要手机应用、即时响应或邮件成功到达才能继续业务。
8. 项目负责人能从真实记录识别等待与逾期事项，统计中的每项结果可以回到具体项目解释。
