# PCM 阶段规划与讨论说明

> 这是一份给项目参与者看的阶段地图。它说明现在在哪、接下来先做什么、以后再做什么。
> 当前版本：2026-09-04
> 技术现状截止：2026-09-03

## 一、先把几个名字分开

### 商业阶段

说的是 PCM 这个项目能不能成为一门可持续的生意：有没有客户、能不能赚钱、能不能稳定交付、什么时候值得做平台。

### Demo 技术阶段

说的是 `pcm-demo` 这套验证工具本身做到哪一步。

### 产品开发流程阶段

说的是某一个客户软件项目从需求到交付的内部开发过程。

以后讨论时必须带上完整名称，避免把 Demo 做完误认为商业平台做完，也避免把某个客户项目交付误认为 PCM 已经产品化。

## 二、目前的真实情况

截至 2026-09-03，可以这样理解：

- `pcm-demo` 的第 0～18 步和 Demo 流程阶段一的需求循环已经有代码；
- `pcm-demo` 已有单机多产品协调能力；
- 设计文档记录过 381 项历史自动化测试结果，这不代表商业模式已经验证；
- Demo 流程阶段二目前还没有实现；
- 第 9、14、15 步的新合同和双产品真实并发仍有需要补齐的真实验证；
- “修迹”目前有 BR-001、BR-002 完整循环的记录，不能把它说成全部功能已经完成；
- 正式 PCM 和对外商业平台目前都没有应用代码；
- 产品目录中的 4 项都是 `prd-v1`，表示已有产品定义，不表示已有 4 个成品。

这些事实不阻止我们开始市场验证，但对外介绍时不能把未完成的能力说成已经具备。

## 三、接下来的商业阶段

### B0：前置准备与规划整理

这一阶段的结果是把项目关系、商业方向、阶段方法和当前章程讲清楚。本目录的规划文档就是 B0 的收口资料。

### B1：真实市场与交付验证——当前阶段

B1 不追求一次建立完整平台，而是回答四个问题：

1. 有没有真实客户愿意付钱；
2. 客户愿意为什么样的内容付多少钱；
3. 一个项目的完整成本和实际周期是多少；
4. 这个交付过程能不能重复，而不是只能靠临时加班完成。

当前主要做：

- 开始对外宣传和获取咨询；
- 使用人工方式沟通、报价、确认范围和收款；
- 使用现有 `pcm-demo` 完成符合条件的客户项目；
- 按统一方式记录成本、周期、修改、验收和售后；
- 同时继续补齐影响真实交付的 Demo 缺口；
- 根据真实结果决定正式 PCM 最小版本做什么。

当前不要求：

- 正式 PCM 已经完成；
- 商业平台已经完成；
- Demo 流程阶段二已经完成；
- 所有技术栈已经支持；
- 一开始就实现在线支付、客户自助操作和实时生产进度。

### B2：稳定交付与正式 PCM

当 B1 有了足够真实数据后，再决定：哪些交付内容应该固定成套餐，哪些环节最值得自动化，正式 PCM 的第一版应该先解决什么问题。

### B3：商业平台化

当人工运营已经明显限制订单量、交付速度或准确性时，再做客户门户、订单系统、商品管理、支付和 PCM 接口。

## 四、技术工作怎么并行

B1 期间技术工作分为四条线：

| 工作线 | 当前作用 |
|---|---|
| 现有 `pcm-demo` | 支撑真实项目交付，修复实际遇到的问题 |
| Demo 真实验证 | 补第 9、14、15 步和多产品并发等真实证据 |
| 正式 PCM | 先讨论产品范围和核心问题，不直接复制 Demo 的本地实现 |
| Demo 流程阶段二 | 以后用于完整产品体验审计和持续提质，不作为 B1 门槛 |

技术线可以并行，但每条线都要说明当前对 B1 的帮助。不能因为“以后可能有用”就无限扩张。

## 五、当前阶段的门槛

### B1 开始的条件

- 当前商业章程已经确定；
- 有一套能执行的沟通、报价、范围确认、交付和验收方式；
- 清楚知道目前能做什么、不能承诺什么；
- 有办法记录每个真实订单的成本和结果。

### B1 结束时要拿到的证据

- 真实咨询和成交情况；
- 实际报价和最终成交价格；
- 每个项目的完整投入和成本；
- 实际交付时间、修改次数和客户等待时间；
- 验收、退款、售后和争议情况；
- 哪些需求适合当前能力，哪些需求不适合；
- `pcm-demo` 在真实交付中暴露的新问题；
- 是否值得进入 B2，以及 B2 应先解决什么。

B1 暂时不预设必须完成多少单、达到多少利润率或多少转化率。先拿到真实数据，再根据数据定标准。

## 六、后续讨论顺序

### 第一组：开始接单前

1. 确定交付内容、范围、版本和验收方式；
2. 确定 E1、E2、E3 三种内部交付等级如何使用；
3. 确定报价和完整成本记录方式；
4. 确定付款、需求变更、延期、验收和售后规则；
5. 确定哪些项目直接不接。

### 第二组：接单同时推进

6. 确定对外宣传内容和宣传渠道；
7. 确定现有成品如何展示、报价和交付；
8. 确定真实订单如何进入 `pcm-demo`；
9. 确定每单如何保存源码、文档和交付记录；
10. 确定哪些 Demo 技术缺口优先补齐。

### 第三组：取得初步订单数据后

11. 确定正式 PCM 的第一版范围；
12. 确定商业平台是否值得开始建设；
13. 确定客户门户、订单、商品、付款和交付的优先顺序；
14. 确定是否恢复 Git 历史交付；
15. 确定 Demo 流程阶段二的投入时机；
16. 确定是否扩展 Spring Boot、Vue 等技术架构。

## 七、新会话怎么继续

每次新会话按这个顺序开始：

1. 先看[项目发展总纲](./项目发展总纲.md)，确认整体方向；
2. 再看本文，确认当前商业阶段和讨论队列；
3. 再看[当前商业阶段章程](./当前商业阶段章程.md)，确认当前执行规则；
4. 只阅读本次问题涉及的补充资料；
5. 讨论结束后，只更新真正发生变化的那份规划文档。

一次会话只解决一个主要问题，例如形成一个决定、确定一项交付规则、解决一个成本疑问，或完成一次阶段判断。不要为了“全部讨论完”而一次设计所有远期细节。

## 八、什么时候需要重新规划

出现以下情况时，重新看当前阶段是否仍然合适：

- 实际成本明显超出报价假设；
- 客户普遍要求当前没有的能力；
- 项目周期无法达到当前承诺；
- 返工或售后变成主要工作；
- 人工操作已经成为主要瓶颈；
- Demo 技术缺口已经直接影响客户交付；
- 正式 PCM 或商业平台的建设收益发生变化。

如果只是一次普通讨论，没有新决定或新证据，不需要额外创建会议文档。
