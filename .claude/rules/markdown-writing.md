# Markdown 文档写作

目标是让人和 Agent 用较低的理解成本获得准确、够用的信息，不追求最短篇幅或形式齐全。适用于本次编写或实质修改的文档，不因局部修改重写全文；第三方原文、生成文档、历史记录和机器依赖的格式不擅自改写。

## 表达与组织

- 先明确读者和用途：理解问题、作出决定、执行操作或查询细节，不必为此专设章节。尽早说明结论、当前状态或任务，补充理解所需的背景，不长篇铺垫。
- 使用直接、具体、通俗的完整表达，写清对象、动作、条件和结果；不用口号、抽象名词或过度压缩的短语代替说明。例如，用“请求失败后保留输入并允许重试”，而不是“完善异常恢复闭环”。
- 保留准确的技术术语，按读者需要解释首次出现的概念和缩写；避免自创术语、内部黑话和同义称呼轮换。引用、路径和编号用于定位，不能代替必要解释，也不让读者连续跳转才能理解当前内容。
- 结构服务内容和查找：简单内容用段落或列表，对比、参数查询等确有收益时用表格。不为填模板添加空泛章节、状态标签或重复内容；已有交付合同和机器格式必须遵守，不额外叠加形式。
- 同一意思优先集中说明，删除没有新增作用的重复。长文摘要、危险操作前的提醒、独立章节的必要前提可以保留；摘要帮助定位，正文补充依据，不反复完整复述。跨文档保留必要上下文并引用权威说明，避免复制出多份事实源。

## 细节与精简

- 细节按用途取舍：决策说明问题、结论、依据和取舍；操作说明前提、步骤、成功标准及必要失败处理；参考资料保证准确、完整且易查；Rules、AGENTS 和 Skill 明确触发条件、行为与例外，少重复背景论证。不统一限制字数或强制章节。
- 精简优先删除重复总结、无交付价值的过程流水和显而易见的解释；保留影响判断或执行的前置条件、约束、关键理由、适用例外、风险、恢复与验证方式。不以“更短”为由省略必要信息，或把事实、假设、建议和未验证结果混为一谈。
- 难懂时先定位缺失的背景或具体含义；一句解释或一个例子能消除歧义时应补充，不盲目删字。示例只解释必要问题，不扩展成无关教程。
- 完成前从读者角度检查：能否理解核心意思，作出所需判断、完成操作或找到信息？是否有重复、含糊词或需要猜的步骤？删去某段会不会导致误解？直接修正文档，不额外生成写作自评报告。
