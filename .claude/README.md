# AI Agent 开发能力与工作流编排

## 这套目录提供什么

`.claude/` 提供可复用的 AI Agent 能力、角色约定和少量通用工具说明，帮助项目从了解现状、澄清需求和技术设计，到实现、真实验证、审查与 Git 提交。

每个 Skill 都是**独立能力**：可以直接按当前任务调用，也可以被其他工具、团队模板或 AI 动态生成的计划组合。编排负责决定先后、重复、跳过和停止条件；Skill 不把自己绑定到固定的上游或下游。因此，这套目录可以同时服务新项目、既有项目、功能开发、Bug 修复、重构和小改动。

## 基本原则

- 从真实目标、现有代码、配置、测试和项目约定出发，不为了套流程而补造中间产物。
- 编排与能力解耦。可以有多套可选编排模板，也可以由 AI 依据项目状态和风险临时设计编排。
- 活动需求和活动 TRD 可以随着代码事实调整；已完成并归档的**历史**需求和 TRD 必须保持不可变。后续演进通过新的需求和新的 TRD 记录。
- 用户已有未提交修改是受保护的上下文：先识别、避免覆盖，不擅自 `reset`、`restore`、`checkout` 或 `clean`。
- 验证以真实行为和风险为中心，不能把局部 Mock 当作最终交付证据。
- 开发阶段不创建、启动或管理 Docker 或 Docker Compose；按项目现有方式运行开发服务和验证工具。
- 开发所需 `.env` 可以在安全边界内创建或维护，但秘密必须保持 Git 忽略，输出、日志和提交中不得泄露秘密。

## 运行环境

将本目录复制到目标仓库后，必须先确认基础工具、目录权限和项目自身运行依赖。不同项目可能使用不同语言、框架、数据库、浏览器或第三方服务，但“按仓库约定安装并检查完整开发环境”是所有项目开发都不能省略的步骤；不能因为具体技术栈不同，就删除或跳过运行环境说明。

### A. 基础运行环境（硬性）

| 项 | 要求 | 缺位时 |
|---|---|---|
| **Claude Code** | 本机已安装并可打开项目会话 | 无法使用本套面向 Claude Code Agent / Skill 机制的能力 |
| **Git** | 当前项目及实际开发涉及的各目标仓库均为 Git 仓库 | 无法可靠取得状态、差异、审查基线和提交记录 |
| **目录授权** | 代码仓库位于当前项目目录之外时，需在 Claude Code 中授权对应目录，例如使用 `/add-dir` | Agent 无法读取、修改或验证目标仓库 |
| **权限策略** | 项目 `.claude/settings.json` 需允许实际使用的 Git、Node.js、包管理器、测试和构建命令；使用 `git -C <repo>` 时，权限规则需匹配该命令前缀 | 安装、验证、审查或 Git 命令会被权限系统拦截 |
| **项目运行时与包管理器** | 按仓库贡献说明、版本文件、锁文件和构建配置安装正确版本的语言运行时、包管理器及项目依赖 | 不得凭猜测换用其他版本或跳过安装；先补齐环境再执行构建和测试 |
| **本地服务与数据依赖** | 按项目约定准备数据库、中间件、后端服务、浏览器、第三方沙箱、迁移和初始化数据 | 保留真实验收要求，明确缺失条件；不得用 Mock 或删除验收场景伪装完成 |
| **本地配置** | 按项目示例和说明准备开发 `.env` 或等价本地配置，并确认真实秘密已被 Git 忽略 | 配置缺失时先补齐安全的本地配置；不得提交或输出真实凭据 |

开始开发前至少检查：

1. 阅读 `README`、贡献说明、Agent 指令、版本文件、锁文件和构建配置；
2. 确认语言运行时、包管理器、依赖和项目命令可执行；
3. 确认必要数据库、服务、迁移、初始化数据和本地配置可用；
4. 确认测试、静态检查、类型检查、构建和浏览器验收所需工具已安装；
5. 确认目标目录权限和 Git 工作区状态满足安全开发要求。

### B. Codex 独立审查环境（推荐，非硬性）

`codex-review` 可作为独立能力直接调用。需要使用 Codex 进行只读审查时，应同时具备：

1. **Node.js ≥ 18.18**，用于运行插件 companion；
2. **Codex CLI** 已安装并完成登录：
   ```bash
   npm install -g @openai/codex
   codex login
   codex --version
   codex login status
   ```
3. **Claude Code 插件 `codex@openai-codex`** 已安装并启用：
   ```text
   /plugin marketplace add openai/codex-plugin-cc
   /plugin install codex@openai-codex
   /reload-plugins
   /codex:setup
   ```
4. 项目 `.claude/settings.json` 中启用插件：
   ```json
   {
     "enabledPlugins": {
       "codex@openai-codex": true
     }
   }
   ```
5. 项目权限策略允许 companion 所需的 `Bash(node *)`、Codex 探测命令和只读 Git 命令。

Codex 环境不可用时，先按顺序检查 `node -v`、`codex --version`、`codex login status`、插件安装状态、插件启用配置和 companion 路径。无法恢复时，可以根据风险使用 `reviewer` Agent 或其他真正独立的只读审查路径；不得伪造 Codex 结论。Codex、`reviewer` 和其他审查方式均为独立能力，不构成固定上下游依赖。

### C. 前端浏览器验收环境（涉及 UI 时硬性）

`playwright-cli` 可作为独立能力直接调用。在 `dev-workflow` 内，只要需求包含 UI、用户交互或浏览器可见结果，默认必须使用 Playwright 或项目已有的等价真实浏览器能力完成验收，不能只依赖代码阅读、单元测试、Mock 或口头确认。

| 优先级 | 通道 | 安装与配置 |
|---|---|---|
| 1（首选） | **Playwright MCP** | 安装并启用 Claude Code 插件 `playwright@claude-plugins-official`；项目 `.claude/settings.json` 的 `enabledPlugins` 中应启用该插件 |
| 2（兜底） | **playwright-cli** | 本目录已包含 `.claude/skills/playwright-cli/`；本机还需安装并确保 `playwright-cli` 命令可执行 |
| 3 | **项目已有等价浏览器能力** | 按目标仓库说明安装浏览器驱动、测试依赖和启动命令，并保证能执行真实动态交互 |
| 4 | **用户现场验收** | 仅当前三种自动化方式均不可用，或验收必须依赖人的主观审美、无障碍体验或外部设备时使用 |

浏览器环境缺失时，仍应完成可执行的命令类验证和代码审查，但所有受影响的 UI 验收保持未完成状态，直到自动化浏览器验证成功或用户完成不可替代的现场验收。不得删除 UI 验收项后宣称功能完成。

| 能力 | 用途 | 是否可独立调用 |
|---|---|---|
| `project-intake` | 了解项目事实、运行方式、约束与初始风险 | 是 |
| `project-bootstrap` | 将前后端或全栈基础模板有限范围项目化，并收口身份、配置、联调、视觉和验证基线 | 是 |
| `solution-design` | 为跨模块或关键技术方向形成设计选择；其他 Skill 不以它为必需前提 | 是，可选 |
| `requirement-breakdown` | 把业务目标梳理为可讨论、可演进的需求边界 | 是 |
| `trd-design` | 形成或调整面向当前实现的技术设计 | 是 |
| `dev-workflow` | 从目标理解到实现、验证、风险审查和交付的完整开发闭环 | 是 |
| `codex-review` | 使用可用的 Codex 环境对代码、文档或分支差异进行独立只读审查 | 是，可选 |
| `commit-changes` | 按功能结果自动规划一个或多个提交并精确创建本地 commit | 是 |
| `playwright-cli` | 自动化浏览器交互、检查网页和执行浏览器验证 | 是 |
| `session-rule-retrospective` | 复盘一次 AI 会话或工作流后，把可复用、跨会话的工程经验去重、归类、增量写入 `.claude/rules/` | 是 |

`dev-workflow` 是唯一承载完整开发闭环的开发能力，同时仍可独立调用并根据输入、代码事实、风险和可用环境自适应执行；其他 Skills 提供各自专注的能力，不构成必经关卡。
`codex-review` 和 `commit-changes` 既可由开发者直接调用，也可由 `dev-workflow` 或其他编排按风险与交付需要自动调用。

## 可选编排示例

下面只是一个常见的**可选编排**示例，不是必须遵循的流水线：

```text
project-intake
→ requirement-breakdown
→ trd-design
→ dev-workflow
```

实际工作中可以跳过、替换、重复或重新排序这些能力。例如，跨模块技术决策不清楚时，可在任何合适位置加入 `solution-design`；已有明确 Bug 时可以直接进入 `dev-workflow`；小范围且风险较低的修改也可以只使用需要的检查和 `commit-changes`。

编排器或当前 AI 应根据目标、代码事实、依赖关系、风险和可用环境决定下一步，而不是恢复固定的编号依赖链。

## 开发能力：dev-workflow

`dev-workflow` 面向功能、Bug、重构和小改动，可从活动 TRD、Backlog 大需求、功能描述、故障现象或已有代码上下文独立开始。它负责理解目标和现状、自适应安排实现、执行真实验证、组织必要审查、裁决建议并收敛交付；不要求上游 Skill 已运行，也不把自身绑定到固定下游能力。

它不会要求先拥有特定来源文档，也不会把活动 TRD 当成不可修改的输入。若发现当前设计、接口约定或验收方式与代码事实不一致，应在当前需求范围内调整活动 TRD；不要回写已经完成的历史文档。影响本次目标正确性的旧 Bug 应修复或明确升级，不能仅因其较早出现而忽略。

Leader 可以直接实现，也可以在边界清楚时派发 `dev` Agent 完成内聚改动和局部验证；需要时再使用 `commit-changes` 做精确提交。任务拆分、并行程度、实现技术和验证轮次由当前工作判断决定，但完成证据不能因此缩减。

### 正式 TRD 的默认交付路径

正常正式 TRD 开发默认覆盖六个阶段：理解与校准、实现与随行测试、完整自动化验证、审查与修复、真实运行与功能验收、交付收敛。这六个阶段描述应完成的工作，不是固定状态机，不对应六份过程文档，也不禁止在实现、测试、审查和验收之间反复循环。

实现方法可以随语言、框架、项目惯例和风险灵活调整；完成标准保持严格：全部适用验收条件必须有实际证据，适用测试、检查和构建必须真实执行，依赖服务、接口、数据库或 UI 的功能必须完成相应真实联调与验收。

## 开发中的真实验证

验证应随项目类型和风险调整，但不能任意挑选最容易通过的项目。正式 TRD 要求 `TRD 验收条件覆盖率：100%`，每项应能对应到实现位置、验证方式和实际结果，并覆盖关键成功路径、失败路径、状态、权限、数据一致性和受影响回归：

- 必须实际运行全部适用的测试、静态检查、类型检查、构建、接口测试、迁移验证或项目既有回归；“已经写了测试”或“代码看起来正确”不能替代执行结果。
- 后端涉及持久化时，使用**真实数据库**、真实迁移和必要的**初始化数据**验证读写、约束和失败处理；仅 Mock 数据库不能证明最终行为。
- 前端依赖服务端能力时，使用**真实后端**和真实数据完成接口联调。局部 Mock 可辅助单元测试或隔离排查，但 Mock、拦截响应和假接口不能替代最终真实集成验收。
- UI、用户交互或浏览器可见结果默认必须通过 Playwright 或等价真实浏览器能力执行动态验收矩阵，覆盖全部适用 UI 验收条件、完整成功路径、关键失败路径、错误反馈、权限与状态差异、持久化和相邻回归；只验证 happy path 不足以完成。
- 依赖真实服务时，使用项目现有本地运行方式，不在开发阶段通过 Docker 或 Docker Compose 代替项目约定。
- 开发 `.env` 仅放本地必要配置，并确认被忽略；不要把凭据写入文档、测试输出或 Git 历史。
- Agent 应先主动处理可修复的配置、服务、迁移和测试数据问题。只有不可替代的外部凭据、不可控外部服务、专用设备、人工审批或必要数据缺失导致部分真实验证无法完成时，结果才可标记为**已实现但未完全验证**，并说明缺口与补验方法；不得标记为**已完成**。

## 角色分工

| 角色或能力 | 负责内容 | 边界 |
|---|---|---|
| Leader | 理解目标、组织工作、处理活动 TRD、决定验证与审查范围、裁决建议、组织交付 | 对最终取舍负责 |
| `dev` Agent | 在目标与边界明确时实现代码并完成局部真实验证 | 不提交、不推送、不做重大产品或架构裁决 |
| `reviewer` Agent | 独立、只读、基于证据地发现正确性、安全、数据和回归风险 | 不改文件、不写审查档案、不作最终裁决 |
| `codex-review` | 在 Codex 可用时提供独立、只读的审查发现 | 不改代码、不替 Leader 做裁决 |

Leader 自审始终必需。正式 TRD 驱动的正常功能默认至少完成一次独立审查；只有严格意义上的微小、低风险修改才可免除，且 Leader 必须在最终说明中简短记录行为影响和免除理由。是否属于微小修改按行为影响判断：涉及业务规则、数据写入、权限、接口兼容、跨服务集成或用户可见流程时，不按微小低风险处理。

独立审查应获得完整的本次范围最终代码或 diff、适用验收条件和已有验证证据。`codex-review`、`reviewer` Agent 和其他独立路径都是可选审查方式，不要求双引擎成对执行，也不存在某个工具不可用时的固定替代链。Leader 逐项裁决发现：修复有证据的合理阻断问题并重跑受影响验证，也可以拒绝不适用或证据不足的建议；但影响完成判断的 `VERIFICATION_GAPS` 必须补证，必要时重新审查，只有证明与当前范围或完成条件无关才可关闭。独立审查不替 Leader 作最终决定。

## Git 与过程记录

提交应按可独立理解、验证过的功能结果组织。开发者要求提交全部修改时，`commit-changes` 先分析完整变更，再自动拆分边界清晰的独立结果；同一功能所需的代码、测试、迁移、配置和说明保持在一起，不按文件类型或开发步骤机械拆分。自动分组以完整文件为默认安全边界；同一文件混合多个必须拆开的结果时，不冒险进行不可靠的局部暂存，而是先明确冲突边界。每个提交只精确暂存当前分组，检查完整暂存差异和实际提交文件；默认只 commit、不 push，不用宽泛暂存命令污染用户无关修改。

普通开发不创建运行档案或完整过程流水。只有长期中断且确有恢复需要的工作，可以临时使用 `.pcm-workflow/<需求标识>/progress.md` 记录当前事实、未完成事项和恢复条件；恢复后删除，或将需要长期保留的结论写入用户可见的需求、活动 TRD 或交付说明。不要把可从代码和 Git 获取的信息重复归档。

不保留额外的 Manifest 或 spec 中间层：目标、实现、测试、Git 和必要的活动 TRD 已足以承载可追溯的交付事实。额外过程文件往往会复制状态并造成过期、冲突和无效维护。

## 复制到新项目

1. 复制 `.claude/` 到目标仓库，并保留仓库自己的贡献规范和安全要求。
2. 根据项目实际环境补齐被忽略的本地配置，例如开发 `.env`，不要复制真实凭据。
3. 从最适合当前目标的独立能力开始；空白项目通常可先用 `project-intake` 了解约束，再按需要梳理需求、技术设计或直接开发。
4. 用项目自身的测试、构建、服务与浏览器环境验证，不假设所有项目使用同一套工具或编排模板。

## 常见问题

**Q：没有 Codex 也能开发吗？**
能。`dev-workflow` 不依赖 Codex，也不要求双引擎审查。正式 TRD 驱动的正常功能仍默认至少完成一次独立审查，可使用 `reviewer` 或其他真正独立的路径；只有严格微小、低风险修改可由 Leader 说明理由后免除。Leader 始终负责自审、真实验证并裁决审查发现。

**Q：前端、后端或前后端分离项目怎么用？**
后端验证真实数据库、迁移、初始化数据和接口行为；前端依赖后端时连接真实后端，在浏览器中联调关键路径。前后端可以分别推进，但依赖关系必须以真实集成为准。

**Q：空白项目怎么开始？**
先用 `project-intake` 识别运行环境、忽略规则和基础约束；再按当前不确定性选择需求梳理、技术设计或直接实现。不需要先完成一套固定流程。

**Q：小改动或 Bug 修复也要走完整流程吗？**
不需要机械展开正式 TRD 的完整工作量，但仍要按行为影响完成相称验证。只有严格微小、低风险修改可免除独立审查；涉及业务规则、数据写入、权限、接口兼容、跨服务集成或用户可见流程时不能按小改动降级。`dev-workflow` 既能覆盖完整闭环，也能用于小范围任务，其他独立能力可按需使用。

**Q：没有接口契约怎么办？**
以现有代码、实际调用方、测试和可运行行为为依据，明确尚不确定的边界并补充必要验证。接口契约有帮助，但不是开始开发或完成当前验证的硬性前提。

**Q：中途被打断怎么办？**
先查看工作区和 Git 的真实状态。长期中断且需要交接时，可临时记录 `.pcm-workflow/<需求标识>/progress.md`；不要把短暂工作变成永久过程档案。

**Q：历史 TRD 发现需要调整怎么办？**
已完成的历史需求和 TRD 不修改。后续升级、重构或补完建立新的需求和新的 TRD；当前实现需要修复旧代码时，把本次决策和范围写在当前活动 TRD 中。

**Q：为什么没有额外的 Manifest 或 spec 层？**
这些中间层会重复需求、代码、测试与 Git 中已经存在的事实，容易失效。独立能力按当前目标读取真实上下文，只有对协作和交付仍有价值的活动 TRD 才需要维护。
