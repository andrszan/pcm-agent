# 人工调度的 AI Agent 产品开发流程

> 本文只定义**人作为调度者**使用 Claude Code 与本仓库能力完成 Web 产品开发的默认流程。当前不讨论 PCM 程序、状态机、节点协议或机器可解析输出。
>
> 本流程面向前后端分离项目：根仓库管理项目文档与协作记录，`frontend/`、`backend/` 初始化后作为独立 Git 仓库管理。若实际项目只涉及部分仓库，只执行适用步骤。

## 一、全局执行规则

1. **每一步都有完成条件。** 未达到完成条件、存在未解决阻塞或证据不足时，不进入下一步。
2. **Skill 只负责自身领域。** 不假设固定上下游，不自动调用其它自定义 Skill，不把提交、分支、合并或最终状态同步塞进领域 Skill。
3. **Git 动作显式拆分。**
   - 普通领域 Skill、`dev-workflow`、`session-rule-retrospective` 和 Subagent 不 stage、不 commit、不建分支、不合并、不 push；
   - `commit-changes` 是唯一负责 stage/commit 的 Skill，并按仓库分别调用；
   - 建分支、切换分支和合并是流程中的显式人工调度步骤，不属于 `commit-changes`。
4. **保护工作树。** 每一步开始和结束都检查目标仓库状态；不得覆盖用户已有修改，不用宽泛暂存或破坏性清理命令。
5. **以真实证据完成。** 文档步骤检查内容一致性；开发步骤运行适用测试、构建、真实服务、数据和浏览器验收。无法完成时准确标记缺口，不用 Mock 或口头判断冒充完成。
6. **历史不可变。** 活动需求和活动 TRD 可在当前范围内调整；已经完成并归档的需求和 TRD 不回写，后续变化建立新需求和新 TRD。
7. **默认只本地提交，不 push。** 是否推送或创建远程合并请求由项目另行决定。

## 二、会话安排

- 每次新启动 Claude Code CLI 会话后，必须先执行一次 `/reload-plugin`，确认本项目已启用插件及其 Skills 已加载，再开始执行流程；同一会话内无需重复执行。
- 产品定义、总体方案、工程架构、Backlog、单需求 TRD、开发实现等大型领域步骤，建议分别新开会话，减少上下文污染。
- `ui-ux-framework after` 强烈建议使用独立新会话，以获得更接近独立审查的视角。
- `after` 发现实现问题后，返回原 `dev-workflow` 会话修复；原开发会话保留了实现取舍、失败方案和验证上下文。
- `commit-changes` 是独立职责，但只是短时 Git 操作，不强制新开会话。
- `session-rule-retrospective` 默认在被复盘的原开发会话中执行；新会话通常缺少真实失败、根因和用户纠正证据。

## 三、项目初始化流程

### 第 0 步：获取产品初稿（可选、流程外）

- 能力：`pcm-product-factory`
- 适用：需要从候选题目中形成产品初稿时。
- 输出：产品初稿。
- 完成条件：产品方向和初稿内容已经由人确认。

`pcm-product-factory` 是专用产品选题能力，不是核心开发流程的必经步骤。已有产品想法或资料时直接进入第 1 步。

### 第 1 步：建立项目工作区

- 操作：复制或拉取本仓库作为新项目工作区，移除原仓库 Git 历史，准备项目文档目录。
- 完成条件：当前目录是新项目的根工作区，`.claude/`、`AGENTS.md` 等能力文件可用，尚未误带原仓库历史或无关项目资料。

这是人工操作步骤，不由某个领域 Skill 隐式完成。

### 第 2 步：项目需求与产品定义

- 能力：`project-intake`
- 输入：产品想法、产品初稿或已有资料。
- 输出：当前项目权威的需求与产品功能文档。
- 完成条件：目标用户、产品范围、核心流程、非目标、关键约束和待确认事项已经收敛；仍有实质歧义时继续对话。

### 第 3 步：总体技术方案

- 能力：`solution-design`
- 输入：产品定义、现有工程事实、用户硬约束；如需模板选型，再额外提供可读的模板资产目录或清单。
- 输出：总体技术方案，以及各独立交付单元的基础来源与采用方式。
- 完成条件：系统边界、主要技术选择、交付单元、跨单元协作、关键风险和未决事项已经确认。

模板资产是可选输入，不是 `solution-design` 的隐藏依赖；具体模板仓库、索引文件和复制规则属于本流程或人工操作约定。

### 第 4 步：组装基础工程

- 操作：根据第 3 步确认的基础来源，把所需模板或独立工程放入 `frontend/`、`backend/` 等目标目录；清除临时克隆目录。
- 完成条件：目标工程目录完整、来源明确、没有嵌套的上游 `.git` 或临时模板仓库，实际目录与技术方案一致。

### 第 5 步：核验项目准备状态

- 能力：`project-readiness`
- 输入：产品定义、技术方案、当前工程目录、开发者可提供的资源信息。
- 输出：项目准备清单。
- 完成条件：当前开发必需项均为 `ready` 或已经明确 `not-applicable`；`missing`/`pending` 项若阻断当前开发，必须先补齐或由人确认替代方案。

不得伪造外部凭据、账号、素材或不可替代资源来消除阻塞。

### 第 6 步：项目化基础工程

- 能力：`project-bootstrap`
- 输入：当前基础工程、产品定义、技术方案和准备清单。
- 输出：完成项目化的根目录、前端和后端工程。
- 完成条件：模板示例身份已替换，项目配置和必要文档已落地，适用安装、构建、测试、启动和基础联调已经验证；留下待提交变更，不提交。

### 第 7 步：初始化并提交三个仓库

1. 在根目录、`frontend/`、`backend/` 分别初始化 Git，主分支设为 `main`；不适用的仓库跳过。
2. 分别检查忽略规则、秘密、临时文件和实际 diff。
3. 对每个仓库单独执行 `commit-changes`，形成初始本地提交。

完成条件：每个适用仓库都有明确的初始提交，工作树状态符合预期，没有跨仓误纳入内容。

### 第 8 步：工程架构设计

- 能力：`engineering-architecture`
- 输出：工程架构文档；默认只提出稳定规则候选，不修改 `AGENTS.md`，除非人明确把规则同步纳入本次任务。
- 完成条件：分层、模块边界、目录职责、依赖方向、共享准入和演进条件能够指导后续文件归属。
- Git：完成后对根仓库执行 `commit-changes`。

### 第 9 步：产品级 UI/UX 框架

- 能力：`ui-ux-framework bootstrap`
- 输出：产品级 UI/UX 框架文档；不适用时明确说明并跳过。
- 完成条件：产品表面、信息架构、Shell、导航、共享视觉与交互约束已经确认。
- Git：有文档变更时对根仓库执行 `commit-changes`。

### 第 10 步：拆分 Backlog

- 能力：`requirement-breakdown`
- 输出：Backlog 总览和需求详情卡。
- 完成条件：每个大需求具有明确产品结果、范围、依赖、验收方向和建议顺序；当前首个需求可被选择进入开发循环。
- Git：对根仓库执行 `commit-changes`。

## 四、单需求开发循环

以下步骤每次只处理一个活动需求。

### 第 11 步：选择需求并建立根仓库需求分支

1. 确认三个仓库当前状态和 `main` 基线。
2. 从 Backlog 选择一个可开始需求，确认依赖已满足。
3. 在根仓库从最新 `main` 创建需求分支，使用稳定且可识别的分支名。

完成条件：活动需求唯一、范围明确，根仓库需求分支正确，开始前状态已记录。

### 第 12 步：形成最终活动 TRD

1. 新会话执行 `trd-design`，默认只创建或更新当前活动 TRD。
2. 若需求涉及 UI/UX，执行 `ui-ux-framework before`；该模式自行判断适用性，并在适用时更新活动 TRD。
3. 人检查并确认最终 TRD：范围、产品行为、技术方案、验证场景和待确认事项足以指导实现。
4. 对根仓库需求分支执行 `commit-changes`，提交最终 TRD。

发现 Backlog、产品文档或总体方案需要调整时，先报告影响；只有人明确纳入本次范围才跨文档修改。

### 第 13 步：建立代码仓库需求分支

- 根据 TRD 判断受影响的代码仓库。
- 在每个受影响仓库中，从最新 `main` 创建与需求对应的功能分支。
- 不受影响的仓库不机械建分支。

完成条件：所有受影响仓库都位于正确功能分支，未混入上一需求或其它工作。

### 第 14 步：实现与验证

- 新会话执行 `dev-workflow`，输入最终活动 TRD 和目标仓库。
- `dev-workflow` 负责实现、适用测试、真实运行、联调、浏览器验收和独立审查，但不提交、不建分支、不合并、不推送，也不同步最终 Backlog 状态。
- 开发完成后，检查每个受影响仓库的 diff、验证证据和剩余工作树状态。
- 对每个受影响代码仓库分别执行 `commit-changes`。

完成条件：`dev-workflow` 给出“已完成”或准确的非完成状态；只有“已完成”且各代码仓库变更已经提交，才能进入体验审查。

### 第 15 步：开发后 UI/UX 审查与修复循环

在独立新会话执行 `ui-ux-framework after`，输入活动 TRD、各代码仓库功能分支相对其 `main` 的完整差异、任何尚未提交的补充修改、可访问的真实页面和已有验证证据。工作树已提交且干净时，不能用空的 working-tree diff 代替分支完整差异。

- **不适用或通过**：进入第 16 步。
- **实现偏差或局部体验缺陷**：
  1. 返回原 `dev-workflow` 会话；
  2. 根据审查证据修复并重新运行受影响验证；
  3. 对发生变化的代码仓库分别执行 `commit-changes`；
  4. 回到独立审查会话或新建等价独立会话，再次执行 `after`；
  5. 重复直到通过、明确不适用，或准确报告阻塞。
- **TRD、产品决定或项目级 UI/UX 框架本身需要改变**：暂停代码修复，先由人确认应返回的设计层；在根仓库需求分支更新并提交相应文档，再回到原 `dev-workflow` 会话按新基线修改和验证。不得把代码偏差静默改写成新规范，也不得让实现会话自行决定高影响设计变化。
- **仅有非阻断建议**：由人决定纳入当前需求、记录为后续候选或明确拒绝；未纳入当前范围的建议不应阻止本需求收尾。

`after` 只审查和报告，不直接实现、不提交。

### 第 16 步：合并代码仓库并在 `main` 最终验证

对每个受影响代码仓库分别执行：

1. 确认功能分支工作树干净、提交完整；
2. 切换到最新本地 `main`；
3. 按项目约定将功能分支合并到 `main`；
4. 在 `main` 上重新运行与合并结果相关的最终检查；
5. 记录合并结果和验证证据。

这是显式 Git 操作，不由 `dev-workflow` 或 `commit-changes` 代替。任一仓库合并冲突或最终检查失败时，先解决并重新验证，不进入状态收尾。

### 第 17 步：同步需求最终状态

回到根仓库需求分支，根据代码仓库 `main` 上的真实结果：

1. 更新活动 TRD 的实施结果、实际验证、完成状态和完成日期；
2. 同步 Backlog 总览与对应详情卡；
3. 保证状态准确：未完成或验证受阻时保留阻塞和缺口，不得标记完成；
4. 对根仓库需求分支执行 `commit-changes`。

完成条件：TRD、Backlog、代码合并结果和验证证据一致。

### 第 18 步：合并根仓库并检查全局状态

1. 将根仓库需求分支合并到根仓库 `main`；
2. 分别检查根仓库、`frontend/`、`backend/` 的当前分支、`git status` 和最近提交；
3. 确认没有遗留临时目录、意外未提交文件、未合并需求分支或跨仓状态不一致。

根仓库最后合并，保证文档中的最终状态建立在代码仓库已经合并并验证的事实之上。

### 第 19 步：复盘本次执行规则

- 从根仓库最新 `main` 创建短期复盘分支，再返回原 `dev-workflow` 会话执行 `session-rule-retrospective`；这样既保留原会话证据，也避免直接修改 `main`。
- 只把本次真实发生、已证实、项目内高概率复现且有明确规避动作的问题沉淀到 `.claude/rules/`。
- Skill 只修改 rules 并留下待提交文件，不自行提交。
- 若有 rules 变更，对根仓库复盘分支执行 `commit-changes`，随后显式合并回根仓库 `main` 并检查状态；无变更时删除或结束该空分支，并明确“无需提交”。

复盘完成后，本需求循环结束。开始下一个需求前，确保各适用仓库均从最新 `main` 创建新分支。

## 五、异常与停止条件

遇到以下情况时暂停流程，不用“先继续后补”掩盖问题：

- 需求范围、重大架构、安全、兼容性或不可逆迁移无法安全决定；
- 不可替代的外部凭据、账号、服务、设备、审批或数据缺失；
- 用户已有修改与当前任务发生重大冲突；
- 测试、构建、真实联调、浏览器验收或独立审查仍有影响完成判断的问题；
- 任一仓库分支、提交、合并或工作树状态不清楚；
- TRD、Backlog 与代码真实结果不一致。

停止时应说明：当前完成范围、已验证证据、真实阻塞、已尝试动作、保留的变更和解除条件。
