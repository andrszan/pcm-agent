# 人工调度的 AI Agent 产品开发流程

> 本文只定义**人作为调度者**使用 Claude Code 与本仓库能力完成 Web 产品开发的默认流程。当前不讨论 PCM 程序、状态机、节点协议或机器可解析输出。
>
> 本流程面向前后端分离项目：根仓库管理项目文档与协作记录，`frontend/`、`backend/` 初始化后作为独立 Git 仓库管理。若实际项目只涉及部分仓库，只执行适用步骤。

## 一、全局执行规则

1. **每一步都有完成条件。** 未达到完成条件、存在未解决阻塞或证据不足时，不进入下一步。
2. **Skill 只负责自身领域。** 正文不假设固定上下游、不点名或编排其它自定义 Skill，不把提交、分支、合并或最终状态同步塞进领域 Skill。执行任务的 Agent 可以依据工作区规则和当前任务事实，按需选择已加载的工具适配或专业辅助能力；这不建立核心领域 Skill 的固定调用链。
3. **Git 动作显式拆分。**
   - 普通领域 Skill、`dev-workflow`、`session-rule-retrospective` 和 Subagent 不 stage、不 commit、不建分支、不合并、不 push；
   - `commit-changes` 是唯一负责 stage/commit 的 Skill，并按仓库分别调用；
   - 建分支、切换分支和合并是流程中的显式人工调度步骤，不属于 `commit-changes`。
4. **保护工作树。** 每一步开始和结束都检查目标仓库状态；不得覆盖用户已有修改，不用宽泛暂存或破坏性清理命令。
5. **以真实证据完成。** 文档步骤检查内容一致性；开发步骤运行适用测试、构建、真实服务、数据和浏览器验收。无法完成时准确标记缺口，不用 Mock 或口头判断冒充完成。
6. **历史不可变。** 活动需求和活动 TRD 可在当前范围内调整；已经完成并归档的需求和 TRD 不回写，后续变化建立新需求和新 TRD。
7. **默认只本地提交，不 push。** 是否推送或创建远程合并请求由项目另行决定。
8. **区分最终范围与验证切片。** 最终产品范围表达当前产品承诺；首条验证切片只用于尽早验证高风险假设，不表示缩减、延期或完成最终范围。任何改变产品承诺的删减都必须显式确认。
9. **体验质量属于完成条件。** 用户可见范围不仅要逻辑闭环，还要检查任务是否足够简单、内容是否易懂、信息与操作层级是否清楚、视觉表达是否符合产品定位；不能用组件可用、页面可点或构建通过代替体验结论。
10. **资料交接属于人工调度层。** 下述步骤号和固定路径只用于人工调度时交接资料，不形成下游 Skill 的隐藏前置、固定输入格式或自动调用链。
11. **媒体按需调度，不新增固定步骤。** UI 设计或开发任务按工作区规则评估媒体价值，需要时调用 `media-assets` 获取、检查和固化素材；产品开发负责业务关联。具体执行约定由该工具维护，不在领域 Skill 中建立固定调用链。
12. **README 只维护稳定入口、使用合同和文档地图。** 根仓 README 面向首次接触项目的客户、负责人和接手者，使用通俗语言说明产品定位、目标用户、当前可用范围与主要限制、仓库组成、最短全栈启动或正常使用路径及权威文档入口；前端、后端等独立业务代码仓 README 面向对应仓库的开发与运行维护，说明本仓职责、环境要求、最短启动与联调方式、配置和秘密边界、代码入口、验证、构建及运行责任。README 不承载模块内部实现、单个需求或 BR 的开发流水、一次性测试日志/截图/运行输出、历史演进，也不复制 Backlog、TRD、工程架构、OpenAPI 或专项运行文档的详细正文；详细内容进入项目已有的适当受跟踪文档，README 保留必要摘要和可发现链接。当项目定位或范围、正常入口、安装/启动/配置前置、稳定用户行为或限制、恢复/核验入口、账号交接入口、运行责任或权威文档位置变化，并影响某个仓库 README 承载的摘要、命令、关键前置条件或文档地图时，必须更新该 README；只改变权威详细文档内部内容且 README 中的稳定摘要、入口和链接不变时，不机械修改 README。修改稳定事实时必须替换或删除失效、重复和模板说明，不在末尾持续追加新段落。README 中的命令、链接和关键前置条件必须按当前工程事实核验；不强制固定标题、文档树、恢复命令或额外 Manifest。

## 二、会话安排

- 每次新启动 Claude Code CLI 会话后，必须先执行一次 `/reload-plugin`，确认本项目已启用插件及其 Skills 已加载，再开始执行流程；同一会话内无需重复执行。
- 产品定义、总体方案、工程架构、Backlog、单需求 TRD、开发实现等大型领域步骤，建议分别新开会话，减少上下文污染。
- UI/UX 框架按跨需求影响显式调用；`product-experience-audit` 只在阶段二对完整集成产品执行全项目级审计。
- `commit-changes` 是独立职责，但只是短时 Git 操作，不强制新开会话。
- `session-rule-retrospective` 默认在被复盘的原开发会话中执行；新会话通常缺少真实失败、根因和用户纠正证据。

## 三、项目初始化流程

### 流程外：产品构思（可选）

需要先构思时，可以使用 `pcm-product-factory`，默认通过讨论选定方向、确认命名后交付产品初稿；只有用户明确要求时才直接生成。初稿内容结构随产品决定，不是核心开发流程的前置产物。

正式流程从第 1 步开始，一句话想法或已有资料即可作为输入；已有工作区时直接进入产品定义沟通，不要求先写完整 PRD。

### 第 1 步：建立项目工作区

- 操作：复制或拉取本仓库作为新项目工作区，移除原仓库 Git 历史，准备项目文档目录。
- 完成条件：当前目录是新项目的根工作区，`.claude/`、`AGENTS.md` 等能力文件可用，尚未误带原仓库历史或无关项目资料。

这是人工操作步骤，不由某个领域 Skill 隐式完成。

### 第 2 步：项目需求与产品定义

- 能力：`project-intake`
- 输入：产品想法、产品初稿或已有资料。
- 输出：当前项目权威的需求与产品功能文档，包括最终产品范围、非目标、用户使用的核心术语，以及需要尽早验证的高风险产品或体验假设。
- 完成条件：目标用户、最终产品范围、核心流程、首次成功结果、关键约束、复杂度取舍和待确认事项已经收敛；仍有实质歧义时继续对话。识别高风险假设不等于决定具体开发排期，也不能静默缩小最终范围。

### 第 3 步：基础工程选型

- 操作：基于第 2 步的产品定义、开发约束和本次提供的可读选型参考资料选择基础项目；没有参考资料、已有适用工程或项目不需要模板选型时，第 3、4 步共同标记为不适用，不得猜测模板。
- 输出：仅从参考资料中选择基础项目，并明确 `frontend` 和 `backend` 的 `id`、`git_url`、`default_branch`、`path`、`reason`；项目明确不需要某一端时对应值为 `null`。
- 完成条件：所有成功选项都能在本次参考资料中逐项核对，字段完整；不输出参考资料之外的模板或自建方案。

本步骤只负责基础项目选型，不负责 clone、复制、清理、项目化、总体技术方案或提交。

### 第 4 步：组装基础工程（选型适用时）

- 操作：严格按照第 3 步已确认的选型结果，将所需模板或独立工程放入 `frontend/`、`backend/` 或其它目标目录；记录来源和 commit，清除上游 `.git` 与临时目录。
- 输入：第 3 步的选型结论；组装阶段不重新进行技术选型。第 3 步不适用时，本步骤同步跳过，后续能力直接读取当前真实工程事实。
- 完成条件：目标工程目录完整、来源明确、没有嵌套的上游 `.git` 或临时模板仓库，实际目录与选型结论一致；无法安全确认来源或目录归属时停止并报告。

### 第 5 步：核验项目准备状态

- 能力：`project-readiness`
- 定位：为当前 PCM 自动化开发周期建立一次开发资源准备基线。本周期后续不按需求或模块重复执行该 Skill；生产部署准备不属于本步骤。
- 输入：当前权威产品范围、适用基础工程选型、当前工程与配置事实，以及开发者本次可提供的真实开发资源资料。资源资料是动态候选池，不要求固定文件名、格式、字段或资源类型。AI Agent 工作区自身的媒体工具及其私有配置不属于该输入，也不写入项目准备清单或目标前后端运行配置。
- 执行动作：识别完成编码、开发环境联调和开发环境真实验收所需、且必须由调用方提供的外部服务、账号、凭据、素材、私有数据或专用设备；匹配候选前先验证受保护实际配置中的非空运行凭据与资源绑定，满足开发合同时原样保留，不用候选池中的维护、共享或更宽权限身份替换，也不把候选凭据探针结果误记为最终项目凭据结果；清单只描述最终选定绑定，不得提及、比较或说明未采用候选，否定表述也不例外；只有绑定缺失、失效或不合格时才对照资源资料匹配候选。在授权范围内优先创建项目专用开发/测试资源和最小权限运行凭据。资源使用稳定产品级环境身份，不以单个需求编号命名长期数据库或存储作用域；保持既有有效绑定，不为命名偏好擅自重建资源。服务不支持派生项目身份时，只有调用方明确授权的非管理、非生产共享开发身份，且数据、操作、收件人或其它实际作用范围满足开发合同，才可以兼容使用；共享管理或根凭据、生产身份和可访问合同外资源的身份不得写入应用配置，无法派生合格开发身份时属于第二类阻塞。权限与隔离按实际可见范围和范围外拒绝判断，不因“共享”标签或仅返回获授权资源的列表接口成功而误判不可用。将每项 `ready` 外部运行资源的最终凭据绑定写入被 Git 忽略的实际 `.env` 或等价配置，同步无秘密 `.env.example` 与公开说明，并使用最终运行凭据完成真实可用性、权限和隔离验证。
- 输出：项目准备清单，以及实际完成的开发资源、受保护开发配置和公开配置示例。准备清单只记录资源标识、配置键和脱敏证据，不记录秘密值。
- 完成条件：所有进入项目准备清单的当前开发必需外部资源均已真实可用；不存在以下两类阻塞：开发必需外部资源在候选池中缺失、当前环境无法安全生成且无兼容替代，或已匹配资源真实不可用、凭据无效、权限不足、隔离不合格，或缺少开发所需接口能力、可用配额、回调/白名单及其它既定能力。

依赖安装、migration、Seed、业务实现、产品内测试账号、完整联调和浏览器验收由后续开发完成。只服务生产部署或生产运行的正式域名、DNS/TLS、生产资源与凭据、生产回调与配额、监控、备份恢复、容量和发布安全属于自动化开发及清单准入范围外。项目准备清单正文任何位置都不得列举、命名或汇总这些事项，也不得以“未纳入清单”、范围外、未来事项、非阻塞、无状态或 `not-applicable` 章节保留它们；开发 SMTP TLS、localhost 回调、开发白名单、沙箱范围和开发配额仍按当前开发用途纳入。产品规则、隐私保留和其它设计事项同样不写入清单。

不得伪造外部凭据、账号、素材或不可替代开发资源来消除阻塞。只有候选满足已经确认的兼容合同才可直接替代；会改变开发技术边界、安全、成本或运行方式的替代必须先取得相应决定。

### 第 6 步：项目化基础工程

- 能力：`project-bootstrap`
- 输入：当前工程事实、产品定义、适用的基础工程选型结论和准备清单；已有项目可另外提供现有技术方案与设计资料。
- 输出：完成项目化的根目录、前端和后端工程。用户可见项目只落实已经确认的品牌、视觉和交互事实；尚无产品级体验方向时保持中性、可替换的基础样式，不把模板默认配色、字体、首页或组件外观认定为产品设计。
- 完成条件：模板示例身份已替换，项目配置和必要文档已落地；根仓与适用独立代码仓的 README 已按各自读者和职责收口为稳定入口、使用合同和文档地图，模板残留、失效命令、重复正文和漂移链接已经清理，README 中适用的最短启动、联调、健康检查与验证入口及关键前置条件已经按当前工程事实核验；适用安装、构建、测试、启动和基础联调已经验证。详细设计、执行证据和历史内容留在项目已有的适当受跟踪文档中；不为形式统一创建空文档或固定文档树。留下待提交变更，不提交。

当前标准初始化流程存在 Tailwind CSS v4 CSS-first 前端时，在 `project-bootstrap` 完成后、第 8 步初始提交前显式调用 `tailwind-theme`。调用只提供当前产品资料和实际前端工程，并请求依据产品和前端完成风格定制。Agent 可按项目事实自主选择保留默认、采用全部或部分 preset、适配或 custom，并按实际改动执行相称验证、诚实报告结果；具体选择、修改与验证规则以 [`tailwind-theme`](skills/tailwind-theme/SKILL.md) 为唯一真源，不在流程文档重复定义。

这是初始化阶段的条件性能力调用，不新增固定编号步骤，也不由 `project-bootstrap` 隐式调用。标准初始化中只因没有适用前端而跳过；`project-bootstrap` 不能自行把模板默认主题认定为最终产品主题，但 `tailwind-theme` Agent 可以依据产品与工程事实选择保留默认且无修改完成。存在前端但不符合已经约定的 Tailwind CSS v4 CSS-first 模板合同时属于工程事实或模板合同失败，不能按不适用或外部资源阻塞跳过；其它问题按真实可修复性继续处理或准确报告失败、阻塞。

### 第 7 步：总体技术方案

- 能力：`solution-design`
- 输入：产品定义、已组装并完成项目化的当前工程事实、开发约束和第 3 步已确认的基础工程选型。
- 输出：总体技术方案。
- 完成条件：系统边界、主要技术选择、交付单元、跨单元协作、关键风险和未决事项已经确认，且方案与实际工程事实一致。

### 第 8 步：初始化并提交适用仓库

1. 在根目录和适用的 `frontend/`、`backend/` 交付单元分别初始化 Git，主分支设为 `main`；不适用的仓库跳过。
2. 分别检查忽略规则、秘密、临时文件和实际 diff。
3. 产品工作区根的 `.agents/`、`.claude/` 和 `plugins-lock.json` 是仓库组建时从已定稿权威能力模板取得的只读提交输入；允许读取、核对 Git 状态、精确暂存并原样提交，不得创建、修改、删除、移动、格式化、清理、忽略或重写，也不得因版本、测试产物判断或权限安全偏好要求修复。可确认存在真实秘密或凭据时只报告并停止，不修改模板内容。
4. 对每个仓库单独执行 `commit-changes`，形成初始本地提交。

完成条件：每个适用仓库都有明确的初始提交，工作树状态符合预期，没有跨仓误纳入内容。

### 第 9 步：工程架构设计

- 能力：`engineering-architecture`。
- 适用：必要步骤。简单项目也必须基于产品定义、准备清单、总体技术方案和当前实际工程形成明确的工程归属与依赖规则，不提供“不适用”或暂缓路径。
- 输入：第 2 步两份产品定义、第 5 步项目准备清单、第 7 步总体技术方案，以及第 8 步确认 clean 的适用仓库和当前工程事实。
- 输出：固定工程架构文档 `docs/design/工程架构设计.md`；默认不修改 `AGENTS.md`、`CLAUDE.md` 或其它项目规则。
- 完成条件：单一 `docs/design/工程架构设计.md` 必须为非空受控文件，并对每个包含业务代码且相关的适用交付单元分别闭合 Current/Target、职责/边界、依赖和代表性文件归属：前端覆盖装配/路由页面、功能、远程/局部/跨页状态、模型映射和共享 UI；后端覆盖入口、编排规则、持久化适配、事务、授权、错误与副作用恢复；每单元至少有一个文件放置演练。文档还须以架构决策说明分层、关键接口与数据契约、配置与运行、质量门禁、安全和演进条件；Current 与 Target 有差异时说明最小迁移。只维护此单份根仓文档，不固定框架目录，也不以行数阈值拆分；不能仅列出原则或模式名称。根仓库及适用子仓均保持各自 `main` 且 clean。
- Git：工程架构完成后，对根仓库执行一次 `commit-changes` 核验；即使文档相对当前提交没有变化，也必须完成该次调用并确认无变更，不制造 diff，不处理其它路径或子仓库。若该 Skill 发现文档事实矛盾，应严格不修改、不暂存、不提交并报告；随后可由外层人工调度通过普通指令限定通用 Agent 只修正固定文档并精确提交，不把该修正误记为 commit-changes Skill 内部行为，也不强制拆成两个 Skill 问答。

### 第 10 步：产品级 UI/UX 框架

- 能力：`ui-ux-framework`。
- 适用：项目尚无能够指导后续需求的产品级框架，现有框架明显失真，或当前问题会改变产品表面、主导航、Shell、全局视觉语义、共享组件语义或客户定制边界。
- 条件性参考：当第 9 步工程架构资料涉及前端交付边界、共享状态或跨需求界面语义时，人工调用方将 `docs/design/工程架构设计.md` 作为 `ui-ux-framework` 的输入参考；该参考不改变此 Skill 的独立性。
- 输出：按项目文档约定维护的产品级 UI/UX 框架，或明确的不适用结论；涉及产品表面、Shell、导航、页面模式、sticky、滚动或响应式转换时，框架包含可由后续需求引用的 App Shell Contract。
- 完成条件：产品表面、信息架构、Shell、导航、页面模式、共享视觉与跨需求交互约束已经收敛；适用的 App Shell Contract 明确区域职责、常规滚动所有者、sticky 基准、宽窄屏转换及媒体使用、缺失和替换的稳定规则。设计 Agent 已从内容识别、场景理解、品牌表达和产品展示主动评估媒体价值，有明确跨需求收益且在授权范围内时纳入框架，没有收益时不为装饰强制配图。只有会实质改变跨需求体验骨架、迁移成本或兼容性的具体决定保持待确认，其余低风险结构形成有依据和重议条件的默认 Target；没有把单需求设计、参考资源代码或页面实现混入框架。
- Git：有文档变更时对根仓库执行 `commit-changes`。

本步骤不是每个需求的固定前置步骤。若新的产品表面、Shell、主导航或视觉语言会显著影响基础工程项目化，可在第 6 步写入视觉基线前提前执行本步骤，再基于后续工程事实校正；这属于人工调度选择，不形成固定 Skill 链。单需求设计由 `trd-design` 根据其可访问的需求、产品、界面和设计资料独立完成；没有项目级框架资料时，不阻止单需求设计或开发。

### 第 11 步：拆分 Backlog

- 能力：`requirement-breakdown`
- 输入：产品定义、相关工程事实、第 9 步的 `docs/design/工程架构设计.md`，以及适用时调用方提供的跨需求体验决定（已确认 Target 或有依据的默认 Target），用于关联模块边界、技术约束和产品表面演进；没有第 10 步产物时仍独立拆分。
- 输出：完整覆盖最终产品范围的 Backlog 总览和需求详情卡，以及建议的首条验证切片。
- 完成条件：每个大需求具有明确产品结果、范围、依赖、验收方向和建议顺序；已检查可以合并、删除或推迟确认的复杂度；首条验证切片由一个或多个可独立完成的正式需求组成，能够尽早验证关键假设，并明确尚未覆盖的最终范围。切片不是半完成需求、Mock 演示或最终范围缩减。每个项目还须按 `requirement-breakdown` 的“项目数据基线与首次交付”合同明确适用性和正式需求归属：接手者按说明准备真实服务后，用单一初始化入口得到可登录、可操作的自然数据现场，并可明确重置目标环境恢复完整起点；所需对象存储／文件随数据共同恢复。不能只在 Backlog 末尾追加 Seed 标题。

首次身份与基础初始化随最早需要它们的业务交付，后续需求同步维护角色、业务关系和文件，完整恢复收口按真实依赖安排。默认只规划初始化与重置，不为所有项目机械增加保留式补齐模式或固定末尾节点；无相关数据时记录不适用事实，但不能以支持注册、单角色或数据少省略已经承诺的接手使用结果。

按用户结果拆分 Backlog，不按目录拆分。已确认体验 Target 只在演进既有产品表面本身形成独立、可观察的用户结果，且其它需求开始前确实必须完成时，才形成正式迁移需求和严格前置依赖；否则作为相关业务需求的体验约束，不按页面、组件、CSS、目录或参考资源拆分。工程依赖方向同样只用于识别实现边界，只有对应的另一正式需求在当前需求开始前确实必须完成时，才形成严格前置依赖。

- Git：对根仓库执行 `commit-changes`。

## 四、阶段一：单需求开发循环

以下步骤每次只处理一个活动需求。

### 第 12 步：选择需求并建立根仓库需求分支

1. 确认根仓库和适用代码仓库的当前状态与 `main` 基线。
2. 从 Backlog 选择一个可开始需求，确认依赖已满足。
3. 在根仓库从最新 `main` 创建需求分支，使用稳定且可识别的分支名。

完成条件：活动需求唯一、范围明确，根仓库需求分支正确，开始前状态已记录。

### 第 13 步：形成最终活动 TRD

1. 新会话执行 `trd-design`，默认只创建或更新当前活动 TRD；调用时随活动需求传入第 9 步产物及其它相关资料，用于模块归属、公开能力和架构 delta 判断。存在与本需求适用的跨需求体验决定时，只引用其来源、适用范围、Current/Target 和本需求是遵循还是改变；默认 Target 还保留依据和重议条件，不复制整份框架，也不把第 10 步变成固定前置。对用户可见需求，除完整路径、状态、反馈、失败、恢复、响应式和可访问性外，还要检查能否删除或合并步骤、字段、决策和跳转，明确用户术语、内容主次、主要行动、关键文案意图以及不应暴露的内部概念；同时从内容识别、场景理解、品牌表达和产品展示主动评估媒体价值，有明确收益且在授权范围内时直接纳入设计，不等待用户点名，也不要求每个页面配图。
2. 当核心任务、信息架构、导航、状态表达或视觉方向存在多个实质方案，仅靠文字无法判断，且实现后返工成本明显时，提供能够解决当前疑问的最低成本证据，例如任务流、少数关键状态草图、可抛弃点击原型或真实项目中的窄范围预览。证据来源和格式不固定，也不要求为普通局部变化制作原型。
3. 人检查并确认最终 TRD：范围、产品行为、体验复杂度、技术方案、验证场景和待确认事项足以指导实现；触及前述高影响体验选择时，应查看实际原型或渲染结果，而不是只确认文字。已有项目设计资料可以作为输入，但不是 `trd-design` 的固定依赖。
4. 如果 TRD 暴露出会改变跨需求产品体验骨架的高影响问题，由人决定是否单独调用 `ui-ux-framework` 处理；不得把单需求设计或开发后验收重新拆成固定 UI 步骤。
5. 对根仓库需求分支执行 `commit-changes`，提交最终 TRD。

发现 Backlog、产品文档或总体方案需要调整时，先报告影响；只有人明确纳入本次范围才跨文档修改。活动需求涉及媒体时，TRD 还应明确其用户用途、来源类型、静态或动态落点、权限或失败降级及真实验收方向，并按全局规则基于用途选择复用、检索或定制生成/编辑；这不把任一媒体能力设为固定上游，也不建立 Skill 嵌套调用链。

### 第 14 步：建立代码仓库需求分支

- 根据 TRD 判断受影响的代码仓库。
- 在每个受影响仓库中，从最新 `main` 创建与需求对应的功能分支。
- 不受影响的仓库不机械建分支。

完成条件：所有受影响仓库都位于正确功能分支，未混入上一需求或其它工作。

### 第 15 步：实现与验证

- 新会话执行 `dev-workflow`，输入最终活动 TRD、目标仓库和第 9 步产物；TRD 引用了跨需求体验决定时，同时提供对应来源或可核验事实，只使用与本次实现相关的部分，不重新执行工程架构或产品级 UI/UX 框架设计。
- `dev-workflow` 负责实现、适用测试、真实运行、联调、浏览器验收和独立审查。用户可见改动必须同时验证任务是否足够简单、界面文案是否易懂、信息与操作层级是否清楚、页面构图是否服务真实产品任务，而不是仅由基础组件拼装；开发 Agent 同时主动复核媒体能否改善内容识别、场景理解、品牌表达或产品展示，有明确收益且在授权范围内时按用途直接落实，没有收益时不机械配图；存在适用体验决定时，建立“决定及 Current/Target/范围（默认 Target 含依据与重议条件） → 本需求可观察结果 → 实现位置 → 真实浏览器与截图证据 → 实际结果”映射。自动化测试可以使用隔离测试库；涉及持久化的用户流程在完成前必须以实际开发配置连接开发库完成真实浏览器验收，并按 `dev-workflow` 规则处理最小、非敏感、可复位的成功态开发数据。它不提交、不建分支、不合并、不推送，也不同步最终 Backlog 状态。
- 当本需求使某个仓库 README 所承载的项目定位或范围、正常入口、安装/启动/配置前置、稳定用户行为或限制、恢复/核验入口、账号交接入口、运行责任、摘要或权威文档链接发生变化时，必须同步该 README；只改变详细交付文档内部内容且 README 的稳定摘要、入口和链接不变时，不机械修改 README。纯内部实现、测试日志、截图和一次性排错证据不写入 README。详细账号矩阵、对象清单、复杂恢复、安全操作和专项验收优先维护在项目已有受跟踪文档中，README 只保留必要摘要和链接；项目已明确选用 README 承载且内容规模适合时可直接记录。修改时必须替换或删除旧事实，不按需求编号持续追加。完成前实际核验 README 中受影响的命令、链接和关键前置条件。
- 当前需求涉及数据基线时，按 `dev-workflow` 的“项目数据基线与交付恢复”实际证明单入口初始化、正常使用后重复保护、明确重置及范围外不变、所需媒体恢复、逐角色登录和主要任务；数据必须符合本产品使用情境，不能只有测试状态矩阵。后续业务变化同步维护当前基线；不因已完成过一次 Seed 需求而免除本次受影响恢复核验。
- 开发完成后，检查每个受影响仓库的 diff、验证证据和剩余工作树状态。
- 若 TRD 涉及媒体资源，产品界面使用已固化的静态资源或适用的真实上传资产验证加载、缺失、失败和恢复；fixture 只作为测试输入，不充当产品资产或业务数据，也不以随机占位图、临时第三方 URL 或静态 Mock 冒充完成。
- 对每个受影响代码仓库分别执行 `commit-changes`。

完成条件：`dev-workflow` 给出“已完成”或准确的非完成状态；只有“已完成”、受影响仓库 README 中的稳定入口和使用合同已经同步并按工程事实核验、失效或重复说明已经替换或删除、各代码仓库变更已经提交，才能进入第 16 步。README 中的命令、链接、关键前置条件不可用，或必需的详细交付文档无法从 README 发现时，不得标记完成；本需求没有改变 README 所承载的稳定入口、摘要、前置条件或文档地图时，不要求机械修改。涉及 UI 的需求还必须有真实浏览器交互、实际读取的代表性渲染结果，以及与任务简化、文案和视觉层级相称的验收证据；没有适用的 UI 变化时不机械执行视觉检查。

### 第 16 步：合并代码仓库并在 `main` 最终验证

对每个受影响代码仓库分别执行：

1. 确认功能分支工作树干净、提交完整；
2. 切换到最新本地 `main`；
3. 按项目约定将功能分支合并到 `main`；
4. 在 `main` 上重新运行与合并结果相关的最终检查；
5. 记录合并结果和验证证据。

这是显式 Git 操作，不由 `dev-workflow` 或 `commit-changes` 代替。任一仓库合并冲突或最终检查失败时，先解决并重新验证，不进入状态收尾。

### 第 17 步：同步需求最终状态

回到根仓库需求分支，根据代码仓库 `main` 上的真实结果：

1. 更新活动 TRD 的实施结果、实际验证、完成状态和完成日期；
2. 同步 Backlog 总览与对应详情卡；
3. 保证状态准确：未完成或验证受阻时保留阻塞和缺口，不得标记完成；
4. 对根仓库需求分支执行 `commit-changes`。

完成条件：TRD、Backlog、代码合并结果和验证证据一致。

### 第 18 步：复盘本次执行规则

1. 保持根仓库位于当前需求分支，返回执行本需求 `dev-workflow` 的原 Claude Code 会话，再执行 `session-rule-retrospective`；原会话中的失败、根因、修复和用户纠正是规则判断的主要证据。
2. 只把本次真实发生、已证实、项目内高概率复现且有明确规避动作的问题沉淀到 `.claude/rules/`；代码、产品、需求或一次性问题不在复盘中顺手修改。
3. Skill 只修改 rules 并留下待提交文件，不自行提交。没有候选通过准入门槛时，无副作用结束并明确“无需沉淀、无需提交”。
4. 有 rules 变更时，在同一个根仓库需求分支执行 `commit-changes`，形成独立规则提交；不创建复盘分支，不把规则混入需求状态提交。

完成条件：原开发会话已经完成复盘；结果为无规则变更，或规则变更已在当前根仓库需求分支精确提交。

### 第 19 步：合并根仓库并检查全局状态

1. 确认根仓库需求分支已包含第 17 步的状态同步提交，以及第 18 步可能产生的独立规则提交；
2. 将该需求分支合并到根仓库 `main`；
3. 分别检查根仓库和各适用代码仓库的当前分支、`git status` 和最近提交；
4. 确认没有遗留临时目录、意外未提交文件、未合并需求分支或跨仓状态不一致。

根仓库最后合并，保证文档和可选规则都建立在代码仓库已经合并、验证和复盘的事实之上。完成后本需求循环结束；开始下一个需求前，各适用仓库均从最新 `main` 创建新分支。

阶段一重复第 12–19 步，直到当前已知正式范围内的需求均完成开发、合并、最终验证和状态收尾。首条验证切片完成后先记录其验证结论及对后续范围的影响；只有阶段一已知正式范围完成，才进入阶段二。

## 五、阶段二：全项目级产品体验审计与迭代

### 1. 建立审计范围和运行条件

阶段二只在阶段一已知正式需求全部完成第 12–19 步后开始。审计对象是各适用仓库 `main` 组成的完整集成产品和当前正式范围内全部主要用户任务，不是单个页面、单个需求、首条验证切片或局部改动。

从当前产品定义、正式 Backlog、已完成 TRD、各仓库 `main`、路由、测试和可运行行为中识别：

- 主要用户角色、核心用户目标和跨页面任务；
- 当前完整集成版本和可访问环境；
- 项目专用且真实可登录的开发账号、可复位开发数据和清理方式；
- 代表性桌面与窄屏，以及适用辅助技术路径；
- 允许执行的写入和明确禁止的资金、外发、生产数据及其它高影响副作用；
- 已有功能验收、UI/UX 框架和其它预期依据。

审计范围以用户任务和风险状态表达，不以页面清单代替；普通运行不要求创建新的审计章程、Manifest 或过程目录。缺少会阻断主要任务的环境、角色、数据或真实浏览器能力时，先按项目方式补齐；无法补齐则阶段二保持阻塞，不降级成截图审查后宣称完成。

### 2. 执行全项目级产品体验审计

在独立新会话显式执行 `product-experience-audit`。输入阶段一完成的完整项目范围、各适用仓库 `main` 的版本事实、可访问集成环境、全部主要用户任务、运行边界和已有证据。

Skill 负责实际执行范围内任务，收集代表性截图和相称的动态证据，输出任务覆盖、经核验候选、重复/未纳入项和覆盖缺口。它不修改业务代码、产品定义、技术设计或正式 Backlog，不创建正式需求，也不自动调用后续能力；默认直接返回结果，只有用户明确指定项目已有候选接收位置时才按其契约精确追加。

完成条件：本轮审计覆盖完整集成产品的主要用户任务和跨需求、跨模块衔接，能区分实际覆盖、未覆盖、候选、重复、低证据观察和高影响待决事项；只访问页面、只审一个需求、只看截图或只走 happy path 不算完成。

### 3. 按政策分流候选

由调度会话基于审计证据执行分流，不要求人逐条审批普通候选。进入阶段二即表示人授权 AI 对满足下述政策、且不触及高影响边界的候选自主完成需求化、设计、开发、验证和收尾；已有领域 Skill 中针对普通文档草案的逐项确认不重复执行，但任何实质性产品、架构、安全、兼容或不可逆取舍仍按原 Skill 边界暂停确认：

- **重复或已有归属**：向已有活动项补充证据，或记录为重复，不新建需求。
- **误判、无用户影响依据或纯主观偏好**：明确不纳入；可以保留为设计机会，但不自动触发开发。
- **证据不足**：补齐环境、身份、数据或动态证据后重新判断，不把疑点直接写入正式 Backlog。
- **价值或时机不足**：说明影响的用户任务、发生频率或潜在损失；不能证明值得当前处理时保留为候选，不因为“可以改进”就自动开发。
- **可以更简单地解决**：优先评估删除、合并、减少步骤、修改默认值或复用现有模式；只把达到目标所需的最小可验证改动需求化。
- **高信心 Bug、可用性缺陷和边界明确的低风险改进**：自动进入正式需求化。
- **改变产品目标、正式范围、核心任务、品牌方向、安全/隐私、不可逆兼容或外部副作用**：暂停该项，由人确认产品和风险边界；其它无依赖候选可以继续。

候选只有在用户结果、范围、证据和验收方向已经明确后才获得正式需求 ID。单个内聚候选可以由调度会话按现有 Backlog 结构直接形成需求；一批候选需要合并、拆分、排序或重算依赖时，显式执行 `requirement-breakdown`，并使用其“依据充分资料直接生成”路径完成质量检查和更新，不再逐批等待人确认普通草案。需要改变权威产品定义时先执行 `project-intake` 并等待相应高影响决定。这些是调度层选择，不由审计 Skill 自动串联。

### 4. 将候选纳入正式 Backlog

正式需求必须先进入根仓库 `main` 上的 Backlog，才能按第 12 步被选择：

1. 确认根仓库和适用代码仓库均位于最新 `main`，工作树状态清楚；
2. 从根仓库最新 `main` 创建短期候选入池分支；
3. 在该分支新增正式需求 ID、Backlog 总览项和详情卡，只写已经通过准入门槛的用户结果、范围、依赖和验收方向；
4. 检查候选之间的合并、拆分、依赖和建议顺序，对根仓库执行 `commit-changes`；
5. 将候选入池分支显式合并回根仓库 `main`，检查合并结果和工作树，再结束该短期分支。

候选入池只建立后续可选择的正式需求，不提前创建活动 TRD、代码分支或完成状态，也不修改已归档历史。入池失败、合并冲突或 Backlog 质量检查未通过时，不进入第 12 步。

### 5. 复用单需求开发循环

每个已经进入根仓库 `main` Backlog 的正式需求都建立新的活动 TRD，不回写已归档的历史需求。然后复用第 12–19 步：

1. 从最新 `main` Backlog 选择该需求并建立根仓库需求分支；
2. 执行 `trd-design`；调度会话对没有实质性取舍的普通 TRD 自主完成审核，只有触及产品、架构、安全、兼容或不可逆边界时才暂停给人确认；
3. 建立受影响代码仓分支，执行 `dev-workflow`、合并和 `main` 最终验证；
4. 同步新需求和活动 TRD 的最终状态，在原开发会话完成规则复盘，最后合并根仓库需求分支。

阶段二发现的是新演进工作，不能为了节省文档而把多个无关问题塞进一个 TRD，也不能把所有视觉建议汇总成没有独立用户结果的“全量美化”需求。

### 6. 针对性回归和完整复审

每个候选修复完成后，重新执行原复现任务、受影响状态和相邻跨页面路径，确认问题消失且没有引入新的任务断点。已有自动化和单需求验收不能替代这次针对原体验证据的回归。

一批正式需求完成后，再次在独立会话执行全项目级 `product-experience-audit`，以新的各仓库 `main` 版本重新覆盖全部主要任务，并重点复核本轮受影响任务：

- 新出现且达到准入门槛的候选继续进入本阶段分流和开发循环；
- 仅有重复、明确不纳入、低证据偏好或不阻断完成的设计机会时，不为追求“再也找不到建议”而无限迭代；
- 出现新的关键覆盖缺口时先补验，不能用上一轮证据替代当前版本。

### 7. 阶段二完成条件

只有同时满足以下条件，阶段二才完成：

1. 审计范围覆盖当前产品全部主要用户任务，而非只覆盖页面；
2. 适用动态任务已在真实浏览器和真实开发/测试服务上执行，主要界面和关键状态有代表性截图，动态结论有相称的交互、状态、网络或可访问性证据；
3. 所有发现已经去重、分类和分流，没有未处理的高信心阻断或高优先级问题；
4. 自动纳入的正式需求已经完整走完第 12–19 步，并通过针对原发现的体验回归；
5. 最终完整复审没有新增达到自动纳入门槛的问题；
6. 与主要任务有关的环境、角色、数据、视口或动态证据缺口已经关闭；
7. 完成结论不依赖阶段三收到或核验任何人工反馈。
8. 适用的数据基线与当前集成版本一致：接手者可按说明初始化到可登录、可操作的现场，并通过明确重置恢复完整起点；所需持久化文件与数据共同可用。本轮审计修复若改变该合同，已有需求中的基线、说明和受影响恢复证据已同步，不能只保留修复前的旧基线。

无法满足时应准确标记当前已完成范围、阻塞、保留候选和解除条件，不以“后面还会人工体验”宣布阶段二完成。

## 六、阶段三：人工反馈驱动迭代（可选）

### 1. 接收并分诊反馈

阶段三只在收到人工体验、测试、客服、用户研究或其它外部反馈时执行。没有反馈时明确跳过，无需创建空报告或候选池。

对一批相关反馈在独立会话显式执行 `product-feedback-triage`。Skill 将反馈拆为可核验事实、用户痛点和建议方案，核验可安全核验的内容，拆分混合问题、合并重复项，并输出可需求化候选、待补证项和不纳入项。清楚完整的单条反馈可以走“无需额外分诊”快速路径，不为了流程形式继续追问。

### 2. 分流和开发

阶段三复用阶段二的证据、去重和高影响边界政策：

- 普通、证据充分且边界清晰的问题无需逐条人工审批，可以进入正式需求化；
- 未核验反馈先补证，不把截图、语气或反馈数量直接当作事实和优先级；
- 反馈者提出的解决方案只是假设，不能越过产品和技术设计；
- 高影响产品、安全、品牌、兼容和不可逆决定由人确认。

正式纳入后，先按阶段二“将候选纳入正式 Backlog”的步骤完成根仓库入池和合并；按需要使用 `project-intake` 或 `requirement-breakdown` 时，沿用阶段二的高影响确认边界和普通事项自主授权。随后从最新 `main` Backlog 完整复用第 12–19 步，每项修复仍需针对反馈原场景执行回归，不能只依赖实现者自述或单元测试。

### 3. 可选边界和停止条件

阶段三处理完当前已收到的反馈，且所有纳入项、待补证项、高影响待决项和不纳入项都有准确处置后即可结束。后续出现新反馈时可以重新执行，不需要保持常驻流程。

阶段三不能：

- 回头替阶段二补主要任务覆盖、动态证据或最终复审；
- 因人工尚未体验而降低阶段二完成标准；
- 把没有收到反馈解释为产品没有问题；
- 把每个反馈者偏好直接变成开发任务。

## 七、异常与停止条件

遇到以下情况时暂停流程，不用“先继续后补”掩盖问题：

- 需求范围、重大架构、安全、兼容性或不可逆迁移无法安全决定；
- 不可替代的外部凭据、账号、服务、设备、审批或数据缺失；
- 用户已有修改与当前任务发生重大冲突；
- 测试、构建、真实联调、浏览器验收或独立审查仍有影响完成判断的问题；
- 任一仓库分支、提交、合并或工作树状态不清楚；
- TRD、Backlog 与代码真实结果不一致；
- 阶段二缺少主要任务所需的真实环境、授权角色、可复位数据、安全测试条件或动态浏览器证据；
- 阶段二仍有未分流、未修复或未复审的高信心阻断和高优先级候选；
- 试图用静态截图、代码阅读、Mock、单页巡游或历史结果替代当前版本的任务级动态证据；
- 阶段三反馈尚未核验，却准备直接写入正式需求或开始开发；
- 审计或反馈涉及重大产品、安全、隐私、品牌、兼容或不可逆决定，且无法按现有事实安全推断。

停止时应说明：当前阶段、已完成范围、已验证证据、真实阻塞、已尝试动作、保留的候选或变更，以及解除条件。
