# project-readiness — 项目准备状态与清单维护

## 定位

这是一个可独立调用的项目准备状态分析能力。它根据用户提供的资料、当前项目目录和已有文档中的最新事实，识别项目实际需要的开发条件，主动核验能够安全检查的内容，并生成或更新项目准备清单。

它不规定调用时机，也不要求任何其它 skill 先运行。项目可以处于产品定义、技术方案、模板项目化、业务开发或发布准备中的任意阶段；每次调用都应重新读取当前可获得的事实，不能依赖上次调用的缓存、记忆或固定流程顺序。

> 准备清单记录已确定方案的实现条件，不记录尚未决定的技术候选偏好，也不替代产品定义、技术设计或模板选型。

## 核心原则

1. **先读取，再判断，再落盘。** 先读取用户资料、当前项目文件、相关规范和已有准备清单，基于证据判断当前状态。
2. **事实优先。** 当前代码、依赖、配置、测试、迁移、运行结果和开发者明确确认高于猜测；说明性文档不能替代工程证据。
3. **不制造技术决策。** 只核验当前资料已经确定的技术和服务；技术尚未确定时记录未决事实，不根据本机工具、常见模板或 AI 偏好擅自选型。
4. **一项一项推进。** 发现多个问题时，按对当前开发或真实验证影响最大的事项逐步讨论，不发送大段空白问卷。
5. **区分阶段影响。** 明确某项是当前开发必要、某个里程碑必要、发布时必要、可选增强还是明确不适用，不把所有未来依赖都提前变成阻塞。
6. **安全核验。** 可以读取和维护开发 `.env` 以完成真实核验，但不得在文档、日志、回复、提交或外部审查中暴露秘密原文。
7. **清单可更新。** 清单反映当前事实和当前方案；技术决策、工程结构或外部依赖变化后，应更新受影响条目，而不是保留过期结论。

## 可接受的输入

用户可以提供任意组合：

- 项目名称、需求说明、产品功能说明或原始立项资料；
- 技术方案、模板选择说明、Backlog、TRD 或交付约束；
- 一个或多个目标仓库、前端/后端目录或其它工程路径；
- 现有项目准备清单，希望核验、回填或纠正；
- 已知的服务、第三方账号、素材、测试数据、部署或合规要求；
- 希望只检查某一类准备项，例如数据库、环境变量、浏览器验收或外部服务。

没有完整资料也可以开始。此时先读取当前目录中能够找到的项目资料和工程事实，明确哪些判断有证据、哪些仍无法判断，不为了填满表格而虚构准备项。

## 工作方式

### 1. 读取当前上下文

先按项目实际情况读取：

- `CLAUDE.md`、`AGENTS.md`、README、贡献说明和版本文件；
- 需求、产品功能说明、技术方案、Backlog、TRD 等当前项目文档；
- 前端、后端及其它实际涉及仓库的目录结构、Git 状态、依赖清单、锁文件、构建配置、测试配置和启动说明；
- `.env.example`、配置 schema 和安全忽略规则；真实 `.env` 仅在必要的本地核验范围内读取；
- 已有项目准备清单及其最近可验证的证据。

如果资料之间存在冲突，区分“当前事实”“已确认决定”“目标状态”“当前假设”和“待确认事项”，指出影响，不自行选择其中一版。

### 2. 确定当前准备范围

根据最新可获得的产品、技术和工程事实，识别实际需要准备或核验的内容。准备项可以包括：

- 代码仓库、目录访问和分仓库边界；
- 运行时、包管理器、依赖清单和 lockfile；
- 数据库、中间件、本地服务、迁移和初始化数据；
- 开发环境变量、`.env`、`.env.example` 和配置契约；
- 第三方开发账号、回调地址、白名单、沙箱和测试账户；
- 原型、文案、图片、字体、测试数据及授权记录；
- 本地启动、健康检查、接口联调、构建、测试和浏览器验收条件；
- 部署、域名、TLS、备份恢复、隐私删除和发布级安全条件。

只有当前资料已经确定或工程已经实际使用的技术和服务，才进入具体准备项。例如技术方案已经确定数据库后，可以核验该数据库的连接；数据库尚未决定时，只记录“数据库方案待确定”，不能把某个客户端存在写成选型结论。

简单项目不必机械覆盖全部类别。对当前阶段没有实际价值的内容应省略或标记 `not-applicable`，不为了凑齐清单创建空条目。

### 3. 主动核验与对话确认

AI 能安全执行的检查应主动执行，例如：

- 检查目录、仓库边界、Git 忽略规则和工作树状态；
- 检查运行时、包管理器、依赖清单、锁文件和项目命令；
- 检查配置键是否齐全，但不输出秘密值；
- 按项目既有方式检查服务连通性、迁移、初始化和健康入口；
- 执行适用的安装、测试、构建或启动就绪检查；
- 涉及 UI 时检查真实浏览器验收条件是否可用。

涉及付费、开通账号、生产权限、不可逆操作、人工审美或只能由开发者确认的事项，不擅自执行，用 `pending` 记录需要确认的内容和实际影响。

不能用 Mock、静态 JSON、假接口或“工具已安装”冒充真实服务已经可用。外部服务不可控或必要资料缺失时，保留真实验收要求，准确记录验证缺口和补验方式。

### 4. 阶段性同步

经过一组核验或一个重要主题明确后，用简短总结同步：

```text
当前已确认：...
已核验的准备条件：...
当前缺失或待确认：...
对开发或验收的实际影响：...
我的建议：...
```

总结用于继续讨论，不等同于正式文档，也不代表用户已经同意落盘。

### 5. 获得同意后生成或更新清单

准备写入或覆盖正式清单前必须：

1. 说明本次读取了哪些资料和工程事实；
2. 说明准备新增、修改、状态回填或删除哪些条目；
3. 指出仍保留的假设、未验证事项和实际影响；
4. 说明为什么当前信息足够生成或更新清单；
5. 明确询问用户是否现在写入文档。

只有用户明确同意后才能创建或改写正式准备清单。用户希望继续核验或讨论时，继续处理，不用草稿代替确认。

## 默认产出

默认路径：

```text
docs/requirements/项目准备清单.md
```

如果用户提供了已有清单，先读取完整内容，说明准备修改的范围，只更新受当前事实影响的部分，不进行无关重写。

每项至少记录：

| 字段 | 含义 |
|---|---|
| 项目 | 准备内容的短名称 |
| 是否必要 | 当前阶段、指定里程碑或发布是否需要 |
| 核验方式 | AI 可执行的命令/步骤，或需要开发者确认的事项 |
| 状态 | `ready` / `missing` / `pending` / `not-applicable` |
| 脱敏证据 | 检查摘要或开发者确认，不含秘密原文 |
| 实际影响 | 缺少时具体无法做什么 |
| 补齐方式 | 需要谁提供什么，或如何重新验证 |

状态含义：

- `ready`：已经通过检查或明确确认可用；
- `missing`：已经确认缺失或不可用；
- `pending`：尚待提供、确认或核验；
- `not-applicable`：根据当前范围、方案或交付目标不需要。

清单开头应包含当前阶段摘要，说明项目当前可以做什么、不能做什么，以及状态判断依据的日期或最新核验范围。清单结尾应总结当前阻塞、可安全延期的依赖、补齐责任和重新核验条件。

## 开发环境、Docker 与 `.env`

### 使用已有服务

- PCM 开发环境默认已准备数据库和常用中间件，但必须按当前技术方案和实际配置确认项目是否使用，以及连接是否可用。
- 优先读取项目配置、连接并验证已有服务。
- 不因为需要数据库或中间件就自行启动容器。
- 不把 Docker、Docker Compose、镜像、容器网络列为默认开发准备项。
- 正常开发期间不默认生成 Dockerfile 或 Compose 文件。
- 如果用户最终需要容器化交付，应作为单独的交付需求另行确认。

### AI 管理开发 `.env`

AI 可以读取、创建和修改开发环境 `.env`，也可以使用用户提供的数据库密码、测试账号和第三方开发 API Key 做真实核验。必须遵守：

- 确认真实 `.env` 已被 Git 忽略；
- 不提交、stage 或展示真实 `.env`；
- 不把秘密复制到需求文档、准备清单、技术设计、任务记录、审查材料、提交信息或普通回复中；
- 命令输出、日志和核验记录只保留脱敏证据；
- 不把秘密发送给外部服务或第二审查引擎；
- 可以维护 `.env.example`，但其中只能放变量名、安全示例和说明，不放真实值。

遵循项目已有的配置加载方式。后端 `.env` 中的 JSON 数组等配置不能用 `source .env` 代替项目配置解析；需要注入子进程时，使用安全的键值读取方式，并确保输出脱敏。

## 更新已有清单

再次调用本 skill 时：

1. 先读取现有清单、相关最新文档和当前工程事实；
2. 说明哪些条目仍有效，哪些状态已经漂移，哪些条目因方案变化需要重写；
3. 只核验和回填本次实际涉及的范围，不重新生成与当前目标无关的内容；
4. 不把历史核验结果当成当前事实；
5. 如果准备清单反映的技术方案与最新技术方案冲突，先报告冲突及影响，不悄悄覆盖技术决策；
6. 如果某项已不再适用，标记 `not-applicable` 并保留简短依据，不直接删除有追溯价值的历史信息。

## 结束方式

完成分析或文档写入后，只汇报：

- 当前准备状态和依据；
- 已创建或更新的文件；
- 关键 `ready`、`missing`、`pending` 和 `not-applicable` 项及实际影响；
- 尚未解决的事项和补齐/补验方式；
- 用户当前可以选择的下一步。

下一步只提供选择，不把任何其它 skill 描述为强制依赖或固定后续。

## 反模式

- 在没有读取当前资料和工程事实时直接套用固定清单；
- 因为本机存在某个客户端、模板使用某项技术或 AI 熟悉某项技术，就把它写成项目选型；
- 把尚未确定的候选技术伪装成已确认依赖；
- 把所有未来能力都标为当前开发阻塞；
- 用 Mock、静态 JSON、假接口或工具版本存在冒充真实服务可用；
- 未经用户同意创建或覆盖正式清单；
- 把真实 `.env`、API key、数据库密码或第三方原始响应写入文档、日志、审查材料或回复；
- 自动启动数据库、中间件或 Docker 容器；
- 修改产品需求、技术方案或代码来掩盖准备缺口；
- 把其它 skill、固定 Agent 或固定调用顺序写成此能力的必经流程。
