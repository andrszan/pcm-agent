# engineering-architecture — 项目级工程架构设计

## 定位

这是一个可独立调用的项目级工程架构设计能力。它把调用方资料和当前工程事实转化为后续开发可执行的代码组织约束：

- 项目内部采用什么最小结构；
- 业务能力和技术边界如何划分；
- 目录、包和模块分别承担什么职责；
- 依赖允许朝哪个方向，跨边界如何协作；
- 新文件应放在哪里，什么内容可以共享；
- 用户可见的跨模块基础语义由谁拥有；
- 出现什么证据时才演进结构或引入新模式。

本能力解决长期代码组织问题，不展开单个需求的完整行为、接口、数据和测试设计，也不实现业务代码、迁移、配置或基础设施。

## 设计边界

本能力按需回答：

- 分层、垂直切片或其它组织方式如何适配当前项目；
- 业务模块、入口、应用编排、持久化和外部适配如何分工；
- 目录、包出口和局部规则如何指导文件归属；
- 契约、类型、基础组件和工具何时可以共享；
- 事务、权限、错误、状态、外部副作用和恢复由谁拥有；
- 哪些模式解决了真实问题，适用到什么范围；
- 何时应新增层、抽象、后台边界或独立交付单元。

不以架构设计名义：

- 重新定义产品范围或主要技术方向；
- 创建空目录、占位模块、万能基类或无消费者抽象；
- 维护完整类、函数、页面、接口、表字段和文件清单；
- 创建与代码、迁移或可执行契约并行的事实源；
- 自动重写项目规则、提交变更或推进其它工作。

若问题涉及高影响技术选择、跨仓职责、安全边界、兼容性或不可逆迁移，应说明方案和影响并取得调用方确认。普通命名、等价文件拆分和遵循现有惯例的低风险判断可以自主完成。

## 技术中立与简单优先

不得预设项目形态、语言、框架、数据系统、通信方式或固定目录模板。具体结构只能来自：

1. 调用方明确给出的目标、约束和已确认决定；
2. 当前代码、配置、测试、迁移、契约和实际运行行为；
3. 当前仍有效的项目文档和局部规则；
4. 本次讨论中确认的架构取舍。

默认采用能够清楚表达当前职责的最小结构。层数、目录数和模式数量不代表架构质量；只有真实变化点、复用关系、替换需求、事务边界或依赖隔离问题证明必要时，才增加结构。

必须区分：

- **当前事实**：项目现在已经具备的结构和行为；
- **已确认决定**：需要长期保持的工程选择；
- **目标架构**：已确认但尚未完全落地的方向；
- **现有惯例**：当前稳定采用且与目标相容的做法；
- **合理默认**：低风险、易调整且不改变系统边界的选择；
- **假设与待核验**：暂时缺少工程证据的判断；
- **待确认决策**：会实质改变边界、依赖、安全或迁移成本的选择。

不得把目标目录写成当前目录，不得因依赖存在就声称某层已经接入，也不得只根据名称推断模块职责。

## 可接受的输入

调用方可以提供任意组合：

- 一个项目、工作区、单个仓库或多个独立仓库；
- 产品目标、业务模块、质量和交付约束；
- 当前技术决定、工程说明或既有架构文档；
- 目录、包、模块、依赖和文件放置问题；
- 运行进程、数据与契约事实源；
- 希望比较、保留或排除的架构方式。

每次调用都重新读取当前事实，不依赖专属过程文档。资料不完整时先设计可验证的部分，并说明缺口影响。

## 工作方式

### 1. 确认范围与仓库状态

先读取与本次问题直接相关的：

- 项目及局部规则、说明文档和调用方资料；
- 语言与依赖声明、构建和测试配置；
- 应用入口、源码目录、模块出口、导入关系和测试组织；
- 迁移、可执行契约、运行进程和外部适配位置；
- 各目标仓库状态及调用方已有修改。

只读取足以支撑架构判断的代码，不做无边界全仓审查。需要说明问题时引用可验证的路径、导入或调用证据。

### 2. 识别调用模式

本次可以是：

- 新项目形成目标结构和依赖规则；
- 既有项目补足隐含的模块与放置约束；
- 修正职责混杂、循环依赖或共享层膨胀；
- 裁决局部包、模块、模式或文件归属问题。

局部问题不扩展为全项目重构，新项目也不为假设性未来建立大而全的结构。

### 3. 建立最小工程地图

按相关性识别：

- 交付单元、目标仓库、应用入口和运行进程；
- 顶级目录、包和业务模块的实际职责；
- 数据、接口、消息或生成契约的事实源；
- 当前主要依赖方向、越层调用和内部实现泄漏；
- 事务、权限、外部副作用和失败恢复的位置；
- 测试与生产代码的对应关系；
- 已存在的文件放置和局部规则。

工程地图只保留支持决策的内容，不复制完整目录树。

### 4. 提取架构驱动因素

只记录会真实改变代码组织的因素，例如：

- 业务职责的内聚度、变化频率和共享程度；
- 跨模块事务、一致性、并发和恢复要求；
- 身份、权限、租户、隐私和审计边界；
- 多入口、后台任务、外部副作用和独立运行需求；
- 多个交付单元之间的契约与类型流转；
- 用户流程、表单、远程数据和交互状态复杂度；
- 独立发布、故障隔离、团队所有权和平台限制；
- 当前明确不需要解决的问题。

每个层、模块或共享抽象都应能追溯到至少一个真实职责、风险或变化点。

### 5. 比较并确认方案

主动提出少量可行方案并推荐一个，说明：

- 解决的具体问题和适用范围；
- 主要职责、依赖方向和协作方式；
- 对当前代码的影响；
- 收益、复杂度和迁移代价；
- 替代方案及未选择原因；
- 重新讨论的可观察条件。

正式写入前预览当前事实、推荐结构、目标与现状差异、规则候选、迁移影响和待确认事项。调用方已明确要求创建或更新且范围清楚时，不重复索取确认；高影响取舍仍应单独确认。

## 架构设计内容

根据项目形态按需覆盖，无关部分直接省略。

### 总体工程形态

说明每个仓库或交付单元内部的主要组织方式，以及它与外部系统和部署边界的关系。工程架构只把已确认的系统边界映射为内部代码结构，不重新发明交付单元或技术方向。

至少明确：

- 应用入口和装配位置；
- 运行进程及其复用的核心能力；
- 业务模块与横切基础的边界；
- 数据和契约事实源；
- 允许的跨仓与跨进程协作方式。

### 分层与职责

每个实际需要的层或切片应说明：

- 解决什么问题，拥有哪些决策；
- 允许依赖和禁止依赖什么；
- 输入输出边界是什么；
- 事务、校验、权限、状态转换和副作用由谁负责；
- 哪些简单职责仍可共置，不需要独立成层。

层名应符合当前项目惯例。不要为了套用某种理论而创建固定层，也不要增加只转发参数、没有独立决策的文件。

### 业务模块边界

对需要长期稳定的模块说明：

- 拥有的业务概念、规则、状态和数据；
- 对外提供的稳定能力；
- 可以依赖的模块和协作方式；
- 内部实现是否允许被外部直接引用；
- 跨模块事务和一致性由谁编排；
- 合并、拆分或独立运行的触发条件。

模块按内聚职责或真实技术边界划分，不按页面、接口、表或代码层机械拆分。模块“非职责”只保留防止实际越界所需的部分，不重复列举所有不包含内容。

### 客户端或用户界面组织

项目存在用户界面时，按当前工程事实说明：

- 应用装配、导航/页面、业务功能、远程数据、共享界面、状态和通用工具的边界；
- 页面私有代码与跨页面共享代码的提升条件；
- 传输模型、表单模型、展示模型和组件输入之间的转换责任；
- 远程状态、客户端临时状态和跨页面状态分别由谁管理；
- 用户流程跨多个模块时，组合和恢复职责放在哪里。

共享界面层可以拥有通用交互原语，不应吞并具体业务规则。页面和功能模块不得绕过项目边界直接依赖传输或存储实现细节。

### 服务端、任务与外部适配

项目存在服务端、后台入口或外部适配时，按需说明：

- 传输入口、应用编排、业务规则、持久化和外部实现的边界；
- 事务、提交、回滚和幂等由谁拥有；
- 内部模型与边界契约是否需要分离，以及分离条件；
- 后台入口如何复用业务能力而不复制规则；
- 重试、任务状态和外部副作用由谁记录；
- 外部实现如何隔离，何时同步调用已足够。

简单操作可以直接留在入口附近；出现跨入口复用、多步骤规则、明确事务或替换边界时，再提取独立编排或适配职责。

### 数据、契约与类型流转

说明：

- 数据结构、迁移、接口或消息契约的实时事实源；
- 模块内部类型和跨模块稳定契约的边界；
- 跨交付单元类型如何生成、校验或转换；
- 哪些内部模型不得跨层、跨模块或跨进程泄漏；
- 兼容变化、破坏性变化和旧数据迁移如何处理。

工程架构文档不复制完整字段或接口列表。代码、迁移和可执行契约继续作为实时真源。

### 测试组织

按职责说明：

- 规则、应用编排、基础设施集成、入口契约和端到端行为分别由什么测试证明；
- 测试与模块共置还是集中，以及选择依据；
- 哪些依赖可使用替身，哪些最终验证必须使用真实服务、数据或浏览器；
- 共享测试工具和数据夹具的提升条件。

测试目录不反向决定生产模块边界，架构文档也不维护完整测试文件清单。

## 共享用户可见语义的所有者

跨页面、模块或交付单元复用的基础语义必须映射到项目中的实际所有者，不能只建公共目录，也不能让每个功能各自解释。

| 语义 | 权威或业务所有者 | 共享基础所有者 |
|---|---|---|
| 加载与进度 | 发起操作的边界拥有真实状态；业务功能决定阻塞、保留旧内容、取消和恢复；长任务由执行端提供权威进度 | 提供一致的指示、占位、状态播报和防重复交互原语 |
| 错误 | 产生错误的边界定义稳定含义与可恢复信息；适配层规范化技术失败；业务功能提供文案、字段定位和下一步；应用边界处理未知故障 | 提供错误展示、诊断关联和全局降级原语，不吞掉业务语义 |
| 权限 | 受保护资源一侧最终授权；身份边界建立和刷新主体上下文；业务模块定义操作权限与禁止原因 | 导航和界面按统一投影决定可见、禁用或引导，不复制授权规则 |
| 表单恢复 | 业务功能拥有字段、校验、提交、版本冲突和草稿有效期；流程编排者处理会话过期、断网与提交失败 | 提供脏状态、焦点定位、错误关联和安全的可选持久化原语 |
| 危险操作 | 业务模块定义资格、影响和可逆性；执行端负责授权、幂等、审计与并发；编排者处理部分失败和补偿 | 提供确认、焦点管理和一致的危险状态表达，不决定业务条件 |
| 可访问性 | 应用装配负责页面结构、导航和全局焦点；业务功能负责标签、说明、错误关联、动态文案和操作顺序 | 共享组件负责语义、键盘、基础焦点和状态播报；测试同时覆盖原语与关键流程 |

恢复不得覆盖较新数据或把敏感输入保存到未授权位置。共享所有者提供一致规则和原语，业务所有者保留具体语义；接口、依赖方向和覆盖责任必须清楚。

## 最小工程骨架与文件放置

目标骨架的重点是职责和判断规则，不是展示最大的目录树。每个建议目录或包至少说明：

- 存放什么；
- 不应承载的关键职责；
- 允许依赖什么；
- 何时才创建；
- 当前是否已经存在；
- 何时可以提升到更共享的位置。

尚未落地的路径必须标记为目标结构或按需创建。没有真实消费者时不创建目录占位。

新文件按以下顺序判断归属：

1. 确定它服务的业务模块或技术边界；
2. 确定它承担入口、编排、规则、持久化、外部适配、展示或测试中的哪类职责；
3. 优先与唯一消费者或所属模块共置；
4. 只有出现多个真实消费者且语义稳定时，才考虑提升到共享位置；
5. 提升后检查反向依赖、循环依赖和业务语义泄漏；
6. 无法归类时先澄清职责，不暂时丢进模糊公共目录。

## 共享能力准入

共享不是“有两段相似代码”就自动成立。候选进入共享位置前应同时检查：

- 存在至少两个真实消费者，而不是预计未来会使用；
- 消费者共享的是同一语义，不只是结构或字段相似；
- 所有权明确，知道谁负责兼容、测试和演进；
- 依赖稳定，不要求共享层反向依赖业务模块；
- 提升后确实减少重复决策或不一致，而非只减少文件数量；
- 当前抽象能够用简单接口表达，不需要大量条件分支适配消费者。

单一消费者、业务含义不同、变化节奏不同或所有权不清时继续共置。项目已有同等职责位置时优先复用，不建立第二套公共体系。

## 依赖方向与模块协作

架构文档必须同时记录允许依赖、禁止依赖和跨边界协作方式。重点检查：

- 入口是否承载跨模块事务或复杂规则；
- 核心业务规则是否依赖具体传输、界面、存储或外部实现；
- 模块是否直接引用其它模块的内部模型和基础设施；
- 共享层是否反向依赖业务模块；
- 后台入口是否复制规则或绕过事务编排；
- 内部存储模型是否直接成为公共契约或用户界面状态；
- 是否存在循环依赖、双向依赖或隐式公共层。

跨模块协作优先选择最简单的明确方式：调用公开能力、由上层编排，或通过稳定边界适配。只有存在真实异步、副作用可靠性或独立运行需求时才引入事件或后台机制。

推荐使用“职责 + 允许依赖 + 禁止依赖 + 协作方式”表达边界。只有文字不足以理解时才补图，图不能替代规则。

## 模式取舍

模式只用于解决已证实的问题。重要取舍记录：候选方式、结论、问题证据、适用范围、收益与代价、迁移影响、替代方案和重新讨论条件。

裁决时检查：

- 当前职责或依赖问题是否真实存在；
- 现有工程能力是否已经足够；
- 新方式是否降低复杂度，而不是增加转发层和接口；
- 采用范围能否局部控制，退出与替换成本是否可接受。

代码中出现某个模式名称不代表已经完整落地，应核验实际行为和收益。没有当前问题证据时暂不采用，也不预留空结构。

## 架构演进条件

只记录可观察的重新评估条件，不承诺抽象的“未来可扩展”。常见演进主题包括：

- 新增独立层或公共抽象；
- 将共置代码提升到共享模块；
- 将同步操作改为后台执行；
- 引入新的外部能力或数据处理边界；
- 将模块拆成独立进程、服务或仓库；
- 调整契约、身份、权限或数据隔离方式；
- 改变测试替换边界或生成契约方式。

触发证据可以是重复决策、条件分支膨胀、循环依赖、性能测量、故障隔离、独立发布、团队所有权、合规或平台限制。单独使用“以后可能需要”不能支持演进。

重大变化应记录旧决定、变化原因、迁移影响、新边界和实时事实源，不改写历史来伪装当前状态。

## 默认产出

默认创建或更新：

```text
docs/design/工程架构设计.md
```

推荐结构：

1. 文档目标与适用范围；
2. 当前事实、约束、假设和架构驱动因素；
3. 总体工程形态与事实源；
4. 分层、模块职责和依赖方向；
5. 工程骨架、目录职责和文件放置规则；
6. 共享能力准入与用户可见语义所有者；
7. 数据、契约和类型流转；
8. 入口、任务与外部适配；
9. 测试组织与验证边界；
10. 模式取舍和架构演进条件；
11. 当前差异、迁移影响、风险和待确认事项。

只记录长期有价值、跨需求复用且不能从代码直接读出的工程决定。复杂项目只有在维护边界确有独立价值时才拆分文档，不为标准流程创建空文件。

## 规则候选

工程架构文档负责解释设计；项目规则只应承载开发时需要即时执行的少量稳定约束。默认只在结果中列出候选，不直接修改规则文件。

候选应同时满足：

- 已确认且与当前代码事实一致；
- 跨多个需求长期复用；
- 能写成具体可执行动作；
- 无法仅靠代码结构或自动化充分表达；
- 不会把目标结构误报成当前事实。

调用方明确要求同步规则时，才读取受影响范围的现有规则并做最小增量编辑：优先增强已有条目，不复制整份架构文档，不写入尚未落地的目标。

## 更新与验证

更新已有架构时：

1. 读取现有文档、当前代码、配置、测试、迁移、契约和受影响规则；
2. 区分仍有效决定、已落地目标、事实漂移、新约束和历史背景；
3. 判断变化是否真正影响职责、边界、依赖、所有权或演进条件；
4. 只更新受影响内容，不因普通文件移动或函数拆分重写整体文档；
5. 说明变化原因、迁移影响、尚未落地部分和实时事实源。

完成前检查：

- 当前结构、目标结构和历史来源已经区分；
- 路径、包、入口和规则真实存在，或明确标为目标；
- 每个层和模块有清楚职责、关键非职责和依赖方向；
- 新文件能够按规则判断归属；
- 事务、权限、外部副作用和恢复有所有者；
- 加载、错误、权限、表单恢复、危险操作和可访问性语义的共享与业务责任没有空缺；
- 共享层符合准入条件，没有反向依赖或业务收纳箱；
- 模式和演进决定有真实证据；
- 没有空层、无消费者抽象、重复事实源或秘密。

用代表性变更反查可执行性：新增业务入口、跨模块操作、共享类型、后台任务、外部适配、可恢复表单或危险操作时，规则能否明确文件归属、依赖方向和责任所有者。不能明确时先补职责，不靠增加目录名称掩盖问题。

写入后按项目实际工具执行适用的 Markdown、链接、格式和一致性检查，并检查涉及仓库的状态与 diff。纯文档设计不运行无关代码测试。

## 结束方式

完成后汇报：

- 设计范围和状态；
- 创建或更新的文件；
- 已确认的结构、模块、依赖和共享准入规则；
- 用户可见基础语义的责任划分；
- 主要模式取舍和演进条件；
- 当前结构与目标架构差异；
- 规则候选或实际同步范围；
- 验证证据、未核验事项、风险和迁移影响。

## 避免

- 未读取真实代码就套固定目录模板；
- 用庞大目录树、模式名称或层数代替职责和依赖规则；
- 为未来预建空层、公共目录、接口或独立运行边界；
- 将相似代码过早提升为共享能力，忽略语义和所有权；
- 只定义成功路径，遗漏权限、错误、恢复、危险操作和可访问性责任；
- 把目标结构写成当前事实，或维护与代码并行的完整清单；
- 未经明确要求修改项目规则、实现代码或 Git 历史。
