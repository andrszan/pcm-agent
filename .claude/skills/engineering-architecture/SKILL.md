# engineering-architecture — 项目级工程架构设计

## 定位

这是一个可独立调用的项目级工程架构设计能力。它把已经确认或能够从工程事实中核验的总体技术方向，转化为后续开发可以执行的代码组织约束：系统内部如何分层，业务能力如何分模块，目录和包分别承担什么职责，依赖应朝哪个方向，文件应放在哪里，以及何时才值得引入新的层、共享抽象、设计模式或独立部署边界。

它解决的是总体技术方案与单项需求实现之间的工程组织缺口。总体技术方案可以确定交付单元、主要技术栈和系统边界，单项技术设计可以描述某个需求如何协作；本能力负责建立跨需求长期复用的工程结构和依赖规则，使后续 Agent 不必在每个需求中重新猜测代码归属。

在从零开始的项目中，通常适合在基础模板已经选定并形成可读取的真实仓库后主动调用，例如模板项目化完成之后。这个时机只是可选编排建议，不是本能力的内部前置条件。既有项目、单仓项目、前后端分仓项目、服务端项目、客户端项目或需要调整现有架构的项目都可以独立调用；不得要求固定数量的 Git 仓库，也不得自动调用或依赖其它 Skill。

## 与其它能力的边界

本能力负责回答：

- 项目内部采用什么分层或垂直切片方式，各层和各模块分别负责什么；
- 业务模块、基础设施、入口层、后台任务和外部适配之间如何依赖与协作；
- 目录、包和局部规则如何帮助开发者判断新文件的归属；
- 哪些类型、契约或基础能力可以共享，什么条件下才允许提升到共享层；
- MVC、分层架构、模块化单体、Repository、Unit of Work、CQRS、事件驱动等模式是否适用，以及适用到什么范围；
- 何时需要调整架构、增加新层、引入中间件或拆分独立服务；
- 哪些稳定且可执行的规则需要同步到仓库的 `AGENTS.md` 或等价 Agent 指令。

本能力不负责：

- 重新定义产品目标、用户范围、业务功能或验收边界；
- 重新选择语言、框架、数据库、通信协议、部署形态或基础模板；
- 再写一份与总体技术方案重复的系统上下文、交付单元或模板选型说明；
- 拆分 Backlog、安排开发顺序或维护运行期需求状态；
- 为一个具体需求设计完整行为、接口、数据变化和验证场景；
- 实现业务代码、迁移、页面、接口、测试、配置或基础设施；
- 为了展示架构完整性而创建空目录、空包、占位模块、万能基类或无消费者抽象；
- 维护完整类、函数、文件、页面、接口、表字段或索引清单；
- 创建 Manifest、运行 Schema 或另一套与代码并行的架构事实源；
- 启动任何其它 Skill、固定 Agent、开发流程或提交操作。

如果架构讨论暴露出尚未决定的项目级技术方向，记录冲突及其影响，并在当前对话中与用户讨论；不要静默替总体技术方案作出高影响选择。普通目录命名、等价文件拆分和遵循现有惯例的低风险判断可以自主完成。

## 技术中立与简单优先

正文不得预设项目使用前端、后端、Web、MVC、领域驱动设计、Clean Architecture、微服务、REST、关系数据库、特定语言或特定目录模板。具体结构只能来自：

1. 用户明确给出的目标、约束和已确认决定；
2. 当前项目代码、依赖、配置、测试、迁移和实际运行行为；
3. 已有总体技术方案、模板来源和仓库规则中仍与工程事实一致的内容；
4. 本次讨论中经过确认的架构取舍。

默认选择能够清楚表达当前职责的最小结构。层数、目录数和模式数量不代表架构质量。一个直接模块足以承载职责时，不为“分层完整”增加 service、repository、domain、adapter 或 interface；只有真实变化点、复用关系、替换需求、事务边界或依赖隔离问题证明必要时，才增加相应结构。

## 输入与事实优先级

用户可以提供任意组合：

- 项目、根工作区、一个仓库或多个独立仓库路径；
- 产品定义、需求说明、Backlog 或业务模块资料；
- 已有总体技术方案、工程架构文档或单项技术设计；
- 基础模板来源、模板说明和项目化结果；
- 当前目录、包、模块、依赖或文件放置问题；
- 希望采用、比较、保留或排除的架构风格和设计模式。

每次调用先读取足以判断边界的真实上下文，通常包括：

- 根和各目标仓库的 `README.md`、`AGENTS.md`、`CLAUDE.md` 及更具体的局部规则；
- 语言版本、依赖清单、锁文件、构建配置、测试配置和入口代码；
- 当前源码目录、包边界、模块出口、导入关系和测试组织；
- 与工程结构有关的产品范围、总体技术方案和模板派生说明；
- 数据库迁移、可生成契约、运行进程和外部适配器等架构事实；
- 各目标 Git 仓库的状态和用户已有修改。

事实优先级如下：

1. 当前代码、配置、迁移、测试和可运行行为决定当前实现事实；
2. 当前目录内更具体的 `AGENTS.md` 或等价规则约束该目录；
3. 用户本次明确的新决定控制目标状态；
4. 活动总体技术方案和工程架构文档记录仍有效的稳定决定；
5. 模板和历史文档只提供来源与背景，不自动覆盖派生后的项目事实；
6. 通用架构经验只能作为候选方案，不能当作项目事实。

必须区分：

- **当前事实**：代码和仓库现在已经具备的结构与行为；
- **已确认决定**：项目长期需要保持的技术与工程选择；
- **目标架构**：尚未全部落地，但经过确认的工程组织方向；
- **现有惯例**：仓库已经稳定采用且与当前目标相容的做法；
- **合理默认**：低风险、容易调整且不改变系统边界的工程选择；
- **假设与待核验**：暂时无法从代码、文档或运行行为确认的事项；
- **待确认决策**：会实质改变边界、依赖、安全、兼容性或迁移成本的选择。

不得把目标目录树写成当前目录，不得因依赖已安装就声称某层已经接入，也不得根据目录名称推断模块职责。

## 工作方式

### 1. 识别调用模式

先判断本次属于哪一种或哪几种：

- **新项目工程架构设计**：技术方向和基础工程已经存在，需要形成目标分层、模块与依赖规则；
- **既有项目架构补全**：代码已经运行，但目录和依赖规则主要依赖隐含惯例；
- **架构调整或演进**：现有结构出现职责混杂、循环依赖、共享层膨胀或新运行边界；
- **局部架构问题**：只需要裁决某个包、层、模块、模式或文件放置问题；
- **不属于本能力**：主要目标是产品定义、技术栈选型、模板项目化、单需求设计或代码开发。

只设计用户要求和工程事实需要的范围。局部问题不扩展成全项目重构，新项目也不为假设性未来建立企业级结构。

### 2. 建立当前工程地图

建立能够支撑决策的最小工程地图，至少按相关性识别：

- 交付单元和目标仓库；
- 应用入口、运行进程和部署边界；
- 现有顶级目录和包职责；
- 业务模块、共享基础和外部适配位置；
- 数据、接口、消息或生成契约的事实源；
- 当前主要依赖方向和越层调用；
- 测试与生产代码的对应关系；
- 已存在的 Agent 规则和局部放置约束。

只读取与架构范围相关的代码，不做无边界全仓审查。需要说明架构问题时使用可验证的路径、导入关系和调用证据，不编造不存在的类、包或目录。

### 3. 提取架构驱动因素

根据项目实际情况识别会改变工程组织的因素，例如：

- 业务模块数量、职责内聚度和变化频率；
- 跨模块事务、数据一致性和并发要求；
- 身份、权限、租户或隐私隔离；
- 多个运行进程、后台任务或外部副作用；
- 多个交付单元之间的契约和类型流转；
- 前端页面、交互状态和远程数据复杂度；
- 团队 ownership、并行开发和独立发布需求；
- 测试替换、基础设施替换或平台限制；
- 当前明确不需要解决的问题。

架构驱动因素必须能够解释为什么需要某个边界或层。无法追溯到真实职责、风险或变化点的结构，不进入目标架构。

### 4. 提出并裁决方案

AI 应主动提出少量可行方案并给出推荐，不让用户从空白开始设计。方案比较至少说明：

- 解决的具体问题；
- 主要职责与依赖方向；
- 对当前代码和模板的影响；
- 收益、复杂度和迁移代价；
- 替代方案及未选择原因；
- 当前适用范围和重新讨论条件。

对有意义的架构取舍、兼容性变化、跨仓边界、安全边界或大范围迁移取得用户确认。普通命名、局部文件拆分和现有规则已经明确的放置判断不升级为审批事项。

### 5. 先预览，再写入

在第一次正式写入前，向用户预览：

- 当前工程事实和主要问题；
- 推荐的分层、模块与依赖方向；
- 拟采用、局部采用和明确不采用的模式；
- 目标目录结构与当前结构的差异；
- 准备创建或更新的架构文档；
- 准备增量同步的 `AGENTS.md` 或局部规则及同步理由；
- 明确不创建的目录、代码、Manifest 和重复清单；
- 需要迁移但不属于本次设计落盘的实现工作。

用户明确确认后才写入正式工程架构文档或调整 Agent 规则。用户仍在讨论时继续对话，不用文档草稿代替架构裁决。

## 架构设计范围

根据项目形态按需覆盖以下内容，无关项直接省略。

### 总体工程形态

说明每个仓库或交付单元内部采用的主要组织方式，以及它与总体技术方案中系统、服务和部署边界的关系。总体工程形态不能重新发明交付单元或技术栈，只把已经确认的外部边界映射为内部代码结构。

### 分层与职责

为实际需要的层明确：

- 层解决什么问题、拥有哪类决策；
- 允许依赖哪些层，禁止依赖哪些层；
- 哪些输入输出属于边界契约；
- 事务、权限、校验、状态转换和外部副作用由谁拥有；
- 哪些职责仍可直接共置，不需要独立成层。

层名必须符合项目语言和框架惯例。不得为了照搬 Clean Architecture、MVC、DDD 或其它范式，强制创建固定的 controller、service、repository、domain、use-case、adapter 目录。

### 业务模块边界

对每个需要长期稳定的模块说明：

- 模块负责的业务概念和规则；
- 明确不负责的内容；
- 对外提供的能力或稳定入口；
- 可以依赖的模块和协作方式；
- 模块内部实现是否允许被其它模块直接引用；
- 跨模块事务或一致性由谁编排；
- 拆分、合并或独立部署的触发条件。

模块应按内聚业务职责或真实技术边界划分，不按页面、接口、数据库表或代码层机械拆分，也不因 Backlog 中存在同名需求就自动创建模块。

### 客户端或前端组织

项目存在客户端或前端时，按实际框架与交互复杂度说明：

- 应用装配、路由/页面、业务 feature、远程数据、共享 UI、状态和通用工具的边界；
- 页面私有代码与跨页面共享代码的提升条件；
- API DTO、表单模型、ViewModel、组件 Props 和数据库模型之间的边界；
- 远程状态、客户端临时状态和全局状态分别由谁管理；
- 通用组件何时可以依赖业务语义；
- 用户可见流程跨多个模块时，组合职责放在哪里。

不得假设所有前端都采用按 feature、按 route 或按层组织；从当前框架、已有惯例和业务变化点中选择最小方案。

### 服务端或后端组织

项目存在服务端或后端时，按实际框架与业务复杂度说明：

- 传输入口、请求/响应契约、应用用例、领域规则、持久化和外部适配的边界；
- 数据库 Session、事务和提交/回滚由谁拥有；
- 数据库模型、领域模型和外部 DTO 是否需要分离以及分离条件；
- 跨模块调用是否通过公开用例、领域能力、端口或事件；
- 配置、日志、错误、数据库连接等横切基础能力的归属；
- 什么时候直接在端点内完成简单操作，什么时候提取用例或服务。

不得把 Repository、Unit of Work、接口层或领域模型作为后端的默认必需结构。

### 后台任务与外部适配

项目包含 worker、定时任务、事件消费者或外部服务时，说明：

- 后台入口如何复用应用能力而不复制业务规则；
- 任务事实、重试、幂等和外部副作用的边界；
- HTTP 入口、worker 和命令行入口是否共享同一用例层；
- 外部 SDK、邮件、对象存储、支付、搜索等适配实现放在哪里；
- 什么时候同步调用足够，什么时候需要 outbox、队列或独立进程。

### 数据、契约与类型流转

说明：

- 数据结构、迁移、接口或消息契约的实时事实源；
- 模块内部类型和跨模块稳定契约的边界；
- 客户端类型如何从服务端契约获得或校验；
- 哪些模型不得跨层或跨进程泄漏；
- 兼容性和破坏性变化如何处理。

工程架构文档不复制完整表结构或接口列表。可执行契约、Schema、迁移和代码继续作为实时真源。

### 测试组织

按职责说明测试位置和替换边界：

- 纯规则、应用用例、基础设施集成、入口契约和端到端行为分别由什么测试证明；
- 测试是否与模块共置或集中，以及选择理由；
- 哪些依赖可以使用替身，哪些最终验证必须使用真实数据库、服务或浏览器；
- 共享测试工具和 fixture 的提升条件。

不在架构文档中维护完整测试文件清单，也不让测试目录结构反向决定生产模块边界。

## 工程骨架与文件放置规则

目标工程骨架的重点是职责和判断规则，不是画出最大的目录树。

每个建议目录或包至少说明：

- 存放什么；
- 明确不存放什么；
- 允许依赖什么；
- 何时才创建；
- 何时可以把代码提升到更共享的位置；
- 当前仓库中是否已经存在。

目标目录树只展示理解边界所需的层级。尚未落地的路径必须标记为目标结构或按需创建，不得描述成当前事实。没有真实代码消费者时，不创建目录占位。

对新文件应提供可执行的放置判断，例如：

1. 先确定它服务的真实业务模块或技术边界；
2. 再确定它属于入口、用例、规则、持久化、外部适配、展示或测试中的哪类职责；
3. 优先与唯一消费者或所属模块共置；
4. 出现至少两个真实消费者且语义稳定时，才考虑提升到共享位置；
5. 提升后检查是否引入反向依赖、循环依赖或业务语义泄漏；
6. 无法归类通常表示职责未澄清，不把文件暂时丢进 `utils`、`common`、`shared` 或 `misc`。

### 常见共享位置的准入条件

以下名称只是常见示例，不要求项目采用：

- **`core` / `foundation`**：只放跨业务、稳定、由应用整体拥有的基础能力；不得成为任意代码的收纳箱。
- **`shared` / `common`**：只有多个模块共享同一稳定语义时才建立；相似但含义不同的类型不因字段一致而合并。
- **`utils` / `lib`**：只放无业务所有权、依赖少且边界明确的工具；业务规则留在所属模块。
- **`service` / `application` / `use_cases`**：只有出现需要编排的业务操作、跨入口复用、明确事务所有权或多步骤规则时才建立。
- **`repository` / `data_access`**：只有数据访问逻辑确实复用、查询复杂度需要隔离、存储可替换或测试边界有真实价值时才引入。
- **`domain`**：只有存在值得脱离框架表达和测试的稳定领域规则、状态转换或值语义时才形成独立边界。
- **`adapters` / `infrastructure`**：只有外部系统、持久化或平台实现需要与业务决策隔离时才建立。

项目已有同等职责位置时优先复用和收敛，不在旁边建立第二套命名体系。

## 依赖方向与模块协作

工程架构必须同时记录允许依赖和禁止依赖。只写“分层”而不写依赖规则，不能指导后续实现。

按项目实际情况检查：

- 入口层是否直接承载跨模块事务或复杂业务规则；
- 领域规则是否依赖 Web 框架、UI 框架、数据库 Session 或具体外部 SDK；
- 业务模块是否直接引用另一个模块的内部模型或基础设施实现；
- 共享层是否反向依赖业务模块；
- 页面或通用 UI 是否直接访问传输细节；
- 后台任务是否调用 HTTP router、复制规则或绕过事务用例；
- 数据库模型是否未经边界转换直接成为公共 API、组件状态或跨模块契约；
- 是否存在循环导入、双向依赖或为了复用而形成的隐式公共层。

推荐使用“职责表 + 允许依赖 + 禁止依赖 + 协作方式”表达边界。只有依赖关系复杂到文字难以理解时才增加 Mermaid 等图；图必须与正文一致，不能替代规则。

跨模块协作优先使用最简单的明确方式：直接调用公开能力、由应用用例编排、通过稳定端口适配，或在确有异步与解耦需求时使用事件。不得为了避免普通函数调用而把单体内部全部事件化，也不得为了减少文件数量让模块直接修改彼此内部状态。

## 设计模式裁决

设计模式是解决具体问题的工具，不是架构成熟度清单。不得因为用户举例、框架名称或行业惯例就默认采用某个模式。

每个重要模式按以下格式裁决：

```text
模式或风格：...
结论：采用 / 局部采用 / 暂不采用 / 不适用
解决的问题：...
适用范围：...
收益与代价：...
对当前工程的影响：...
替代方案及未选择原因：...
重新讨论条件：...
```

至少注意：

- **MVC** 常用于描述交互入口、视图和模型的职责关系，但通常不足以单独描述跨模块事务、后台任务、外部适配和分仓系统；应说明它在哪个交付面或层次适用。
- **分层架构** 可以提供依赖方向，但层数应由职责决定，不为形式完整增加转发层。
- **模块化单体** 适用于需要模块边界但尚无独立部署依据的系统；需要配套公开入口和禁止依赖规则。
- **Clean Architecture / Hexagonal Architecture** 可以借用依赖反转和端口适配原则，不要求照搬固定目录和大量接口。
- **Repository / Unit of Work** 只有在数据访问隔离、事务协调或替换测试具有真实价值时采用；框架已有 Session 或事务能力可能已经足够。
- **CQRS** 只有读写模型、规模、性能或团队边界存在真实差异时采用；普通查询和命令分文件不等于 CQRS。
- **事件驱动 / outbox** 适合异步副作用、可靠任务和跨边界通知，不自动替代同步核心事务。
- **微服务** 需要独立发布、扩缩容、可靠性、技术隔离或团队 ownership 证据；目录模块多不是拆服务理由。

如果现有代码已经采用某种模式，先核验实际行为和收益，不因名称存在就假设实现完整，也不为理论纯度强制重构。

## 架构演进规则

工程架构文档应记录可观察的演进触发条件，而不是承诺“未来可扩展”。根据项目实际情况说明何时重新评估：

- 新增独立层或公共抽象；
- 将共置代码提升到共享模块；
- 将同步操作改为后台任务或队列；
- 引入缓存、搜索、事件总线或新的持久化类型；
- 将模块拆为独立服务或仓库；
- 将同步运行模型改为异步；
- 更换接口契约、认证体系或数据隔离方式；
- 调整测试边界或生成契约方式。

触发条件应来自重复代码、复杂度、性能测量、故障隔离、独立发布、团队 ownership、合规或平台限制等证据。不得使用“以后可能需要”“为了扩展性”作为单独理由。

架构演进不改写已经归档的历史决定来伪装当前状态。活动工程架构文档可以随项目事实调整；重大方向变化应说明旧决定、变化原因、迁移影响和新的事实源。

## 默认产出

默认创建或更新一份综合工程架构设计：

```text
docs/design/工程架构设计.md
```

推荐结构：

1. 文档目标与适用范围；
2. 当前工程事实、约束与架构驱动因素；
3. 总体工程形态与事实源；
4. 各交付单元的分层与职责；
5. 业务模块边界；
6. 工程骨架、目录/包职责与文件放置规则；
7. 依赖方向、允许依赖与禁止依赖；
8. 数据、契约与类型流转；
9. 入口、后台任务与外部适配；
10. 测试组织与验证边界；
11. 设计模式裁决；
12. 架构演进条件；
13. 当前差异、迁移影响、风险和待确认事项。

只保留长期有价值、跨需求复用且不能从代码直接读出的工程决定。实际目录、包、类、函数、接口、数据库结构、迁移和测试继续以代码及可生成事实为准。工程架构文档不能要求读者依赖外部模板或当前会话才能理解边界，但也不复制现有 README、总体技术方案和仓库规则的全部内容。

复杂项目只有在各交付单元确实有独立维护价值时才拆分前端、后端、客户端或服务端架构文档。拆分前说明理由并取得用户确认，不为标准流程创建空文档。

## 与 `AGENTS.md` 等仓库规则的同步

工程架构文档承担设计解释，`AGENTS.md` 或等价 Agent 指令承担开发时需要即时执行的少量规则。默认采用双层方式，但不是每次都必须修改规则文件。

只有同时满足以下条件的规则才建议同步：

- 已经过确认并与当前代码事实一致；
- 会反复影响后续文件放置、依赖方向或职责判断；
- 可以由开发者在修改代码时直接执行；
- 足够稳定，不是单需求实现细节或暂定目标；
- 现有更具体规则尚未覆盖，且不会造成冲突或重复。

同步前必须：

1. 读取目标目录及其父级和子级的现有规则；
2. 判断应放在根规则、仓库规则还是局部目录规则；
3. 复用现有术语和结构，小范围增量修改；
4. 如果现有规则与目标设计冲突，先向用户说明当前事实、目标状态和迁移影响；
5. 不复制整份架构文档，不加入决策历史、备选方案或尚未落地的目标目录；
6. 保留更具体的子目录规则优先级，不用根规则覆盖局部事实。

以下内容通常只留在工程架构文档，不同步到 Agent 规则：方案比较、模式理论、历史背景、长期演进候选、尚未确认事项和完整目标目录树。

以下内容适合按需同步：明确的目录职责、文件放置原则、允许/禁止依赖、共享层准入条件、事务所有权和修改前必须读取的局部事实源。

## 更新已有工程架构

更新时：

1. 读取现有架构文档、当前代码、依赖、配置、测试、迁移和所有受影响的 Agent 规则；
2. 区分仍有效决定、已经落地的目标、发生漂移的当前事实、新约束和仅属于历史的内容；
3. 检查代码变化是普通实现细节，还是分层、模块、依赖、模式或演进条件发生稳定变化；
4. 只修改受影响的架构内容，不因普通文件移动、函数拆分或单个接口变化重写整体文档；
5. 同步检查 Agent 规则是否需要增量调整，避免文档和规则互相矛盾；
6. 说明变化原因、迁移影响、尚未落地部分和新的实时事实源。

普通类名、函数、文件拆分、测试文件组织和不改变职责的目录微调通常不需要更新工程架构文档。层级职责、模块所有权、公共入口、依赖方向、事务所有权、运行进程、共享层准入条件或重要模式取舍发生变化时，才需要更新。

## 自审与验证

正式写入前后必须检查：

### 事实一致性

- 当前结构、目标结构和历史来源已经区分；
- 所引用的路径、包、入口和规则实际存在，或明确标记为目标；
- 文档没有用模板说明覆盖派生项目事实；
- 总体技术方案、工程架构、仓库规则和代码之间不存在未说明冲突；
- 各目标仓库的用户已有修改受到保护。

### 架构完整性

- 每一层和模块都有清楚的职责、非职责和依赖方向；
- 新文件能够根据规则判断归属；
- 跨模块事务、权限、外部副作用和后台任务有明确所有者；
- 共享层不是任意代码收纳箱；
- 没有循环依赖、反向依赖或跨模块内部实现耦合；
- 模式采用有真实问题和收益依据；
- 没有为未来预建无消费者的抽象、空层或独立服务。

### 文档与规则质量

- 工程架构文档记录稳定决定，不复制完整代码事实；
- 目标目录树保持必要深度，没有维护完整文件清单；
- `AGENTS.md` 只包含可执行、稳定、与当前事实一致的规则；
- 根规则与局部规则没有冲突或机械重复；
- 没有新增 Manifest、运行状态、固定 Skill 链或架构审批状态机；
- 没有写入秘密、个人绝对路径或未验证的外部事实。

### 可执行性检验

至少使用几个代表性变更反查规则，例如：

- 新增一个业务接口或页面时，文件应该放在哪里；
- 新增一个跨模块业务操作时，事务和编排由谁拥有；
- 新增一个被多个模块使用的类型时，何时可以提升到共享层；
- 新增后台任务时，如何复用业务规则；
- 新增外部服务适配时，如何隔离具体 SDK；
- 简单 CRUD 是否真的需要新建 service 或 repository。

如果规则不能给出明确判断，先补足职责或依赖说明，不通过增加更多目录名称掩盖问题。

写入后根据项目实际工具执行适用的 Markdown、链接、格式或文档检查，并检查每个涉及仓库的 `git status` 和 diff。纯文档设计不需要运行无关代码测试；如果同时修改 Agent 规则，应搜索受影响目录和已有约束，确认规则与当前代码一致。

## 结束方式

最终状态只能是：

- **已完成**：确认范围内的工程架构文档和必要规则已经写入，自审与适用文档检查通过，没有已知架构冲突；
- **已设计但未完全核验**：设计已写入，但部分仓库、运行事实、外部契约或迁移影响无法核验；必须列出缺口和补验方式；
- **阻塞**：项目级技术方向、仓库访问、用户修改冲突或高影响架构取舍无法安全确定。

完成后汇报：

- 本次设计范围和状态；
- 创建或更新的工程架构文档；
- 已确认的分层、模块和依赖规则；
- 采用、局部采用和暂不采用的主要模式；
- 同步到哪些 `AGENTS.md` 或局部规则，以及为什么；
- 明确没有创建的空目录、业务代码和重复事实源；
- 当前结构与目标架构的主要差异；
- 未核验事项、迁移影响和重新讨论条件；
- 实际执行的文档、路径、Git 和一致性检查。

不要自动启动其它 Skill、开发任务、提交或推送，也不要把任何能力声明为强制前置或后续。

## 反模式

- 收到项目名称或技术栈后直接套用固定目录模板；
- 把“架构设计”等同于生成一棵庞大的目录树；
- 为了体现分层预建空的 controller、service、repository、domain、adapter 或 shared；
- 把 MVC、DDD、Clean Architecture、CQRS 或微服务当作默认成熟度目标；
- 不读取真实代码和现有 `AGENTS.md`，另起一套相互冲突的架构规范；
- 只描述各层名称，不说明职责、非职责、允许依赖和禁止依赖；
- 将所有 DTO、模型、工具或常量集中到全局目录，忽略业务所有权；
- 将相似代码过早提升到 `common`、`shared`、`utils` 或万能基类；
- 把数据库模型直接当作公共 API、前端状态或跨模块契约，却不说明边界；
- 让 worker、命令行或定时任务调用 HTTP router，或复制一套业务规则；
- 为避免普通模块调用而把单体内部全部事件化；
- 用“未来可能扩展”解释新增中间件、独立服务或抽象层；
- 把目标结构、已确认决定或模板声明误报成已经落地的当前事实；
- 在架构文档中维护完整类、函数、文件、接口、表和索引清单；
- 创建架构 Manifest、运行 Schema、审批流水或另一套事实源；
- 把本能力固定在某套编排顺序中，或让它自动调用其它 Skill；
- 未获得用户确认就写入正式架构文档或覆盖现有仓库规则；
- 只更新架构文档却留下与其冲突的 Agent 规则，或只改规则而不保留必要设计理由。
