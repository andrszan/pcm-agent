# engineering-architecture — 项目级工程归属合同

## 定位与边界

这是一个可独立调用的项目级工程架构设计能力。它依据调用方资料和当前工程事实，按实际构建、运行、发布和业务边界识别适用交付单元（如前端应用、后端服务/API、worker、CLI）；仓库只是容器。产出的架构文档应让后续开发能判断：新文件放在哪里、谁拥有语义、可以依赖什么、跨边界如何协作，以及何时值得演进结构。

本能力只设计文档，不实现业务代码、迁移、配置或基础设施，不创建空目录、占位模块、接口或 barrel export。先确认目标仓库和已有修改，只改调用方授权的文档；默认不修改 `AGENTS.md` 或其它项目规则，不执行 Git 写操作。

- **技术中立、简单优先**：不预设语言、框架或目录模板，只为已证实的职责、变化点、复用、事务、替换或依赖隔离增加结构；现有简单结构足够时保留它。
- **承接既定决定**：沿用调用方已确认的产品范围、交付单元和总体技术决定及其依据，不重新选型或补写未发生的方案比较。发现与工程事实冲突时，说明冲突和影响后请求调整。
- **按影响请求决定**：本次会实质改变系统边界、依赖方向、安全、公共契约、兼容性或迁移成本的选择，须说明候选、影响和推荐理由并取得调用方确认。普通命名、等价文件拆分、沿用既有惯例和其它低风险可逆判断可以自主完成。

调用方资料不完整时，读取足以支撑判断的真实工程材料，完成可验证部分，说明缺口、影响和待确认事项；不要求固定的前置资料、路径或其它能力。

## 工作方法

### 1. 核验事实与设计依据

读取本次问题直接相关的项目与局部规则、已有架构文档、构建和依赖声明、入口、源码和模块出口、导入关系、测试、迁移、可执行契约、运行进程及外部适配。引用可核验的路径、导入、调用或运行证据，不做无边界全仓审查。

明确区分：

- **Current 事实**：当前代码、迁移、可执行契约、测试或实际运行行为能够证明的结构与职责；不按目录名、历史说明或文档目标补全现状。
- **已确认 Target**：已确认但尚未完全落地的工程目标。
- **假设/待确认**：缺少依据，或仍需调用方决定的内容。

只提取会改变归属或依赖的驱动因素，例如业务内聚、跨模块一致性、权限和审计、多入口、外部副作用、稳定契约、独立发布、故障隔离、团队所有权、已有性能测量或平台限制；同时说明当前明确不需要解决的问题。每个 Target 目录、模块、抽象或隔离边界都应能追溯到这些依据。未确认的容量、延迟或并发预期不能单独证明需要新边界。

基础工程已就绪但业务尚未实现时，已确认的产品需求和总体决定可以支撑必要 Target，不必等待业务代码出现才设计归属；它们不能证明业务已在 Current 中实现。“以后可能需要”仍不是增加结构的依据。

再次更新文档时，依据本次核验事实原位修订受影响的 Current、Target 和迁移状态，同步相关目录图、职责说明与差异记录；已落地的目标转为 Current，已完成的迁移不再保留为待执行要求。历史依据通过必要的基线说明或 Git 历史保留，不用追加总免责声明覆盖仍标为 Current 的过时描述。只核验本次变化涉及的边界及相关协作，不为刷新文档重新扫描全仓；未核验范围如实说明，不推定其它目标或迁移也已完成。

### 2. 建立 Current 工程地图

先列相关代码仓库和适用业务代码交付单元；按真实构建、运行、发布和业务边界识别，纯文档或静态资产可基于证据标为不适用。按每个适用单元给出有限目录树，仅保留入口、稳定目录/包/模块和事实源，每个路径标为 `[当前]` 并说明真实职责。

分别记录已核验的公开出口、依赖方向、内部实现泄漏、循环或越层依赖，以及相关事务、权限、错误、副作用、恢复的归属和测试对应关系；跨单元关系另列。尚不存在的业务职责不得补成 Current，也不因业务尚未实现而忽略已确认需要承载它的应用或服务。

### 3. 决定必要的工程组织

只对本次尚未明确的工程归属、模块组织和依赖问题比较少量真实可行方案。重要决定写入架构决策矩阵：问题与证据、候选与结论、适用范围、收益与代价、未选原因、Current/Target 影响，以及必要迁移和可观察的重议条件。已确认决定保留依据并说明工程落点；低风险选择没有实质分歧时采用合理默认，不为填表制造替代方案。

MVC、分层、六边形和 DDD 不是互斥四选一。按实际需要考虑以下取舍，不必逐轴展开无关内容：

| 取舍轴 | 要判断的内容 |
|---|---|
| 项目形态 | 单体、多应用、库、客户端、服务端、任务进程或多仓的真实边界 |
| 顶级组织 | 按功能、技术、交付单元或混合组织，如何服务当前协作与变化 |
| 模块内部层次 | 入口、编排、规则、持久化、展示等职责是否需要独立组织 |
| 外部依赖隔离 | 何处需要隔离传输、数据库、文件、第三方或消息实现，何处直接使用已足够 |
| 领域建模强度 | 复杂规则、状态、不变量或统一语言是否需要模型边界 |
| 客户端组织 | 应用装配、页面/功能、状态和共享界面的边界 |

模式名称只能作为取舍的简写，不能代替依据、适用范围和代价，也不要求采用整个模式。跨模块协作优先使用公开能力、上层编排或稳定边界适配；只有真实异步、可靠副作用、独立运行或故障隔离证据成立时，才引入事件、队列、后台机制或拆分服务。

### 4. 明确 Target、职责与依赖

按每个适用单元给出有限 Target 目录树，只写稳定边界和必要迁移路径，不维护完整文件清单。与 Current 相同的部分可明确沿用，不重复绘制；跨单元关系另列。路径按适用情况标记：

- `[当前]`：已存在且继续承担相同边界；
- `[目标]`：已确认但尚未落地；
- `[按需]`：满足创建条件时才建立；
- `[迁移]`：从 Current 到 Target 的临时位置或动作，不作为稳定边界。

对每个单元的主要目录、包或模块说明状态、职责、关键非职责、允许/禁止依赖、创建及提升到共享位置的条件。稳定模块还须说明拥有的语义、规则、状态或数据，对外能力或受控出口、允许调用者、私有实现禁区，以及适用的一致性、错误、兼容性和恢复责任。架构文档说明这些责任归谁，不默认替每个需求冻结事务隔离级别、锁序、查询条数、索引组合、测试数据规模或逐项验证方法；只有它们已经是跨需求稳定合同，或有具体测量、并发、安全、合规证据要求统一时才记录。目录与模块一一对应时合并说明，不重复填表。

**稳定边界与内部粒度分开约束。** 已确认的业务所有者、目录/包/模块边界、公开出口、私有禁区和依赖方向必须保持；内部文件名、数量和等价拆分可按真实职责调整。目录名、文件行数或单文件形态本身不构成架构偏差：千行页面是调查信号，不是拆分阈值；小模块可保持单文件，职责清楚的 `components` 等目录也可保留。但不得将已确认的稳定边界静默打平到巨型入口/页面、无明确归属的公共目录或同名平铺文件，也不得跨所有者合并、绕过公开出口或引用私有实现。依据真实职责和已确认约束判定偏差，并记录最小迁移，不按外观机械重构。

Target 路径是设计，不是立即创建清单。已确认边界适用于当前开发时，由第一个真实用例落入；没有真实消费者或迁移工作时，不提前建立结构。

新文件先找所属业务或技术边界，再判断具体职责，优先在该边界内与唯一消费者共置；通过共享准入后才提升。无法唯一判断时补充边界说明，不丢入模糊公共目录。

共享候选须同时满足：至少两个真实消费者、相同且稳定的语义、明确所有者和兼容/测试责任、不会反向依赖业务模块、确实减少重复决策，并可用简单接口表达。代码相似但语义、变化节奏或所有权不同，继续共置，不进入 `common` 或 `utils`。

按各单元的实际职责补充以下归属，不因清单存在而虚构职责或增加层次：

- **前端应用**：应用装配/路由页面、业务功能、远程状态、局部状态、跨页面状态、传输到展示模型映射和共享 UI。
- **后端服务/API，以及具备相同职责的 worker 或 CLI**：入口/公开契约、编排/业务规则、一致性与事务、持久化/外部适配、授权、错误规范化、副作用/重试/恢复。

前后端不能互相替代说明。事务由一致性编排者拥有；授权由受保护资源一侧最终裁决；技术错误由产生或适配边界规范化，业务语义由业务模块拥有；外部副作用、重试和恢复由发起/执行边界及业务编排者分担，恢复不得覆盖更新数据或泄露敏感输入。已有总体决定明确这些语义时，这里说明其工程归属，不另写一套规则正文。

### 5. 设计必要迁移与演进

明确 Current/Target 差异；需要迁移时，设计最小、可逆且可验证的路径：保持已有契约和行为，逐个迁移真实消费者，无调用者后移除旧路径。没有差异或无需迁移时直接说明，不为填表制造重构任务；首次实现尚不存在的业务不等于迁移已有代码。

每项演进给出可观察触发条件，例如已测量的性能瓶颈、重复决策、循环依赖、稳定的多消费者语义、真实异步可靠性需求、独立发布、故障隔离、合规或团队所有权，并说明届时应复核的契约、测试和运行行为。

## 产出与检查

默认只创建或更新根仓单份 `docs/design/工程架构设计.md`；项目已有根仓文档约定或调用方指定其它根仓路径时沿用，不为各仓库或交付单元另建架构文档。

文档保留上述工程事实、设计依据、重要决策、逐单元 Current/Target 地图、职责与依赖、必要迁移和演进条件。章节和表格可合并，同一事实只展开一次；无变化或不适用的内容简要说明，不填空泛章节。规则候选仅按需列出已经确认、跨需求稳定、可执行且无法仅靠结构或自动化表达的约束，不将尚未落地的 Target 写入规则。

完成前，按每个适用业务代码交付单元至少一个代表性文件进行放置演练，并把结论写入文档：能否唯一判断所属边界、是否需要公开出口、允许依赖谁和禁止绕过谁，涉及的错误、事务、兼容或恢复由谁负责。演练验证归属和依赖，不固定内部文件清单；发现模糊处应补充边界或具体待确认事项，而不是增加抽象名称。

同时检查：

- 每个适用单元均有明确的 Current 和 Target，跨单元关系没有替代单元自身说明；
- 现状、已确认目标和待确认事项分开，结构与演进有依据，既定决定未被重复选型；
- 公开/私有边界及共享准入清楚，必要偏差已有迁移说明，内部文件粒度仍可调整；
- 文档不含秘密、完整文件清单或与代码并行维护的实时事实清单，修改未超出授权范围；
- 按项目实际工具执行适用的 Markdown、链接、格式和一致性检查，检查受影响仓库状态与 diff；纯文档设计不运行无关代码测试。

## 完成输出

简要说明文档位置、覆盖的仓库与交付单元、关键新增或调整决定、文件放置演练和文档检查结论，以及未核验范围、待确认事项和未解决限制。无需复述完整目录树或各张表；需要调用方决定的问题仍须在回复中讲清事实、选项、影响和推荐，不能只给文档引用。
