# engineering-architecture — 项目级工程归属合同

## 定位

这是一个可独立调用的项目级工程架构设计能力。它依据调用方资料和当前工程事实，按实际构建、运行、发布和业务边界识别适用交付单元（如前端应用、后端服务/API、worker、CLI）；仓库只是容器。它产出可执行的归属合同，使后续开发能唯一判断：新文件放在哪里、谁拥有语义、可以依赖什么、跨边界如何协作，以及何时才值得演进结构。

本能力不实现业务代码、迁移、配置或基础设施；不重定义产品范围、既有交付单元或主要技术方向；不创建空目录、占位模块、接口或 barrel export。

## 原则与事实边界

- 技术中立：不预设语言、框架、数据系统、通信方式或目录模板。结构只能来自调用方已确认的决定、当前代码/迁移/契约/测试/运行行为、有效项目文档和局部规则。
- 简单优先：只为已证实的职责、变化点、复用、事务、替换或依赖隔离增加层、目录和模式；现有简单结构足够时保留它。
- Current 是事实：当前代码、迁移、可执行契约、测试和实际运行行为才是 Current 事实源。架构文档可表达已确认的 Target，不能把 Target、推测或目录名称混写成 Current。
- 目录树是边界图，不是文件清单：只详细到稳定目录、包和模块边界；目标路径只写入文档，不创建空目录、占位模块、接口或 barrel export。
- 稳定边界与内部粒度分开：已确认的业务所有者、目录/包/模块边界、公开出口、私有禁区和依赖方向是约束；边界内部的文件名、数量和等价拆分可以按真实职责调整。不得把已确认边界静默打平到巨型入口/页面、通用收纳目录或同名平铺文件，也不得以“文件组织调整”为由跨所有者合并或绕过公开出口。
- 保留 Git 边界：先确认目标仓库和已有修改，只改调用方明确要求的文件；不自动提交、推送、暂存、改写历史或重写项目规则。

调用方资料不完整时，读取足以支撑判断的真实工程材料，完成可验证部分，并把缺口、影响和待确认事项明确列出；不要求固定的前置资料、路径或其它能力。

会实质改变系统边界、依赖方向、安全、公共契约、兼容性或迁移成本的选择，必须说明候选、影响和推荐理由并取得调用方确认。普通命名、等价文件拆分、沿用既有惯例和其它低风险可逆判断可以自主完成。

## 模式不是互斥选项

MVC、分层、六边形和 DDD 不是必须从中四选一的互斥架构。按项目事实在相关轴上记录实际取舍，而不是为完整性贴模式名：

| 取舍轴 | 依据与记录方式 |
|---|---|
| 项目形态 | 单体、多应用、库、客户端、服务端、任务进程或多仓的真实交付和运行边界 |
| 顶级组织 | 按功能、技术、交付单元或混合组织；记录顶级目录为何服务当前协作与变化 |
| 模块内部层次 | 仅记录真实存在或已确认需要的入口、编排、规则、持久化、展示等职责 |
| 外部依赖隔离 | 何处隔离传输、数据库、文件、第三方或消息实现，以及直接使用已足够的范围 |
| 领域建模强度 | 仅在复杂规则、状态、不变量或语言统一确有证据时记录模型边界 |
| 客户端组织 | 按当前事实记录应用装配、页面/功能、远程状态、局部状态和共享界面边界 |

模式名称只能作为上述取舍的简写，必须同时给出证据、适用范围、代价和不采用部分。无证据时不预建 `domain`、`application`、`infrastructure` 或 `shared` 模板。

## 工作方法

### 相关事实

读取本次问题直接相关的项目与局部规则、已有架构文档、构建和依赖声明、入口、源码和模块出口、导入关系、测试、迁移、可执行契约、运行进程及外部适配。引用可核验的路径、导入、调用或运行证据，不做无边界全仓审查。

明确区分：

- **Current 事实**：已存在且可由代码、迁移、契约、测试或运行证明；
- **已确认 Target**：调用方确认但尚未完全落地的目标；
- **假设/待确认**：缺少证据，或会改变边界、兼容性、安全、成本或迁移成本的判断。

### Current 工程地图

先列出相关代码仓库及其中包含业务代码且与当前范围相关的适用交付单元；按实际构建、运行、发布和业务边界识别，纯文档或静态资产可基于证据标为不适用。再按每个适用单元形成有限的 Current 目录树，只保留入口、稳定目录/包/模块、事实源和已知依赖方向。每个路径标记为 `[当前]`，并说明它的真实职责；未读到证据就不补全。

每个适用单元分别记录当前公开出口、内部实现泄漏、循环或越层依赖、事务/权限/错误/副作用/恢复所在处，以及测试和生产代码的对应关系；跨单元关系另列，不以一方合同替代另一方。Current 图不是目标建议。行数只用于发现调查点，不是拆分阈值；千行页面须调查职责、消费者、变化和依赖。

### 架构驱动因素

仅提取会改变归属或依赖的证据，例如业务内聚和变化频率、跨模块一致性、权限和审计、多入口与后台任务、外部副作用和恢复、稳定契约、独立发布、故障隔离、团队所有权、性能测量或平台限制。也记录当前明确不需要处理的问题。

每个 Target 目录、模块、抽象或隔离边界都必须可追溯到一个驱动因素；“以后可能需要”不是依据。

### 多维决策

围绕前述取舍轴比较少量真实可行方案。对每个重要决定写入架构决策矩阵：问题和证据、候选、结论和适用范围、收益与代价、Current/Target 影响、最小迁移、未选原因，以及可观察的重议条件。低风险选择没有实质分歧时直接采用合理默认，不为填充矩阵制造替代方案。

跨模块协作优先使用公开能力、上层编排或稳定边界适配。只有真实异步、可靠副作用、独立运行或故障隔离证据成立时，才引入事件、队列、后台机制或拆分服务。

### Target 工程地图

在已确认决定基础上，先列相关代码仓库和适用交付单元，再按每个适用单元给出有限 Target 目录树；Current 与 Target 无变化也须明确写出。跨单元关系另列，使用以下标记：

- `[当前]`：Current 已存在且在 Target 中继续承担相同边界；
- `[目标]`：已确认但尚未落地；
- `[按需]`：满足创建条件时才建立；
- `[迁移]`：为从 Current 到 Target 的临时位置或动作，不伪装成稳定边界。

Target 图只写稳定边界和必要迁移路径，不维护完整文件清单。没有真实消费者或迁移工作时，不能把 `[目标]`、`[按需]` 写成应立即创建的目录、模块、接口或出口。已确认的目录、包或模块所有者一旦适用于当前工作，就必须由第一个真实用例落入该稳定边界；代表性文件放置只验证归属和依赖，不固定边界内部的文件名、数量或统一层次。若 Current 已把多个职责堆入巨型入口/页面、通用收纳目录或同名平铺文件，须把它写为 Current 偏差并给出最小迁移，不能将其视为 Target 的等价实现。

### 边界与放置合同

每个适用交付单元必须分别闭合合同：明确 Current 和 Target（无变化也明确）；对其相关主要目录、包或层说明状态（`[当前]`/`[目标]`/`[按需]`/`[迁移]`）、职责、关键非职责、允许和禁止依赖、创建条件及从局部提升到共享位置的条件。

对每个稳定模块，必须说明：

- 拥有的语义、规则、状态或数据；
- 对外提供的稳定能力或受控出口；
- 允许调用者与跨模块协作方式；
- 不得被外部引用的私有实现禁区；
- 协作时的事务、错误、兼容性和恢复责任。

新文件按顺序判断：先找所属业务或技术边界，再判定其具体职责，优先与唯一消费者共置；只有通过共享准入后才提升；无法唯一判断时，补充边界合同而不是丢入模糊公共目录。这里的“共置”和“等价文件拆分”只发生在已确认稳定边界内部；把前端职责集中回巨型路由/页面或通用 `components`、`hooks`、`services`、`shared` 收纳箱，把后端业务包降级成同名平铺文件，或让任一交付单元跨所有者引用私有实现，都属于架构 delta，必须显式记录并给出最小迁移。

共享候选必须同时满足：至少两个真实消费者、相同且稳定的语义、明确所有者和兼容/测试责任、不会反向依赖业务模块、确实减少重复决策，并可用简单接口表达。两处相似代码但语义、变化节奏或所有权不同，继续共置，不进入 `common` 或 `utils`。

当前范围内存在前端应用时，按事实为该单元说明应用装配/路由页面、业务功能、远程状态、局部状态、跨页面状态、传输到展示模型映射，以及共享 UI 的所有权和边界；不以固定目录命名代替这些判断。

当前范围内存在后端服务/API（及具备相同职责的 worker 或 CLI）时，按事实为该单元说明入口/公开契约、编排/业务规则、一致性与事务、持久化/外部适配、授权、错误规范化、副作用/重试/恢复的所有权和边界。

前后端同时存在时必须各自闭合合同，不能互相替代。事务由一致性编排者拥有；授权由受保护资源一侧最终裁决；技术错误由产生或适配边界规范化、业务语义由业务模块拥有；外部副作用、重试和恢复由发起/执行边界及业务编排者分担，恢复不得覆盖更新数据或泄露敏感输入。

### 迁移与演进

明确列出 Current/Target 差异，并设计最小、可逆且可验证的迁移：先保持已有契约和行为，再逐个迁移真实消费者，最后在无调用者后移除旧路径。没有迁移证据时，不把重构、拆服务或引入中间件写成既定工作。

每项演进须给出可观察触发条件，例如已测量的性能瓶颈、重复决策、循环依赖、稳定的多消费者语义、真实异步可靠性需求、独立发布、故障隔离、合规或团队所有权；同时说明届时应复核的契约、测试和运行行为。

## 默认产出

默认仅创建或更新根仓中的单份：

```text
docs/design/工程架构设计.md
```

项目已有根仓文档约定或调用方指定其它根仓路径时，遵循该路径；不得为每个仓库或交付单元创建本地架构文档。文档至少包含以下可执行内容：

1. 范围、相关事实、相关仓库和适用交付单元、Current/Target/待确认边界和架构驱动因素；
2. 先列仓库和适用交付单元，再按适用单元给出有限 Current/Target 目录树，并使用 `[当前]`、`[目标]`、`[按需]`、`[迁移]` 标记；跨单元关系另列；
3. 架构决策矩阵，至少记录决策问题、当前证据、候选与结论、适用范围、未选原因、Current/Target 影响、最小迁移和重议条件，而不是罗列模式；
4. 每个适用单元的目录/包职责表，以及每项的状态、非职责、允许/禁止依赖、创建和提升条件；
5. 每个适用单元的稳定模块表，说明语义所有权、公开能力/出口、允许调用者、私有禁区、协作与错误/兼容责任；
6. 每个适用业务代码单元至少 1 个代表性文件放置演练，覆盖新文件归属、公开边界和依赖方向；
7. Current/Target 差异、最小迁移和可观察演进条件；
8. 规则候选与待确认事项。

规则候选只列出已经确认、跨需求稳定、可执行且无法仅靠结构或自动化表达的约束；默认不修改规则文件，也不将尚未落地的 Target 写入规则。

## 完成检查

完成前，按每个适用业务代码单元至少一个代表性文件反查合同，而不只检查章节是否齐全：每个文件是否能唯一判断所属稳定目录、包或模块，是否需要公开出口，允许依赖谁，禁止绕过谁，跨模块错误/事务/兼容或恢复由谁负责；边界内部的文件粒度是否仍可调整，而已确认边界是否不会被巨型入口/页面、通用收纳目录或同名平铺文件静默替代。若任何答案模糊，应补充边界、模块合同或待确认事项，而不是添加抽象名称。

同时确认：

- 已逐个适用交付单元明确 Current 和 Target，即使无变化；前后端并存时均已各自闭合；
- Current 只引用代码、迁移、契约、测试或运行行为的事实，Target 已清晰标记；
- 目录树有限且没有把文档路径当作待创建脚手架；
- 共享候选通过准入，且没有业务收纳箱或反向依赖；
- 模式、服务拆分、消息机制和演进均有项目证据；
- 文档没有秘密、完整文件清单或与代码并行的实时事实源；
- 按项目实际工具执行适用的 Markdown、链接、格式和一致性检查，并检查受影响仓库状态与 diff；纯文档设计不运行无关代码测试。

## 完成输出

完成后说明：

- 本次覆盖的仓库、交付单元和未核验范围；
- 创建或更新的架构文档；
- 已确认的架构决策、Current/Target 工程骨架、目录和模块公开边界；
- 代表性文件放置演练的结论，以及仍无法唯一判断的归属；
- Current/Target 差异、必要迁移、演进条件和规则候选；
- 验证证据、待确认事项、风险和未解决限制。

## 避免

- 未读取事实就套固定 React、Vue、FastAPI、FSD、DDD、Clean、客户端、服务端或 `components`、`hooks`、`services`、`types`、`shared` 目录模板；
- 将 MVC、分层、六边形和 DDD 误作必须互斥选择，或以模式名代替归属合同；
- 将 Target、假设或迁移路径陈述为 Current；
- 以相似代码为由过早进入 `common`、`utils` 或 `shared`；
- 直接导入另一模块内部模型、存储实现或私有路径；
- 为未来创建空层、公共目录、接口、barrel export、服务或消息队列；
- 省略事务、权限、错误、副作用和恢复的所有权；
- 未经明确要求修改实现、项目规则或 Git 历史。
