# project-bootstrap — 有限范围基础模板项目化

## 定位

这是一个可独立调用的、技术中立的项目初始化能力。它把已经存在的基础模板、脚手架或通用工程，收口为一个具有明确项目身份、可运行基础和可继续开发边界的项目。

它关注“项目已经从模板派生出来之后，正式开发前还需要完成哪些有限调整”，而不是重新设计产品或重写技术栈。目标是让读者看得出当前项目是什么、如何运行、哪些基础约定已经生效，同时保留模板提供的有效工程能力。

默认只处理低到中等风险的项目基线调整：身份、文档、示例配置、最小联调边界、前端视觉令牌、模板测试迁移和验证入口。每项修改都必须能说明它为什么属于项目化基线，而不是业务功能。

## 明确不负责

本能力不负责：

- 产品需求访谈、需求拆分、Backlog 编写或验收范围裁决；
- 完整业务功能、页面、数据模型、迁移、API、权限流程或状态机开发；
- 重新选择语言、框架、数据库、通信协议或部署架构；
- 自动 clone、pull、sync 或向上游模板回写；
- 把上游模板的更新自动合并到当前项目；
- 预建没有真实职责的业务目录、空模块、占位 API 或占位数据库迁移；
- 为当前项目化目标擅自引入、创建或管理需求和技术方案未要求的新基础设施、外部服务或架构复杂度；
- 删除用户修改、重置工作树、强制覆盖文件、提交或推送 Git 变更；
- 使用 Mock、静态 JSON 或固定响应冒充真实运行验证。

如果发现需要重大架构调整、破坏性迁移、产品范围决定或不可逆删除，暂停并报告，不把它隐藏在“项目化”名义下。

## 输入与技术中立

用户可以提供任意组合：

- 一个目标项目目录、根仓库或多个独立子仓库；
- 模板来源目录、脚手架说明或模板元数据；
- 需求、Backlog、技术方案、README、迁移说明或现有项目约定；
- 希望保留、替换、删除或暂缓的具体范围；
- 前端品牌、字体、主题色、排版或响应式要求。

没有明确技术栈时，从当前仓库的代码、锁文件、构建配置、测试、运行说明和实际命令中发现事实。不得因为项目存在 `frontend/`、`backend/`、`package.json`、`pyproject.toml` 或某个常见框架就假设它们必然存在或采用固定做法。

当前项目工程文件、依赖、配置、测试、迁移和可运行行为是项目现状的优先事实源。模板说明只用于识别来源和残留；模板派生后，不得继续把上游模板描述成当前项目状态。

## 工作协议

### 1. 识别项目与本次模式

先读取足以判断范围的内容：目标目录结构、根和子目录的 `README`、`AGENTS.md`/`CLAUDE.md`、版本文件、锁文件、构建配置、环境示例、入口代码、测试配置、模板元数据和用户提供的项目文档。

判断本次属于哪一种或哪几种：

- **模板派生后的项目化**：保留模板工程能力，替换项目身份和基础文档；
- **既有项目的模板残留清理**：清理仍影响项目理解或验证的中性模板内容；
- **基础环境重新基线化**：对齐启动、测试、联调、契约或视觉基础；
- **新项目脚手架收口**：从可运行脚手架进入可以开始业务开发的状态；
- **不属于本能力**：主要目标是业务开发、架构重选、需求决策或上游同步。

如果目标目录或模式无法安全判断，先说明缺失事实，不猜测。

### 2. 分仓库保护工作树

对每一个实际涉及的 Git 仓库分别执行并记录：

```text
git -C <repo> status --short --branch
git -C <repo> diff --stat
git -C <repo> check-ignore -v <候选本地配置或生成文件>
```

如目录不是 Git 仓库，也要确认其上级仓库边界和文件归属。把以下内容列入保护项：

- 用户已有的已暂存、未暂存和未跟踪修改；
- `.env`、密钥、证书、令牌和其它本地秘密；
- 锁文件、生成文件、数据库文件和本地测试数据；
- 其它仓库或其它需求正在修改的文件；
- 无法确认来源或用途的模板文件。

不得使用 `git reset`、`git restore`、`git checkout`、`git clean`、宽泛 `rm`、宽泛覆盖或宽泛 `git add` 清除冲突。发现同一文件混有用户修改和本次目标时，先保留原内容并报告冲突，不用整文件重写掩盖它。

### 3. 建立项目化基线清单

基于实际文件建立以下分类。每一项都标记现状、建议、影响和证据来源：

| 分类 | 优先检查内容 | 通常可处理的范围 |
|---|---|---|
| 项目身份 | 项目名、包名、应用标题、描述、OpenAPI metadata、版权/署名、模板标识 | 替换仍展示模板身份的值，保持包管理和运行兼容 |
| 文档与规范 | README、贡献说明、AGENTS/CLAUDE、启动和测试说明、来源说明 | 改成当前项目事实，保留仍有效的通用规范 |
| 配置与秘密 | `.env.example`、配置 schema、脚本参数、公开 URL、日志级别 | 只保留代码真正读取的变量和安全示例；真实 `.env` 不写入 |
| 运行与联调 | 开发代理、服务边界、健康检查、OpenAPI/Schema 入口、启动命令 | 修复最小的本地联调和健康检查入口，不新增业务接口 |
| 前端视觉 | 主题令牌、字体、背景、排版、状态色、焦点态、响应式基础 | 只在存在前端且有明确项目视觉要求时调整共享样式入口 |
| 模板残留 | 模板首页、测试断言、示例模块、模板专属文件、未使用组件 | 先搜索引用；只删除会误导项目或造成不必要负担的残留 |
| 验证基线 | lint、格式化、类型检查、单测、构建、启动、浏览器入口 | 将模板断言迁移为项目基础断言，保留有效基础设施测试 |

不得为了使清单看起来完整而增加空的业务模块。健康检查、错误边界、基础 API client、主题切换等如果仍是项目基础能力，应保留并重新命名或补充说明，而不是仅因来自模板就删除。

### 4. 检查需求与技术方案冲突

如果用户提供了需求、Backlog 或技术方案：

1. 读取其中与基础工程、开发闸门、启动方式、仓库边界、视觉、契约和隐私有关的内容；
2. 对照当前工程事实，区分“已有”“计划要求”“模板残留”和“本次建议”；
3. 识别项目化调整是否会改变已定义的业务行为、技术约束或交付边界；
4. 只提出最小文档修正建议，不趁机实现业务功能；
5. 已归档或明确不可变的历史文档不直接改写；需要演进时报告新文档或待确认决定。

需求和技术方案冲突时，不自行偏向代码或文档。先指出冲突、影响和最小解决方式。没有提供正式文档时，不根据项目名称臆测产品身份或业务范围。

### 5. 先输出计划，再等待确认

在第一次写入前，必须输出可审阅的计划并等待用户明确确认。计划至少包含：

- 本次目标和判断的项目化模式；
- 各仓库的工作树状态与保护项；
- 按仓库分组的创建、修改、删除、保留、跳过和待确认文件；
- 每项修改的原因、与模板的关系和潜在兼容影响；
- 计划执行的命令、测试和真实运行验证；
- 发现的需求/技术方案冲突；
- 明确不纳入本次的内容；
- 仍需用户决定的不可安全推断事项。

用户未确认前只能读取和分析，不得写入正式项目、删除文件、安装依赖或运行会改变项目状态的脚手架命令。用户确认部分范围时，只执行确认的部分，重新标注剩余项目。

默认允许纳入的内容：

- 项目身份和元数据替换；
- README、贡献规范和启动说明的项目化；
- 与代码实际读取情况一致的环境示例；
- 最小开发代理、健康检查或契约入口修正；
- 前端共享主题令牌、字体、背景、排版和状态基础；
- 模板首页与测试断言迁移；
- 经过引用确认的模板专属文件清理；
- 当前事实文档的局部修正。

默认延期到首个真实业务需求的内容：

- 认证、会话、权限、业务路由和业务表单；
- 业务模型、Alembic/数据库迁移、种子和演示业务数据；
- 完整 API 模块、OpenAPI 业务 DTO 和生成类型；
- React Hook Form、Zod 或其它复杂业务表单依赖；
- AI/Embedding 客户端、调度器、通知业务和推荐算法；
- 业务级错误码、状态机、权限投影和隐私窗口。

明确禁止借项目化名义加入需求和技术方案未要求的新业务能力、基础设施、外部服务、架构复杂度、全局状态管理或大规模组件重写。

### 6. 精确执行

用户确认后，按以下原则修改：

- 先编辑已有文件，只有目标明确要求且确实缺失时才创建文件；
- 使用小范围替换，保留现有项目结构、可用依赖和有效模板能力；
- 不用重新初始化脚手架、切换 preset 或全量生成命令覆盖当前文件；
- 删除前用 `Grep`/`Glob` 检查引用、脚本、测试和文档关联；无法确认时保留并列为待清理；
- `.env` 可以在本地验证边界内读取或维护，但不把秘密写入示例、文档、日志、测试固件、diff 摘要或回复；
- 只修改确认的仓库和文件范围，不跨仓库批量操作。

### 7. 自适应验证

先从 README、package scripts、Makefile、`pyproject.toml`、CI 配置和测试配置发现项目实际命令，再执行适用验证。不要假设所有项目都有同一套命令。

根据本次改动选择并实际运行：

- 格式化、lint、静态检查和类型检查；
- 单元、集成和现有回归测试；
- 前端构建、后端导入/启动检查或项目等价构建；
- 真实本地服务启动、健康检查和契约入口检查；
- 前后端联调时使用真实服务和真实数据，不用 Mock 代替最终证据；
- 涉及 UI 时使用项目已有 Playwright、浏览器工具或等价真实浏览器能力，至少检查主要入口、加载结果、响应式视口和浏览器控制台/失败网络请求。

验证失败后先修复本次范围内的可修问题，并重跑受影响验证。环境缺失、外部服务不可控或必须人工确认时，保留原验收标准并准确标记未验证范围，不把降低标准后的结果称为完成。

### 8. 结束与状态

最终状态只能是：

- **已完成**：确认范围内的修改已落地，适用检查和真实验证有证据，没有已知阻断问题；
- **已实现但未完全验证**：确认范围内的修改已落地，但存在不可替代的外部服务、凭据、设备或人工条件缺口；必须说明缺口和补验方法；
- **阻塞**：重大决策、用户冲突、仓库访问、不可逆变更或关键运行条件无法安全处理。

最终汇报使用以下结构：

```markdown
## 项目化结果

- 状态：已完成 / 已实现但未完全验证 / 阻塞
- 项目化模式：...
- 涉及仓库：...

### 已修改
- [仓库] `path`：修改目的与结果

### 已创建
- [仓库] `path`：创建目的

### 已删除
- [仓库] `path`：删除依据与引用检查结果

### 保留或跳过
- `path`：保留/延期原因

### 验证
- `command`：结果
- 真实运行或浏览器验证：结果或缺口

### 冲突与限制
- ...

### 下一步
- 只列可选的后续工作，不声明其它 Skill 为强制前置或后续。
```

结束前分别检查各仓库的 `git status --short` 和 diff 范围，确认没有秘密、无关文件、意外删除、跨仓修改或生成物污染。本 Skill 不暂存、不提交、不推送；结束时报告受影响仓库、待提交文件和是否具备提交条件。

## 反模式

- 把“模板项目化”当成重写架构或提前开发业务；
- 没有读取代码和 Git 状态就套用固定文件清单；
- 计划阶段直接写文件，或没有用户确认就删除模板内容；
- 把目标状态、模板说明或 README 当成当前事实；
- 继续保留模板项目名、标题和测试断言，却宣称已完成项目化；
- 为了显得完整预建空路由、空模型、空迁移、空 API 或空服务层；
- 不检查引用就删除健康检查、错误边界、共享组件或锁文件；
- 把真实 `.env`、API key、数据库密码或第三方原始响应写入项目或输出；
- 用 Mock、静态 JSON、截图或代码阅读替代适用的真实构建、启动和浏览器验证；
- 遇到冲突就使用 reset、restore、clean、强制覆盖或宽泛删除；
- 默认安装依赖、切换 shadcn preset、引入全局状态或容器化基础设施；
- 把其它 Skill、固定 Agent 或固定顺序写成此能力的必经流程。
