# project-bootstrap — 有限范围项目化与基线收口

## 定位

这是一个可独立调用、技术中立的项目初始化能力。它把已经存在的模板、脚手架或通用工程收口为具有明确项目身份、可运行基础和可继续开发边界的项目，同时保留仍然有效的工程能力。

处理范围通常包括项目身份、说明文档、受保护的实际本地配置与公开配置示例、最小联调入口、已确认的视觉基线、模板测试迁移和必要残留清理。每项修改都必须能解释为什么属于项目基线，而不是业务功能。

本能力不重选技术栈，不展开完整业务页面、数据模型、接口、权限流程或状态机，也不为“以后可能需要”预建空模块、外部服务和抽象层。遇到重大架构变化、不可逆删除、破坏性迁移或产品范围决策时，说明影响并等待决定。

调用方可以直接提供目标、约束、已确认决定，以及已经确定的外部资源、运行配置和凭据事实；每次执行以当前项目事实为准。已经确定的外部条件是工程项目化的输入，本能力负责让工程按既有合同正确消费它们，不重新选择、创建、派生、轮换或替换外部资源和凭据。

## 输入与事实

调用方可以提供任意组合：

- 一个项目目录、根仓库或多个独立仓库；
- 模板来源、脚手架说明或派生边界；
- 产品、技术、品牌、交付和运行资料；
- 希望保留、替换、删除或暂缓的具体范围；
- 已确认的名称、配置、联调、视觉或验证要求。

没有明确技术说明时，从当前仓库的代码、依赖锁定、构建配置、测试、运行说明和实际命令中发现事实，不根据目录名、文件名或常见做法推断固定技术方案。

当前工程文件、配置、测试、迁移和可运行行为优先描述现状。来源资料只帮助识别模板身份和残留，不得覆盖派生后的项目事实。

## 工作协议

### 1. 识别项目和本次范围

先读取足以判断边界的内容：

- 项目及局部规则、根仓与适用独立代码仓 README、其它说明文档和调用方资料；
- 仓库边界、Git 状态和用户已有修改；
- 项目元数据、依赖、构建与测试配置；
- 公开配置示例、运行入口和联调说明；
- 共享样式入口、基础页面和模板测试；
- 模板来源信息及疑似残留的引用关系。

判断本次是身份与文档收口、模板残留清理、运行与联调基线修正、已确认视觉基线落实，还是这些内容的有限组合。若主要目标是业务开发、技术方向重选或大范围架构调整，应停止扩大范围。

### 2. 分仓库保护工作树

对每个实际涉及的 Git 仓库分别确认根目录、状态、diff 和文件归属。保护：

- 用户已有的已暂存、未暂存和未跟踪修改；
- 开发配置、密钥、证书、令牌和本地数据；
- 锁定文件、生成文件和无法确认来源的模板文件；
- 其它仓库或其它工作正在修改的文件。

不得使用重置、清理、强制覆盖或宽泛删除消除冲突。同一文件混有用户修改和本次目标时，采用可核对的小范围编辑；无法安全分离时保留并说明冲突。

### 3. 建立项目化清单

只列实际需要处理的内容：

| 分类 | 检查重点 | 可处理边界 |
|---|---|---|
| 项目身份 | 名称、标题、描述、包或应用元数据、版权与模板标识 | 替换仍展示模板身份且不破坏运行兼容的值 |
| 文档与规则 | 根仓和适用独立代码仓 README、启动、测试、贡献和来源说明 | 按各仓职责收口为当前项目的稳定入口、使用合同和文档地图，保留仍有效的通用约束 |
| 配置与秘密 | 公开示例、配置校验、脚本参数和公开地址 | 对齐代码实际读取项；秘密只留在受保护的开发配置中 |
| 运行与联调 | 启动、健康状态、开发代理、服务边界和契约入口 | 修复最小可用入口，不新增业务接口 |
| 视觉基线 | 已确认的品牌令牌、字体、排版、背景、状态和焦点基础 | 只落实已确认要求，不重做产品信息架构 |
| 模板残留 | 模板首页、示例模块、测试断言、文案和专属文件 | 检查引用后，迁移或删除会误导项目的内容 |
| 验证基线 | 格式、静态检查、测试、构建、启动和浏览器入口 | 将模板断言改为项目基础断言，保留有效工程测试 |

不为清单完整而增加没有消费者的目录、配置、接口或占位文件。

### 4. 收口 README 稳定入口

README 的标准化对象是读者问题和内容责任，不是所有仓库使用完全相同的标题：

- 根仓 README 面向首次接触项目的客户、负责人和接手者，使用通俗语言说明产品定位、目标用户、当前可用范围与主要限制、仓库组成、最短全栈启动或正常使用路径，以及需求、设计、架构、运行和交付资料的入口；
- 前端、后端等独立业务代码仓 README 面向对应仓库的开发与运行维护，说明本仓职责、环境要求、最短安装启动与联调方式、配置和秘密边界、主要代码入口、验证、构建及运行责任；
- 项目已有等价结构时沿用并最小修正，不为统一标题整份重写。开发验收数据基线、账号交接或其它业务交付事实尚未建立时，不在项目化阶段预造内容；已经存在且适用时，README 应提供其恢复、核验和详细文档入口。

README 只保留稳定的项目事实、使用合同和必要摘要。模块内部设计、单个需求或 BR 的开发流水、一次性日志/截图/测试输出、历史演进、完整 API 清单和其它权威文档正文留在项目已有的适当受跟踪位置，README 通过链接使其可发现。项目已经明确选用 README 直接承载某类交付信息且规模适合时可以保留，但不得在多个仓库重复维护同一详细事实。

收口时逐项核对 README 中的命令、配置键、公开地址、端口、前置服务、健康检查、联调入口、文档链接和成功判断是否符合当前工程事实。修改稳定事实时替换或删除模板、失效和重复说明，不按需求编号在末尾持续追加。适用仓库的 README 无法让接手者发现并执行主要路径时，项目化不能标记为已完成；其它交付文档可以承载详细正文，但不能替代该 README 的必要入口和链接。

### 5. 校准调用方资料

将调用方资料与当前工程事实逐项对照，区分：

- 已经存在且可验证的能力；
- 已确认但尚未落实的目标；
- 仍在展示或影响行为的模板残留；
- 本次需要执行的最小修改；
- 无法安全推断、需要决定的事项。

资料与代码冲突时，说明各自代表的事实、影响和最小解决方式，不静默选择，也不借项目化名义改写业务行为。

### 6. 确认执行边界

第一次写入前，应让调用方能够看清：

- 本次目标和涉及仓库；
- 准备创建、修改、删除、保留或跳过的文件；
- 每项修改的原因、兼容影响和保护项；
- 计划执行的检查与真实运行验证；
- 冲突、未决事项和明确不纳入的内容。

调用方已经明确要求实施且文件范围、行为和删除边界清楚时，可以直接执行，不重复索取确认。涉及新增删除、不可逆变化或无法判断归属时，应先确认相应部分。

## 视觉基线

视觉调整只落实调用方已经确认，或能够从当前有效设计资产和项目规范中核验的基线，例如品牌标识、颜色令牌、字体、排版尺度、背景、状态色、焦点可见性和响应式约束。

没有明确视觉方向时：

- 保持现有可用样式，或采用最小、中性、易替换的基础值；
- 不把临时选择包装成品牌决定；
- 不自行决定应用 Shell、导航结构、页面信息架构或组件体系；
- 不引入新的视觉依赖、预设或大规模组件重写；
- 记录仍待提供的品牌和体验输入，以及它阻碍的具体工作。

即使已有明确视觉方向，也只修改共享基线入口和为验证所需的最小示例，不提前实现业务页面。

## 精确执行

按以下原则修改：

- 优先小范围编辑已有文件，只有目标明确且确实缺失时才创建；
- 保留当前结构、可用依赖和仍有效的模板能力；
- 不用重新初始化或全量生成命令覆盖当前工程；
- 删除前检查代码、脚本、测试和文档引用；无法确认时保留并列为待处理；
- 当工程实际读取合同需要调整时，可以同步维护受保护的实际 `.env` 或等价本地配置及对应公开示例，包括环境变量改名和配置结构迁移；迁移必须复用同一既有资源绑定和真实值，保留资源身份、endpoint 与权限范围，不重新选择、创建、派生、轮换或替换外部资源或凭据；
- 修改 README 时优先改写现有段落并删除失效、重复和模板说明，不把本次执行过程、测试输出或设计正文追加到文件末尾；
- 已经存在且属于开发验收数据基线的目标产品账号及密码按项目规则作为受跟踪交付信息保留；数据库、对象存储、SMTP、OAuth client secret、API key、私钥、令牌及其它用于访问目标产品外部系统或资源的凭据仍属秘密，不得进入公开示例、文档、日志、测试固件、diff 摘要或回复；
- 只修改确认的仓库和范围，不跨仓库批量处理。

通常可以纳入：

- 项目身份和元数据替换；
- 说明文档、启动与测试说明的项目化；
- 与代码读取行为一致的公开配置示例；
- 最小运行、健康状态、联调或契约入口修正；
- 已确认的共享视觉基线；
- 模板首页、示例内容和基础测试断言迁移；
- 经过引用检查的模板专属文件清理。

业务身份流程、权限模型、业务路由、表单、数据模型、迁移、业务接口、业务状态和外部业务能力只在调用方明确把它们作为当前项目化范围且已有确定设计时处理；否则留给实际业务实现。

## 验证

先从项目说明、脚本和配置中发现真实验证方式，不假设固定命令。根据改动实际运行适用的：

- 格式、静态检查和类型检查；
- 单元、集成和现有回归测试；
- 构建、导入或启动检查；
- 本地服务、健康状态和契约入口；
- README 中受影响的安装、启动、联调、健康检查和验证命令，以及相对文档链接和关键前置条件；
- 涉及多个交付单元时的真实联调；
- 涉及 UI 时的真实浏览器入口、目标视口、控制台和失败网络请求检查。

最终联调和体验证据不能只依赖 Mock、静态响应、截图或代码阅读。工程验证失败后，先区分配置读取、变量迁移、脚本、代码、代理、启动、健康入口、前后端连接、测试或浏览器入口等本能力范围内的接线问题，修复并重跑。只有已经使用既有配置排除工程接线问题后，确认外部资源、授权、凭据、服务、设备或付费条件本身不可用时，才保留验收标准并说明失败入口、未验证范围和补验方法；不得用替代资源、新账号或新凭据掩盖失败。

结束前分别检查各仓库状态和 diff，确认没有秘密、无关文件、意外删除、跨仓修改或生成物污染。本能力不暂存、不提交、不推送。

## 结果汇报

按实际情况汇报：

- 状态：已完成、已实现但未完全验证，或阻塞；
- 项目化范围和涉及仓库；
- 创建、修改、删除、保留或跳过的文件及原因；
- 已落实的项目身份、运行、联调和视觉基线；
- 根仓与适用代码仓 README 的收口结果、实际核验入口，以及未修改 README 时合同不受影响的依据；
- 实际执行的检查、结果和未验证范围；
- 冲突、限制、待决定事项和可选后续工作。

## 避免

- 未读取工程事实和 Git 状态就套固定文件清单；
- 把项目化扩展成技术重选、业务开发或大范围架构重写；
- 没有引用检查就删除模板能力、共享基础或锁定文件；
- 无视觉方向时自行决定 Shell、导航、信息架构或组件体系；
- 为显得完整预建空模块、空接口、空迁移或无消费者抽象；
- 为统一格式机械重写全部 README，或把模板教程、模块实现、测试日志、一次性证据和历史演进留在稳定入口中；
- 只在 README 末尾追加新说明，不替换已经失效、重复或冲突的旧事实；
- 用强制覆盖、宽泛清理或 Mock 证据掩盖冲突与验证缺口。
