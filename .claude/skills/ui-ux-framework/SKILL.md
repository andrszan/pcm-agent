# ui-ux-framework — 持续演进的产品 UI/UX 框架

## 定位

这是一个可独立调用的产品级设计能力。它根据产品目标、用户任务、现有界面和真实前端事实，建立或校正跨需求稳定的 UI/UX 框架，避免每个需求、页面或会话重新发明导航、页面结构、术语和视觉语言。

本能力提供主框架方向与代表性参考，由 Agent 根据项目选择、组合并完善。它记录后续页面需要保持一致的产品表面、导航、区域、滚动、响应式和共享表达，不是布局教材、逐页视觉稿或固定审批表单；具体页面美化与实现细节由实际设计和开发完成。

既有项目默认渐进收敛。优先选择能覆盖主要页面类型的代表性任务链验证框架；除非用户明确决定，不一次性重写全部页面。

## 职责与边界

本能力负责：

- 根据用户、角色和任务设计产品表面、信息架构、导航与 App Shell Contract；
- 建立跨页面的内容、视觉、交互状态、响应式和可访问性规则，区分共享体系与品牌定制；
- 从真实实现中识别跨需求框架失真，提出校正或渐进演进方案；
- 按需比较布局预览、查阅兼容源码，为设计与开发提供参考；
- 按项目约定维护框架文档，真正需要负责人决定的事项按下文确认边界处理。

本能力不负责：

- 重新定义产品目标、功能范围、商业策略、Backlog 或开发顺序；
- 接管单个需求的具体用户路径、页面状态、文案逐句定稿和验收条件；
- 直接实现页面、CSS、组件、主题、测试或迁移；
- 对已开发需求执行功能验收、浏览器验收或发布判断；
- 选择前端技术栈，生成完整线框、逐像素视觉稿、全量页面树或组件 API；
- 启动开发、提交或推送。

单需求资料和真实实现都可以作为框架判断输入。只有问题会影响多个需求、产品表面、主导航、Shell、共享表达、视觉语义或品牌与受控定制边界时，才进入本能力的修改范围。

仅查阅资源时，依据当前任务、已有框架决定和实际技术栈读取索引、少量候选预览及选中源码，说明适用部分、复用边界和局限后结束；不进入下文的框架建立、文档写入或确认流程，不因缺少框架文档阻塞查阅，也不改变既定 Shell。页面实现和验证仍由当前开发任务负责。只有发现确属跨需求的框架问题时，才评估框架演进。

## 独立性与事实优先

本能力不依赖固定上游、下游、专属文档、Manifest 或具名工具。已有设计资料可以读取；资料缺失时，继续依据产品说明、代码和可运行页面调查并完成能够安全判断的部分。普通、可逆且在授权范围内的设计事项直接收敛；存在多个候选，或问题涉及安全、数据、权限等主题，本身不构成上抛理由。

按当前问题渐进读取本 Skill 自带参考，不为形式加载全部资源：

| 需要解决的问题 | 按需读取 |
|---|---|
| 区分产品 Shell、页面模式与滚动模型，比较真实布局方向 | [`references/layout-selection-guide.md`](./references/layout-selection-guide.md) |
| 正式确定或演进 Shell、导航、sticky、滚动与响应式合同 | [`references/app-shell-contract.md`](./references/app-shell-contract.md) |
| 需要结构、构图或交互参考，或维护布局资源 | [`references/layout-resource-library.md`](./references/layout-resource-library.md)、少量候选预览及选中资源的源码 |

`assets/layout-source-snapshots/` 保存带预览和上游依赖的部分框架源码快照，不保证独立运行。依据任务与实际技术栈筛选少量候选，先查看预览比较，再深入选中源码；React + shadcn/ui 项目优先考察兼容的本地资源，但不因资源存在而决定技术栈或布局。允许合理复用，不要求为原创重写，也不把现有资源当作设计上限。兼容性核对、演示内容替换和未闭合交互的处理见资源库参考。

开始前读取足以支撑判断的真实上下文，通常包括：

- 根仓库和目标前端仓库的项目规则、状态与用户已有修改；
- 产品定义、当前需求、活动设计和技术资料；
- 路由树、App Shell、布局、Provider、主题和全局样式入口；
- 代表性列表、详情、表单、任务流、设置和后台页面；
- 真实 token、字体、图标、组件、素材和内容来源；
- 可运行页面、浏览器测试、截图以及已有体验证据。

事实优先级：

1. 当前代码、配置、素材、测试和可运行页面决定实现事实；
2. 当前目录更具体的项目规则约束修改边界；
3. 用户本轮明确决定控制目标状态；
4. 仍有效的产品、设计和技术文档记录长期决定；
5. 历史稿、模板和竞品只作为参考；
6. 通用 UI/UX 经验只能提出候选，不能冒充项目事实。

不得把目标设计写成现状，也不得把一个页面的偶然实现直接提升为全局规则。新项目记录有依据的目标与适用范围即可；既有项目发生调整时，再区分当前实现、已确认但未实现的目标、可由后续设计承接的事项、待验证假设、负责人待决和必要迁移，不为每项普通选择填写状态表，也不把这些不同性质的内容统称为待确认。

## 三层框架模型

以下是分析维度，不是文档章节清单。按当前产品选取会影响跨页面一致性的决定；不因某个维度列在这里，就展开完整组件词典、状态矩阵或定制规则。

### 1. 稳定 UX 架构

记录不应由单个需求或局部定制随意改变的体验骨架：

- 产品表面、用户角色、核心任务和主要设备；
- 信息架构、入口、主导航、上下文导航和页面层级；
- App Shell、组织或租户上下文、账户区和返回关系；
- 列表、详情、创建编辑、任务流、设置和工作台等页面模式；
- 文档滚动或视口工作区、常规滚动所有者、sticky 基准、溢出边界和额外滚动区的任务理由；
- 保存、取消、确认、危险操作、草稿保留和冲突恢复；
- 加载、空态、无结果、离线、错误、只读、无权限和失权；
- 响应式重排、导航收纳、键盘路径、焦点、触控目标和辅助技术语义。

### 2. 共享内容与视觉体系

记录跨页面复用的表达、构图和组件语言：

- 用户能理解的对象名称、动作名称、状态名称、语气和术语表；
- 页面标题、导航、按钮、字段、帮助、空态、错误和恢复文案的职责与一致性；
- 语义色、主题、状态色、字体职责、字阶、行高和数据展示原则；
- 页面宽度、留白、密度、分组、圆角、边界、阴影和动效原则；
- Button、Input、Card、Table、Dialog、Alert、Badge、Toast 等组件的适用语义和组合规则；
- 页面标题区、筛选区、主操作、危险操作、空态和错误恢复模式；
- 图标、图片、图表、数据可视化和 reduced motion 原则。

主动评估哪些产品表面适合通过摄影、插画或产品图改善内容识别、场景理解、品牌表达和产品展示，不等待用户点名素材。对适用表面明确媒体用途、风格与构图、文案留白、响应式裁剪和缺失或替换原则；需要特定品牌构图时可直接确定定制方向，不要求先穷尽图库。无明确收益的表面保持克制，不要求每页配图；只记录跨页面稳定规则，不在此展开逐页获取、批量生成或开发后验收。

内容设计必须使用用户任务语言，避免把接口、数据库或内部状态直接暴露给用户。相同对象、动作和状态在导航、标题、按钮、帮助与反馈中应保持一致；确需使用不同称呼时，要能解释语境差异。

代码中的 token、组件和样式文件是实现事实源；框架文档记录职责、语义、真实路径和提升条件，不复制完整值或 API。已有具备产品依据的基础视觉主题时，以其颜色、字体与排版尺度、圆角、阴影、边框和间距作为 Current，重点定义这些基础值如何服务页面层级、内容密度和组件语义；不因进入框架设计就重新选一套主题。确有品牌、可读性或任务适配问题时，说明具体冲突、必要调整和验证方向，不以个人审美偏好推翻已落实基线。

共享体验规则以产品任务和一致性需要为依据。新项目可以在页面尚未实现时确定统一术语、状态和视觉语义；从局部模式提炼共享规则时，确认业务语义一致且确有共享收益，不因外观相似强行统一。是否提取公共组件、采用何种目录归属或代码抽象，由工程设计与实现决定，本能力不设置消费者数量门槛。

### 3. 品牌与受控定制层

承载产品品牌和有限的场景化定制：

- Logo、产品名、品牌主色和辅助色；
- 字体、插画、摄影、图标细节和视觉母题；
- 首页文案、品牌语气、Footer 和品牌归属；
- 可选模块、受控导航项、密度或圆角预设；
- 只属于某一品牌、版本、部署、行业或业务场景的资产。

存在多品牌、版本或部署定制需要时，说明定制范围与替换条件；否则记录当前品牌表达即可，不预建设计定制体系。定制不得绕过权限、错误恢复、危险操作、可访问性、响应式和核心任务语义，也不得把单一场景的颜色、文案、素材或导航静默提升为全局默认。

## 产品特异性与页面构图

统一不等于模板化。框架必须让用户看出“这是什么产品、我在处理什么对象、下一步做什么”，而不是只得到一套通用后台外观。

- 导航和 Shell 由用户、任务频率、页面层级、信息密度和设备场景推导；后台不自动等于永久侧边栏，SaaS 不自动等于顶部导航、Hero 和 Footer。
- 必须明确 Shell、页面模式和滚动模型三个层级；“单栏”“卡片式”“F 型”不能代替产品导航决定，“固定导航”“响应式处理”也不能代替滚动所有者、sticky 基准和宽窄屏转换合同。
- 页面先建立任务叙事、信息层级和操作主次，再选择组件。
- Card 只用于需要独立边界的内容组，Table 只用于需要比较和扫描的重复结构，Badge 只承载简短状态或分类；它们不是所有内容的默认容器。
- 工作台或概览页只有在用户需要同时判断多类信号并采取下一步行动时才成立，不能用统计卡片和图表填充缺少任务结构的页面。
- 页面标题、关键状态、主操作和主要内容应形成清晰阅读顺序；次要元数据和低频操作不能与主任务争夺注意力。
- 使用产品真实对象、动作、关系、状态和素材建立辨识度，避免“数据概览”“资源管理”“执行操作”等可替换到任何产品的空泛表达。
- “现代”不自动等于蓝紫渐变、大量阴影、玻璃效果、过度圆角、插画或动画；视觉选择必须服务产品定位和任务。

## 建立或演进框架

### 1. 判断是否属于产品级问题

先确认问题是否会改变多个需求的设计选择。单页面布局、单流程状态或开发后验收不自动升级为框架工作；主导航、Shell、跨页面术语、页面构图规则、共享状态语义或品牌与受控定制边界才属于框架范围。

同步本次范围、推荐方向和真正需要负责人决定的问题。用户已请求建立或更新框架时，在该范围内推进；不为普通布局选择或文档落盘重复请求确认，也不发送逐字段问卷。当前任务相关且已经到解决时机的未决，应先调查并在授权内自行收敛，或在实际越权时准确交接；不为此全盘重审上游产品与技术决定。

### 2. 建立当前体验地图

从前述真实上下文中提取与本次问题相关的表面、任务、导航、页面模式和共享表达，识别已有稳定规则与实际偏差。只读取足以支撑判断的代表性切片，不为了“全面”扫描每个组件，也不为新项目尚不存在的页面建立现状清单。

### 3. 提取驱动因素并比较方案

框架方向应由任务频率、内容与数据管理的主次、设备、角色、页面规模、信息密度、跨上下文切换、品牌边界和迁移成本解释。需要布局选择时，先按需读取 `references/layout-selection-guide.md`；在收敛方向前可以比较少量相关预览，让参考参与构图判断，确定方向后再深入选中源码。

比较少量有实质任务或架构差异的可信方向，并推荐其一；只有一个方向符合事实时不为凑数制造替代方案。说明所服务的用户任务、导航与内容组织、窄屏变化和主要取舍即可；已有项目需要调整时再说明迁移影响。多个可信方向仍可依据已确认目标和可逆性自主选择，不把“有选项”本身当作负责人待决。

不能只比较颜色、圆角或阴影。可由事实推导的低风险选择直接收敛，只有实际超出授权的实质高影响取舍才等待确认。

### 4. 建立最小框架

只覆盖当前产品和近期真实需求需要的规则。选择一条能覆盖多个页面类型的纵向任务链作为代表性切片，例如“工作台 → 列表 → 创建 → 详情”，用于验证导航、表达、构图、状态和视觉语义是否一致，而不是要求一次重写所有页面。

需要确定布局时，参考 `references/app-shell-contract.md` 中的区域示例，按项目选择、组合或补充，在框架文档中讲清表面与布局、导航层级、区域分工、滚动与常驻关系、sticky 基准及窄屏转换。用简短说明或区域图表达即可，不要求逐表填写，也不只写“采用侧边栏”“移动端适配”。

新项目记录目标与适用范围；既有项目再按实际变化补充当前实现、偏差和必要迁移。具体组件、路由和 CSS 写法由开发完善，不把结构示例扩展为逐页实现规格。

## 文档与确认门槛

### 文档内容

用户已请求建立或更新框架时，直接沿用项目已有的权威文档约定；只有归属不清、存在相互冲突的多份文档或需要迁移时才请求决定。没有既有约定时，默认维护一份综合文档：

```text
docs/ui-ux/framework.md
```

不适用时只在最终结果中说明依据，不创建文档或空目录。文档保留后续页面需要一致遵循的产品决定、依据和适用范围，引用必要的工程事实路径：

- 同一个决定只在一处完整说明；其他章节只补充局部影响，不另建“已收敛决定”重复正文。
- 新项目说明目标设计即可，不把目标冒充现状；既有框架调整时再补充实际偏差与必要迁移。不逐项填写状态、审批或重议条件。
- 组件、交互状态和可访问性内容按产品需要记录共同基线、特有规则与例外，不重复通用教材或完整组件 API。
- 代表性任务链和自审清单用于检查设计；只有产生后续需要引用的决定时才写入文档，不默认输出检查过程。
- 保留影响设计判断的证据与真实缺口，不记录本轮读取流水或罗列不属于本能力职责的未执行测试。不创建 Manifest、逐页资产清单或空文档树。
- 可后置的事项只在相关正文自然说明为何现在不解决、由哪项后续设计或什么证据承接，以及最迟在哪个页面类型、实施或发布条件出现前解决，不另建强制台账。
- 负责人或用户作出决定后，在授权范围内更新活动框架正文的权威位置，清除已失效的待确认、候选和阻塞表述；不改归档或历史记录，也不另加重复的决定摘要。

### 确认边界

依据已核验事实，在请求范围内直接收敛普通设计规则。只有决定实际超出本次授权，并会产生下列实质高影响时，才交由负责人确认：

- 改变产品承诺、产品表面、主导航、Shell 或核心任务与返回关系的跨需求体验骨架；
- 实质改变权限、危险操作、失败恢复语义，产生明显不可逆后果；
- 实质改变既定品牌方向、共享术语、视觉语义或可访问性基线，替换全局设计基础设施，带来明显迁移成本或破坏已发布兼容性。

判断依据是实际影响和授权边界，而不是是否涉及安全、数据、字体、token 等主题，也不是候选数量。沿用已有安全基线、补齐失败提示、按既定术语统一命名、低风险布局延伸、等价窄屏收纳和普通文档落盘不另行确认；实际越权的高影响改变即使只有一个可行方案，也必须交接负责人。交接应自包含地说明准确问题、已核验事实、约束、可行选项、各自影响、推荐及理由，并明确只阻碍框架的哪一部分；其余授权内合同继续完成。整体框架或文档仍处于既有批准环节时保持该合同，不以自主处理普通事项替代所需批准。

## 自审与结束

完成前用一条代表性任务链检查：

- 用户能否找到任务，当前表面、对象、导航与返回关系是否清楚；
- 布局、内容密度与操作层级是否服务真实任务，而非通用组件堆叠；
- 滚动、常驻区域和 sticky 关系是否明确，窄屏、键盘与焦点是否保留必要能力；
- 共享术语、状态与品牌表达是否一致，已有实现与目标是否混淆；
- 参考中的演示行为是否被误认为已实现，文档是否只留下跨页面需要一致的决定；
- 当前任务已到解决时机的未决是否已经收敛，只有实际越权的高影响取舍才交接负责人，没有接管单需求设计、实现或验收。

本能力可以读取真实浏览器和截图作为框架判断证据，但不宣称具体功能或页面已经完成交付。结束状态为：

- **已完成**：目标框架决定已确认或已按事实形成默认 Target，并按项目约定写入；适用范围的 App Shell Contract 已闭合，没有以笼统候选代替可实施结论；合理后置事项不影响当前合同使用。
- **方案待确认**：仅剩会实质改变跨需求体验骨架、迁移成本或兼容性且超出现有授权的具体决定待确认，其余合同已完成；不把受未决选择影响的部分当成已确认基线。
- **阻塞**：核心产品、导航、品牌、可访问性或兼容性事实无法安全取得。

最终只汇报确认的框架决定、文档变化、真实证据、已知偏差和未解决限制。若需要负责人决定，直接给出完整交接内容，不能只引用文档。本 Skill 不暂存、不提交、不推送。
