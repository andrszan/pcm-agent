# ui-ux-framework — 持续演进的产品 UI/UX 框架

## 定位

这是一个可独立调用的产品级 UI/UX 框架能力。它让项目可以边开发边设计，而不让每个需求、页面或 AI 会话各自发明一套界面：先从产品目标、用户任务、现有页面和真实前端事实中建立最小框架，再在需求开发中局部延展，并通过实现后的审查持续收敛。

本能力不要求项目开始时设计完所有未来页面，也不把视觉冻结成传统阶段交付物。它维护的是跨需求仍有稳定价值的设计契约：产品有几个表面，用户如何导航和完成任务，页面属于什么 Shell 和层级，常见状态如何反馈，视觉语言和组件语义如何复用，桌面与移动端如何协同，以及客户可以定制什么、不能破坏什么。

框架存在是为了支持持续交付，不是暂停产品开发进行一次全量翻新。既有项目默认渐进收敛：优先选择能覆盖主要页面类型的纵向任务链验证框架，后续需求触及旧页面时再迁移；除非用户明确决定，否则不一次性重写全部页面。

## 与其它能力的边界

本能力负责：

- 识别家庭端、内容端、任务执行端、运营后台、认证入口、营销站等真实产品表面；
- 设计产品级信息架构、主导航、页面 Shell、上下文切换和跨页面体验规则；
- 建立共享视觉语言、语义 token、排版与密度原则、组件语义和页面模式；
- 定义加载、空态、错误、只读、失权、冲突、成功、危险操作和恢复等跨需求状态；
- 定义桌面、平板、移动端、打印、键盘、焦点、对比度和 reduced motion 原则；
- 区分稳定产品体验、共享视觉体系与客户品牌定制；
- 审查真实实现是否偏离已经确认的框架，并提出最小修复和演进建议；
- 在用户确认后维护项目级 UI/UX 框架文档。

本能力不负责：

- 重新定义产品目标、功能范围、商业策略、Backlog 或开发顺序；
- 替代产品定义、大需求拆分、单需求技术设计或工程架构设计；
- 为具体需求设计接口、数据模型、事务、权限实现或完整技术协作；
- 直接实现页面、CSS、组件、主题、浏览器测试或迁移；
- 生成完整线框、逐像素视觉稿、全量页面目录、完整组件树或 Props/API 清单；
- 选择前端框架、组件库、CSS 方案或重构工程目录；
- 因为依赖已经安装，就声称某种布局、组件或设计系统已经接入；
- 自动调用其它 Skill、启动开发、执行交付、创建 commit 或 push。

产品定义中的视觉意图可以作为输入；本能力把它发展为跨页面的设计规则。单需求 TRD 继续描述当前需求的具体行为、状态和验收，工程架构继续决定代码边界；后续实现能力负责将已确认框架落实为代码并完成真实浏览器验收。

## 简单优先与反模板化

不要把“统一 UI”理解成套用流行模板。导航和 Shell 必须由真实用户、任务频率、角色边界、页面层级、信息密度和设备场景共同推导：

- “后台项目”不自动等于永久左侧栏；
- “SaaS”不自动等于顶部导航、Hero 和 Footer；
- “现代设计”不自动等于蓝紫渐变、大量阴影、玻璃效果、过度卡片化或动画；
- “移动优先”不自动等于把桌面布局纵向堆叠；
- 安装了 shadcn、Material、Ant Design 或其它组件库，不代表项目已经拥有产品级设计系统。

框架质量首先取决于任务是否易完成、信息层级是否清楚、状态是否完整、页面是否一致、移动端和辅助技术是否可用；视觉精致度服务于这些目标，不能掩盖信息架构问题。

## 输入与事实优先级

用户可以提供任意组合：

- 项目、根工作区、前端仓库或页面路径；
- PRD、需求说明、Backlog、活动 TRD、技术方案或工程架构；
- 当前页面、截图、设计稿、原型、竞品或品牌资料；
- 现有路由、App Shell、布局、主题 token、全局样式、组件库和静态资产；
- 希望建立、延展或审查的 UI/UX 问题；
- 明确的 `bootstrap`、`before` 或 `after` 模式。

每次调用先读取足以判断范围的真实上下文，通常包括：

- 根和目标前端仓库的 `README.md`、`AGENTS.md`、`CLAUDE.md` 及局部规则；
- 产品定义、活动设计文档和当前需求；
- 路由树、应用 Shell、全局 Provider、主题和样式入口；
- 代表性列表、详情、表单、任务流程、设置和后台页面；
- 真实 token、字体、图标、组件、素材及其来源；
- 浏览器测试、截图或可运行行为；
- 各目标 Git 仓库状态和用户已有修改。

事实优先级：

1. 当前代码、样式、配置、素材、测试和可运行页面决定当前实现事实；
2. 当前目录更具体的 Agent 规则约束实现和修改边界；
3. 用户本轮明确决定控制目标状态；
4. 活动产品、UI/UX、技术和工程文档记录仍有效的长期决定；
5. 历史设计稿、模板和竞品只提供来源与参考；
6. 通用 UI/UX 经验只能作为候选方案，不能冒充项目事实。

必须区分：

- **当前事实**：现在已经存在并可验证的界面、规则和资产；
- **已确认框架**：跨需求应继续遵循的产品级设计决定；
- **目标状态**：已经确认但尚未完全实现的框架；
- **现有惯例**：多个真实页面已经稳定采用且与目标相容的模式；
- **局部决定**：只服务当前页面或需求，不自动升级为全局规则；
- **合理默认**：低风险、易调整且不改变用户任务或产品表面的判断；
- **假设与待核验**：尚不能从事实确认的设计前提；
- **待确认决策**：会改变主导航、Shell、品牌、核心流程、可访问性、兼容性或迁移成本的选择；
- **已知偏差**：当前实现与确认框架不一致，但尚未纳入本次迁移的设计债务。

不得把目标设计写成当前事实，也不得把历史偶然实现直接认定为规范。

## 三层框架模型

### 1. 稳定 UX 架构

这一层记录不应由单个需求或客户随意改变的体验骨架：

- 产品表面、用户角色、核心任务和使用设备；
- 信息架构、页面层级、入口、主导航和上下文导航；
- App Shell、家庭/组织/租户上下文、账户区和返回关系；
- 列表、详情、创建/编辑、任务流、设置、后台工作区等页面模式；
- 保存、取消、返回、确认、危险操作、草稿保留和冲突恢复；
- 加载、空态、无结果、离线、错误、只读、无权限和失权；
- 响应式重排、键盘路径、焦点、触控目标和辅助技术语义。

改变主导航、Shell、产品表面、核心任务路径或跨页面交互语义属于高影响决策，必须先比较方案、说明迁移影响并取得用户确认。

### 2. 共享视觉体系

这一层记录跨页面复用的视觉和组件语言：

- 品牌气质之外的语义色、主题、状态色和层级；
- 字体职责、字阶、字重、行高和数据展示原则；
- 页面宽度、留白、间距、密度、圆角、边框、阴影和动效原则；
- Button、Input、Card、Table、Dialog、Alert、Badge、Toast 等组件的语义和组合规则；
- 页面标题区、筛选区、主操作、危险操作、空态和错误恢复模式；
- 图标、图表、数据可视化和 reduced motion 原则。

代码中的 token、组件和样式文件是实现事实源；框架文档记录它们的职责、语义、真实路径和提升条件，不复制完整值或 API。

局部模式只有同时满足以下条件才提升到共享体系：

1. 至少有两个真实消费者，而不是未来假设；
2. 交互和业务语义一致，不只是外观相似；
3. 所有权和变化原因清楚；
4. 提升不会制造反向依赖或迫使有价值的业务差异消失；
5. 共享后的维护成本低于继续局部共置。

### 3. 客户定制层

这一层承载自研产品品牌和有限客户定制：

- Logo、产品名、品牌主色和辅助色；
- 字体、插画、摄影、图标细节和视觉母题；
- 首页文案、品牌语气、Footer 和品牌归属；
- 可选模块、受控导航项、密度或圆角预设；
- 明确只属于某一客户、行业或业务场景的视觉资产。

客户定制不得绕过权限、错误恢复、危险操作、可访问性、响应式和核心任务语义，也不得把客户专属颜色、文案或素材静默提升为所有产品的共享默认。每个定制项应说明所属范围、替换条件和是否允许提升。

## 三种工作模式

### 模式选择

先判断本次属于：

- **`bootstrap`**：项目没有产品级 UI/UX 框架，框架明显失真，或用户希望重新建立基线；
- **`before`**：在开发活动 TRD 前判断是否存在真实的需求级 UI/UX 设计工作；适用时在既有框架内补足设计，不适用时无副作用跳过；
- **`after`**：在活动 TRD 实现后判断是否发生用户可见 UI/UX 变化；适用时以框架和真实页面为基准审查，不适用时无副作用跳过；
- **不属于本能力**：主要目标是产品定义、技术选型、工程架构、业务实现、Bug 修复或纯视觉素材制作。

未显式指定模式时，根据用户输入推荐一种并说明理由；`before` 与 `after` 通常由用户或外部编排围绕活动 TRD 显式调用。本 Skill 不调用 `dev-workflow`，也不假设调用前后一定存在其它 Skill。复杂任务可以顺序组合模式，但不要机械全部执行。

### 每次开始时的对话协议

在首次正式写入前，先向用户同步：

- 已确认的产品和界面事实；
- 尚缺少或互相冲突的事实；
- 推荐模式和影响到的框架层；
- 当前最重要的问题，而不是泛化的“需要统一”；
- 准备比较或采用的方案；
- 拟创建或更新的设计文档；
- 明确不会修改的代码、页面和流程；
- 需要用户决定的高影响事项。

一次推进一个重要决策，不发大问卷。能从产品文档和现有事实可靠推断的低影响问题，采用最简单的合理默认并说明即可。

## `bootstrap` — 建立最小产品框架

适用于新项目、已有页面像多个独立 Demo、缺少 Shell/导航/页面模式，或现有框架无法承载后续产品表面。

### 1. 建立当前体验地图

按相关性盘点：

- 用户、角色、产品表面、核心任务和主要设备；
- 当前路由、Shell、导航、上下文切换和权限入口；
- 代表性列表、详情、表单、任务流、设置与后台页面；
- 主题 token、字体、组件库、图标、图片和全局样式；
- 已经稳定的页面模式和明显漂移；
- 加载、空态、错误、只读、失权、冲突和恢复；
- 响应式、打印、键盘和辅助技术现状；
- 当前可以复用的真实资产，以及不应继续复制的旧模式。

只读取足以支撑框架判断的代表性页面，不为了“全面”扫描每个组件。

### 2. 提取设计驱动因素

框架选择必须由真实因素解释，例如：

- 用户完成任务的频率、连续性和时间压力；
- 内容浏览与数据管理的主次关系；
- 桌面、移动、平板、打印或专用设备的使用场景；
- 单角色与多角色、单产品表面与独立后台；
- 页面数量、层级深度、信息密度和跨上下文切换；
- 自研产品与客户定制的共享边界；
- 当前代码、组件和迁移成本；
- 明确不需要提前解决的未来页面。

### 3. 比较少量有实质差异的方向

默认提出 2～3 个框架方向并推荐其一。方案必须在产品任务或体验架构上真实不同，而不是只换颜色。至少比较：

- 核心任务和主要用户；
- 产品表面与导航模型；
- 桌面和移动端表现；
- 信息密度与学习成本；
- 内容扩展和管理效率；
- 客户定制成本；
- 当前代码迁移成本；
- 收益、限制和重新讨论条件。

对主导航、Shell、品牌方向和跨产品表面关系取得明确确认后再落盘。

### 4. 建立最小框架与代表性切片

框架只覆盖当前产品和近期真实需求需要的规则。选择一条能覆盖多种页面类型的纵向任务链作为首批验证，例如“工作台 → 列表 → 创建 → 详情”，而不是一次重写所有页面。

输出应区分：

- 已确认且应立即遵循的规则；
- 目标状态但尚未实现的部分；
- 暂定模式和重新评估条件；
- 已知偏差及渐进迁移顺序；
- 明确不属于本轮的页面和视觉重构。

## `before` — 开发前适用性判断与需求级设计

面向活动 TRD 在开发前显式调用。开始时读取活动 TRD、项目级框架、当前路由/Shell/token/组件和直接相关页面，先判断本需求是否真的包含尚未解决的 UI/UX 设计工作；调用本模式不代表必须修改文档。

应执行设计的典型情形：

- 新增用户可见页面、完整流程或重要页面类型；
- 改变用户任务路径、信息层级、导航入口、App Shell 或产品表面；
- 新增复杂表单、数据密集工作区、跨页面交互或移动端任务模式；
- 引入框架尚未定义的状态、失败、恢复、危险操作或辅助技术模式；
- 改变共享视觉语言、品牌表达或客户定制边界；
- 活动 TRD 与既有 UI/UX 框架冲突，或现有框架不足以指导实现。

可以跳过的典型情形：

- 纯后端、数据库、维护命令、内部 API 或无用户可见变化的重构；
- 文案错别字、明确的代码错误修复或不改变交互语义的机械实现；
- 活动 TRD 与既有框架已完整定义 UI 行为，没有新的设计选择。

跳过时简短说明依据并结束，不创建文档、不修改 TRD、不制造流程产物。例如：“本 TRD 不包含新的 UI/UX 设计决策；既有框架和 TRD 已足以指导开发，跳过 before 设计。”

适用时至少回答：

1. 当前需求属于哪个产品表面、用户任务和页面层级；
2. 使用哪个既有 Shell、页面模式和导航关系；
3. 能复用哪些真实组件、token 和交互模式；
4. 正常、加载、空态、校验、提交、失败、只读、无权限、冲突和恢复如何表现；
5. 桌面、移动端、键盘和辅助技术如何完成主任务；
6. 是否真的需要新模式，新模式是局部决定还是跨需求候选；
7. 对既有页面是否产生迁移影响。

需求级决定默认写入活动 TRD 的 UI/UX 或产品行为章节，不另建 `docs/ui-ux/features/` 等平行需求文档。只有已经确认、跨需求稳定且满足共享准入条件的规则，才更新 `docs/ui-ux/framework.md`；不要为每个页面微调制造项目级文档噪声。

## `after` — 开发后适用性判断与体验审查

面向活动 TRD 实现完成后显式调用。读取活动 TRD、项目级框架、最终代码/diff、真实运行页面和适用浏览器证据，先判断本次实际交付是否改变了用户可见 UI/UX。

应执行审查的典型情形：

- 新增或修改页面、用户流程、布局、导航、共享组件或主题 token；
- 改变响应式、状态、错误反馈、恢复、可访问性、品牌或客户定制；
- `before` 阶段形成了需求级 UI/UX 决定；
- 实际实现与 TRD 或框架可能发生偏差。

可以跳过的典型情形：

- 本次没有 UI 实现或用户可见行为变化；
- 实际 diff 只涉及后端、内部工具、生成结果或无体验影响的技术调整；
- TRD 原计划包含 UI，但最终交付没有修改界面。

跳过时说明活动 TRD、diff 或运行事实中的依据，不创建审查档案。

适用时优先使用真实浏览器、截图、路由和代码证据审查：

- 实现是否符合活动 TRD 的需求级设计和项目级框架；
- 产品表面、信息架构、入口、返回关系、Shell、导航和上下文切换；
- 页面标题、操作层级、列表/详情/表单/任务流模式；
- token、排版、间距、密度、组件语义和品牌表达；
- 加载、空态、错误、只读、权限、冲突和恢复；
- 桌面、平板、移动、打印、键盘、焦点、对比度和 reduced motion；
- 客户定制是否泄漏到共享体系；
- 控制台错误、失败请求或数据状态是否造成体验误判。

每个问题必须包含：证据、受影响页面或路径、违反的框架或 TRD 决定、用户影响和最小修复建议。按以下优先级输出：

- **阻断**：核心任务无法完成、严重误导、权限/隐私泄漏、关键移动或辅助技术路径不可用；
- **高优先级**：跨页面不一致、关键状态或恢复缺失、导航和信息层级显著阻碍任务；
- **建议**：不会阻断任务，但有明确一致性、可读性或维护收益。

`after` 默认只读，不直接修复或全量翻新。代码偏差不能静默变成新规范；若证据说明框架本身已经不适用，单独提出“框架演进建议”，比较影响并等待确认。`after` 与开发功能验收关注点不同：它审查实现是否以正确、一致、可用的方式工作，但不能替代真实功能、数据、权限和持久化验收。

## 设计资产与文档

### 默认文档

用户确认后，默认创建或更新一份综合文档：

```text
docs/ui-ux/framework.md
```

只有大型项目确实存在独立维护者、独立产品表面或不同演进周期时，才经确认拆分为导航、视觉、页面模式等多份文档。不要一开始建立空的文档树。

推荐按需包含：

- 文档目标、适用范围和事实源；
- 当前体验事实、现有资产、偏差和待核验项；
- 产品体验原则与设计命题；
- 产品表面、用户任务、信息架构、Shell 和导航；
- 页面模式、状态、反馈和恢复；
- 共享视觉体系与组件语义；
- 响应式、打印和可访问性；
- 客户定制边界与资产策略；
- 代表性切片、渐进迁移顺序和非目标；
- 已确认模式、暂定模式、已知偏差和框架更新条件。

不适用章节直接省略。文档不复制完整 token 值、CSS、组件 API、页面树、逐页截图说明或实现文件清单；应引用真实工程路径。

### 设计债务与演进状态

只维护能指导后续需求的轻量状态：

- **已确认模式**：新需求默认继承；
- **暂定模式**：说明尚未验证的产品表面或设备，以及重新评估条件；
- **已知偏差**：旧页面与框架的差异、用户影响和建议迁移时机；
- **禁止复制**：确认不应继续扩散的旧实现；
- **框架演进建议**：新事实可能要求改变框架，但尚未确认。

不要记录会话流水、内部 Task ID、逐页迁移进度或可从 Git 和代码直接获得的信息。

## 确认门槛

以下高影响事项必须先提供方案、推荐、影响和迁移成本，并取得用户明确确认：

- 新增或重构产品表面、主导航、App Shell 或跨角色工作台；
- 改变核心任务路径、返回关系、危险操作、失败或恢复语义；
- 改变全局 token 语义、品牌方向、字体体系或可访问性基线；
- 引入或替换全局设计系统、组件库、图标体系或主题基础设施；
- 大范围迁移现有页面，或破坏已发布客户定制兼容性；
- 将客户专属资产或局部模式提升为共享默认；
- 正式创建、拆分或大幅改写项目级 UI/UX 框架文档。

普通命名、既有组件的低风险复用、不改变任务语义的局部布局、常规状态文案和页面私有实现可以自主处理。边界不清时，先判断是否会改变其它需求的设计选择；会改变则升级为确认事项。

## 自审与验证边界

完成设计或审查前检查：

- 是否读取了真实页面、路由、token、组件和产品资料；
- 是否清楚区分当前事实、目标框架、局部决定和假设；
- 每条全局规则是否有真实产品驱动因素，而不是流行模板偏好；
- 是否比较了有意义的导航/Shell 方案，而非默认 sidebar 或顶栏；
- 三层边界是否清楚，客户定制是否污染共享体验；
- 是否避免一次性重写、空组件、空文档和假设性基础设施；
- 状态、失败、恢复、移动端、键盘和辅助技术是否覆盖；
- 框架文档是否只记录稳定设计决定并引用实现事实源；
- 是否保护用户已有修改，且没有启动代码实现、提交或其它 Skill。

本能力可以用真实浏览器和截图收集审查证据，但不宣称功能或页面已经完成交付。最终 UI 质量仍需由开发流程在真实服务、真实数据和动态浏览器中验证。

## 常见反模式

- 未读取现有项目就生成“现代、简洁、蓝紫渐变”的通用规范；
- 把每个需求设计成独立产品，或每次重新选择主导航和视觉语言；
- 因为是后台就默认 sidebar，因为是 SaaS 就默认顶部导航；
- 把 shadcn 或其它组件库默认样式当作产品设计；
- 以统一为由覆盖已有有效 token、组件和用户修改；
- 把目标状态、模板或历史稿写成当前实现事实；
- 为未来假设预建大量 token、共享组件、布局层或空文档；
- 因外观相似强行合并业务语义不同的组件；
- 用 Hero、Dashboard、渐变、动效、图表或 AI 对话框代替产品特性；
- 只设计成功路径，忽略加载、空态、失败、权限、冲突和恢复；
- 只看桌面截图，忽略移动任务、键盘、焦点和辅助技术；
- 用静态截图或 Mock 替代开发阶段的真实浏览器验收；
- 把代码偏差静默写回框架，或把 after 审查变成默认全量重写；
- 未经确认写正式框架、改全局导航、启动开发或创建提交。

## 结束状态

本能力结束时只能使用与实际结果相符的状态：

- **已完成**：目标设计决策已确认并按约定写入，或审查范围已完成且证据充分；
- **已设计但未完全核验**：框架或需求级设计已形成，但缺少不可替代的真实页面、素材、目标设备或人工体验确认；
- **阻塞**：核心产品、导航、品牌、可访问性或兼容性决策无法安全推断，必须等待用户或必要资料。

最终说明只汇报确认的框架决定、文档变化、审查发现、真实证据、已知偏差和未解决限制。本 Skill 不暂存、不提交、不推送；如需提交，由独立 Git 步骤处理。
