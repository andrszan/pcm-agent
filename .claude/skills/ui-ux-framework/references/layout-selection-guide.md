# 布局选择指南

本参考用于产品级 UI/UX 框架需要选择或演进 App Shell、导航、页面模式、sticky 区域与滚动模型时。它帮助从项目事实收敛布局决定，不提供按项目类型机械套用的模板答案。

## 1. 先区分三个决策层

### 产品 Shell

Shell 决定跨路由稳定存在的区域、主导航、上下文、账户入口和内容承载方式，例如：

- 顶部全局导航；
- 侧边栏工作区；
- 顶部全局栏与侧边上下文导航的复合 Shell；
- 列表与详情并列的对象工作区；
- 工具栏、画布和停靠面板组成的创作 Shell；
- 移动端底部一级导航与页面栈；
- 面向单一专注任务的最小 Shell。

### 页面模式

页面模式服务具体任务，不等同于整个产品 Shell。常见模式包括：

- 单列阅读或表单；
- 筛选与结果列表；
- 高密度队列或表格；
- 列表—详情；
- 对象详情、时间线与上下文栏；
- 分步任务流；
- 设置分区；
- 卡片或媒体网格；
- 多信号判断与行动工作台。

同一产品通常混合多种页面模式。不能用“卡片式”“双栏”回答全局导航和 Shell 问题。

### 滚动模型

滚动模型必须说明：

- 谁拥有常规纵向滚动；
- sticky 元素相对哪个滚动容器定位；
- 哪些区域保持常驻；
- 是否允许局部独立滚动及其任务理由；
- 宽屏与窄屏是否改变滚动所有者；
- 如何避免无意形成 `body`、`main`、列表三层嵌套滚动。

“导航固定”“主页面可滚动”不足以指导实现。

## 2. 提取布局驱动因素

只使用会改变结构的项目事实：

| 驱动因素 | 需要判断的问题 |
|---|---|
| 产品表面 | 是否存在面向不同角色、权限或工作上下文的独立表面？ |
| 一级入口 | 数量、层级和变化频率是否适合持续横向展示？ |
| 任务频率 | 用户是在少数入口间浏览，还是需要高频跨模块切换？ |
| 对象上下文 | 用户是否需要在队列、消息、搜索和详情之间持续理解同一对象？ |
| 信息密度 | 页面主要是阅读、表单、媒体，还是扫描、比较和批量操作？ |
| 设备与输入 | 主要视口、触控、键盘和窄屏是否要求改变导航形态？ |
| 状态保持 | 筛选、选择、草稿或工作上下文是否需要跨路由保留？ |
| 迁移成本 | 当前 Shell、路由、权限和页面模式需要怎样的渐进迁移？ |

“SaaS”“后台”“现代”“移动优先”等标签只能帮助提出候选，不能替代这些事实。

## 3. Shell 候选与适用倾向

| Shell 候选 | 更可能适用 | 主要风险 |
|---|---|---|
| 顶部全局导航 | 一级入口较少、层级浅、偏浏览或内容传播、页面主要由文档滚动 | 入口增长后拥挤或换行；全局工具与业务导航竞争 |
| 侧边栏工作区 | 模块较多、高频切换、层级较深、桌面操作密集 | 为低频入口占用持续空间；窄屏转换和折叠状态复杂 |
| 顶部全局栏 + 侧边上下文导航 | 多产品表面、多工作区、全局工具与当前任务需要分层 | 双重导航可能重复；必须说明各自职责 |
| 列表—详情工作区 | 邮件、客服、审批、资产、工单等对象驱动任务 | 窄屏需要转为页面栈；多滚动区容易失控 |
| 画布与停靠面板 | 编辑器、设计、地图、流程编排或分析工具 | 键盘、焦点、面板尺寸和溢出管理成本高 |
| 移动端底部导航 | 3～5 个稳定一级入口、单手触达优先 | 入口数量和层级有限；桌面端不能机械放大 |
| 最小专注 Shell | 向导、阅读、播放、创作或高风险确认 | 缺少全局上下文与退出路径时容易困住用户 |

项目可以按产品表面采用不同 Shell，但必须说明边界和共享关系，不能让每个页面自行选择。

## 4. 页面模式选择

- 阅读和资料维护优先保持可读行宽，不因全局 Shell 存在而强行使用全宽。
- 扫描、比较、批量操作和运营队列需要更宽工作区；不能统一套用窄内容容器。
- 列表—详情适合需要保持选择上下文的高频对象处理；窄屏通常转为列表页与详情页堆栈。
- 分步任务流只在步骤具有真实依赖、风险或认知分段价值时使用，不能把普通表单拆成 Wizard。
- 工作台只有在用户需要同时判断多类信号并采取行动时成立；统计卡和图表不能替代任务结构。
- Card、Table、Tabs、Badge、Dialog 等组件是页面模式的实现材料，不是页面模式本身。

## 5. 滚动与 sticky 选择

### 文档滚动

适合内容自然向下展开、页面阅读顺序稳定的场景。Header 可以 sticky，但主内容不再建立独立纵向滚动容器。

### 视口工作区

适合需要常驻导航、工具栏或多个工作区区域的操作型应用。应明确：

- Shell 如何占满或至少覆盖视口；
- 主内容是否是唯一常规滚动所有者；
- Sidebar、Header 和 route toolbar 相对哪个容器保持常驻；
- 弹层或局部面板关闭后焦点回到哪里。

### 独立面板滚动

只在用户必须同时保持多个区域上下文时使用，例如列表与详情并列。每增加一个滚动区域，都要说明其任务价值、尺寸边界、键盘可达性和窄屏替代方式。

优先使用 `position: sticky` 表达容器内常驻关系。只有元素必须脱离正常布局并相对视口定位时才考虑 `fixed`，同时说明占位、遮挡、安全区和缩放行为。

## 6. 收敛顺序

1. 画出产品表面、角色、核心任务和主要路由族。
2. 为每个表面选出具有真实差异的 Shell 候选；没有实质替代方案时不为形式凑数。
3. 选择代表性列表、详情、创建编辑或任务流，检查 Shell 是否能承载真实密度与状态。
4. 明确宽屏和窄屏的导航转换、返回关系和任务等价性。
5. 为每个页面模式指定滚动所有者、sticky 区域和内容宽度倾向。
6. 记录 Current、Target、偏差、迁移切片和重新评估条件。
7. 需要结构或交互参考时，再读取 [`layout-resource-library.md`](./layout-resource-library.md) 中最接近当前问题的单个资源。

## 7. 反默认检查

完成选择前确认：

- 没有因为“后台”默认采用侧边栏；
- 没有因为“官网”默认采用顶部导航和 Hero；
- 没有因为页面较多就增加 Dashboard；
- 没有用 Card、Table 或 Tabs 的组合替代信息架构；
- 没有把参考资源的颜色、尺寸、文案和导航项当作项目事实；
- 没有用“响应式处理”掩盖具体的导航转换和滚动归属；
- 没有让临时最小 Shell 在没有 Target 和重议条件的情况下成为长期默认。
