# solution-design — 项目级技术方案设计

## 定位

这是一个可独立调用的项目级技术设计能力，用于确定跨模块、相对稳定、变更成本较高的技术决定。若用户提供了可读的选模资料，还应先确定项目需要哪些独立交付单元，再为各单元评估适合的模板或独立新建基础，并明确采用方式、派生边界和跨交付单元集成责任。

它不要求事先运行任何需求、拆分、模板选择或设计 Skill，也不规定完成后必须进入哪种开发流程。用户可以只带一句想法开始，也可以提供产品文档、既有代码、历史设计、选模资料或明确的技术约束。没有可读选模资料时仍须独立完成技术方案，只是不能把具体模板选择写成已验证结论。

## 与其它设计层次的边界

本 skill 负责回答：

- 项目需要哪些独立交付单元，各单元应采用哪个正式模板或独立新建基础，以及如何使用这些基础；
- 系统由哪些部分组成，各自负责什么；
- 模块、服务、仓库和外部系统之间如何协作；
- 哪些项目级技术原则必须保持一致；
- 哪些事实由选模资料、项目代码、迁移或可生成契约作为当前阶段的实时真源；
- 哪些关键取舍值得长期记录，以及何时需要重新讨论。

本 skill 不负责：

- 产品需求和功能定义；
- 单个模块即将如何编码的详细实现方案；
- 完整类、函数、目录或页面组件清单；
- 预先维护详细数据库表、字段和索引文档；
- 预先维护完整业务接口列表；
- 将普通实现细节固化成项目级规则；
- 准备、克隆、拉取、同步或修复选模资料指向的外部模板资产；
- 将上游模板变化自动同步到已派生项目；
- 为模板选型绑定固定子 Agent、必经 skill 或运行顺序。

核心原则：

> 开发前文档记录稳定、跨模块、变更成本高的决策；频繁变化且可从代码或工具生成的实现事实不重复维护。

## 技术中立原则

正文不得默认项目使用某种：

- 编程语言或运行时；
- 前端、后端或客户端框架；
- 数据库、缓存、消息系统或 ORM；
- HTTP、REST、GraphQL、RPC 或其它通信协议；
- 测试框架、包管理器、构建工具或部署平台。

具体技术只能来自：

1. 用户明确给出的硬约束、组织要求和新决定；
2. 当前项目代码、依赖、配置、测试、迁移和实际运行行为中的事实；
3. 本次调用中从用户提供的可读选模资料及按需核验的候选工程证据中确认的事实；
4. 当前讨论中经过确认的选择。

用户硬约束和当前项目不可改变的事实是候选准入条件。正式模板只有在满足对应交付单元的条件后才具有复用优先级，不能因已登记而覆盖项目约束，也不能据此绑定其它交付单元的技术选择；对已派生项目，当前项目工程事实高于上游模板声明。

推荐技术时至少说明适用条件、收益、代价、主要风险和替代方案，不因模板已登记、历史惯用搭配或 AI 熟悉某项技术就默认选它。Skill 正文不得硬编码当前模板的 ID、数量、固定组合、技术栈或个人绝对路径。

## 基于传入资料的模板评估

### 资产读取与验证

只有用户或调用方传入了可读的选模资料时，才执行模板评估。先读取实际提供的资料，确认其中声明的候选、定位方式和选型边界，再定位本次相关候选；不预设资料的文件名、目录结构、序列化格式或契约路径。

在 PCM 第 3 步的调用模式中，调用方传入的 `catalog.json` 是本次模板候选真源。Agent 必须读取本次实际传入的 catalog，不依赖历史记忆、缓存或硬编码清单；完成选型后，最终自然语言回复必须明确报告每个适用交付单元的 `repository_id`、`template_id` 和采用方式。该回复面向人阅读，不要求 Agent 输出 JSON，也不要求 Agent 生成独立的基础工程来源文件；编排器会另行使用结构化模型从最终回复中提取已作出的选择。

选模资料用于发现候选并提供选型依据。资料已经明确声明适用场景、关键差异和能力边界时，可以据此完成当前阶段的模板比较；只有资料不足、内部冲突、明确要求进一步核验，或选择风险需要工程证据时，才按需读取候选的依赖、配置、源码、测试、README 或其它可读事实。资料声明和工程事实不一致时，指出冲突及影响，并以实际依赖、配置、源码、测试和可运行行为判断候选当前能力。

不得依赖上次调用的缓存、模型记忆或硬编码候选清单。选模资料不可读或依据不足时，仍继续完成不依赖模板的技术设计，并把模板来源、选型或兼容性核验标记为待确认；本 Skill 不自行 clone、pull、同步或修复外部资产。

### 独立选型、基础来源与采用方式

先根据需求确定项目需要哪些独立交付单元，例如前端、后端、内容站点、任务服务或其它项目；不从现有模板库存反推项目边界，也不机械假定项目必须同时具备前端和后端。然后分别提取各交付单元的工程形态、用户硬约束、组织要求、安全边界和当前项目不可改变的事实。

对每个交付单元独立选型：

1. 排除不满足该单元准入条件的候选；
2. 在合格正式模板中选择能够完成交付且改造成本最低的一项；
3. 不因其它交付单元的框架、数据库、运行模型或历史惯用搭配绑定当前选择；
4. 没有合适的正式模板时，明确提出以最接近模板实质派生或独立新建；
5. 不为假设性需求提前增加交付单元、基础设施或技术复杂度。

模板候选按独立、自包含的工程基础评估。本 Skill 不预设技术组合或推荐套餐；一个项目共同采用多个模板，只表示各交付单元具有各自来源，不形成新的组合资产身份或默认优先级。

每个交付单元分别记录两个维度：

- **基础来源**：`正式模板` 或 `独立新建`。模板必须存在于用户提供的选模资料中，且影响选择的关键事实已由资料充分说明或经过按需核验；
- **采用方式**：来源为正式模板时，记录为 `直接继承`、`裁剪派生` 或 `实质派生`。直接继承保留模板主要工程结构；裁剪派生删除不需要的页面、依赖或基础设施；实质派生替换、扩展或调整关键框架、持久化方式、运行模型或主要工程结构。来源为独立新建时，采用方式记为 `不适用`，不得套用模板继承或派生分类。

采用方式不改变历史来源。发生实质改造时，不得描述成模板原样适用；正式模板如果带来更大偏离、风险或迁移成本，可以不选，但必须说明排除原因、替代方案和额外成本。

### 跨交付单元兼容判断与派生验证

各交付单元独立选型后，再检查它们在当前项目中的实际协作条件。默认允许模板按需求共同使用，但不声称任意模板无条件兼容，也不预先维护完整兼容矩阵。只根据项目需要和工程证据识别真实限制，至少按需检查：

- 通信协议、数据格式和契约真源；浏览器前端不能直接调用只提供原生 gRPC 的后端，除非候选工程证据证明项目具备浏览器兼容传输、网关或其它适配层；
- API 地址、环境变量、跨域和本地联调拓扑；
- 认证、会话、授权、CSRF 与安全边界；
- 文件上传、流式响应、SSE、WebSocket 等特殊能力；
- 构建、测试、部署和运行环境是否协调。

发现硬性不兼容时，说明冲突并重新评估受影响交付单元的候选。没有发现已知冲突只表示选型当前可行，不表示组合已经过运行验证。

选型阶段确认候选是否满足自身准入条件、是否存在已知冲突以及需要补充哪些集成工作。用户确认选型并开始派生后，应在独立项目中根据基础来源和采用方式初始化：正式模板按已确认方式直接继承、裁剪或实质派生，独立新建则创建项目基础，不执行模板裁剪。随后补齐通信和配置，并执行每个所用模板声明的安装、检查、测试和构建命令；任意两个交付单元存在通信或共享运行边界时，还必须验证适用的关键接口、跨域、认证、契约和本地联调，并按项目交付要求验证或明确记录部署边界。尚未执行的集成、部署或交付检查记录为派生初始化验证项，不把它虚构成已验证事实，也不因正常的待验证事项自动否定已经有充分依据的模板选择。

### 选模资料不可用时

如果用户希望选择基础模板，应由用户或调用方传入可读的选模资料；本 Skill 不执行 clone、pull、sync 或资产修复。

- 用户没有传入选模资料，或提供的入口缺失、不可读时，不猜测路径，不用缓存或记忆补全清单，明确报告缺失的事实源，并将相关模板选型标记为未完成。此时可以继续讨论已知需求、硬约束和项目事实，但不得把未验证选择写成正式决定。
- 选模资料可读，但当前选型规则、候选边界或派生责任未声明且影响正式结论时，明确标记相应核验未完成。仍可分析资料中能够确认的候选，但在补齐关键依据前，不把缺失含义写成已验证结论；不依赖缺失依据的项目级设计讨论可以继续。
- 选模资料中的局部候选引用失效、关键事实不足或内部声明冲突时，记录问题并继续评估其它有效候选。受影响候选只能作为未验证参考展示，不能形成正式选择；局部错误不扩大成整个选型失败。
- 所有正式模板都不满足某个交付单元的硬约束时，说明相关候选的排除原因，再针对该单元提出实质派生或独立新建方案，不为了保持模板优先而降低硬约束。
- 已派生项目的模板仓库暂时不可用时，当前项目事实仍然有效；只有重新选型、来源核验或上游差异比较保持未完成。

### 派生后的事实源切换

派生前，用户传入的选模资料用于发现和比较候选；需要时再以候选工程证据补充验证。确认选择或开始派生时，技术方案按交付单元记录基础来源、采用方式、实际采用的技术组成、直接继承内容、修改或移除内容、项目新增内容、跨交付单元集成责任和后续事实源。

派生后，目标项目的代码、依赖、配置、测试、迁移和实际运行行为接管实时事实源；上游模板只保留为来源和历史选型依据。上游模板后续变化不自动同步到项目，不自动触发项目修改，也不自动重写总体技术方案。只有用户明确要求重新选型、重新基线化、替换基础模板或吸收上游变化时，才重新评估迁移、兼容、风险和回退影响；重新评估时也不得把上游当前状态描述成项目当前状态。

## 工作方式

### 1. 读取上下文并复述

每次调用先阅读用户提供的需求、产品说明、当前项目代码、依赖、配置、测试和历史设计。只有用户传入了选模资料时，才重新读取其实际内容，并按资料充分性和本次风险决定是否核验相关候选工程事实；不沿用上次调用缓存。首次回应至少区分：

- **当前事实**：从当前项目，以及适用时从用户提供的选模资料和按需读取的候选工程证据中可以确认的内容；
- **外部约束**：用户指定、组织要求或现有系统强制的条件；
- **模板选型状态**：项目交付单元、各单元已验证候选、基础来源、采用方式、适配证据、主要偏离和未完成核验；
- **跨交付单元协作状态**：已知兼容限制、拟定集成契约和派生初始化验证项；
- **待决问题**：会影响架构基线、项目级架构或跨模块协作的事项；
- **初步建议**：当前推荐的项目构成、各单元基础、理由、明显取舍和能力缺口。

事实冲突时先区分当前状态和目标状态：当前状态由项目代码、依赖、配置、测试、迁移和运行行为等工程证据判定；用户本次明确的硬约束和新决定控制目标状态、候选准入和迁移方向。对派生前候选，先依据本次传入的选模资料判断，必要时再以候选工程证据核验其中声明；历史设计和说明性文档不是绝对事实。正式登记只表明模板是当前可选的独立项目起点，不代表它与其它模板形成推荐搭配。现状与目标不一致时，明确记录差异和迁移影响，不把目标决定描述成已经实现的事实。

### 2. 对话式设计

按风险和依赖关系逐个讨论主题，一次只推进一个重要决策。AI 应主动给出可比较的方案，而不是让开发者从空白开始设计。

通常需要按项目实际情况覆盖：

- 系统上下文、目标与技术约束；
- 项目交付单元、各单元候选模板、基础来源、采用方式、适配证据和派生边界；
- 应用、模块、服务、仓库和外部系统边界；
- 交付单元之间的通信、配置、认证、安全、契约和联调验证责任；
- 关键数据流、调用方向和依赖原则；
- 认证、授权、数据隔离和安全边界；
- 跨模块错误、时间、金额、标识、分页、空值等公共语义；
- 数据持久化原则与迁移方式；
- 接口或消息契约的实时真源与变更协作；
- 配置、环境变量和秘密管理；
- 测试分层、真实联调和用户可感知验收策略；
- 日志、诊断、性能、可恢复性等与项目规模匹配的质量原则；
- 本地开发、构建、发布和最终交付边界；
- 关键风险、暂缓项和后续触发条件。

简单项目不必机械覆盖每一项。只讨论确实影响当前项目的决定，不为了“完整”制造空章节。正式模板应优先进入对应交付单元的比较范围，但其登记状态既不能代替需求适配和工程事实判断，也不能形成跨交付单元的隐含搭配。

### 3. 阶段性同步

每完成一组相关决定，简要同步：

```text
已确认的技术决定：...
项目交付单元及各单元基础来源：...
采用方式、理由与取舍：...
跨交付单元契约与派生验证项：...
模板适配、偏离与未验证事项：...
仍待决定：...
会影响的范围：...
```

如果新决定推翻旧决定，指出被替代内容、影响范围和是否需要迁移，不悄悄覆盖。

### 4. 获得同意后再写文档

在写入正式技术方案前必须：

1. 说明项目级关键决定已经覆盖到什么程度；
2. 说明选模资料读取是否完成，各交付单元的基础来源和采用方式是否明确，跨交付单元契约是否已经覆盖，以及是否仍有阻碍定稿的未验证事项；
3. 指出仍未决定但不妨碍当前定稿的事项；
4. 预览准备写入的文件结构，包括基础模板资产选型与派生边界的落点；
5. 说明为何采用单文件或拆分文件；
6. 明确询问用户是否现在生成或更新文档。

只有用户明确同意后才落盘。用户仍想讨论时继续沟通，不用文档草稿代替对话。模板事实源缺失或无法验证时，不把推测的模板选择写成正式决定。

## 默认产出

默认生成一份综合技术方案：

```text
docs/design/技术方案.md
```

推荐结构：

1. 文档目标与适用范围；
2. 当前事实、约束与假设；
3. 基础模板资产选型与派生边界；
4. 系统上下文和总体边界；
5. 组成部分、职责与依赖方向；
6. 关键流程或数据流；
7. 跨模块技术约定；
8. 数据持久化与迁移原则；
9. 契约真源与变更协作；
10. 安全、配置与秘密管理；
11. 测试、联调与质量策略；
12. 开发、发布和交付边界；
13. 关键决定、风险、暂缓项与更新条件。

“基础模板资产选型与派生边界”在适用时至少按交付单元记录：选型状态、基础来源、采用方式、用于追溯的模板 ID（如有）、实际采用的技术组成和适用条件、硬约束匹配、主要替代方案及未选择原因、能力缺口、直接继承内容、修改或移除内容、项目新增内容，以及派生后的实时事实源。交付单元之间存在通信或共享运行边界时，还应记录相关通信、配置、认证、安全、契约与部署边界，以及尚待执行的派生初始化验证。

在 PCM 第 3 步中，技术方案 Markdown 是人读产物；编排器依据 Agent 最终自然语言回复和本次 catalog 的结构化裁决结果，经过确定性的 repository/template 引用校验后，将机器交接数据写入步骤结果 `steps/03.json` 的 `template_selection`。Skill 不直接创建、维护或声称该机器交接文件，也不能用自身推测替代 Agent 未明确报告的选择。

技术方案必须自成体系。模板 ID 只能用于追溯，不能替代技术内容；读者不打开外部选模资料，也应能理解最终项目构成、各单元选择、边界、偏离、集成责任、风险和实施依据。不复制完整外部清单，只写入当前项目需要长期保留的结论。

当项目复杂度、团队评审边界、前后端变更频率或上下文经济确实需要时，可以拆成前端、后端、接口协作等文件。拆分前说明理由并获得用户同意，不创建没有独立价值的空文档。

## 数据设计边界

默认不创建详细数据库设计文档，不预先维护完整表结构。

技术方案只记录长期有价值的原则，例如：

- 采用何种持久化类型及原因；
- 实时结构事实来自模型、Schema、迁移文件、原生定义或其它项目实际机制；
- 结构变更和迁移如何管理；
- 事务、一致性、软删除、时间、金额、标识等需要统一的约定；
- 备份、初始化、测试数据或兼容策略中确有必要的部分。

字段、索引和关联关系以当前代码与迁移为准。最终交付确实需要 ER 图或数据字典时，应优先从完成后的实现生成，再按用户需要定稿。

## 接口契约边界

默认不在技术方案中维护完整业务接口列表。

项目应根据实际协议选择可执行或可生成的契约真源，例如 API 描述、Schema、IDL、消息定义或代码生成产物。HTTP 项目可以采用 OpenAPI 和交互式接口文档，但这不是对所有项目的强制假设。

技术方案只记录稳定的协作约定，例如：

- 契约真源的位置、所有者和更新方式；
- 路径或方法命名原则；
- 认证与授权传递；
- 成功、错误、分页、时间和空值语义；
- 兼容性、版本和破坏性变更处理；
- 前后端或服务间如何发现并确认契约变化。

并行开发确实需要临时约定时，只在相应模块的实现设计中记录必要草案；运行时代码或生成契约可用后，由它接管实时事实源。

## 开发环境与 `.env`

- 运行方式、数据库、中间件、容器化和部署形态以用户约束、当前项目事实和已确认方案为准。
- 不为当前设计擅自引入新的基础设施、容器编排或外部服务；确有必要时说明收益、成本、替代方案和验证责任。
- AI 可以读取、创建和修改开发 `.env`，并使用已提供的开发凭据进行真实核验，但不能伪造外部凭据。
- 真实 `.env` 必须被 Git 忽略；秘密不得进入方案文档、日志证据、审查上下文或提交信息。
- `.env.example` 只记录变量名、安全示例和说明。

## 更新已有技术方案

更新时：

1. 读取现有方案和当前项目代码、依赖、配置、测试、迁移及可获得的运行事实；
2. 只有本次需要重新评估模板且用户传入了可读选模资料时，按“基于传入资料的模板评估”重新核验相关候选；
3. 区分仍有效的项目级决定、已经漂移的项目事实、新的约束、历史模板来源和当前项目相对原模板的偏离；
4. 对已派生项目，以当前项目工程事实判断现状，不用上游模板覆盖当前实现；
5. 只有用户明确要求重新选型、重新基线化、替换基础模板或吸收上游变化时，才把模板变化转化为迁移建议；
6. 说明变化、原因、兼容或迁移影响和涉及范围；
7. 只修改受影响的项目级内容，不因普通字段、单个接口、内部函数或目录调整重写总体方案。

已派生项目更新时，即使原选模资料暂时不可用，也应根据当前项目事实更新总体方案；需要重新选型、来源核验或上游差异比较时，将其标记为未完成，不猜测上游状态，也不删除已有来源记录。

通常只有以下变化才需要更新项目级方案：项目交付单元、基础来源或采用方式、派生边界、主要语言或框架、仓库形态、服务边界、通信协议、认证体系、主要持久化类型、全局错误语义、关键安全边界或发布形态发生改变。上游模板自身的普通更新不自动构成当前项目方案更新理由。

## 结束方式

完成讨论或写入后，汇报：

- 已确认的项目级决定；
- 各交付单元的基础选型状态、来源、采用方式、适配理由和主要偏离；
- 选中的模板标识或来源（如用户提供且可核验，仅用于追溯）；
- 跨交付单元契约、已知兼容限制和派生初始化验证状态；
- 当前阶段的实时事实源，以及是否已经从模板事实切换到项目事实；
- 创建或更新的文件；
- 仍未决定、未完成核验的事项与触发条件；
- 对现有实现或后续模块设计的影响；
- 用户可以选择的下一步。

不要把任何其它 skill 声明为必须的前置或后续步骤。

## 反模式

- 收到需求资料后直接生成技术方案。
- 把熟悉的语言、框架、数据库或协议当成默认答案。
- 未读取用户本次传入的选模资料，就依据缓存、记忆或硬编码清单推荐模板。
- 在正文硬编码当前模板 ID、数量、固定组合、技术栈或个人绝对路径。
- 选模资料不足、冲突或当前风险需要工程证据时，仍不按决策需要核验候选依赖、配置、源码、测试和实际工程行为。
- 让正式模板覆盖用户硬约束、组织要求或当前项目事实。
- 因前端模板无依据地绑定数据库、后端运行模型或其它交付单元的选择，或反向绑定前端框架。
- 把多个模板共同用于项目描述成官方组合、推荐套餐或新的正式资产身份。
- 声称任意模板组合都已兼容，或没有运行验证却把跨交付单元契约描述成已经验证。
- 在选择前机械假定项目必须同时具备前端和后端，或为了凑齐项目构成引入无关模板。
- 发生实质派生却继续描述成模板原样适用，或因采用方式变化而丢失模板来源记录。
- 选模资料不可用时自行 clone、pull、sync、猜测路径或虚构选型结论。
- 项目派生后继续把上游模板当成当前项目实时真源，或因上游变化自动同步和重写方案。
- 最终方案只记录模板 ID，要求读者查阅外部选模资料才能理解。
- 用一份项目级方案提前规定所有实现细节。
- 同时维护代码事实和手写数据库/接口清单。
- 为标准流程创建空的前端、后端、数据库或接口文档。
- 未经项目事实或用户确认就引入新的基础设施、容器编排或外部服务。
- 把开发秘密写入文档、审查材料或提交。
- 为模板选型新增必经 skill、固定子 Agent，或把本 skill 固定在某套编排顺序中。
