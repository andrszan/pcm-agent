# solution-design — 项目级总体技术方案设计

## 定位

这是一个可独立调用的项目级技术设计能力。它把调用方资料和当前工程事实整理为跨模块、跨交付单元且变更成本较高的技术决定，主要回答：

- 系统由哪些应用、服务、仓库、运行进程和外部系统组成；
- 各部分拥有什么职责、数据和决策，边界在哪里；
- 关键流程、数据和调用如何跨边界流转；
- 身份、权限、错误、状态、恢复、安全和契约语义如何保持一致；
- 重要方案为什么这样选择，何时需要重新评估。

本能力不展开单个需求的完整实现清单，也不以总体方案名义创建业务代码、基础设施或迁移。若问题实质上属于产品范围、具体实现或不可逆迁移决策，应指出所需决定和影响，不把假设写成结论。

## 事实、决定与假设

先读取与当前设计有关的代码、依赖、配置、测试、迁移、契约、运行说明和项目文档。具体技术只能来自：

1. 调用方明确给出的目标、约束和已确认决定；
2. 当前项目可验证的工程事实；
3. 本次讨论中确认的方案取舍。

必须区分：

- **当前事实**：工程现在已经具备的结构和行为；
- **已确认决定**：需要长期保持的选择；
- **目标状态**：已确认但尚未完全落地的方向；
- **假设与待确认事项**：证据不足或仍需选择的内容。

当前代码、配置、迁移、测试和真实运行结果优先描述现状；历史说明和来源资料只提供背景。不得把依赖存在、目录名称、文档目标或模板声明误报成已落地事实。

资料不完整时可以先设计有证据的部分，同时说明缺口会阻碍哪项判断。对低风险、容易调整且不改变系统边界的表达可采用合理默认；涉及主要技术、安全边界、兼容性、跨仓职责、外部副作用或不可逆变化时，应比较方案并取得调用方确认。

## 可接受的输入

调用方可以提供任意组合：

- 产品目标、用户流程、质量要求和交付约束；
- 一个或多个工程、仓库、运行进程或外部系统路径；
- 已确认的技术决定、组织规范和合规要求；
- 现有技术方案及希望更新的范围；
- 运行、联调、故障、性能或安全证据；
- 需要裁决的系统边界或总体技术问题。

## 工作方式

### 1. 建立最小工程地图

只读取足以支撑本次判断的范围，识别：

- 系统上下文、交付单元、仓库和部署边界；
- 应用入口、运行进程、外部依赖和数据事实源；
- 当前主要调用方向、契约和跨单元流程；
- 已确认约束、现状与目标之间的差异；
- 影响总体方案的风险、缺口和待决问题。

不为追求完整而扫描整个代码库，也不编造不存在的模块、接口或运行能力。

### 2. 提取设计驱动因素

按项目实际需要分析：

- 用户流程是否跨越多个交付单元；
- 数据所有权、事务、一致性、并发和迁移约束；
- 身份、权限、隐私、审计和秘密边界；
- 外部系统、异步任务和不可逆副作用；
- 契约兼容性、独立发布和团队协作要求；
- 可用性、性能、可诊断性和恢复目标；
- 当前明确不需要解决的内容。

每个重要结构或技术约定都应能追溯到真实职责、约束或风险。

### 3. 比较重要取舍

承接调用方已确认的技术选择及其实际理由，除非本次明确要求重新评估，否则不重新选型；不补写未发生的历史比较。已有理由只是默认取舍时如实保留，不包装成特殊架构需求。缺少历史理由时不从当前代码反推已确认的选择过程。

只对本次确实需要作出的重要技术决定提出少量可行方案并推荐一个，不为已确定的每项依赖机械比较替代方案。比较说明：

- 要解决的问题和适用范围；
- 收益、代价、主要风险和迁移影响；
- 对现有工程与交付单元的影响；
- 替代方案及未选择原因；
- 重新讨论的可观察条件。

简单项目只保留真正影响系统边界和长期协作的决定，不为“架构完整”增加服务、层、协议或外部资源。

### 4. 明确系统边界与协作

总体方案应按需说明：

- 每个交付单元拥有的职责、数据和外部副作用；
- 允许的依赖与调用方向，禁止绕过的边界；
- 关键流程由谁编排，失败时由谁恢复；
- 同步、异步和批处理协作的选择依据；
- 契约事实源、所有者、认证传递和兼容策略；
- 日志、追踪、健康状态和故障定位责任；
- 本地开发、测试、发布和部署之间的边界。

技术方案记录稳定语义和所有权，不复制完整接口、字段、目录或实现清单；这些内容继续以代码、迁移和可执行契约为实时事实源。业务流程只展开足以解释系统边界、技术取舍、数据所有权、一致性或失败恢复的部分；具体业务资格、逐状态操作和页面行为以产品定义或相应详细设计为准，不在这里维护第二份规则正文。迫使系统采用事务、版本控制、幂等或补偿的业务约束仍应作为设计依据保留，不把关键流程压缩为空泛原则。

## 跨交付单元的用户可见语义

用户流程跨越多个应用、服务或仓库时，不能只描述传输协议。按实际涉及的语义明确事实源、权威判断者、边界映射和展示责任。以下内容用于识别真实设计问题，不要求逐项生成章节；共同语义集中定义，具体流程只补充差异。

### 身份

- 用户、账号、组织、租户、会话和业务主体分别由谁标识与维护；
- 同一主体跨单元使用什么稳定标识，在哪里完成映射；
- 未登录、会话过期、账号停用、身份切换和主体不存在分别如何表达；
- 身份信息变化如何传播，哪些数据允许缓存以及何时失效。

### 权限

- 受保护资源一侧必须拥有最终授权判断，客户端显示和路由守卫只作体验投影；
- 角色、权限和资源范围如何传递，变更后何时生效；
- 禁止访问、资源不存在和不应泄露资源存在性的场景如何区分；
- 批量操作、跨主体操作和后台任务使用谁的权限上下文。

### 错误

- 统一区分输入错误、业务冲突、权限失败、依赖故障、超时和未知错误；
- 明确稳定错误标识、字段错误、用户文案、可重试性和诊断关联信息分别由谁提供；
- 边界转换不得丢失恢复所需信息，也不得向用户或日志泄露秘密和内部实现；
- 局部失败、部分成功和跨单元补偿如何向用户解释。

### 状态

- 区分服务端业务状态、处理进度、客户端临时状态和展示状态；
- 约定加载、空结果、成功、处理中、部分完成、陈旧、离线和失败的含义；
- 明确轮询、推送、刷新或重新进入页面后，用户看到的状态从哪里恢复；
- 多个单元对同一业务状态的命名和可执行操作必须一致。

### 恢复

- 明确哪些操作可以安全重试，幂等依据和重复提交结果是什么；
- 会话过期、版本冲突、网络中断和依赖暂不可用后，用户如何继续而不丢失有效输入；
- 长任务和跨单元流程如何查询进度、恢复、取消或人工介入；
- 危险或不可逆操作的确认、执行结果、补偿边界和失败后指引由谁拥有。

## 默认产出

默认创建或更新：

```text
docs/design/技术方案.md
```

文档面向后续设计和开发，开头先说明适用范围、系统组成与关键技术决定，让接手者快速知道需要承接哪些约束。随后按真实决定和查阅需要组织短段落、列表、表格或必要图示，不预设章节数量、统一模板或篇幅上限。

同一技术决定的边界、依据、代价、失败语义和重新讨论条件尽量集中说明；只有存在独立内容时才拆章节，不在边界、流程、安全、风险和取舍汇总中反复完整描述同一事实。当前事实、已确认决定、目标与假设仍需清楚区分，不以精简为由省略重要约束。

正式方案保留影响设计的稳定能力、限制、兼容条件及必要事实来源。配置和资源明细引用已有权威记录；本轮读取文件的清单、资源探针流水、测试或命令输出、未执行操作列表和临时 Git 状态不作为方案正文。已有流程按职责处理的正常中间状态，不另列为长期技术风险或新增人工确认任务。部署拓扑、运行边界等确实影响系统设计的约束仍应说明，不因尚未实施而一律排除。

复杂项目只有在交付单元或维护边界确有独立价值时才拆分文件。正式写入前应向调用方说明拟落盘范围、关键决定和未决事项；调用方已明确要求创建或更新且范围清楚时，不重复索取确认。

## 更新与验证

更新已有方案时，只修改受稳定决定或工程事实漂移影响的部分，并说明旧结论、变化原因、迁移影响和新的事实源。普通字段、函数或内部文件调整不应触发总体方案重写。

完成前检查：

- 当前事实、目标状态和假设没有混写；
- 边界、数据所有权、依赖方向和恢复责任明确；
- 跨单元用户可见语义不存在相互矛盾的定义；
- 方案取舍有证据、代价和重新讨论条件；
- 文档没有复制可由代码或契约生成的明细；
- 没有写入秘密或未验证的外部事实。

按项目实际工具执行适用的文档、链接、格式和一致性检查。完成后在执行回复中说明主要设计结果、修改文件、实际检查和未核验范围，以及真实存在的未完成或待决定事项；不全文复述技术方案，不为记录执行证据向正式方案追加调查流水。

## 避免

- 跳过工程事实，直接套用固定架构或技术组合；
- 把目标、来源说明或依赖存在写成当前实现；
- 用完整目录、接口或表结构清单替代稳定边界；
- 用假设性扩展引入没有当前依据的基础设施和抽象；
- 只设计成功路径，遗漏跨单元的权限、错误、状态和恢复语义；
- 自动修改业务实现、Git 历史。
