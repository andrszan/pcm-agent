# solution-design — 项目级技术方案设计

## 定位

这是一个可独立调用的项目级技术设计能力，用于确定跨模块、相对稳定、变更成本较高的技术决定。

它不要求事先运行任何需求、拆分或设计 skill，也不规定完成后必须进入哪种开发流程。用户可以只带一句想法开始，也可以提供产品文档、既有代码、历史设计或明确的技术约束。

## 与其它设计层次的边界

本 skill 负责回答：

- 系统由哪些部分组成，各自负责什么；
- 模块、服务、仓库和外部系统之间如何协作；
- 哪些项目级技术原则必须保持一致；
- 哪些事实由代码、迁移或可生成契约作为实时真源；
- 哪些关键取舍值得长期记录，以及何时需要重新讨论。

本 skill 不负责：

- 产品需求和功能定义；
- 单个模块即将如何编码的详细实现方案；
- 完整类、函数、目录或页面组件清单；
- 预先维护详细数据库表、字段和索引文档；
- 预先维护完整业务接口列表；
- 将普通实现细节固化成项目级规则。

核心原则：

> 开发前文档记录稳定、跨模块、变更成本高的决策；频繁变化且可从代码或工具生成的实现事实不重复维护。

## 技术中立原则

正文不得默认项目使用某种：

- 编程语言或运行时；
- 前端、后端或客户端框架；
- 数据库、缓存、消息系统或 ORM；
- HTTP、REST、GraphQL、RPC 或其它通信协议；
- 测试框架、包管理器、构建工具或部署平台。

具体技术只能来自：

1. 用户给出的硬约束；
2. 现有代码和项目配置中的事实；
3. 当前讨论中经过确认的选择。

推荐技术时至少说明适用条件、收益、代价、主要风险和替代方案，不因 AI 熟悉某项技术就默认选它。

## 工作方式

### 1. 读取上下文并复述

先阅读用户提供的需求、产品说明、代码、配置和历史设计。首次回应至少区分：

- **当前事实**：从资料或代码可以确认的内容；
- **外部约束**：用户指定、组织要求或现有系统强制的条件；
- **待决问题**：会影响项目级架构或跨模块协作的事项；
- **初步建议**：当前推荐方案、理由和明显取舍。

不要把历史文档当成绝对事实；已有代码、可执行配置和用户的新决定可能更权威。发现冲突时先说明冲突及影响。

### 2. 对话式设计

按风险和依赖关系逐个讨论主题，一次只推进一个重要决策。AI 应主动给出可比较的方案，而不是让开发者从空白开始设计。

通常需要按项目实际情况覆盖：

- 系统上下文、目标与技术约束；
- 应用、模块、服务、仓库和外部系统边界；
- 关键数据流、调用方向和依赖原则；
- 认证、授权、数据隔离和安全边界；
- 跨模块错误、时间、金额、标识、分页、空值等公共语义；
- 数据持久化原则与迁移方式；
- 接口或消息契约的实时真源与变更协作；
- 配置、环境变量和秘密管理；
- 测试分层、真实联调和用户可感知验收策略；
- 日志、诊断、性能、可恢复性等与项目规模匹配的质量原则；
- 本地开发、构建、发布和最终交付边界；
- 关键风险、暂缓项和后续触发条件。

简单项目不必机械覆盖每一项。只讨论确实影响当前项目的决定，不为了“完整”制造空章节。

### 3. 阶段性同步

每完成一组相关决定，简要同步：

```text
已确认的技术决定：...
理由与取舍：...
仍待决定：...
会影响的范围：...
```

如果新决定推翻旧决定，指出被替代内容、影响范围和是否需要迁移，不悄悄覆盖。

### 4. 获得同意后再写文档

在写入正式技术方案前必须：

1. 说明项目级关键决定已经覆盖到什么程度；
2. 指出仍未决定但不妨碍当前定稿的事项；
3. 预览准备写入的文件结构；
4. 说明为何采用单文件或拆分文件；
5. 明确询问用户是否现在生成或更新文档。

只有用户明确同意后才落盘。用户仍想讨论时继续沟通，不用文档草稿代替对话。

## 默认产出

默认生成一份综合技术方案：

```text
docs/design/<项目名>-技术方案.md
```

推荐结构：

1. 文档目标与适用范围；
2. 当前事实、约束与假设；
3. 系统上下文和总体边界；
4. 组成部分、职责与依赖方向；
5. 关键流程或数据流；
6. 跨模块技术约定；
7. 数据持久化与迁移原则；
8. 契约真源与变更协作；
9. 安全、配置与秘密管理；
10. 测试、联调与质量策略；
11. 开发、发布和交付边界；
12. 关键决定、风险、暂缓项与更新条件。

当项目复杂度、团队评审边界、前后端变更频率或上下文经济确实需要时，可以拆成前端、后端、接口协作等文件。拆分前说明理由并获得用户同意，不创建没有独立价值的空文档。

## 数据设计边界

默认不创建详细数据库设计文档，不预先维护完整表结构。

技术方案只记录长期有价值的原则，例如：

- 采用何种持久化类型及原因；
- 实时结构事实来自模型、Schema、迁移文件、原生定义或其它项目实际机制；
- 结构变更和迁移如何管理；
- 事务、一致性、软删除、时间、金额、标识等需要统一的约定；
- 备份、初始化、测试数据或兼容策略中确有必要的部分。

字段、索引和关联关系以当前代码与迁移为准。最终交付确实需要 ER 图或数据字典时，应优先从完成后的实现生成，再按用户需要定稿。

## 接口契约边界

默认不在技术方案中维护完整业务接口列表。

项目应根据实际协议选择可执行或可生成的契约真源，例如 API 描述、Schema、IDL、消息定义或代码生成产物。HTTP 项目可以采用 OpenAPI 和交互式接口文档，但这不是对所有项目的强制假设。

技术方案只记录稳定的协作约定，例如：

- 契约真源的位置、所有者和更新方式；
- 路径或方法命名原则；
- 认证与授权传递；
- 成功、错误、分页、时间和空值语义；
- 兼容性、版本和破坏性变更处理；
- 前后端或服务间如何发现并确认契约变化。

并行开发确实需要临时约定时，只在相应模块的实现设计中记录必要草案；运行时代码或生成契约可用后，由它接管实时事实源。

## 开发环境、Docker 与 `.env`

- PCM 开发环境默认使用已准备的数据库和中间件服务。
- Agent 应读取配置、连接并验证已有服务，不自行启动依赖容器。
- Docker 和 Docker Compose 不属于默认开发流程，不默认生成 Dockerfile 或 Compose 文件。
- 容器化交付仅在用户明确提出时作为独立交付设计讨论。
- AI 可以读取、创建和修改开发 `.env`，并使用开发凭据进行真实联调。
- 真实 `.env` 必须被 Git 忽略；秘密不得进入方案文档、日志证据、审查上下文或提交信息。
- `.env.example` 只记录变量名、安全示例和说明。

## 更新已有技术方案

更新时：

1. 读取现有方案和当前代码/配置；
2. 区分仍有效的决定、已经漂移的事实和新的约束；
3. 说明变化、原因与影响范围；
4. 只修改受影响的项目级内容；
5. 不因普通字段、单个接口、内部函数或目录调整重写总体方案。

通常只有以下变化才需要更新项目级方案：主要语言或框架、仓库形态、服务边界、通信协议、认证体系、主要持久化类型、全局错误语义、关键安全边界或发布形态发生改变。

## 结束方式

完成讨论或写入后，汇报：

- 已确认的项目级决定；
- 创建或更新的文件；
- 仍未决定的事项与触发条件；
- 对现有实现或后续模块设计的影响；
- 用户可以选择的下一步。

不要把任何其它 skill 声明为必须的前置或后续步骤。

## 反模式

- 收到需求资料后直接生成技术方案。
- 把熟悉的语言、框架、数据库或协议当成默认答案。
- 用一份项目级方案提前规定所有实现细节。
- 同时维护代码事实和手写数据库/接口清单。
- 为标准流程创建空的前端、后端、数据库或接口文档。
- 把 Docker 当作开发数据库和中间件的默认启动方式。
- 把开发秘密写入文档、审查材料或提交。
- 把本 skill 固定在某套编排顺序中。
