# 前端能力对比验证

使用 `evals.json` 的同一任务、输入副本、模型、插件版本、技术栈及浏览器条件比较：

- 实验组加载本 Skill，并实际调用其要求的插件入口。
- 验证封装能力价值时，基线组仅实际调用 `ui-ux-pro-max:ui-ux-pro-max`，不读取本 Skill；改进现有版本时，先保存旧版 Skill 及引用资源，以旧版为基线。两种比较分别标注，不能混算，也不能用完全不使用插件的结果冒充基线。

每例使用独立输出目录；精修例先分别复制原始夹具，不让两个执行者编辑同一文件。浏览器分别使用专属页面或命名 session，不能通过全局关闭清理。截图和运行结果放在根工作区 Git 忽略的 `.test-screenshots/` 下独立评估目录，不写回夹具或提交结果流水。

先检查真实调用接线：开发角色工具包含 Skill，执行记录中出现指定入口的实际调用及成功结果。角色定义或插件变更后使用新会话验证，旧会话可能缓存工具列表；不能以只读 Skill 正文代替。

对功能断言优先用实际浏览器行为或确定性检查，静态关键词不能证明调用、交互和导航吸顶。精修例使用短视口形成真实滚动，不靠保留无意义留白制造长页面。视觉比较采用一致视口与相近状态，盲评时隐藏实验组标签；评审围绕用户任务和设计约束，不追求固定分数。

保留调用、交互、渲染、耗时和真实缺口的相称证据。工具中断、API 重试和未覆盖范围单独说明，不将它们直接归因为 Skill 效果。单次样例通过不能证明普遍视觉提升或效率收益。

用创建工具提供的结果查看器展示原始输出与断言结果。Skill 维护时的对比评估不构成产品运行中的人工审批环节。

新增用例覆盖高频调度、内容阅读和已确认绿色品牌的文案精修。前两例检查首次方向比较与产品依据，后一例检查不重新选型、减少重复解释且保留必要规则；不是要求不同产品必须使用不同色相。首次比较的执行记录只能证明选择过程，不能单独证明视觉质量。

文案评估结合渲染与真实任务，逐项指出重复解释和必要信息。不要用总字数下降作为通过标准：阅读正文、内容摘要、业务口径和风险提示可能正是产品核心。装饰性眉题、重复副标题、按钮教学与口号应有具体删除依据；缩小字号、降低对比或隐藏关键规则不算精简。

跨产品视觉比较由评审结合各自任务、截图和实现判断，并说明构图、密度、排版与表面的差异或合理相似。组件层次、语义配色、图形适配和动态反馈在实际渲染与操作中判断，不按图片或特效数量计分。行为断言、视觉判断与跨项目结论分别记录。
