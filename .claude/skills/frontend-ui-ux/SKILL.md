# 前端设计与实现

## 定位与边界

把当前授权范围内的产品任务，做成可理解、可操作、有产品辨识度的前端成果。直接调用 `ui-ux-pro-max` 插件，补充项目特有的产品约束、实现协作和体验验证；不复制插件知识库，也不以调用插件代替判断与实现。

官网、内容产品、后台与平台都需要有辨识度的组件和交互，不把高频工具等同于未经设计的默认控件。精致感落实在排版、表面层次、色彩关系、几何细节、状态反馈和动效节奏上；按使用频率和操作风险调整表达强度，而不是按产品类别取消设计。

本能力可独立处理 HTML 原型、正式框架前端、局部页面或组件精修，以及纯品牌／主题任务。只完成调用方授权的范围：设计任务不擅自扩成开发，局部修改不重做全局设计。已有原型转正式框架时，复刻用户看到和使用的结果，不机械复制 DOM 或演示代码。

不重新定义产品范围，不管理需求清单或运行状态，不实现服务端业务和数据库，不自行更换技术栈、迁移稳定架构，不承担全产品质量审计，不执行 Git 写操作。模拟交互、隐藏按钮和浏览器成功提示分别不能证明真实持久化、服务端权限或外部调用完成。

## 执行

### 1. 明确任务与设计依据

读取目标工程规则、当前变更、实际技术栈及与任务直接相关的产品资料、原型、页面、组件和接口。弄清使用者、核心任务、结果、范围、必要状态和目标设备。

区分首次设计、原型迁移、既有界面精修和品牌／主题任务。已有产品的真实设计、明确品牌及已交接的选定方向作为基线；同视口、同内容比较原型迁移结果。模板默认、检索首选和尚在探索的首稿不自动成为已确认品牌。信任前序有效交接，不要求补做历史选型证明，也不因插件推荐不同而推翻已确定设计；明确本次需要保留的设计关系及允许校准的实现细节。

普通、可逆的布局与交互细节自行收敛。权限、关键业务状态、操作后果等已经影响本次体验时，先按资料解决；超出授权且无法安全决定时，讲清具体问题、事实、选项、影响与推荐。不要把每个样式选择交给调用方，也不要把关键规则留到代码写完再猜。

### 2. 实际调用插件，形成具体设计

先通过 Skill 工具调用 `ui-ux-pro-max:ui-ux-pro-max`，再按任务选择适用专项入口。调用方式和兼容性见插件调用参考。不可调用时如实交接缺少什么，不把直接读文件、运行搜索脚本或仅在回复中写出名称冒充 Skill 调用成功。

用产品对象、核心任务、内容密度、使用环境与品牌依据指导插件检索，不把行业标签或检索排名当作设计决定。首次建立且没有明确品牌／视觉方向时，获取建议后简短比较少量适合产品的不同方向，通常两个即可；比较同时包含色彩关系和排版、密度、构图或表面中的非色彩维度：既不能只给同一模板换主色，也不能只换布局而直接沿用检索首选配色。依据真实任务选择一个再实现，具体方法见视觉参考。已有明确方向时直接继承，只查询当前相关维度；普通局部修改不重新选型。

用简洁的专业表述确定信息与操作主次、布局、视觉锚点、术语、密度及必要状态，然后实现；不默认创建设计报告。设计术语必须落实为可观察的结果，不用“高级、现代、精致”代替决定。

### 3. 实现或专业委派

遵循真实工程归属，复用适用组件与资源，完成页面、状态、响应式和授权的数据接入。选当前任务的关键组件先打磨，再推广到同类：卡片的内容与操作层次、按钮的主次与色彩关系、表单及选择控件的状态、图标与文字的几何对齐。不能以“后台需要克制”为由直接交付默认组件拼装，也不为变化让同义操作随意换色。

主动设计关键操作的即时反馈和状态变化，按动效参考处理悬停／按下、选择、展开、加载及结果之间的连续性。合适位置可以有细腻弹性、图形变化或轻量趣味，但不添加无需求的交互、不伪造成功或等待。主动使用定制 SVG、协调的多色图标、插画与生成图片丰富当前产品表面，选择适合品牌、内容和组件的表达，不等待调用方逐张点名；通过工作区可用媒体工具取得并检查真实资产。媒体、图形与动效服务理解和品牌，保持减少动效、键盘与触控下的完整可用性。

前端先行时，集中模拟数据访问与必要状态，确保创建、修改、读取和跨页面操作连贯；不为原型造复杂假后端。可继续接入真实服务，不把模拟逻辑散落在组件里。已有真实接口时按当前授权接入。

先做文案取舍：标题、控件和布局已说明的内容，不再用副标题、卡片介绍、装饰性英文小标题或页脚总述重复解释。说明文字只有在帮助理解业务信息、作出选择、完成输入或处理风险／结果时才保留，不为填充版面生成口号和小字；通过删除或重组减少负担，而不是缩小字号或把废话塞进 Tooltip。必要标签、规则、风险与失败恢复仍须清楚可见。内容型页面的正文与有事实的信息介绍不按冗余说明删除。

**页面始终使用正式业务内容。** 不在标题、角标、提示、按钮、空态等位置加入 Demo、原型演示、模拟数据、仅供展示、等待接入后端等开发过程说明，也不换成隐晦的同义提示。实际模拟范围和未完成能力在开发交接中说明。

委派前按任务模板写清产品目标、设计依据、关键行为、工程归属和局部验证。任务中明确写出需要调用的完整插件 Skill 名称，并要求实际调用；检查接收方具备 Skill 工具和插件。传递本能力中适用的约束或可读取的文件路径，不假设子 Agent 继承主会话。受限开发角色不再委派，整合与独立评审由主 Agent 负责。

先统一导航、主题、共享组件和数据边界，再按内聚模块并行；共享文件明确负责方，不为并行把一条连贯任务机械按页面拆散。并行只在工具、范围和资源允许时使用。

### 4. 真实预览与有界修正

用可用真实浏览器完成当前范围的主要任务，实际读取代表性渲染或截图；检查滚动后的导航、相关状态、宽窄屏和原型保真。执行相称类型、构建和功能检查，不能以构建、DOM 或组件测试代替体验验证。

完整原型、完整前端或重要页面／模块交付时，主 Agent 安排独立体验评审，按 [评审指令](agents/experience-reviewer.md) 提供任务、设计依据与有效运行证据。独立评审用分离上下文，不要求外部服务或固定角色；普通局部修改以自查及相关验证为主。执行角色无法委派时交接给主 Agent，不冒充独立评审完成。

以实际渲染和完整交互片段检查关键组件，不能只因功能能用或首稿已生成就结束。层次平淡、对齐粗糙、反馈生硬、动态衔接或文案仍有具体问题时，按内聚问题做下一轮精修，复验后再判断；需要时继续多轮，不把独立评审当作形式步骤。保留已经成立的设计，不为提高自评分反复推翻。关键组件与交互满足产品表达、操作和可访问性要求，采纳的问题解决且验证通过即可结束；等价偏好、堆装饰或“还能更好”不足以无限追加轮次。必要浏览器或运行条件缺失时保留未验证范围，不删减完成条件。

## 交付

交付当前任务的可运行 HTML 或正式前端代码、必要资产和测试。首次选定的视觉方向、关键产品依据与保留边界在正常交接中简述，需要长期使用时沿用已有文档位置；不另建候选报告、完整 token 清单、组件词典、迭代流水或第二套设计真源。

简洁报告成果位置、实际验证、重要差异与未完成事项。清楚区分独立前端体验完成、局部接入完成和真实业务集成完成。设计判断、实现与验证由执行 Agent 负责，不要求调用方或流程负责人再作审美批准、重跑验收或逐项复述完成证据。
