# dev-workflow — 自适应开发与可验证交付

## 核心承诺

`dev-workflow` 独立完成从理解目标、实现、验证到交付收敛的开发闭环。需求功能完成、核心路径与适用关键风险有可信证据、没有已知阻断缺陷或未决重大选择，即可标记为“已完成”；不以每一种验证方法或观察周期全部结束为前提。

先保护用户已有工作和秘密。识别每个相关仓库及其 staged、unstaged 和 untracked 状态；无关修改不得覆盖、回退或混入本次交付。禁止破坏性清理和秘密泄露。本 Skill 保留经过验证的待提交变更，不暂存、不提交、不创建或切换分支、不合并、不推送。

普通运行不创建阶段报告、任务文件、Manifest、Run ID、尝试记录或独立审查档案。代码、Git、活动需求资料和测试输出是主要恢复来源；确需长期协作记录时只使用项目已有约定。

## 理解范围与适用闸门

输入可以是活动 TRD、Backlog 大需求、功能描述、Bug、重构目标、Issue、验收反馈或代码上下文。开始前读取足以判断目标和证据的资料：

- 当前需求、验收条件、产品与设计约束；
- 相关代码、配置、接口、数据模型、迁移和测试；
- 项目规则、运行方式、目标仓库和用户已有修改；
- 权限、兼容性、依赖服务、真实数据与验证入口；
- 对 UI 范围适用的现有页面、Shell、术语、组件、素材和稳定交互模式；
- 与当前范围相关、可访问且可核验的工程架构资料。

有此类工程架构资料时，按需读取模块职责、公开能力、依赖方向、目录职责、文件归属和 Current/Target 差异，并与当前代码、契约、测试和运行事实交叉核验；资料未提供、不相关、漂移或不足时，仍独立工作，只暴露无法安全判断的高影响缺口，不索取固定文件、步骤或其它 Skill。

没有正式 TRD 时，把用户目标、Bug 复现条件或重构约束转换为可检查的完成条件。资料缺失时根据代码和运行事实继续；只有会改变产品结果、数据语义、安全、兼容或不可逆方向且无法安全推断的决定，才请求用户裁决。

闸门用于识别必要交付证据，不是穷尽验证方法的清单。先区分功能缺失、真实缺陷、关键证据缺口与非阻断的方法限制；已有有效证据足够时，不反复补验。业务期限和冻结历史不得篡改，但可用受控测试数据、测试时钟或真实服务的短窗口验证时间边界，并明确证据范围；不冒充长期现场观察，也不要求特定开发样本等满业务周期。

闸门按行为影响判断，不按改动行数机械套用：

- 纯内部重构且不改变用户可见行为时，执行相关代码、接口和回归验证，不强制浏览器、截图或 UI 评价。
- 涉及 UI、用户交互、用户可见文案或浏览器结果时，体验闸门和浏览器证据适用。
- 依赖数据库、服务、中间件、接口、权限或持久化时，真实环境与数据闸门适用。
- “改动很小”“组件测试已过”“辅助工具不可用”都不能用于跳过本来适用的证据。

## 实现与协作

围绕目标完成必要代码、配置、迁移、初始化数据和测试。实现优先落在其归属模块内；跨模块协作使用稳定公开能力，需突破稳定边界时作为设计偏差或架构 delta 处理，不为架构整洁进行无关重构。验证随实现进行，失败后先定位和修复，再重跑失败项及受影响回归。不要为当前任务引入无关抽象、基础设施或技术栈。

### README 稳定入口合同

README 是对应仓库的稳定入口、使用合同和文档地图，不是需求流水或所有交付信息的默认收纳位置：

- 根仓 README 面向首次接触项目的客户、负责人和接手者，使用通俗语言维护产品定位、目标用户、当前可用范围与主要限制、仓库组成、最短全栈启动或正常使用路径及权威文档入口；
- 前端、后端等独立业务代码仓 README 面向对应仓库的开发与运行维护，维护本仓职责、环境要求、最短启动与联调方式、配置和秘密边界、代码入口、验证、构建及运行责任；
- 当项目定位或范围、用户可发现入口、安装/启动/配置前置、稳定用户行为或限制、开发数据的恢复/核验入口、账号交接入口、运行责任、摘要或权威文档链接变化，并影响某个仓库 README 所承载的稳定合同时，必须更新该 README；只改变权威详细文档内部内容且 README 中的稳定摘要、入口和链接不变时，不机械修改 README；
- 纯内部重构、测试日志、截图、一次性排错过程、运行输出和历史演进不写入 README。详细账号矩阵、对象清单、复杂恢复、安全操作和专项验收优先维护在项目已有受跟踪文档中，README 只保留必要摘要和可发现链接；项目已明确选用 README 直接承载且内容规模适合时可以保留；
- 修改稳定事实时必须改写现有段落并删除失效、重复、模板或冲突说明，不按需求或 BR 编号在末尾持续追加，也不复制 Backlog、TRD、工程架构、OpenAPI 或专项文档的详细正文；
- 完成前实际核验受影响的 README 命令、链接和关键前置条件。稳定入口或使用合同没有变化时，README 保持不变不构成文档缺口。

不强制所有项目使用相同标题、文档目录、恢复命令或额外 Manifest。一项详细事实只保留一个权威位置，其它 README 通过摘要和链接引用。

Leader 始终负责理解完整范围、整合实现、自审、验收证据和结束状态。边界清楚、内聚且可独立验证时，可以调用 `Agent(dev)`；派发内容应包含目标、约束、可修改范围、验证方式和回报要求。Leader 不为体现多 Agent 而强制派发，也不重复实现同一工作。

需要独立审查时，可以调用 `Agent(reviewer)`，也可以复用仍适用且覆盖完整范围的已有独立审查结果。对应 writer 交还、格式及适用静态检查完成、目标范围形成稳定的可审查版本后再派发；审查期间不并行修改该范围，不相交工作仍可继续。

完整性审查必须读取权威工作区的完整最终变更，包括未跟踪文件内容，并获得验收条件、适用架构约束和已有验证证据。同一仓库按风险域并行审查时，指定一位 Reviewer 承担完整性责任；其余专项 Reviewer 围绕本域条款、相关 diff 和跨模块合同取证，遇到具体跨域风险再扩读，不重复承担全量审查。专项结论不能替代完整性覆盖；隔离 checkout 的提交基线不能代表另一个工作区的未提交实现。

## 需求与代码质量闸门

- 每个适用完成条件都要建立 `条件 → 实现位置 → 验证方式 → 实际结果` 的证据映射。
- 有适用工程架构约束时，增加 `架构约束/模块归属 → 改动位置与依赖关系 → diff/导入/调用证据 → 结果` 映射。
- 有真正适用于本需求的已确认 Target 或有依据的默认 Target 时，增加 `体验决定（来源、Current/Target、适用范围；默认 Target 含依据与重议条件） → 本需求可观察结果 → 实现位置 → 真实浏览器与截图证据 → 实际结果` 映射；实现不得静默偏离，确需偏离时按活动 TRD 和影响范围处理。不因此扩大为全局重构，截图也不能替代真实动态行为验证。
- 实际运行与改动相关且项目适用的单元、集成、接口、E2E 和回归测试，以及静态检查、类型检查和构建；不能只选择最容易通过的一项。
- 写了但未运行的测试、代码阅读和“理论上正确”不算验证。Agent 已提供可定位的真实命令和结果，且相关代码、依赖、配置、迁移、测试与环境没有影响结论的变化时，Leader 复用该证据，不因执行者变化重复运行；后续变化只使受影响证据失效。
- Bug 或高回归价值行为应增加或更新能防止复发的测试；清除本次产生的临时代码、调试输出、硬编码假数据和绕过实现。
- 每次运行第三方工具、依赖安装、测试、构建、覆盖率或浏览器验证后，检查本轮新增的未跟踪项。确认是可重新生成且无需版本控制的产物时，按项目 `AGENTS.md` 自动在其所属 Git 仓库根 `.gitignore` 添加并复验最小规则；不重复已有规则，不用宽泛模式隐藏交付内容，不删除产物，也不取消跟踪已有文件。
- 项目已有覆盖率阈值时必须满足；没有阈值时按风险覆盖核心成功路径、关键失败路径、状态流转、权限、数据一致性和相邻回归，不凭空发明统一比例。
- 测试、检查或构建失败后，修复并重跑失败场景和受影响范围，不能用一次较窄的通过掩盖仍存在的相关失败。

## 真实环境与数据闸门

需求依赖服务、数据库、中间件、接口或持久化时，必须使用项目真实支持的开发环境证明集成可用：

- 按项目方式启动服务，检查健康状态、启动日志和相关运行错误；
- 使用真实开发数据库和中间件，执行必要迁移与可重复初始化数据；
- 使用适用的真实开发账号、角色、权限和业务数据完成任务；
- 需求创建或调整登录、角色、权限及其 Seed/fixture 时，为最终保留在交付开发数据中的普通用户、业务角色、产品管理员和产品超级管理员准备项目专用、不冒用真实个人身份、真实存在且可登录的开发账号；这些账号及密码是受版本控制的产品交付信息，不得改称演示账号、体验账号或假账号，也不得附加演示租户、隔离业务数据、生产禁用 Seed 等部署阶段限制；
- 在项目约定的受跟踪 README 或独立账号文档中记录每个交付开发账号的适用开发环境、登录入口、角色、账号、密码、初始化、恢复或重建方式及必要已有开发数据说明。开发完成前从正常入口逐个核验账号真实存在、密码可登录、角色一致、已有开发数据可见、代表性允许行为及适用的关键越权拒绝；创建、修改或删除账号时同步文档。账号只存在于数据库、一次性命令输出或 Agent 上下文中，不算完成交接；临时测试中创建后删除或事务回滚、未保留在最终交付开发状态中的短期账号无需逐个记录；
- 项目采用的初始化、恢复或重建方式必须重复执行不新增重复账号、不覆盖其管理范围外的已有账号或数据，并保持项目已有安全要求；
- 调用真实接口并核对响应，写入后通过重新查询、刷新、重新进入或数据库状态确认持久化；
- 前后端最终联调不得用 Mock、拦截响应、内存集合、假 Repository 或硬编码数据替代真实后端与真实数据；
- 自动化测试可以按项目现有方式使用隔离测试库；依赖持久化且有用户可见流程时，最终开发验收必须使用实际开发配置连接开发库，在真实浏览器中从正常入口完成核心成功流程，通过刷新或重新进入确认结果仍可读取，并在证据中记录脱敏的环境和数据源标识；
- 核心成功流程自然产生可安全保留的记录时，可以作为当前开发验收现场保留；只有接手者自主体验或稳定复验确实需要，且该记录已经纳入项目可重复执行的初始化、恢复或重建方式及受跟踪说明时，才作为最终交付开发数据保留。其它临时数据应按项目方式复用、清理或回滚，不得无界累积、泄露敏感信息或保留资金、真实外发、权限提升、一次性凭据等高影响副作用。留存数据只是验收证据链的一部分，不能替代浏览器、接口和持久化验证；
- 运行实例与本地定义不一致时，先核对实际路由或契约；确认实例陈旧后，只重启本会话启动或归属明确的服务再验收；
- 主动解决可恢复的配置、启动、迁移和测试数据问题，不能把普通环境准备留给用户。

### 项目数据基线与交付恢复

当前需求建立或调整完整项目数据基线时，交付结果是：接手者拿到当前项目、按受跟踪说明准备真实服务后，执行一个初始化命令或等价单一入口即可得到完整、自然、可操作的现场；有登录能力时可用交付开发账号从正常入口登录并完成主要任务；明确放弃现场后，可通过受保护的重置入口清空约定项目环境并恢复完整起点。不能只交付原开发机器中的一份数据库、若干测试账号或几个需要自行猜测顺序的脚本。

先核对已有迁移、Seed、fixture、账号、业务记录、所需文件、对象存储、运行说明和测试，复用有效能力并收口为一个项目级入口；不新增互相覆盖的平行脚本。默认实现初始化与重置两种语义，命令名和技术栈由项目决定；除非需求明确，不增加向已使用现场合并新版基线的 `ensure` 模式。命令自身失败后的受控续接仍属于必需恢复行为。

按实际项目履行以下合同：

- 初始化编排必要结构、参考数据、身份、关系、业务内容及依赖文件；已有完整初始化时安全结束，正常使用后重跑不重复创建、覆盖编辑／消耗／已读／删除或恢复被撤销权限，未知已有数据不被认领或清空。
- 重置的删除边界在操作前明确：约定整个项目环境时，必须包括使用者后来新增的账号、记录、会话、任务、上传文件和派生对象，而非仅删除 Seed 初始对象；严格保护其它环境及共享资源。实际目标、归属、必要恢复资源和确认均通过后才能删除，取消或预检失败无破坏性影响。
- 数据应符合产品领域的名称、数量、日期、状态和关系，并留下主要任务可操作的起点；不以需求编号、fixture 标签、随机海量记录、技术失败状态堆砌代替数据质量。近期安排在初次建立／重置时合理，普通重入不改变历史。
- 业务确有对象存储或本地持久化文件依赖时，源文件或可靠生成输入、真实对象、处理结果和业务绑定必须一起恢复并可从正常路径读取；只有数据库引用或临时 URL 不算完成。没有相关业务时不额外创建媒体或存储依赖。
- 初始化和重置具备与风险相称的互斥、在途写入保护、失败反馈和重试；跨数据库与对象存储不假设原子回滚，部分删除后不得丢失恢复依据或提前宣称成功。
- 资源采用稳定产品级身份，开发与测试的写入和清理范围清楚，不把需求编号固化为长期数据库、账号或存储名称。可操作开发基线与确定性测试 fixture 分离，测试负责自己的数据和对象，不无界累积。
- README 或其可发现的受跟踪说明包含环境、前置服务、单一入口、数据影响、账号入口、主要已有任务、成功判断、失败恢复与再次验证方式；适用账号密码按项目交付规则记录，基础设施凭据继续保密。

完成前实际验证：从项目专用空环境建立完整基线；重复初始化；正常使用并修改／删除数据后重跑初始化；在目标内新增账号、业务记录及适用文件后明确重置并再次初始化；证明范围外哨兵数据和对象不变。验证错误目标、取消、并发及具有长期回归价值的失败／中断恢复场景。每个交付角色从正常入口登录，检查角色、数据、允许与拒绝行为及主要任务；有媒体时验证真实文件、处理状态、绑定与权限。通过刷新、重进、接口或数据状态核验持久化，必要截图按项目规则保存并实际读取以评价数据质量。

为入口安全、重复执行、删除范围、跨存储一致性和失败恢复增加或更新适用自动化测试并实际运行。数据库写入成功、一个角色登录、静态截图或测试通过不能单独替代完整恢复证明。不能仅因现有现场有用而跳过空环境恢复，也不能因为 schema 已迁移就宣布账号与业务数据齐全。

首次身份与基础初始化随最早需要它们的业务交付；后续需求新增角色、主要任务、关键状态或文件，或改变配置、恢复入口与账号交接时同步维护已有基线。不等待固定的“最后一条 Seed 需求”才准备数据，也不为每项无关改动机械修改 Seed。无相关持久化数据时按事实说明不适用；没有独立基线需求不等于免除适用交付合同。

可以按项目规则读取和管理开发 `.env`。用于登录目标产品的交付开发账号及密码属于受跟踪产品交付信息；PCM 或目标产品用于访问其它系统或资源的数据库、对象存储、SMTP、OAuth client secret、API key、私钥、令牌、Git、云、服务器、基础设施账号等凭据仍属秘密，必须保持 Git 忽略，日志和交付说明必须脱敏。不得仅为方便当前任务擅自安装基础设施、容器编排或外部依赖。

## 自包含产品体验闸门

只要改动产生用户可见 UI、交互、文案或浏览器结果，就必须在当前开发闭环内完成体验判断。项目已有设计资料、稳定页面和组件惯例是输入，不是前置依赖；第三方 UI Skill 不可用也不能跳过以下结果。

### 用户任务与简化

- 从正常入口以目标角色完成完整任务，确认用户能理解当前所在、目标对象、下一步和完成结果。
- 检查是否存在无价值步骤、重复输入、跨页面来回定位、必须记忆的信息、隐藏入口或不必要确认。
- 简化以降低理解和操作成本为目标，不以“点击越少越好”机械裁剪必要的安全、确认和上下文。
- 覆盖成功、关键校验、失败、恢复、刷新、重新进入、权限和相关状态变化；只走 happy path 不足以完成。

### 内容设计与术语

- 页面标题、导航、对象、动作、状态、字段、按钮、帮助、空态、错误和成功反馈使用目标用户能理解的语言。
- 同一对象、动作和状态在受影响界面保持一致；不能把接口、数据库、枚举、堆栈或实现术语直接暴露给用户。
- 文案应说明发生了什么、用户可以做什么；“请求失败”“参数非法”“记录写入成功”等技术化结论不足以支持恢复和决策。
- 危险操作、不可逆影响、权限差异和数据后果必须在行动前清楚表达。

### 信息、操作层级与页面构图

- 第一屏和阅读顺序应明确当前位置、关键状态、主要内容和主操作；次要元数据与低频操作不能争夺主注意力。
- 页面按用户任务、对象关系和决策顺序组织，而不是按后端字段、接口返回或组件种类分区。
- Card、Table、Badge、Tabs、Dialog 等通用组件只在语义适合时使用。连续堆叠 Card、把所有内容塞进 Table、给每条元数据加 Badge，不能代替页面构图。
- 主操作、次操作和危险操作应可区分；筛选、批量操作、行内操作和详情入口应与任务频率和风险相称。
- 空态、加载、禁用、失败、冲突、成功和完成后的下一步要有明确层级与恢复路径。

### 产品特异性与视觉质量

- 页面应体现本产品真实对象、关系、任务、状态、语气和素材，不能只是可替换到任何 SaaS 的统计卡片、通用表格与装饰性渐变。
- 主动评估图片对内容识别、场景理解、品牌表达和产品展示的收益，不等待用户点名；有明确收益且授权范围已确定时，按用途复用合适资产、检索通用摄影或获取定制构图并固化，不默认以占位图、通用图标或空白替代。没有收益的表单和操作界面不机械配图，测试 fixture 不冒充正式素材。
- 定制图片的输入应包含用途、目标容器、比例、主体位置、文案留白与裁剪、色彩风格和禁止元素；信息已经充分时直接使用，只补真实缺口，不追求提示词长度，不机械检索案例、补镜头参数或产出多个方向。只需要方向建议时不生成；已授权且目标与文件落点明确时执行工作区既有固定生成入口取得并检查真实文件，不能只写 prompt、循环检查不存在的文件、另写临时生图程序或静默切换服务。
- 实际查看采用的图像，并在真实页面的桌面和移动视口检查裁剪、标题对比、视觉层级及加载失败表现；标题、按钮和可维护数据由页面承载。仅针对具体缺陷在已授权的有限预算内修正，不以文件存在或接口成功代替验收。
- 检查布局、内容宽度、密度、留白、对齐、排版、颜色、边界、图标、图片和同类组件一致性是否帮助扫描和建立信任。
- 不用 Hero、图表、插画、渐变、阴影或动画掩盖信息架构和任务问题；视觉装饰必须有产品依据。
- 在目标视口和主要输入方式下保持可读、可操作和视觉完整，并覆盖适用的键盘、焦点、标签、错误关联、对比度、触控目标和 reduced motion。

### 真实浏览器与截图证据

具体浏览器或截图工具可替换，但结果强制：

- 使用项目可用的真实浏览器能力，在实际服务、真实开发数据和目标视口中执行任务；组件测试、快照、Mock 页面、DOM 或 accessibility tree 不能替代。
- 检查控制台错误、失败网络请求和必要后端日志；交互成功不能掩盖运行异常。
- 对本次用户可见变化的代表性页面和关键状态生成截图，并实际读取截图本身，判断层级、构图、密度、对齐、排版、颜色、素材和视觉完整性。
- 只生成截图、只检查尺寸、只看 DOM、只断言无溢出，均不构成视觉证据。截图也不能替代动态交互、权限、持久化和失败恢复验证。
- `Agent(dev)` 或 `Agent(reviewer)` 仅凭代码、组件测试或文字声称“视觉正常”，但未提供可实际读取的代表性截图时，视为证据缺口；Leader 必须补齐后才能通过体验或审查闸门。
- 核心用户路径仍缺必要浏览器证据，且浏览器能力或不可替代环境确实缺失时，如实使用“已实现但未完全验证”，列明缺口和补验方式；已有充分证据后的额外观察限制不自动阻止完成。

是否新增永久 E2E 测试，根据项目已有基础设施、场景稳定性、风险和长期回归价值决定；真实浏览器执行本身不可省略。已有 E2E 体系时，为稳定核心场景新增或更新测试并实际运行；没有体系时，不强制为一次需求搭建专属框架。

## 审查闸门

Leader 自审始终需要，覆盖需求遗漏、外部行为、数据、接口、权限、安全、异常、兼容、迁移、用户任务、文案、层级、真实视觉、Mock/假数据、验证证据和工作树范围。

正式 TRD 驱动的正常功能默认至少完成一次独立审查；严格意义上的微小、低风险改动可免除，并说明行为影响和依据。按上述完整性与专项分工覆盖最终变更。涉及 UI 时，应同时提供代表性截图、视口、页面状态和适用设计约束，优先复用开发验收证据。

Leader 逐项判断审查意见，不能把建议当作新增范围的授权；与当前代码、已确认产品规则或真实运行结果冲突时，说明依据和取舍。合理的阻断问题必须修复并重跑受影响验证，影响完成判断的证据缺口必须补齐。修复后针对 finding 和受影响差异复核，保留仍有效的结论，不机械重审未变化部分；不得把旧结论直接用于尚未覆盖的新变更。审查者无法读取职责范围内的变更、适用真实页面或截图时，只能报告缺口，不能用“无发现”证明闸门通过。

## 设计偏差与旧问题

代码、框架、测试或真实运行事实显示活动 TRD 不准确时，在当前范围内校正。局部实现细节不必更新；外部行为、业务规则、数据语义、接口、安全、迁移或验证目标变化时，必须同步仍处于活动状态的需求资料。已归档资料保持只读。

有证据直接影响当前需求正确性、安全、可用性或适用验收的旧 Bug 必须修复；其它相邻问题只作为新发现报告，不因根因明确、低风险或顺手可修而纳入本轮。低概率并发或安全缺陷可依据有效代码与运行证据判断，不以稳定复现为硬前提；修复涉及重大范围或设计变化时仍按既有确认规则处理。

## 完成状态与交付证据

结束状态只能是：

- **已完成**：需求功能已实现，核心路径与适用关键风险已有可信证据，没有已知阻断问题或未决重大选择；可以保留明确说明、且不影响交付判断的验证限制；
- **已实现但未完全验证**：功能已实现，但核心行为或关键风险仍缺必要证据；说明具体缺口、已有证据、影响、已尝试动作和最小补验方式，不把可选验证或长期观察自动列为缺口；
- **阻塞**：重大决定无法安全推断、不可逆变更待确认、用户修改严重冲突、必要仓库不可访问或关键实现条件完全缺失。

确实需要负责人作出决定时，在回复中说明准确问题、必要事实与约束、实质可行选项及其影响、推荐与理由，不能只引用 TRD、diff、日志、章节或行号。

与当前必要验收有关的测试失败、配置错误、服务未启动、可准备的数据不足或必要截图缺失，必须先修复可恢复问题；不能把关键失败包装成“未验证”。已具备关键证据后的非阻断限制只需如实披露，不自动降低结束状态。本需求改变某个仓库 README 所承载的稳定入口、摘要、关键前置条件或文档地图却未同步该 README，README 中受影响的命令、链接或关键前置条件已经漂移，详细交付文档无法从 README 发现，或只追加新说明而保留冲突旧事实时，同样不得标记“已完成”；README 合同未变化且保持不变不属于缺口。

最终交付只保留：

- 用户可见结果与主要实现位置；
- 完成条件到验证结果的映射或摘要；
- 实际运行的测试、检查、构建、接口、浏览器和截图证据；
- 重要设计取舍、活动需求调整、适用的架构 delta 结论和审查结论；
- 适用时说明初始化或恢复实现、交付开发数据、README/账号文档及实际恢复验收结果，不要求固定标题或状态字段；
- 受影响仓库、待提交文件、剩余工作树状态和未解决限制。

不报告内部任务数量、思考过程或尝试流水，不额外生成过程产物。本能力不管理项目级 Backlog 生命周期，不同步最终需求状态或完成日期，不替用户决定重大产品范围、安全模型、破坏性兼容、不可逆迁移或高成本架构变更。
