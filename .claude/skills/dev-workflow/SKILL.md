# dev-workflow — 自适应开发与可验证交付

## 核心承诺

`dev-workflow` 从理解目标到可交付结果负责完整开发闭环。实现方式可以随项目、风险和事实调整，但完成标准不能随意降低：自由度放在“怎么实现”，严格度放在“什么证据才能完成”。只有全部适用交付闸门通过，才可标记为“已完成”。

保护用户已有工作和秘密：先识别当前工作树中的用户修改；无关且不冲突的修改不得覆盖、回退或混入当前交付，归属不明或发生重大冲突时先分析再请示。禁止破坏性清理，禁止泄露秘密。只精确暂存当前功能所需且已验证的文件，提交前检查无关修改、开发 `.env`、临时文件和秘密；默认只 commit、不 push，多仓库分别检查、验证和提交。用户明确要求不提交时不提交。

普通运行不创建过程目录，不生成阶段报告、任务文件、Manifest、Run ID、任务报告、尝试记录或独立审查报告。代码、Git、活动 TRD 和测试输出是主要恢复来源；中断后应先从这些事实主动恢复。仅对长时间且可能中断的工作，可临时使用 `.pcm-workflow/<需求标识>/progress.md` 记录当前目标、已完成提交、当前工作、下一步和真实阻塞，正常完成后删除。

## 适用输入与独立性

本 Skill 可独立从活动 TRD、Backlog 大需求、功能描述、Bug、重构目标、Issue、验收反馈或已有代码上下文开始；不要求上游 Skill 已运行，不依赖固定下游 Skill、Manifest、运行目录或过程文件，也不把 Backlog 生命周期同步作为交付门槛。

先读取足以判断范围和证据的需求、代码、配置、测试、项目说明与工作树，明确全部验收条件、项目惯例、数据和接口边界、权限与兼容性、依赖服务、真实运行方式及验证入口。微小修改按行为影响而非行数判断；涉及业务规则、数据写入、权限、接口兼容、跨服务集成或用户可见流程时，不得按微小低风险修改处理。

## Leader、dev 与 reviewer

Leader 掌握完整上下文并对最终结果负责：校准目标和活动 TRD，保护用户修改，组织实现，整合跨模块改动，建立验收证据映射，执行最终自动化、真实运行与浏览器验收，裁决审查意见，并决定最终状态和 Git 收敛。

边界清楚、内聚且可独立验证时，可以调用 `Agent(dev)`。派发内容应包含目标、约束、可修改范围、验证方式和回报要求；`dev` 必须实际运行其范围内适用的测试、检查、构建及可独立完成的真实接口或集成验证，如实回报结果和未验证范围，不提交代码，也不把普通可修复环境问题直接升级给 Leader。Leader 不为体现多 Agent 而强制派发，也不重复实现同一工作，但必须审阅、整合并补足整体验收。

Leader 始终自审。`Agent(reviewer)`、`codex-review` 或其他独立路径只读、独立、证据驱动，重点检查需求遗漏、错误行为、关键失败路径、权限和数据风险、Mock 或假数据替代真实集成、相邻回归及证据缺口。审查意见是建议，不是必须盲目采纳的命令；最终取舍和交付状态由 Leader 基于需求、代码与实际验证裁决。

独立审查必须以权威工作区中实际存在的版本为输入。任一相关 Git 仓库含未提交改动时，Leader 应提供该仓库的权威工作区路径、完整 staged/unstaged diff、未跟踪文件范围、活动 TRD 或验收条件及验证证据。隔离 checkout 只能代表其已检出的提交版本，不能自动代表其他工作区的未提交实现；审查者无法读取完整范围时只能报告验证缺口，不能把隔离基线的“无发现”当作真实实现已审查。

## 默认完整执行路径

正常 TRD 工作按适用范围覆盖以下六阶段：

```text
理解与校准
→ 实现与随行测试
→ 完整自动化验证
→ 审查与修复
→ 真实运行与功能验收
→ 交付收敛
```

这是正常路径，不是固定状态机，不规定内部任务数量，也不生成阶段报告或任务文件。实现、测试、审查、修复和验收可以按发现反复迭代：

1. **理解与校准**：确认目标、全部验收条件、代码与运行事实、用户修改和适用闸门；设计与事实冲突时调整活动 TRD。
2. **实现与随行测试**：完成代码、配置、迁移、初始化数据和必要测试；验证随实现持续进行，不全部推迟到最后。
3. **完整自动化验证**：实际运行所有适用测试、静态检查、类型检查、构建及项目已有回归；失败后修复并重跑。
4. **审查与修复**：Leader 自审，按合同完成独立审查；判断意见，修复合理问题并重新验证。
5. **真实运行与功能验收**：启动实际服务，使用真实开发数据库、中间件、接口和数据验证；UI 需求执行真实浏览器验收矩阵。
6. **交付收敛**：核对每项验收证据、运行错误、审查结论、必要文件和 Git 范围，再确定三种最终状态之一。

只有能由需求、代码和运行事实证明某阶段确实不适用时才可跳过，并在最终说明中简述依据。“修改很简单”“时间有限”“理论上没影响”都不是跳过适用工作的理由。

## 开发中调整活动 TRD 和处理旧问题

代码、框架、测试或真实运行事实显示设计不准确时，Leader 在当前会话直接调整活动 TRD，无需返回其他 Skill。类名、函数拆分、局部文件组织、测试布局和等价实现等局部细节不强制更新 TRD；外部行为、业务规则、数据语义、接口、安全、迁移或验证目标变化时，必须同步活动 TRD。

正式归档的需求和 TRD 是只读历史记录，不得回写。已完成但尚未归档的需求只有在其权威生命周期事实已被外部调用方重新激活、且同一需求和活动 TRD 明确成为当前工作范围时，才可继续更新；本 Skill 不自行重开需求或改变生命周期。当前开发若需修复归档历史对应的代码，应把新的稳定决策写入新的活动 TRD；需要独立演进时建立新的需求和活动 TRD。

直接影响当前目标、正确性、可用性或验收的旧 Bug 必须修复。相邻、根因明确、低风险且可完整验证的问题可以一并修复；完全无关、范围大或高风险的问题不得悄悄扩大当前范围，应作为用户可见的独立演进工作。验收命令与代码、框架或运行时事实冲突时，先用证据修正活动 TRD 的验证方式，采用语义等价且正确的验证，不得为迎合错误命令而编写错误代码。

## 交付闸门

所有闸门都按“是否适用”判断；适用性来自需求、代码和运行事实，而不是为了缩短流程的主观解释。

### 需求覆盖闸门

- 正式 TRD 中 **100% 的适用验收条件** 都必须有实际证据。
- Leader 必须能给出 `验收条件 → 实现位置 → 验证方式 → 实际结果` 的映射；复杂需求可用简短表格，简单需求可在交付说明中紧凑表达。
- “已完成”“测试通过”这类笼统结论不够；证据应能定位到测试、命令结果、真实接口调用、浏览器场景、数据库状态或运行日志。
- 没有正式 TRD 时，也要把用户目标、Bug 复现条件或重构约束转换为可检查的完成条件并逐项验证。

### 代码质量闸门

- 实际运行与改动相关且项目适用的单元、集成、接口和回归测试，以及静态检查、类型检查和构建；不得任意只选最容易通过的一项。
- 写了但未运行的测试、只读代码或“理论上正确”的判断都不算验证证据。
- 测试或检查失败后，先定位并修复，再重跑失败场景和受影响回归；不能用一次较窄的通过掩盖仍失败的相关验证。
- 修复 Bug 或高回归价值行为时，增加或更新能防止复发的测试；清除临时代码、调试输出、硬编码假数据和绕过实现。
- 项目已有覆盖率阈值时必须满足；不得凭空发明统一的跨语言代码行覆盖率。没有项目阈值时，按业务风险覆盖核心成功路径、关键失败路径、状态流转、权限、数据一致性和受影响回归。

### 真实环境与数据闸门

需求依赖服务、数据库、中间件、接口或持久化时，必须使用真实开发环境证明集成可用：

- 按项目实际方式启动相关服务，检查健康状态、启动日志和与需求相关的运行错误。
- 使用开发环境已有的真实数据库和中间件，执行必要迁移和可重复、幂等的初始化数据；以真实账号、权限和业务数据完成适用场景。
- 无注册入口的管理系统必须提供可用且安全的初始管理员，或等价的首次使用引导/初始化机制。
- 调用真实接口并核对响应；涉及写入时按需通过重新查询、接口调用、刷新页面或数据库状态确认真实持久化。
- 后端不得用内存集合、硬编码数据或假 Repository 伪装持久化；前端最终联调不得用 Mock、拦截响应或假数据替代真实后端和真实数据。
- Agent 应先主动修复可处理的配置、服务启动、迁移、测试数据和环境问题，再考虑向用户求助；普通环境故障不是停止验证或宣布阻塞的理由。
- 本地实现已定义某项能力、但运行中的服务表现不一致（例如缺失路由或陈旧契约）时，先比较运行实例实际暴露的接口或路由信息与本地定义；确认实例陈旧后，只重启本会话启动或归属明确的服务，再重新验收，不把陈旧进程误判为实现缺失。

工作流可以读取和管理开发 `.env` 以完成真实验证，但 `.env` 和秘密必须保持 Git 忽略，命令输出与交付说明必须脱敏。工作流 **不创建、启动或管理 Docker 或 Docker Compose**；应使用项目已提供或明确支持的开发服务，缺少不可替代条件时按最终状态合同说明。

### 浏览器验收闸门

只要需求包含 UI、用户交互或浏览器可见结果，默认必须使用 `playwright-cli`、Playwright 或项目已有的等价真实浏览器能力执行验收。组件代码、快照、Mock 页面或单独接口响应不能替代真实浏览器执行。

浏览器验收矩阵至少覆盖全部适用项：

| 类别 | 必查场景 |
|---|---|
| 需求覆盖 | 每个 UI 验收条件 |
| 主路径 | 用户从正常入口完成操作的完整成功路径 |
| 输入与失败 | 必填、格式、重复提交、无效输入等关键校验和失败路径 |
| 后端错误 | 业务错误、请求失败及前端反馈 |
| 持久化 | 刷新页面或重新进入后的数据与状态 |
| 状态与权限 | 相关业务状态变化，以及有权限/无权限用户差异 |
| 常见界面状态 | 相关空状态、无搜索结果、搜索、筛选、分页、禁用、加载及加载失败 |
| 相邻回归 | 本次改动可能影响的相邻功能 |
| 运行异常 | 浏览器控制台错误、失败网络请求和必要的后端日志 |

不相关场景不机械执行，但只验证 happy path 不足以完成。真实浏览器执行是强制的；是否新增永久 E2E 代码，则根据项目现有基础设施、场景稳定性、风险和长期回归价值决定。已有 E2E 体系时，应为稳定、核心且有长期价值的场景新增或更新测试并实际运行；没有体系时，可直接用 Playwright 完成本次自动化交互验收，不强制为单次需求搭建框架。登录、权限、支付、关键数据写入和核心状态流转应优先沉淀为可重复测试。

### 审查闸门

- **Leader 自审始终必需**：检查活动 TRD 覆盖、外部行为、业务规则、数据语义、接口、权限、安全、异常、兼容、迁移、Mock/假数据/临时代码、验证证据和工作树范围。
- 正式 TRD 驱动的正常功能默认至少完成一次独立审查；优先使用 `codex-review`，不可用时使用 `Agent(reviewer)` 或其他真正独立的审查路径。Codex 暂时不可用本身不构成阻塞。
- 独立审查必须获得完整的本次范围最终代码或 diff、适用的活动 TRD 或验收条件，以及已有交付验证证据；若相关仓库有未提交改动，还必须获得权威工作区中可读取的完整变更证据。只审查局部材料或隔离 checkout 基线不能证明审查闸门通过。
- 只有严格意义上的微小、低风险修改可以免除独立审查，并在最终说明中简短说明行为影响和免除理由。
- Leader 必须逐项判断审查结果：合理的阻断性问题要修复，并重跑受影响验证；影响完成判断的 `VERIFICATION_GAPS` 必须补充证据，必要时重新审查。只有能证明与当前范围或完成条件无关的缺口才可简短说明后关闭；其余缺口未关闭时不得标记为“已完成”。不适用或证据不足的建议可以拒绝或继续调查，禁止盲目采纳 reviewer。
- 独立审查不裁决最终状态，不修改文件，也不生成单独审查报告；最终结论只进入精简交付证据。

## 完成前必须停止的红旗

以下任一适用情况存在时，**不得标记为“已完成”**：

1. 只写完代码，没有实际运行适用的测试、检查或构建。
2. 只靠代码阅读推断正确，没有启动和检查需求依赖的真实服务。
3. 应验证真实持久化，却使用内存数据、硬编码数据、假 Repository 或最终假数据。
4. 应完成前后端联调，却只验证 Mock、拦截响应或假接口。
5. 涉及 UI，却没有执行 Playwright 或等价真实浏览器验收。
6. 只检查 happy path，没有覆盖全部适用验收条件、关键校验和失败路径。
7. 测试、检查、构建、浏览器控制台、网络请求或服务日志仍有与本次需求相关的错误。
8. 独立审查提出合理的阻断性问题，但尚未修复和重跑受影响验证。
9. 把常规联调、点击验收、补测试或确认功能可用的责任留给用户。
10. 遇到可恢复的配置、服务、迁移或测试数据问题后，没有主动修复和排查就停止。

若出现红旗，继续实现、修复、验证或按下方合同使用其他状态；禁止用截止时间、已投入成本或“应该没问题”覆盖证据缺口。

## 完成状态与交付证据

结束状态只能是以下三种：

- **已完成**：目标已经实现，100% 适用验收条件有通过证据，全部适用自动化、真实环境、数据、浏览器和审查闸门已通过，没有已知阻断性问题，并已按约定提交或用户明确要求不提交。
- **已实现但未完全验证**：代码已经完成，但仅因不可替代的外部凭据、不可控外部服务、专用设备、人工审批或必要数据缺失，无法完成部分真实验证。必须说明已实现和已验证范围、未验证场景、真实缺失条件、已尝试的修复或替代方案，以及条件恢复后的补充验证方法。普通测试失败、配置错误、服务未启动或可准备的开发数据不足不能使用此状态。
- **阻塞**：重大决策无法安全推断、不可逆变更待确认、用户修改严重冲突、必要仓库不可访问或关键实现条件完全缺失，导致无法安全继续。保留有价值修改，并明确阻塞原因、已尝试动作和解除条件。

活动 TRD 可在底部使用以下精简模板；没有活动 TRD 时，在最终交付说明中提供同等证据：

```markdown
## 实施结果

- 状态：已完成
- 主要实现：……
- 验收覆盖：全部 TRD 验收条件已通过
- 自动化验证：……
- 真实运行验证：……
- 浏览器验收：……
- 独立审查：……
- 已知限制：无
```

最终交付只保留用户可见结果、验收映射或摘要、实际运行的验证、重要活动 TRD 调整、审查结论、提交和未解决限制；不报告内部任务数量、思考过程、尝试流水或未采纳的普通建议，也不额外生成过程产物。

## 不负责的内容

本能力不管理项目级 Backlog 生命周期，不修改已完成或归档的历史需求与 TRD，不迁移旧过程档案，也不替用户决定重大产品范围、安全模型、破坏性兼容、不可逆迁移或高成本架构变更。它不规定固定语言、框架、数据库、测试工具、内部任务数量或统一跨语言覆盖率，不恢复固定阶段编号流程或被移除的阶段 Skills，不创建、启动或管理 Docker 与 Docker Compose。
