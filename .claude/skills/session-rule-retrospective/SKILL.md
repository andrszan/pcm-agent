# session-rule-retrospective — 从执行问题中沉淀可复用规则

## 目标

复盘当前会话或调用方指定的一段实际执行，从已经证实的问题中提炼对本项目后续 AI 工作仍有稳定价值的规则，去重、归类并增量写入项目 `.claude/rules/`。

这不是会话流水账、事故档案或“凡错必记”工具。少写或不写是正常结果；规则数量不是质量指标。长期加载一条低价值规则会占用上下文并干扰更重要的指令，因此只保留收益明确的项目约束。

## 写入边界

只修改项目根目录下的 `.claude/rules/**/*.md`。不得修改：

- `AGENTS.md`、`CLAUDE.md` 或其它核心项目指令；
- 用户级或机器本地记忆；
- 产品、设计、任务、事故或交付文档；
- 代码、测试、配置、部署文件和 Git 历史。

写完并自检后保留未暂存变更，供调用方自行处理。本能力不暂存、不提交、不推送。

## 信息来源

以本次执行已经出现的事实为主要输入，例如：

- 实际失败的命令、工具或验证；
- 调试后确认的根因和有效解决方式；
- 审查或调用方明确指出并已核实的问题；
- 调用方对 AI 工作方式的纠正；
- 因项目仓库结构、工具链、权限、数据、并发、隐私或协作边界导致的重复风险。

必要时只读核对当前 `.claude/rules/`、核心项目指令、相关配置和 Git diff。不要为了寻找候选扫描整个代码库；本能力复盘的是指定执行，不是重新审查项目。

证据不足时不编造规则，可以直接得出“本次没有满足门槛的新规则”。

## 七项准入门槛

候选必须同时满足以下七项条件：

1. **已证实**：有失败输出、代码或配置事实、修复后验证，或调用方明确纠正支持；不是猜测。
2. **项目相关**：来自本项目的结构、工具链、数据、安全或协作方式；不是泛化常识。
3. **可复用**：未来另一项工作、另一条命令或另一位执行者仍可能遇到。
4. **触发明确**：能写清何时发生，而不只描述一次结果。
5. **动作可执行**：能给出具体、可检查的正确做法，而非“注意”或“小心”；保留必要前提和例外，不把一次有效方案写成唯一方案，不扩大操作权限或验证范围。
6. **未被有效覆盖**：现有常驻规则、路径规则、核心项目指令、自动化或按需能力没有在同一触发范围内充分表达并交付该约束。
7. **上下文收益为正**：预期减少的重复成本明显高于长期或条件加载成本；若代码、测试或自动化已足够，就不再增加文字规则。

任一条件不满足就不沉淀，不要求逐项汇报筛选过程。

## 加载范围与去重判断

`.claude/rules/` 与按需调用能力的加载范围不同，去重时必须比较“谁会在什么情况下看到并执行这条约束”，不能只做文本搜索。

- **无 `paths` 的规则**：每次项目会话加载，适合需要始终生效的项目级约束。
- **有 `paths` 的规则**：只在读取匹配文件时条件加载，适合稳定绑定特定目录或文件类型的约束。
- **按需调用的能力说明**：只在该能力被调用时生效，不自动覆盖普通开发、调试或审查场景。

因此，不能因为某个按需能力中已有一句相似表述就机械去重。如果同一风险会在未调用该能力的场景中高概率出现，且需要常驻或路径加载才能及时约束，候选仍可通过“未被有效覆盖”门槛。反之，若现有规则、自动化或核心指令已在实际触发范围内给出同样动作，就不重复写入。

需要新增规则时，只提炼项目特有的触发条件和动作，不复制整段能力说明或把偶发流程写成常驻规则。

## 默认拒绝的内容

以下内容通常不进入 rules：

- 拼错命令、漏写路径、替换位置错误等一次性操作失误；
- 网络抖动、短暂服务故障或单次权限工具误判等偶发事件；
- 已被代码修复且有充分回归测试保护的普通产品缺陷；
- 已在相同加载范围内被现有规则、核心指令或自动化充分覆盖的要求；
- 当前工作专属的业务事实、临时数据、账号、端口、运行 ID 或具体失败值；
- 未复现、未验证或仅凭审查猜测的问题；
- “运行测试”“保护秘密”等没有项目特殊性的通用常识；
- 只解释过去、没有未来触发动作的故事性描述。

普通缺陷若揭示了可跨功能复现的 AI 工作模式问题，可以沉淀该模式的测试或操作原则，而不是记录具体页面或接口缺陷。

## 文件组织与写作规范

写入前先了解项目现有规则结构和加载方式，并遵循：

- 文件位于项目根目录 `.claude/rules/`，扩展名为 `.md`，可以按稳定主题使用子目录；
- 每个文件覆盖一个长期主题，使用描述性名称，不按日期、任务、会话或事故命名；
- 优先增强已有主题文件，不为每个问题新建文件；
- 只有规则确实稳定绑定特定路径时才使用 `paths` frontmatter；跨目录和命令入口的约束不要勉强限定；
- `paths` 使用有效的 glob 列表，保持现有 frontmatter 和局部规则优先级；
- 每条规则简洁写清触发条件、必要动作和影响执行的例外；多个独立动作可以使用列表，不限制句数或强制章节；
- 只有减少歧义时才补风险、原因、验证或短示例，不机械套固定段落模板；
- 不写会话流水、日期、动态值、个人信息、本机绝对路径或未经验证的替代方案；
- 无条件加载的内容尤其要短，避免把背景、理论或完整操作手册长期注入上下文。

项目已有相近主题命名时沿用；没有合适主题时，只有至少一个候选确需长期维护才创建宽度适中的新文件。

## 执行流程

### 1. 确认范围与工作树

- 确认项目根目录和当前 Git 状态；
- 识别并保护调用方已有的 `.claude/rules/` 修改；
- 明确复盘的会话或执行范围。

### 2. 提取候选

依据本次执行事实提取候选，明确未来触发场景和期望动作：

- 技术问题：确认足以支持规则的原因与有效动作，不能把未经验证的方案写成规则。
- 调用方明确纠正：确认适用范围和期望行为，不为满足故障分析格式编造根因或修复验证。

候选分析不需要另存记录。

### 3. 逐项裁决

按七项准入门槛判断。问题耗时长、影响大或令人印象深刻，不等于适合成为长期规则。

### 4. 查重并选择加载范围

读取现有 rules，并核对与候选相关的核心指令、自动化和按需说明，按前述加载范围判断实际覆盖。部分覆盖时补充原规则缺失的条件或动作；同主题未覆盖时追加；没有合适主题时才新建。优先采用能在风险发生前及时加载、同时上下文成本最低的方式，不建立冲突的重复条目，也不把目标代码结构或尚未落地的约束写成当前规则。

### 5. 增量编辑

只编辑必要的 rules 文件，保持原有主题、措辞和 frontmatter；不批量格式化或修改边界外文件。

### 6. 自检

检查本次 diff，确认规则符合准入条件、加载范围和写作要求，frontmatter 与 glob 有效，没有秘密或临时信息。本次复盘不得新增 `.claude/rules/` 以外的修改；原开发或调用方已有的变更不属于复盘越界，不回退或清理。

### 7. 汇报

- 有修改：列出本次新增或更新的文件，简述核心规则，说明规则变更尚未暂存或提交。
- 无修改：明确本次未新增或修改规则，没有本次规则变更需要提交；不据此判断整个工作区是否需要提交。
- 只在影响理解时解释主要候选的取舍，不逐项列出所有去重或拒绝结果，也不重复列出待提交文件。

没有候选通过门槛也是成功结果。

## 判定示例

### 可以沉淀

- 项目开发配置含不能被通用 shell 加载方式安全解析的结构化值，且同类验证会反复需要加载；根因和安全动作已验证。
- 项目使用乐观并发控制，测试替身在重试调用中不核对关键版本参数会反复掩盖真实错误；问题已由测试或代码事实证实。
- 工作区包含多个独立仓库，若核心项目指令已经在所有会话有效覆盖仓库检查方式，则去重；若只在某个按需说明中出现而普通开发仍反复踩坑，应重新评估常驻规则价值。

### 不应沉淀

- 某次命令在错误目录执行：一次性操作失误，未证明存在项目级重复机制。
- 某个页面控件重名：应修复界面和测试，不是长期 AI 规则。
- 外部服务短暂不可用：没有稳定触发条件和可执行规避方案。
- 某条业务记录校验失败：应由业务契约、代码和测试表达。
