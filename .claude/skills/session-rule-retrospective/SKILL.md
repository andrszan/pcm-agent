# session-rule-retrospective - 从执行问题中沉淀可复用规则

## 目标

复盘当前会话或用户指定的最近一次 AI 执行，识别其中真实发生的问题，只将对本项目后续 AI 工作仍有稳定价值的经验，去重、归类并增量写入项目 `.claude/rules/`。

这不是会话流水账、事故档案或"凡错必记"工具。少写或不写是正常结果；规则数量不是质量指标。宁可拒绝一个边界不清的候选，也不要让低价值规则长期占用上下文并降低其它指令的遵循度。

## 写入边界

只修改项目根目录下的 `.claude/rules/**/*.md`。不得修改：

- `AGENTS.md`：维护者主动编写的跨 Agent 项目规范；
- `CLAUDE.md`、`.claude/CLAUDE.md`：核心入口和维护者主动指令；
- Auto memory：本 Skill 的目标是团队共享的项目规则，不是机器本地记忆；
- 需求、TRD、Backlog、事故报告或业务文档；
- 代码、测试、配置或部署文件。

写完并通过自检后自动提交本次新增或修改的 `.claude/rules/` 文件，不 push；具体提交要求见“执行流程·提交”。汇报新增、合并、更新和拒绝沉淀的候选。

## 信息来源

以当前会话已经出现的事实为主要输入，包括：

- 实际失败的命令、工具或验证；
- 调试后确认的根因和最终有效方案；
- 独立审查或用户确认的问题及修复结果；
- 用户对 AI 工作方式的明确纠正；
- 因仓库结构、工具链、权限、数据、并发、隐私或流程边界导致的重复风险。

必要时只读核对当前项目的 `.claude/rules/`、`CLAUDE.md`、`AGENTS.md`、相关配置和 Git diff。不要为了寻找更多问题而扫描整个代码库；本 Skill 复盘的是本次执行，不是重新审查项目。

如果当前会话缺少足够事实，不要编造问题。可以输出"本次没有满足门槛的新规则"。

## 候选准入门槛

一个问题只有同时满足以下条件，才允许写入 rules：

1. **已证实**：有失败输出、代码/配置事实、修复后验证或用户明确纠正支持；不是猜测。
2. **项目相关**：来自本项目的仓库结构、工具链、数据、安全或协作方式；不是任何项目都知道的泛化常识。
3. **可复用**：未来另一项需求、另一条命令、另一位 Agent 或另一轮工作流仍可能遇到。
4. **触发条件明确**：能写清"在什么情况下会发生"，而不是只描述结果。
5. **规避动作可执行**：能给出具体、可检查的正确做法；不能只写"注意""小心"。
6. **尚未充分覆盖**：现有 rules、CLAUDE.md、AGENTS.md、项目文档、Skill 或自动化检查没有已经表达同一约束。
7. **上下文收益为正**：规则能避免的重复成本明显高于长期加载成本；若代码、测试或一句现有规则已足够，就不写入 rules。

任一条件不满足就拒绝沉淀，并在结果摘要中给出简短理由。

## 默认拒绝的内容

以下内容通常不进入 rules：

- 拼错命令、漏写 `cd`、替换文本位置错误等一次性操作失误；
- 第三方服务短暂不可用、网络抖动、单次权限分类器故障等偶发环境事件；
- 已被代码修复且有回归测试保护的普通产品 Bug；
- 已存在于 README、AGENTS.md、现有 rules 或某个 Skill 的相同要求；
- 当前需求专属的业务事实、临时数据、账号、端口、Run ID 或具体失败值；
- 未复现、未验证、仅凭审查猜测的问题；
- "运行测试""保护秘密""不要破坏用户改动"等没有项目特殊性的通用常识；
- 为解释过去而写、但未来没有明确触发动作的故事性描述。

例外：普通 Bug 若暴露出可跨功能复现的 AI 工作模式缺陷（例如 mock 无条件成功掩盖乐观锁重试错误），可以把"测试设计原则"沉淀，而不是记录该页面的具体 Bug。

## rules 文件写作规范

写入前必须了解 `.claude/rules/` 的加载机制和格式约束，确保规则能被 Claude Code 正确加载。以下是 Claude Code 官方约束，不是可选建议。

### 文件位置与发现

- 规则文件放在项目根目录的 `.claude/rules/` 下，扩展名 `.md`。
- 文件递归发现，可以按子目录组织，例如 `.claude/rules/frontend/`、`.claude/rules/backend/`。
- 每个文件覆盖一个稳定主题，用描述性文件名（如 `testing.md`、`security.md`），不要按日期、需求号或会话命名。

### 加载机制

- **无 `paths` frontmatter 的规则**：在每次会话启动时自动加载，优先级与 `.claude/CLAUDE.md` 相同。适合需要始终生效的项目级约束。
- **有 `paths` frontmatter 的规则**：条件加载，只在 Claude 读取匹配文件时才加载到上下文。适合只影响特定文件类型或目录的约束，能节省上下文空间。
- 用户级规则 `~/.claude/rules/` 在项目规则之前加载，项目规则优先级更高。

### frontmatter 格式

`paths` 是可选的 YAML frontmatter，使用 glob 模式列表：

```markdown
---
paths:
  - "backend/tests/**/*.py"
---

# 后端测试规则

- 集成测试的 mock 必须验证关键请求参数。
```

没有 `paths` 字段的规则无条件加载。只在规则确实只影响特定路径时才使用 `paths`；跨多个目录或命令入口的约束不要勉强限定。

### glob 模式语法

| 模式 | 匹配 |
|---|---|
| `**/*.ts` | 任意目录下的 TypeScript 文件 |
| `src/**/*` | `src/` 下所有文件 |
| `*.md` | 项目根目录的 Markdown 文件 |
| `src/components/*.tsx` | 特定目录下的 React 组件 |
| `src/**/*.{ts,tsx}` | brace expansion，匹配 `.ts` 和 `.tsx` |

glob 注意事项：

- `[` 是 bracket 表达式开始；无法解析为 bracket 表达式的模式匹配空，不影响同文件其它模式。
- 要匹配文件名中的字面 `[`，转义为 `\[`。
- brace expansion 有预算限制：整个 `paths` 列表共享 1000 个展开模式和 4 MiB；无 brace 的模式不计入。超限的模式按字面处理，其花括号不匹配任何文件。

### 文件内容写作

- 用 Markdown 标题和列表组织；每条规则只保留触发条件、可观察问题和可执行动作，只有能减少歧义时才补原因或验证。
- 规则默认采用“标题 + 1–3 句紧凑正文”，不机械套用四段模板；不写冗长背景、完整代码示例、会话流水或可由动作直接推导的验证步骤。
- 优先合并到已有主题；一条规则应能独立指导未来行动。无 `paths` 的文件每次加载，因此正文越短越好，在不损失语义的前提下控制上下文成本。
- 不写会话流水、日期、需求号或内部 Task ID；Block-level HTML 注释（`<!-- -->`）在注入上下文前会被剥离，可用于给人类维护者留备注。

### 与其它配置的关系

- `.claude/rules/` 是 CLAUDE.md 的模块化补充，不是替代。CLAUDE.md 仍承载核心入口和维护者主动指令。
- 规则不要与 CLAUDE.md、AGENTS.md 或已有规则重复；重复或矛盾的指令会让 Claude 随意选择一个，降低一致性。
- `/compact` 后，无 `paths` 的规则会重新加载；有 `paths` 的规则需要再次读取匹配文件才重新加载。因此高频依赖的约束优先写成无 `paths` 形式。

## 去重与归类

写入前递归读取 `.claude/rules/**/*.md`，同时检查 `CLAUDE.md` 和它直接导入的项目规则入口。对每个通过门槛的候选执行：

1. **完全覆盖**：已有规则已表达相同触发条件和处理方式，不写；
2. **部分覆盖**：在原规则中补充缺失条件或更准确的做法，不新增重复条目；
3. **同主题存在**：追加到最合适的现有主题文件；
4. **没有合适主题**：只有当至少一个候选真正需要长期维护时，才创建一个宽度适中的主题文件。

不要每个问题新建一个文件。文件按稳定主题组织，而不是按日期、需求号、会话或事故组织。优先使用这些主题名；项目已有相近命名时沿用现有命名：

- `tooling-and-environment.md`：命令、运行时、包管理器、环境变量、权限工具；
- `testing-and-verification.md`：测试设计、Mock、集成验证、浏览器验收；
- `git-and-worktrees.md`：多仓库、分支、worktree、提交和改动归属；
- `data-and-migrations.md`：数据库、迁移、初始化、事务、并发；
- `security-and-privacy.md`：秘密、日志、权限、敏感数据；
- `ai-collaboration.md`：Leader/子代理分工、审查、上下文和重复劳动；
- `frontend.md`、`backend.md`：只有确实是单端长期约束时使用。

一般保持 3–8 个主题文件。只有主题明显独立且现有文件会变得混乱时才拆分。

## 规则写法

- 默认使用 `## <短标题>` 加 1–3 句正文，在一句话中尽量同时交代触发条件、失败机制和正确动作；不要为格式完整机械拆成“触发条件/问题/规则/验证”四段。
- 只有复杂规则确实需要消除歧义时才增加列表、原因、验证或短代码片段；示例能由动作直接推导时删除。
- 用现在时描述稳定事实，保留必要路径、配置键和命令形状，不写会话、需求号、动态值、个人信息、未经验证的替代方案或本机绝对路径。
- 只适用于稳定路径时使用 `paths` frontmatter；跨目录或命令入口的规则不要勉强限定。

## 执行流程

### 1. 确认范围与工作树

- 确认项目根目录和当前 Git 状态；
- 识别用户已有的 `.claude/rules/` 修改，保护其内容，不覆盖或回退；
- 明确复盘当前会话还是用户指定的某段执行。

### 2. 提取候选

列出本次执行中的问题候选。每个候选至少包含：事实证据、根因、最终有效方案、可能再次出现的触发场景。

### 3. 逐项裁决

按六项准入门槛判断。不要因为一个问题耗时很长或令人印象深刻就自动收录；耗时不等于可复用。

### 4. 查重与选文件

读取现有 rules 和入口指令，决定忽略、增强已有规则、追加到已有主题或新建主题文件。检查已有规则的 `paths` frontmatter，避免在同一主题上创建加载方式矛盾的重复条目。优先合并，不按会话建档。

### 5. 增量编辑

只编辑必要的 rules 文件。保持原有措辞、标题层级、frontmatter 和主题边界；不批量格式化其它文件。新建文件时按"rules 文件写作规范"选择是否需要 `paths` frontmatter。

### 6. 自检

完成前检查：

- 每条新增内容均通过六项门槛；
- 没有秘密、临时值、动态 ID、内部日志或个人信息；
- 没有与 AGENTS.md、CLAUDE.md、其它 rules 或 Skill 重复；
- 文件按主题组织，没有一问题一文件；
- 规则给出了可执行动作，而非会话总结；
- frontmatter 格式正确，glob 模式有效；
- 除 `.claude/rules/` 外没有修改其它文件。

### 7. 提交

自检通过后自动提交，不等待用户确认：

- 在根仓库操作（`.claude/rules/` 属于根仓库，不在 `frontend/`、`backend/` 子仓库）。
- `git add .claude/rules/` 精确暂存本次 rules 改动；禁止 `git add .`、`git add -A` 或纳入 rules 目录外的任何文件。
- rules 为项目级配置，直接在当前分支提交，无需特性分支。
- commit message 用 Conventional Commits：`chore(rules): <中文简述>`；不得添加 `Co-Authored-By` 署名。
- 不 push。
- 若提交被 pre-commit hook 拒绝或工作树有冲突，如实汇报并停止，不强行绕过。

### 8. 汇报结果

用简洁表格或列表汇报：

- **已新增/更新**：主题文件、规则标题、为什么满足门槛；
- **已去重**：被哪个现有规则覆盖；
- **未沉淀**：候选及拒绝原因；
- **提交**：commit hash、消息和涉及的 `.claude/rules/` 文件；若未产生改动则说明未提交。

若没有候选通过门槛，明确说明未修改任何文件、未提交，并列出主要拒绝原因。这也是成功执行。

## 判定示例

### 应沉淀

- 项目 `.env` 含会被 shell `source` 破坏的结构化 JSON 值，后端验证会反复需要加载同一配置；根因和安全加载方式已验证。写入 `tooling-and-environment.md`。
- 项目使用乐观并发版本，Mock 在第二次调用无条件成功会掩盖陈旧 version 重试；真实缺陷已经审查和测试确认。写入 `testing-and-verification.md`。
- 多个独立 Git 子仓库共同组成工作区，根仓库干净不能代表子仓库干净；如果现有 AGENTS.md 已覆盖，则去重，不再写 rules。

### 不应沉淀

- 某次执行忘记在前端目录运行 pnpm：一次性操作失误；除非反复证明仓库工具会在跨目录调用时产生系统性漂移。
- Playwright 某个页面两个 label 重名：应修复 UI 和测试，不是项目级 AI 工作规则。
- 分类器某一分钟不可用：偶发外部事件，没有稳定规避方案。
- 某条业务记录的 code 校验失败：属于当前 API 契约，应由 Schema 和测试表达。
