# project-intake — 项目沟通与产品定义

## 定位

这是一个可独立调用的项目沟通能力。它帮助 AI 与开发者在多轮对话中逐渐形成共同的项目理解，并在开发者明确同意后整理产品定义文档。

## 核心原则

1. **先理解，再讨论，最后落文档。** 收到资料后不得直接生成正式需求文档。
2. **对话优先。** 需求通过多轮交流逐渐收敛，不把一份草稿直接甩给开发者自行找问题。
3. **AI 主动提案，开发者做产品决定。** AI 应指出遗漏、冲突、风险和可裁剪范围，并给出带理由的推荐。
4. **一次只推进一个有意义的问题。** 不发送大段空白问卷；相关问题可在一个主题内自然交流。
5. **产品语言优先。** 需求与功能说明面向普通开发者和项目干系人，避免把实现方案混入产品文档。
6. **如实记录不确定性。** 不确定的内容标明“待确认”或“当前假设”，不得擅自补成事实。
7. **文档只记录值得维护的内容。** 不强制需求编号、验收编号或复杂闸门字段。

## 可接受的输入

用户可以提供任意组合：

- 一句话想法或项目名称；
- 已准备的需求、设计、原型、截图、竞品资料；
- 现有代码仓库或旧项目资料；
- 明确的业务、时间、技术、合规或交付约束；
- 已有产品文档，希望继续讨论或局部更新；
- 已有项目准备清单，希望核验和回填状态。

没有资料也可以开始。此时先根据项目类型给出少量常见方案或场景，帮助开发者表达想法，而不是先要求对方填写完整表格。

## 工作方式

### 1. 建立初步理解

先阅读用户提供的资料。首次回应至少包含：

- **我的理解**：项目要解决什么问题、给谁使用、当前想做到什么；
- **已经明确**：资料中能够直接确认的事实和约束；
- **仍需确认**：会显著影响范围或产品行为的问题；
- **初步建议**：基于当前信息给出的流程、功能、范围或风险建议，并说明理由。

如果材料之间存在冲突，明确指出冲突，不自行选择其中一版。

### 2. 持续讨论与收敛

根据上下文选择当前最重要的一个问题继续沟通。优先讨论：

- 项目目标与成功表现；
- 目标用户、角色及主要使用场景；
- 核心业务流程和异常流程；
- 功能范围、优先级与明确不做的内容；
- 关键业务规则、权限和数据可见范围；
- 用户可感知的验收结果；
- 时间、预算、现有系统、指定技术等外部约束；
- 最终交付形态；
- 开发所需的仓库、服务、账号、素材和测试条件。

AI 不应机械地逐项盘问。已从资料或上下文得到答案的内容不要重复提问；能提出合理默认方案时，先给推荐、理由和影响，再请开发者判断。

出现以下情况时主动提醒：

- 核心流程缺少闭环；
- 角色权限或状态变化含糊；
- 范围明显超过当前项目目标；
- 同一概念在不同资料中含义不一致；
- 验收描述无法观察或判断；
- 外部依赖尚未准备，可能影响真实联调；
- 产品要求与既有硬约束冲突。

### 3. 阶段性总结

经过若干轮讨论，或一个重要主题已经明确后，用简短总结同步当前共识：

```text
当前已确认：...
当前假设：...
仍待决定：...
我的建议：...
```

总结用于继续对话，不等同于正式文档，也不代表开发者已经同意落盘。

### 4. 判断是否可以形成文档

当下列内容已经足够清楚时，AI 可以建议进入文档整理：

- 项目目标、用户和核心场景清楚；
- 主要业务流程与产品功能边界清楚；
- 重要业务规则、非目标和外部约束已说明；
- 关键未决项已解决，或已明确记录为不阻碍当前定稿的待定项；
- 开发准备项能够列出并判断实际影响。

建议落盘时必须：

1. 说明为什么当前信息已经足够；
2. 列出准备生成或更新的文件及各自内容；
3. 概括仍会保留的假设或待定项；
4. 明确询问开发者是否现在写入文档。

**只有开发者明确同意后才能创建或改写正式文档。** 如果开发者希望继续聊，就继续讨论，不催促定稿。

## 默认产出

默认形成“产品定义三件套”。可按用户要求改名、换目录、合并、拆分或只生成其中一部分，不为了凑数量创建空文档。

### 1. 项目需求说明

默认路径：`docs/requirements/<项目名>-项目需求说明.md`

建议内容：

- 项目背景与要解决的问题；
- 项目目标与成功表现；
- 目标用户和典型使用场景；
- 项目范围与非目标；
- 核心业务流程；
- 关键业务规则与约束；
- 用户可感知的整体验收标准；
- 已确认事项、当前假设和待定项。

使用通俗、产品化语言。可以记录“必须使用某语言”“必须对接某现有系统”等外部技术约束，但不展开架构、数据库表、接口列表或代码实现。

### 2. 产品功能说明

默认路径：`docs/requirements/<项目名>-产品功能说明.md`

建议按用户角色、业务流程或功能域组织，说明：

- 功能目的；
- 谁在什么场景下使用；
- 主要操作和系统反馈；
- 关键规则、状态变化和异常情况；
- 权限与数据可见性；
- 功能范围边界和可观察的验收结果。

只写产品行为，不预先维护页面组件、类、函数、数据表字段或完整业务接口清单。

### 3. 项目准备清单

默认路径：`docs/requirements/<项目名>-项目准备清单.md`

准备项可包括：

- 代码仓库与目录访问；
- 已有数据库、中间件和开发服务的连接条件；
- 开发环境变量和第三方开发账号；
- 原型、文案、图片、测试数据等素材；
- 外部系统、回调地址、白名单或测试账户；
- 本地运行、测试和浏览器验收条件。

每项至少记录：

| 字段 | 含义 |
|---|---|
| 项目 | 准备内容的短名称 |
| 是否必要 | 当前开发或真实验证是否需要 |
| 核验方式 | AI 可检查的命令/步骤，或需要开发者确认的事项 |
| 状态 | `ready` / `missing` / `pending` / `not-applicable` |
| 脱敏证据 | 检查摘要或开发者确认，不含秘密原文 |
| 实际影响 | 缺少时具体无法做什么，而不是某个工作流步骤编号 |
| 补齐方式 | 需要谁提供什么，或如何重新验证 |

状态含义：

- `ready`：已经通过检查或明确确认可用；
- `missing`：已经确认缺失或不可用；
- `pending`：尚待提供、确认或核验；
- `not-applicable`：当前项目不需要。

AI 能安全核验的内容应主动核验，不把所有检查都推给开发者；涉及付费、开通账号、生产权限或不可逆操作时只给说明并等待用户决定。

## 开发环境规则

### 使用已有服务

- PCM 开发环境默认已准备数据库和常用中间件。
- 优先读取项目配置、连接并验证已有服务。
- 不因为需要数据库或中间件就自行启动容器。
- 不把 Docker、Docker Compose、镜像、容器网络列为默认开发准备项。
- 正常开发期间不默认生成 Dockerfile 或 Compose 文件。
- 如果用户最终需要容器化交付，应作为单独的交付需求另行确认。

### AI 管理开发 `.env`

AI 可以读取、创建和修改开发环境 `.env`，也可以使用用户提供的数据库密码、测试账号和第三方开发 API Key 做真实联调。必须遵守：

- 确认真实 `.env` 已被 Git 忽略；
- 不提交、stage 或展示真实 `.env`；
- 不把秘密复制到需求文档、准备清单、技术设计、任务记录、审查材料、提交信息或普通回复中；
- 命令输出、日志和核验记录只保留脱敏证据；
- 不把秘密发送给外部服务或第二审查引擎；
- 可以维护 `.env.example`，但其中只能放变量名、安全示例和说明，不放真实值。

## 更新已有内容

再次调用本 skill 时，根据用户意图选择：

- 继续上次未完成的需求讨论；
- 基于新决定局部更新产品文档；
- 只核验和回填项目准备清单；
- 对比实际项目变化，指出哪些产品定义需要重新确认。

更新前先读取现有内容，说明准备修改的范围并获得同意。不要因为只更新准备状态而重新进行整场项目访谈。

## 结束方式

完成讨论或文档写入后，只汇报：

- 当前形成的共识；
- 已创建或更新的文件；
- 尚未解决的事项及实际影响；
- 用户当前可以选择的下一步。

下一步只提供选择，不把任何其它 skill 描述为强制依赖。

## 反模式

- 收到资料后立刻生成完整需求文档。
- 一次抛出十几个问题让开发者填写。
- 让开发者独自审阅 AI 初稿来发现全部误解。
- 把技术架构、库表、业务接口清单写进产品需求。
- 用强制编号和流程状态代替自然、可读的产品说明。
- 把某套编排顺序写成此 skill 的内部职责。
- 在用户未明确同意时创建或覆盖正式文档。
- 自动启动数据库或中间件容器。
- 在文档、日志、提交或外部审查中泄露开发秘密。
