# product-feedback-triage — 人工反馈核验与候选分诊

## 定位与边界

这是一个可独立调用的产品反馈处理能力。它接收自然语言、截图、录屏、工单、日志或复现材料，理解反馈者遇到的问题，核验可核验内容，拆分混合问题，合并真正重复的反馈，并输出可供项目既有流程采用的证据化候选。

人工反馈是重要信号，不是天然正确的需求。反馈者可能准确描述现象却误判根因，也可能表达真实痛点却提出不适合的方案。本 Skill 不盲从，也不因一次未复现就否定真实感受。

本能力只做反馈核验、分诊和候选输出，不承担：

- 澄清或改变产品目标、目标用户、正式范围和商业方向；
- 把候选编为正式需求、分配需求 ID、设计技术方案或安排开发；
- 直接修复代码、修改项目文件或判断发布是否通过；
- 主动扫描整个产品寻找未知问题或替代完整体验审计；

候选是否进入项目的产品、需求、设计或开发流程，由调用方依据项目事实显式决定。

## 安全、只读与数据最小化

“只读分诊”指不修改项目文件、产品资料、正式需求、配置、代码或 Git 状态。为核验反馈，在调用方已授权、可复位且不影响真实用户的测试环境中，可以使用虚构身份和数据执行必要的可逆操作。

未经明确授权或缺少安全沙箱时，不执行真实付款、真实外发、生产数据写入、不可恢复删除、真实权限变更或其它高影响操作。可以核对危险边界前的已有事实并列出补证条件，不能通过破坏性复现确认猜测。

不安装浏览器、CLI、插件、依赖或基础设施，不启动来源不明或归属不清的服务。可以使用目标项目已可用的代码、测试、真实浏览器、日志、网络、控制台或其它事实通道；某项能力缺失时标记证据缺口，不用静态材料冒充动态验证。

反馈材料可能包含凭据、令牌、会话标识符、联系方式、个人资料或生产数据。只保留分诊必需的脱敏事实和证据指针；不复制秘密、完整日志、非必要个人数据或可重放会话值。无法安全脱敏的材料，只描述与结论直接相关的现象及受限位置。

## 输入与事实优先级

用户可以提供一条或多条反馈、截图或录屏、工单、角色与环境、版本和数据、可访问的产品或代码、日志测试、既有产品资料和已知问题。只读取足以判断本批反馈的上下文，不为了寻找更多反馈扫描整个项目。

事实优先级：

1. 本次在明确角色、数据、版本和步骤下实际复现的行为；
2. 目标项目当前代码、配置、测试、日志和运行事实；
3. 已确认的产品定义、需求、界面承诺和项目规则；
4. 反馈原文、截图、录屏和反馈者语境；
5. 尚未验证的解释和解决假设。

反馈者的感受本身是真实信号，例如“不知道下一步”“完成很费力”；它适用于谁、由什么造成以及如何解决，仍需证据和产品判断。材料冲突时保留冲突，不静默选择方便的一版。

## 拆解与核验

每条反馈先分为三层：

1. **事实主张**：可由环境、步骤、代码、日志或其它证据验证的描述，例如“提交后内容消失”；
2. **用户痛点**：理解成本、操作成本、损失、担忧或目标受阻，例如“不知道是否成功”；
3. **建议方案**：反馈者提出的功能、布局、文案或技术改法，例如“改成分步表单”。

一条反馈含多个独立事实、痛点或决定时拆成原子项；只有共同构成不可分割任务问题时才保留为一项。建议方案始终是待评估假设，不能自动变成候选结果、技术选择或实现指令。

对原子项按内容选择核验方式：

- Bug、交互失败、状态错误、数据或权限主张：优先在明确角色、数据、版本和步骤下复现；
- 文案、布局、遮挡和截图可见状态：核对页面、视口、截图和项目事实；
- “难用”“太慢”“不知道怎么做”：以反馈者角色从正常入口完成任务，观察入口、步骤、等待、重复输入、反馈和恢复；
- 功能请求：先确认要解决的目标、当前替代路径和影响；
- 审美偏好：寻找已确认品牌、设计规则、用户误解或任务影响依据，没有依据则保留为设计机会。

证据边界必须明确：

- 截图只能证明可见文案、布局、遮挡和状态，不能单独证明交互、权限、持久化、请求结果或根因；
- 录屏支持已展示的操作顺序和反馈，不能推断未展示的网络、后端或数据结果；
- 日志和错误响应支持技术异常，仍需结合用户任务判断影响；
- 代码和测试可解释实现与已有保护，不能替代本次动态复现；
- 反馈数量说明信号频率，不能单独决定严重度、产品价值或方案。

无法访问、无法稳定复现或材料不足时，保留反馈原文和已知语境，标记待补证并说明缺失条件。一次未复现可能来自版本、数据、角色、时机或环境差异，不能直接判定反馈错误。

## 快速路径、去重与分级

如果反馈已经清楚给出受影响用户和任务、环境或触发条件、实际与预期、影响范围，以及可重复步骤或充分证据，且没有混合问题、范围冲突或高影响待决事项，则在完成必要事实核对后直接形成候选。不要为了流程追问已经提供的信息或生成中间文档。快速路径不代表自动批准其中的解决建议。

### 去重与分类

按用户目标、受阻任务、触发条件、实际伤害、根因模式和可能处置边界判断重复。合并项保留来源数量、角色、版本、环境、数据和不同表现；表达相似但目标、影响或解决边界不同的反馈不得强行合并。同一根因影响多个页面时，不逐页制造候选。

分类：

- `bug`：违反明确需求、界面承诺、业务结果、权限/数据约束或基本可访问性要求；
- `usability-defect`：任务仍可完成，但存在明确、可复现且显著的理解、操作或恢复障碍；
- `improvement`：有证据的低风险效率、一致性、可读性或体验改进机会；
- `design-opportunity`：涉及品牌、审美、产品方向或尚无用户影响证据的设计假设；
- `coverage-gap`：反馈可信但受环境、身份、数据、设备或工具限制，尚不能得出结论；
- `duplicate`：已被同一候选、既有需求或已知问题覆盖。

纯表扬可作为正向信号保留，但没有明确需保护的行为时不制造候选；明显范围外内容标明不适用，不静默扩展产品。

### 严重度、信心与高影响边界

严重度只按用户影响判断：**阻断**、**高优先级**、**一般**、**建议**。证据信心单独标记为**高**、**中**、**低**。不把两者相加成总分；人数和语气可以说明频率或感知，不能替代任务阻断、可恢复性、影响范围和证据质量。

涉及产品目标、核心任务、品牌和全局体验、权限、安全、隐私、合规、数据完整性、数据保留、真实外发、资金、不可逆操作、破坏性兼容、迁移或高成本架构时，单列已知事实、未核验风险和需有权决定者确认的边界。普通、证据充分、边界清晰的反馈可以建议进入项目既有正式化流程；高影响事项不能因反馈者给出方案就自动采纳。

## 结束与自检

- **已完成分诊**：范围内反馈已拆解，完成适用核验、去重、分类和处置，没有未说明的关键证据缺口；
- **部分完成且待补证**：已完成现有材料允许的分诊，但结论仍需环境、身份、数据、步骤或动态证据；
- **不适用**：没有需要分诊的反馈，或内容只有无需变更的正向信号、完全无行动对象的信息，并已说明依据。

完成前确认：

- 事实主张、用户痛点和建议方案已分开；
- 保留了反馈者角色、版本、条件和适用语境；
- 已安全核验能核验的内容，且未把一次未复现当作反馈错误；
- 截图、录屏、日志、代码、测试和反馈数量都没有超出其证据边界；
- 已执行数据最小化和脱敏；
- 混合问题已拆开，真正重复项已合并；
- 严重度、频率和证据信心已分开，高影响决定没有盲从方案；
- 清楚完整的反馈已走快速路径，未进行流程性追问；
- 只输出候选，没有修改项目、创建正式需求。
