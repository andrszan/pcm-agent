# product-feedback-triage — 人工反馈核验与筛选

## 定位与职责

针对调用方提供的一条或整批产品反馈，结合当前产品和已有需求核验问题、评估改进价值、拆分去重，生成可供后续增量需求规划采用的精简反馈文档。

认可的是问题或改进目标值得处理，不代表认可反馈者的根因判断和解决方案。人工感受是重要信号；它适用于谁、由什么造成、是否值得当前处理，仍需事实和产品依据。既不盲从，也不因一次未复现就否定反馈。

本能力覆盖提供的全部反馈，不重新审计整个产品。核验中发现的直接关联问题可以补充，并标明由本次核验发现；不扩展为无关问题搜集。职责止于候选筛选和文档交接，不改变产品目标或正式范围，不分配正式需求 ID，不决定正式需求颗粒度、开发依赖与顺序，不设计详细交互或技术方案，也不安排开发。

## 输入与写入边界

支持自然语言、整份体验反馈文档、截图、录屏、工单、日志和复现材料；可结合角色、版本、设备、数据条件、可访问产品或代码、产品资料、已有 Backlog 和已知问题。没有固定输入表单，只读取判断本批反馈所需的上下文。

默认新建一份反馈文档，保留原始材料不变：

- 优先使用调用方指定的输出路径；未指定时复用项目已有反馈文档目录，否则使用 `docs/feedback/`，按批次主题选择清楚的文件名，例如 `2026-09-15-列表使用体验-核验反馈.md`。
- 写入前确认目标不与原始反馈或已有文件冲突；同名已存在时选择可区分的新文件名，不覆盖。只有调用方明确要求更新既有分诊文档时，才先读取并原位维护该文档。
- 只写本次反馈文档，不修改原始材料、产品定义、正式 Backlog、TRD、代码或配置；不执行暂存、提交、分支、合并、推送或其他 Git 元数据操作，不创建额外候选池、台账或过程报告。
- 调用方明确要求只在会话中返回时不落盘。没有可分诊内容时直接说明，不创建空文档；有实际问题但均待补证、待决或不纳入时，仍交付处置摘要，不制造推荐项。

为核验反馈，可在已授权、可复位且不影响真实用户的测试环境中执行必要的可逆操作，并按环境约定清理本次测试数据。未经明确授权或缺少安全沙箱时，不执行真实付款、真实外发、生产数据写入、不可恢复删除、真实权限变更或其它高影响操作；核对危险边界前的事实并说明补证条件。

需要动态证据时，主动读取项目 README、适用运行配置和开发账号资料，先复用已有服务；服务未运行时，在授权范围内按项目约定启动必要且归属清楚的开发服务，完成健康检查和真实登录后继续核验，不等待调用方再次提醒。存在 `.pcm/runtime.json` 时使用其分配的地址与端口；未知进程占用时报告冲突，不换端口或结束他人进程。只停止本次明确启动且归属可确认的进程，结束时简述仍保留的服务。

启动前区分服务命令、依赖安装、迁移、初始化和重置，不照抄整段准备命令；本能力不安装浏览器、CLI、插件、依赖或基础设施，不修改配置、不执行迁移或 init/reset。后台 worker 可能消费已有队列并真实外发，启动前核对任务范围与副作用是否已获授权，不能为了核验一项功能启动不受控的共享任务。必要条件超出本能力边界时，报告已尝试的动作、实际失败及最小解除条件，继续其他独立项；端口未响应本身不是可直接结束核验的理由。

使用已有的代码、测试、真实浏览器、日志、网络和控制台等事实通道，不以静态材料冒充动态验证。证据使用项目既有位置与截图约定，不将未获授权的项目写入藏在测试命令中。

只保留必要的脱敏事实和证据指针，不复制凭据、令牌、可重放会话值、完整日志或非必要个人数据。来源包含秘密时使用安全的定位与摘要，不原样抄入反馈文档。

## 批量拆解与核验

### 1. 理解整批反馈

先通读本批材料，分开每条反馈的三层信息：

- **事实主张**：例如“日期错误后提交，已填内容消失”。
- **用户痛点**：例如“必须重填，担心再次丢失”。
- **建议方案**：例如“改成三步向导”。方案只是待评估假设，不自动成为推荐目标。

保留原反馈的设备、角色、场景和限定语，不把桌面建议扩写为所有端要求，也不自行加上“一律”“全站”再反驳。多个独立问题拆开，共同构成不可分割任务障碍的保留为一项。沿用原文编号、标题或段落定位；没有编号时可使用本批次局部编号，不创建正式工单 ID。每个可识别问题都必须能对应到推荐项或明确处置，不能只处理前若干条，也不能因合并丢掉角色、条件和影响差异。

可按用户任务或模块集中核验，复用同一环境和仍有效的证据，减少重复操作；不把同一页面上的所有问题强行合并。清楚完整的反馈直接完成必要事实核对，不进行流程性追问或生成中间文档。

### 2. 按内容选取证据

| 反馈内容 | 核验重点 |
|---|---|
| Bug、交互失败、状态、数据或权限错误 | 明确角色、版本、数据、步骤下的实际行为，与需求、界面承诺或业务约束是否冲突 |
| 文案、布局、遮挡 | 实际页面、视口、可见状态及对理解或操作的影响 |
| 难用、太慢、不知道怎么做 | 从正常入口完成任务，观察入口、步骤、等待、重复输入、反馈与恢复，检查现有替代路径 |
| 新能力或效率改进 | 真实用户目标、当前能力与替代路径、影响和产品范围依据；不能仅因当前没有该能力就推荐新增 |
| 审美、品牌或布局偏好 | 已确认的设计方向、任务影响或明确的产品决定；不能用 Agent 自身审美代替依据 |

本次明确条件下实际复现的行为和当前代码、配置、测试、日志用于判断实际情况；已确认产品定义、需求、界面承诺与规则用于判断预期。原始反馈及语境用于理解用户信号，未验证解释仍是猜测。已有框架、实现和测试说明当前约束与变更影响，不单独证明现状值得保留；新反馈也是评估改进的依据。可以推荐有依据的演进目标，但不能在分诊中改写既定合同或越过重大决定。材料冲突时保留差异和适用条件，不静默挑选方便的一版。

证据不能超出其支持范围：截图支持可见状态，不单独证明交互、持久化、权限或根因；录屏只支持展示的操作与反馈；日志和响应需结合用户任务判断影响；代码与历史测试不替代本次动态复现。反馈数量只说明频率，不能代替严重度或价值判断。

完成可安全执行的运行准备后仍无法访问、不能稳定复现或条件不足时，保留必要原意和语境，说明缺少什么。当前样例成功或某种错误提示正常，不证明原问题已解决；应核对原文件、步骤、版本与失败阶段，差异无法解释时保留待补证，不标为已覆盖或已过时。只询问会改变采用判断且无法自行核实的关键信息，不因个别项待补证或待决而停止其他独立项。

### 3. 筛选与去重

推荐纳入的条件是：问题或改进目标有充分依据，用户影响和期望结果清楚，边界适合进入后续规划，且没有阻碍采用的重大未决。缺陷需要相称的行为证据；改进不必证明已有功能错误，但必须说明当前为什么值得处理。高潜在影响与证据不足可以同时存在，不能把疑点写成确认结论。

- **推荐纳入**：满足上述条件的问题或改进目标；认可目标不等于批准原方案。目标已明确且存在不改变重大边界的合理处理路径时，未确定控件或交互形式不阻碍推荐；页面、Dialog、Sheet 等普通方案选择留给后续设计，不提前设计，也不自动上抛。
- **待补证**：证据不足以判断，说明最少补证条件。
- **待决**：采用目标本身就依赖尚无授权的重大决定，而非仅因实现方案未定。涉及产品目标、核心任务、全局品牌与体验、安全、隐私、数据保留、资金、真实外发、不可逆兼容、迁移或显著成本，且现有事实和授权不能决定。说明已知事实、具体选择、影响和推荐理由；不混入已收敛范围。
- **已覆盖**：同一问题确有仍适用的已有工作覆盖，说明准确归属，不等于已修复。认定问题已解决或反馈已过时，须有对应原问题的验证或可解释的版本变化依据。历史需求写过正确行为但当前仍有缺陷，不是重复，形成新的修复候选并关联历史。
- **不纳入**：当前行为已满足目标、缺少当前改进价值、范围外或仅有无行动对象的偏好，说明依据。正向反馈按需简记，不制造候选。

按用户目标、受阻任务、触发条件、实际影响和处置边界判断重复；共同根因仅在证据支持时作为合并依据，不能把相似表现当作根因相同。合并项保留原来源及有意义的角色、版本、设备和条件差异，不按反馈条数或页面数量制造候选。

分类可使用 `bug`、`usability-defect`、`improvement`、`design-opportunity`，仅在有助理解时标注。严重度按用户影响判断为阻断、高优先级、一般或建议；证据信心独立判断。普通条目不机械填写标签、评分和非目标，显著风险、有限证据和影响采用的边界必须明示。

## 反馈文档

一份文档包含推荐主体和其他处置摘要。共用来源、核验版本、环境、角色及整体证据限制写在开头，条目只补差异。不附完整调查日志，不重复原文和证据，不按固定字数裁剪必要事实。

```markdown
# <批次主题>核验反馈

来源：<原反馈文档或材料位置>
核验范围：<版本、环境、角色及必要限制>
本次增量规划仅采用“推荐纳入的反馈”；其他处置仅供参考，不构成新增范围。

## 推荐纳入的反馈

### <清楚表达问题或改进目标的标题>

- 问题与影响：<谁在什么场景遇到什么障碍，为什么值得处理>
- 核验结论：<实际确认的事实、必要条件与精简证据指针>
- 期望结果：<改善后可观察的用户结果，不预设详细解决方案>
- 来源与关联：<原反馈定位；必要时关联已有需求或注明本次核验发现>

## 其他反馈的处置

| 原反馈 | 处置 | 依据及必要补证、决定或已有归属 |
|---|---|---|
```

可按任务或模块组织推荐项，省略空章节。合并来源直接写在推荐项中，不重复列入处置表。其他处置只保留未进入推荐主体的问题或确需单独说明的被拒绝方案，不用“推荐项已收录”重复条目，也不在文末再次展开整批核验与筛选摘要。必要的风险、采用判断和范围限制就近补充；重大待决事项不能为了表格简短而省略决定所需上下文，可在表后简述。

期望结果应足以支持后续规划和针对原场景的回归，但不提前编写完整验收矩阵、页面方案、组件、接口、数据表或实施步骤。后续可以合并或拆分推荐项，不要求一条反馈对应一个正式需求；所有入选目标都应保持可追溯，不自动执行后续流程。

## 完成检查与回复

写入前后检查：

- 全部原始问题都有推荐归属或明确处置，拆分与合并没有漏掉条件和影响。
- 推荐项有事实与价值依据，未把用户方案、主观偏好或未核验猜测当作已确认目标。
- 已完成可安全执行的必要运行准备，证据缺口不是服务尚未启动；未复现不冒充已解决，已覆盖项确有当前适用归属。
- 问题、影响、核验结论和期望结果足够指导后续规划，没有冗长解决方案或重复字段。
- 待补证、待决和不纳入项与推荐范围清楚分开，未把普通方案选择上抛，未仅凭既有设计否决改进，未扩大原反馈范围后反驳。
- 原始反馈未改动，写入仅限约定反馈文档，证据和来源已脱敏。

最终回复给出文档路径、推荐项数量、主要合并或筛选结果，以及需要注意的补证或待决事项，不再复制整份文档。全部范围完成适用核验并准确处置时说明已完成分诊；有关键证据缺口则说明部分完成且待补证；没有可分诊内容时说明不适用。
