# commit-changes — 精确、安全地提交 Git 变更

## 唯一职责

本能力只整理并提交目标仓库中已经存在的变更：读取真实状态和完整 diff，识别可独立理解的功能结果，精确暂存并创建一个或多个本地提交。唯一允许主动产生的新变更，是按下述严格边界为已确认无需版本控制的可再生成产物补充目标仓库根 `.gitignore`。

除该 `.gitignore` 例外外，它不实现功能、不修复代码或文档、不调整格式、不补测试、不创建或切换分支、不合并、不改写历史，也不 push。任何检查失败都应原样报告并停止，不能在提交过程中自动修改工作树来让检查通过。

本能力可以接收明确文件清单，也可以在调用方要求“提交当前所有修改”时自行规划边界。提供文件范围时不得扩大。只有调用方要求提交目标仓库全部修改、没有限定文件范围，或明确允许仓库卫生变更时，符合下述条件的目标仓库根 `.gitignore` 才能作为受限例外附加；调用方明确要求“仅提交 staged”或限定精确文件集合时，只报告缺失的忽略规则，不修改 `.gitignore` 或创建额外提交。未提供范围时，应从调用意图、Git 状态、完整 diff 和项目事实判断。只有归属实质不清或可能破坏调用方意图时才请求决定。

## 输入

尽量从调用参数和当前对话确定：

- `repo`：目标 Git 仓库路径；所有 Git 命令使用 `git -C <repo>`；
- `intent`：希望提交的功能结果或范围说明；
- `files`：可选的明确文件范围；
- `change_summary`：可选的意图线索，不能代替完整 diff；
- `expected_head`：可选的预期 HEAD，初始仓库可写 `unborn`。

## 开始时的只读检查

先确认仓库和当前状态：

```bash
git -C <repo> rev-parse --show-toplevel
git -C <repo> status --porcelain=v1
git -C <repo> diff --stat
git -C <repo> diff --name-status
git -C <repo> diff --cached --name-status
git -C <repo> diff --check
git -C <repo> diff --cached --check
git -C <repo> rev-parse --verify HEAD
git -C <repo> log --oneline -20
```

随后读取范围内全部 staged、unstaged 和未跟踪文件内容。统计信息不能替代完整 diff；未跟踪文件也必须逐个检查内容、归属和敏感信息。

`rev-parse --verify HEAD` 在初始仓库中失败表示 `unborn`，不是仓库错误。此时跳过依赖历史的读取，仍要检查全部待提交内容。

存在未解决冲突，或正在进行 merge、rebase、cherry-pick、revert 等历史操作时，停止并报告，不擅自解决或继续提交。

提供 `expected_head` 时，在规划前校验当前基线；不一致就无副作用停止。后续每次提交前也要确认 HEAD 等于上一步记录值，防止并发操作改变提交基础。

## 生成产物与 `.gitignore`

检查未跟踪项时，若文件或目录由第三方工具、依赖、测试、构建、覆盖率或浏览器验证生成，先判断它是否需要版本控制。只有同时满足以下条件，才能自动补充忽略规则：

- 来源明确，属于当前目标仓库执行过程产生的本地文件；
- 可以重新生成，且不是源码、锁文件、配置模板、测试 fixture、文档资产、视觉回归基线、正式报告或需要长期保留的验证证据；
- 使用 `git -C <产物父目录> rev-parse --show-toplevel` 得到规范化 `<artifact_repo>`，且它必须等于 `git -C <repo> rev-parse --show-toplevel` 得到的目标仓库 top-level；不相等时当前调用不得修改另一仓库，应报告其路径并分别处理；
- 可以用仅覆盖实际产物的最小规则表达，不需要宽泛通配或忽略整个业务目录。

满足条件时：

1. 读取 `<artifact_repo>/.gitignore`；不存在时可以创建。先使用 `git -C <artifact_repo> check-ignore -v --no-index -- <仓库相对路径>` 检查现有规则，已有等价规则时不重复修改。
2. 未命中时，只向该 `.gitignore` 追加最小规则，不顺手整理、排序或扩展其它规则。
3. 再次执行 `git -C <artifact_repo> check-ignore -v --no-index -- <仓库相对路径>`，必须确认实际产物由预期规则命中；否则停止并保留现场。
4. 将 `.gitignore` 作为完整文件纳入明确提交组。开始时已有固定 staged 组且调用范围允许本例外时，不得将 `.gitignore` 混入该组，应在其后作为独立仓库卫生提交，或与尚未暂存且确实相关的功能组一并提交。

该例外不允许删除产物、执行 `git clean`、对已跟踪文件执行 `git rm --cached`、修改其它仓库、覆盖已有 `.gitignore` 改动或仅为消除 Git 状态而猜测规则。可能含秘密的文件仍按敏感信息边界处理，不能因为已忽略就视为安全。用途、归属、规则影响或已有 `.gitignore` 修改无法安全确认时，不自动修改，报告具体路径和阻塞原因。

## 无变更

若目标范围没有 staged、unstaged 或未跟踪变更：

- 报告“无变更，无需提交”；
- 不执行 `git add`、`git commit`、hook、空提交或任何文件修改；
- 保持工作树、index、HEAD 和分支状态不变后结束。

无变更是正常结果，不使用 `--allow-empty` 制造提交。

## 按功能结果规划提交

一个提交表示一个能够独立理解和验证的功能结果，不表示文件类型、代码层次、执行者或开发步骤。

通常属于同一结果的内容包括：

- 功能实现及其测试；
- 数据结构变化、迁移、初始化数据和依赖它们的实现；
- 同一接口闭环所需的多个交付单元修改；
- 依赖声明及对应锁定文件；
- 配置变化及实际使用它的实现；
- 为准确说明该结果必须同步的文档。

互不依赖的新功能、缺陷修复、重构、基础设施或文档结果通常拆开。若拆分会使中间提交明显损坏、无法构建或语义不完整，应保留为一个完整结果。

默认以完整文件为安全暂存边界。同一文件包含多个独立结果时：

- 能共同形成一个完整结果，可以放入同一提交；
- 必须拆分但无法按完整文件安全归属时，不自动进行交互式 patch、手工补丁或其它局部暂存；
- 报告冲突文件和期望边界，请调用方先分离修改，或明确提供已经验证的局部暂存方案。

开始第一个提交前，完成全部候选变更的只读分组，并确认：

- 每个变更只属于一个提交组，没有遗漏或重复；
- 每组都能说明独立结果，顺序不会破坏后续组的成立基础；
- 必要测试、迁移、初始化数据、配置和说明没有被错误拆开；
- 未跟踪生成物均已分类：需要版本控制的内容进入明确提交组；已确认无需版本控制的可再生成产物由所属仓库的最小 `.gitignore` 规则覆盖；用途或归属无法确认的内容仍属于阻塞；
- 没有开发 `.env`、真实秘密、凭据、令牌、私钥和其它敏感信息。

除上述受限 `.gitignore` 例外外，发现任何问题时不修改、不暂存，报告具体路径和原因后停止。

## 已有暂存内容

调用方已有 staged 内容代表受保护的提交意图，不得擅自取消暂存、重组或与新文件混合。

- 未明确要求提交 staged 内容：停止并报告现有 staged 清单；
- 只要求提交 staged 内容：将当前 index 作为固定范围，完整检查后提交，不混入 unstaged 文件，不触发生成产物 `.gitignore` 例外，也不创建额外提交；
- 要求提交所有修改：先判断 staged 内容能否形成清晰、安全且完整的第一个结果；成立时固定为第一组，再规划剩余修改；不成立时停止，不擅自补入或拆分；
- staged 内容提交成功后，后续组仍使用逐路径精确暂存。

不得为了重新分组使用 reset、restore 或其它命令改变调用方原有 index。

## 精确暂存与提交

对每个提交组依次执行：

1. 再次确认 HEAD 与记录基线一致；初始仓库基线为 `unborn`。
2. 若该组不是调用方已有的固定 staged 组，逐路径暂存：
   ```bash
   git -C <repo> add -- <当前提交组文件...>
   ```
3. 核对完整 staged 集合和内容：
   ```bash
   git -C <repo> diff --cached --name-status
   git -C <repo> diff --cached -- <当前提交组文件...>
   git -C <repo> diff --cached --check
   ```
4. staged 文件集合必须与当前提交组完全一致；完整 diff 必须属于该功能结果，且不含秘密、临时文件或意外内容。
5. 生成符合仓库规范的 message 并提交：
   ```bash
   git -C <repo> commit -m "<message>"
   ```
6. 验证真实提交结果：
   ```bash
   git -C <repo> log -1 --pretty=format:"%h %s%n%n%b"
   git -C <repo> diff-tree --root --no-commit-id --name-status -r HEAD
   git -C <repo> show --stat --oneline HEAD
   git -C <repo> status --short
   ```
7. 将实际提交文件与计划比较，确认 hook 没有意外加入其它内容，再以新的 HEAD 作为下一组基线。

删除、重命名和未跟踪文件同样必须纳入明确分组与完整内容检查。禁止使用 `git add .`、`git add -A` 或其它会扩大范围的暂存命令。

## 检查失败

任何 `diff --check`、`diff --cached --check`、仓库要求的检查或内容检查失败时：

- 原样报告关键错误、涉及路径和当前状态；
- 不自动删除空格、补换行、运行 formatter 或修改任何文件；
- 不降低检查标准，也不继续提交。

如果失败发生在本能力精确暂存之后、尚未执行 `git commit`，且开始该组前 index 为空，应只撤销本能力刚加入的 index 变化，保持工作树不变：

- 有历史提交时，对本组路径执行 `git restore --staged -- <路径...>`；
- `unborn` 仓库中，对本组新增到 index 的路径执行 `git rm --cached -- <路径...>`；
- 随后只读确认 staged 清单为空，再报告并停止。

若开始该组前存在调用方 staged 内容，或无法证明 index 变化完全由本能力产生，则不执行恢复命令，保留现场并报告。恢复 index 不是修复检查问题，不能修改工作树内容。

## Commit 或 Hook 失败

commit、签名、hook 或其它提交错误发生后：

- 原样回报关键错误；
- 不使用 `--no-verify`、`--allow-empty` 或其它绕过方式；
- 不假设 index 和工作树仍与执行前相同；
- 不自动清理 hook 可能修改过的内容；
- 不修改代码、文档或配置来规避失败。

多个提交中途失败时，已成功提交保持不变：不 reset、不 amend、不 rebase、不改写历史。列出已创建提交、失败位置、当前工作树和 index，以及继续处理所需条件。

## 提交信息

提交信息按以下优先级确定：

1. 仓库贡献说明、Git 规范或调用方要求；
2. 最近提交形成的稳定风格；
3. 没有明确规范时使用 Conventional Commits：`<type>(<scope>): <结果>`。

message 必须描述实际 diff 形成的结果，不夸大未实现内容。避免 `update`、`changes`、`complete task` 等无法独立理解的标题，也不包含内部任务标识、运行编号、尝试次数或执行者名称。需要说明动机和影响时可添加简洁 body。

## 安全合同

- 默认只创建本地 commit，不 push，不执行其它远程可见操作；
- 不创建或切换分支，不合并，不改写提交历史；
- 不执行破坏性重置、清理、强制删分支或远程引用操作；
- 不使用宽泛暂存、绕过 hook 或空提交；
- 不提交秘密、开发配置、凭据、私钥、临时文件或无法确认归属的修改；
- 不覆盖、清理或顺手提交调用方其它改动；
- 不以提交成功替代测试、构建、真实联调或业务正确性审查。

调用方要求 push、提交秘密、绕过 hook 或执行破坏性 Git 操作时，拒绝该部分并说明原因。

## 完成输出

成功时基于提交后的真实 Git 结果汇报：

```text
已创建 <数量> 个提交：

1. <hash> <message>
   - <file>

仍未提交：
- none / <path：原因>
```

存在失败或阻塞时，列出已成功提交、失败命令、关键错误、当前 HEAD、staged 与未提交路径，以及恢复或继续条件。不得只复述计划清单。
