# commit-changes — 精确、安全地提交 Git 变更

## 唯一职责

本能力只整理并提交目标仓库中已经存在的变更：读取真实状态和完整候选 diff，识别可独立理解的功能结果，精确暂存并创建一个或多个本地提交。

它不实现或修复功能逻辑，不改变数据、接口、测试断言或业务运行配置的语义，不创建或切换分支，不合并，不改写历史，也不 push。提交准备允许精确维护 `.gitignore`、处理已确认的可再生产物和修复纯格式问题；处理后复核完整 diff 并继续提交，不为可安全判断的准备事项反复请求批准。调用方更窄的文件范围、只读约束和已有暂存意图始终优先。

本能力可以接收明确文件清单，也可以在调用方要求“提交当前所有修改”时自行规划边界。提供文件范围时不得扩大。未提供范围时，应从调用意图、Git 状态、完整候选 diff 和项目事实判断。只有归属实质不清或可能破坏调用方意图时才请求决定。

本能力主动执行的检查仅限 Git 状态、完整候选/staged diff、格式、提交范围与敏感信息检查，以及调用方在本次请求中明确要求的检查。开发验收由调用方或前序负责；除非明确要求，不主动运行测试、lint、type-check、build、服务、浏览器验收、安全审查或代码审查。`git commit` 自动触发的 hook 照常执行，提交成功不代表重新完成开发验收。

## 输入

尽量从调用参数和当前对话确定：

- `repo`：目标 Git 仓库路径；所有 Git 命令使用 `git -C <repo>`；
- `intent`：希望提交的功能结果或范围说明；
- `files`：可选的明确文件范围；
- `change_summary`：可选的意图线索，不能代替完整 diff；
- `expected_head`：可选的预期 HEAD，初始仓库可写 `unborn`。

## 开始时的只读检查

先确认仓库和当前状态：

```bash
git -C <repo> rev-parse --show-toplevel
git -C <repo> status --porcelain=v1
git -C <repo> diff --cached --name-status
git -C <repo> rev-parse --verify HEAD
git -C <repo> log --oneline -20
```

全仓状态用于识别并保护其它修改；候选 diff 和格式检查限定在本次提交范围，例如 `git -C <repo> diff --check -- <本次文件...>`。提交全仓变更时才对全仓执行候选检查。范围外未暂存文件的格式问题不阻断本次提交，也不授权修复；暂存区则始终核对完整集合，按“已有暂存内容”处理，避免提交时混入其它文件。commit hook 仍照常执行，失败按后文处理，不因检查范围有限而绕过。

随后枚举范围内全部 staged、unstaged 和未跟踪路径，读取完整候选内容。统计信息不能替代 diff：准备提交或归属尚待判断的候选都必须完整读取；来源明确且确定不提交的可再生成目录只记录路径和分类，不递归审查其中每个文件。

`rev-parse --verify HEAD` 在初始仓库中失败表示 `unborn`，不是仓库错误。此时跳过依赖历史的读取，仍要检查全部待提交内容。

存在未解决冲突，或正在进行 merge、rebase、cherry-pick、revert 等历史操作时，停止并报告，不擅自解决或继续提交。

提供 `expected_head` 时，在规划前校验当前基线；不一致就无副作用停止。后续每次提交前也要确认 HEAD 等于上一步记录值，防止并发操作改变提交基础。

## 生成产物

检查未跟踪项时，先核验实际内容、来源、所属仓库与可再生性，区分正式交付内容和工具、依赖、测试、构建、覆盖率或浏览器验证产生的临时内容。只有确认属于当前开发范围、不需要版本控制且可再生成的产物，才进入以下准备操作：

- 优先在所属仓库 `.gitignore` 中增加最小规则，复用已有规则，并用 `git check-ignore` 核对命中范围；不使用会隐藏业务文件或正式资产的宽泛规则。
- 明确没有交付或保留价值的临时产物可逐路径删除。删除前核对实际路径和内容，不跟随符号链接到范围外，不使用 `git clean`、模糊通配或范围外递归清理。
- 不因文件名、未跟踪状态或“看起来像产物”就忽略或删除。未知归属文件、业务数据、正式资产、开发资源、秘密以及受保护的已跟踪/暂存内容不按产物清理；实质不清时报告具体问题。
- 准备后重新读取 Git 状态和完整候选 diff；新增 `.gitignore` 纳入相关提交，清理结果简要说明。只修提交准备，不借机修改业务实现或重新验收。

可能含秘密的文件即使已被忽略也不能视为安全。开发配置和凭据仍遵循项目保密规则，不提交，也不以产物名义删除。调用方只允许固定 staged 内容或明确只读输入时，不以准备权限越过该限制。

## 无变更

若目标范围没有 staged、unstaged 或未跟踪变更：

- 报告“无变更，无需提交”；
- 不执行 `git add`、`git commit`、hook、空提交或任何文件修改；
- 保持工作树、index、HEAD 和分支状态不变后结束。

无变更是正常结果，不使用 `--allow-empty` 制造提交。

## 按功能结果规划提交

一个提交表示一个能够独立理解的功能结果，不表示文件类型、代码层次、执行者或开发步骤。“完整结果”只用于判断提交凝聚性和文件分组。

通常属于同一结果的内容包括：

- 功能实现及其测试；
- 数据结构变化、迁移、初始化数据和依赖它们的实现；
- 目标产品交付开发账号的创建、修改或删除、对应 Seed/fixture，以及同步更新的受跟踪账号文档；
- 同一接口闭环所需的多个交付单元修改；
- 依赖声明及对应锁定文件；
- 配置变化及实际使用它的实现；
- 为准确说明该结果必须同步的文档。

互不依赖的新功能、缺陷修复、重构、基础设施或文档结果通常拆开。若拆分会使中间提交明显损坏、无法构建或语义不完整，应保留为一个完整结果。

默认以完整文件为安全暂存边界。同一文件包含多个独立结果时：

- 能共同形成一个完整结果，可以放入同一提交；
- 必须拆分但无法按完整文件安全归属时，不自动进行交互式 patch、手工补丁或其它局部暂存；
- 报告冲突文件和期望边界，请调用方先分离修改，或明确提供已经验证的局部暂存方案。

开始第一个提交前，完成全部候选变更的只读分组，并确认：

- 每个变更只属于一个提交组，没有遗漏或重复；
- 每组都能说明独立结果，顺序不会破坏后续组的成立基础；
- 现有相关测试、迁移、初始化数据、配置和说明没有被错误拆开；
- 未跟踪生成物均已分类：需要版本控制的内容进入明确提交组；不需要版本控制的产物已按上述边界处理或保留，准备产生的 `.gitignore` 变更没有隐藏交付内容；用途或归属无法确认的内容仍须报告，不擅自处理；
- 没有开发 `.env`、PCM 或目标产品用于访问其它系统或资源的数据库/对象存储/SMTP/OAuth client secret/API key/私钥/令牌/Git/云/服务器/基础设施账号等凭据、真实个人认证信息及其它秘密。用于登录目标产品且最终保留在交付开发数据中的开发账号及密码属于受版本控制的产品交付信息，不应按秘密排除；

发现问题时，只在上述产物处理和下述纯格式边界内修复并复核；其它问题不修改、不暂存，报告具体路径和原因后停止。

## 纯格式问题自动修复

若 `diff --check`、staged 内容核对或 commit hook 只暴露范围内明确的纯格式问题，应直接做最小修复并继续提交，不停下来询问。纯格式问题仅包括不改变文字、代码、配置、数据或行为含义的机械排版变化，例如尾随空白、缩进、行尾、文件末尾换行，以及仓库现有 formatter 对范围内文件产生且经 diff 复核确属排版的修改。

处理时必须：

1. 只修改当前提交组内的路径，不扩大文件范围；
2. 优先做针对问题的最小修改；使用仓库现有 formatter 时也只作用于当前范围；
3. 完整复核修复后的工作树与 staged diff，确认除格式外没有内容变化；
4. 对当前组逐路径重新暂存并重新执行原检查；若 commit hook 已自动写入纯格式修改，同样先复核、精确暂存再重试提交；
5. 保留调用方其它 staged、unstaged 和未跟踪内容。

若无法确认修改是否只涉及格式、formatter 改动超出当前组、修复会混入同一路径中不属于当前组的 unstaged 内容，或失败还包含语义、测试、构建等问题，则不得自动处理，按阻塞规则报告并停止。

## 已有暂存内容

调用方已有 staged 内容代表受保护的提交意图，不得擅自取消暂存、重组或与新文件混合。

- 未明确要求提交 staged 内容：停止并报告现有 staged 清单；
- 只要求提交 staged 内容：将当前 index 作为固定范围，完整检查后提交，不混入 unstaged 文件，也不处理未跟踪生成物；
- 要求提交所有修改：先判断 staged 内容能否形成清晰、安全且完整的第一个结果；成立时固定为第一组，再规划剩余修改；不成立时停止，不擅自补入或拆分；
- staged 内容提交成功后，后续组仍使用逐路径精确暂存。

同一提交会话中断后，先根据本会话已执行的命令、提交组和当前完整 staged diff 核对暂存内容。能确认仍属于本次已获授权的提交尝试时，可以继续，不把自身遗留的 staged 机械视为调用方新设的提交意图；已经成功的提交不重做。仅恢复同一 session 不足以证明归属，来源不明或无法解释的变化仍按受保护的外部修改处理，不覆盖、取消暂存或混入提交。

不得为了重新分组使用 reset、restore 或其它命令改变调用方原有 index。

## 精确暂存与提交

对每个提交组依次执行：

1. 再次确认 HEAD 与记录基线一致；初始仓库基线为 `unborn`。
2. 若该组不是调用方已有的固定 staged 组，逐路径暂存：
   ```bash
   git -C <repo> add -- <当前提交组文件...>
   ```
3. 核对完整 staged 集合和内容：
   ```bash
   git -C <repo> diff --cached --name-status
   git -C <repo> diff --cached -- <当前提交组文件...>
   git -C <repo> diff --cached --check
   ```
4. staged 文件集合必须与当前提交组完全一致；完整 diff 必须属于该功能结果，且不含秘密、临时文件或意外内容。
5. 生成符合仓库规范的 message 并提交：
   ```bash
   git -C <repo> commit -m "<message>"
   ```
6. 验证真实提交结果：
   ```bash
   git -C <repo> log -1 --pretty=format:"%h %s%n%n%b"
   git -C <repo> diff-tree --root --no-commit-id --name-status -r HEAD
   git -C <repo> show --stat --oneline HEAD
   git -C <repo> status --short
   ```
7. 将实际提交文件与计划比较，确认 hook 没有意外加入其它内容，再以新的 HEAD 作为下一组基线。

删除、重命名和未跟踪文件同样必须纳入明确分组与完整内容检查。禁止使用 `git add .`、`git add -A` 或其它会扩大范围的暂存命令。

## 失败与恢复

检查、commit 或 hook 失败时，先读取实际错误和当前 Git 状态。只有已授权的产物准备或可确认的纯格式问题，才按前述边界最小修复、复核并重试；其它失败停止提交，并按下述阶段规则处理暂存区和报告。不改变业务逻辑、文字或配置的数据语义、测试断言，不使用 `--no-verify`、空提交或其它绕过方式。

### commit 前检查失败

如果失败发生在本能力精确暂存之后、尚未执行 `git commit`，且开始该组前 index 为空，应只撤销本能力刚加入的 index 变化，保持工作树不变：

- 有历史提交时，对本组路径执行 `git restore --staged -- <路径...>`；
- `unborn` 仓库中，对本组新增到 index 的路径执行 `git rm --cached -- <路径...>`；
- 随后只读确认 staged 清单为空，再报告并停止。

若开始该组前存在调用方 staged 内容，或无法证明 index 变化完全由本能力产生，则不执行恢复命令，保留现场并报告。恢复 index 不是修复检查问题，不能修改工作树内容。

### commit 或 hook 已执行后失败

不假设 index 和工作树仍与执行前相同；除已授权的产物准备和纯格式修复外，保留 hook 可能修改过的内容，不自动回退或清理。

多个提交中途失败时，已成功提交保持不变，不 reset、amend 或 rebase。报告已创建提交、失败位置、当前工作树和 index，以及继续处理所需条件。

## 提交信息

提交信息按以下优先级确定：

1. 仓库贡献说明、Git 规范或调用方要求；
2. 最近提交形成的稳定风格；
3. 没有明确规范时使用 Conventional Commits：`<type>(<scope>): <结果>`。

message 必须描述实际 diff 形成的结果，不夸大未实现内容。避免 `update`、`changes`、`complete task` 等无法独立理解的标题，也不包含内部任务标识、运行编号、尝试次数或执行者名称。需要说明动机和影响时可添加简洁 body。

## 安全合同

- 默认只创建本地 commit，不 push，不执行其它远程可见操作；
- 不创建或切换分支，不合并，不改写提交历史；
- 不执行破坏性重置、`git clean`、强制删分支或远程引用操作；
- 不使用宽泛暂存、绕过 hook 或空提交；
- 不提交秘密、开发配置、PCM 或目标产品用于访问其它系统或资源的凭据、真实个人认证信息、私钥、临时文件或无法确认归属的修改；用于登录目标产品且最终保留在交付开发数据中的开发账号及密码、对应受跟踪账号文档不属于此禁令；
- 不覆盖、清理或顺手提交调用方其它改动；只在上述已核验产物准备和纯格式边界内修改工作树，不能改变功能逻辑或受保护的数据；

调用方要求 push、提交秘密、绕过 hook 或执行破坏性 Git 操作时，拒绝该部分并说明原因。

## 完成输出

成功时基于提交后的真实 Git 结果汇报：

```text
已创建 <数量> 个提交：

1. <hash> <message>
   - <file>

仍未提交：
- none / <path：原因>
```

发生提交准备时，另简要说明忽略规则、已清理产物或纯格式修复的路径及理由，不列无关过程流水。

存在失败或阻塞时，列出已成功提交、失败命令、关键错误、当前 HEAD、staged 与未提交路径，以及恢复或继续条件。不得只复述计划清单。
