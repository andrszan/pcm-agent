# commit-changes — 精确、安全地提交 Git 变更

## 能力定位

读取目标仓库的真实 Git 状态和完整变更，判断哪些文件共同形成一个可独立理解的功能结果，然后精确创建一个或多个本地提交。

本能力可以直接接收明确文件清单，也可以在开发者要求“提交当前所有修改”时自主识别提交边界。它只整理和提交已有变更，不为了凑齐提交而修改代码、文档或配置。

## 可以从什么开始

尽量从调用参数和当前对话中确定：

- `repo`：目标 Git 仓库路径；所有命令使用 `git -C <repo>`；
- `intent`：本次希望提交的功能结果或“提交当前所有修改”等范围说明；
- `files`：可选的明确文件范围；提供时不得擅自扩大；
- `change_summary`：可选的目标说明，只是理解意图的线索，不能代替完整 diff；
- `expected_head`：可选的预期 HEAD，用于发现并发漂移。

调用方没有手工列出 `files` 时，不以此为由要求开发者整理文件。能够从 Git 状态、diff、项目资料和当前对话可靠判断时，直接规划并提交；只有提交归属实质不清或可能破坏用户意图时才请求确认。

## 理解当前变更

开始时只读检查：

```bash
git -C <repo> rev-parse --show-toplevel
git -C <repo> status --porcelain=v1
git -C <repo> diff --stat
git -C <repo> diff --name-status
git -C <repo> diff --cached --name-status
git -C <repo> diff --check
git -C <repo> log --oneline -20
```

继续查看全部相关 staged、unstaged 和未跟踪文件内容，而不是只看统计信息。检查冲突、未完成的 merge、rebase、cherry-pick 或 revert；存在这些状态时停止，不擅自解决或继续提交。

提供 `expected_head` 时，开始规划前必须校验当前 HEAD。后续每次提交前也要确认 HEAD 等于上一步记录的值，防止并发操作改变提交基础。

## 按功能结果规划提交

一个提交表示一个能够独立理解的功能结果，不表示一种文件类型、代码层次、Agent 子任务或开发步骤。

通常放在同一提交中的内容包括：

- 功能实现和对应测试；
- 数据模型、迁移、初始化数据和依赖它们的实现；
- 接口变化和完成同一闭环所需的前后端调整；
- 依赖声明和对应 lockfile；
- 配置变化和使用该配置的实现；
- 功能结果必须同步的说明文档。

以下互不依赖的结果通常拆成不同提交：

- 新功能与无关 Bug 修复；
- 业务变化与无关基础设施调整；
- 独立重构与产品功能；
- 不同模块中可以分别理解和验证的修改；
- 与代码结果无关的工作流或文档调整。

不按前端、后端、测试、文档或文件数量机械拆分。强行拆分会让中间提交明显损坏、无法构建或语义不完整时，应合并为一个完整结果。

自动提交组默认以**完整文件**为安全暂存边界。同一文件同时包含多个独立结果时：

- 如果这些变化共同形成一个可理解、可验证的结果，可以合并到同一提交；
- 如果业务语义要求拆分，但完整文件无法安全归属，不自动进行交互式 patch、手工生成补丁或其他容易误选内容的局部暂存；
- 此时说明冲突文件和期望边界，请开发流程先分离修改，或由用户明确指定经验证可靠的局部暂存方式。

当开发者要求提交全部修改时，默认自动形成一个或多个提交组；边界清晰时不逐组请求确认。存在多个高度混杂且无法可靠归属的结果、同一文件无法安全拆分、疑似无关用户修改或其他可能破坏用户意图的部分时，才停止说明需要确认的具体边界。

## 提交前整体检查

开始创建第一个提交前，先完成全部候选变更的只读分析和分组，确保：

- 每个变更只属于一个提交组，没有遗漏或重复；
- 每组都能说明独立的功能结果；
- 必要的测试、迁移、初始化数据、配置和说明没有被错误分开；
- 没有临时过程文件、构建残留或无关生成物；
- 没有开发 `.env`、真实秘密、凭据、token、私钥或其他敏感配置；
- 提交顺序不会让后续分组失去成立基础。

如果在开始提交前发现问题，不 stage、不修改文件，只报告需要调用方或开发流程处理的内容。

## 精确暂存与提交

对每个自动规划或明确给出的提交组依次执行：

1. 确认当前 index 符合“已有暂存内容”的处理规则，并记录当前 HEAD。
2. 对由本能力规划的未暂存文件逐路径暂存，禁止宽泛暂存：
   ```bash
   git -C <repo> add -- <当前提交组文件...>
   ```
3. 核对完整 staged 文件集合和内容：
   ```bash
   git -C <repo> diff --cached --name-status
   git -C <repo> diff --cached -- <当前提交组文件...>
   git -C <repo> diff --cached --check
   ```
4. staged 集合必须与当前提交组完全一致。完整 diff 必须属于该功能结果，且不包含秘密、临时文件或意外内容。
5. 生成符合仓库约定的 message，然后执行：
   ```bash
   git -C <repo> commit -m "<message>"
   ```
6. 验证实际提交结果：
   ```bash
   git -C <repo> log -1 --pretty=format:"%h %s%n%n%b"
   git -C <repo> diff-tree --root --no-commit-id --name-status -r HEAD
   git -C <repo> show --stat --oneline HEAD
   git -C <repo> status --short
   ```
7. 将实际提交文件与计划分组比较，确认 hook 没有意外加入其他内容；然后基于新的 HEAD 继续下一组。

删除、重命名和未跟踪文件同样必须纳入明确分组和完整内容检查。禁止使用 `git add .`、`git add -A` 或其他会扩大范围的命令。

## 提交信息

提交信息规范按以下优先级决定：

1. 仓库明确的贡献说明、Git 规范或用户要求；
2. 最近提交形成的稳定风格；
3. 没有明确规范时使用 Conventional Commits：`<type>(<scope>): <结果>`。

message 应描述实际 diff 形成的功能结果。`intent` 和 `change_summary` 只是理解素材；不得因为说明不完整而遗漏必要配套内容，也不得在代码没有实现时夸大结果。

不得使用 `update`、`changes`、`complete task` 等无法独立理解的泛化标题，也不得包含内部任务 ID、工作流 run、尝试次数、Agent 名称、`Co-Authored-By` 或其他自动署名。需要补充动机和影响时可以添加简洁 body。

## 已有暂存内容

用户已有 staged 内容是受保护的提交意图，不能擅自 `reset`、取消暂存或与新选择的文件混合。

- 用户没有明确要求提交 staged 内容：停止并报告现有 staged 清单；
- 用户明确要求只提交 staged 内容：完整检查后将其作为固定提交范围，不混入 unstaged 文件；
- 用户要求提交所有修改：先检查 staged 内容是否已经构成清晰、安全的独立结果；成立时将其作为固定的第一个提交组，再规划剩余修改；明显混杂多个无关结果时停止，不擅自重组用户 index。

已有 staged 组提交后，后续自动分组仍必须使用精确暂存。

## 失败与恢复

### 提交前检查失败

如果开始时 index 为空、当前 staged 内容完全由本能力刚刚创建，并且尚未执行 `git commit`，检查失败时恢复本次暂存：

```bash
git -C <repo> restore --staged -- <本次暂存的文件...>
```

只恢复 index，不修改工作树。恢复后再次检查 staged 清单，确认没有遗留本次暂存内容。

### Commit 或 Hook 失败

pre-commit hook、签名、空提交或其他 commit 错误发生后：

- 原样回报关键错误；
- 不使用 `--no-verify` 或 `--allow-empty`；
- 不假设 index 仍与执行前相同；
- 不自动清理 hook 可能修改过的 index；
- 不修改代码或配置规避失败。

### 部分提交成功

多个提交中途失败时，已经成功的提交保持不变：不 reset、不 amend、不 rebase、不改写历史。保留尚未提交的工作树和 index，列出已创建提交、失败位置、当前状态和继续处理条件。

## 完成输出

默认直接返回简洁结果，不创建提交报告文件：

```text
已创建 <数量> 个提交：

1. <hash> <message>
   - <file>

2. <hash> <message>
   - <file>

仍未提交：
- none
```

存在保留修改、失败或阻塞时，明确列出路径和原因。输出中的提交文件必须来自提交后的真实 Git 结果，不能只复述计划清单。

## 安全边界

- 默认只 commit，不 push，也不执行任何其他对外可见 Git 操作；
- 不执行 `reset --hard`、历史改写 rebase、`clean -fdx`、强制删分支或远程引用等破坏性操作；
- 不使用 `git add .`、`git add -A`、`--no-verify` 或 `--allow-empty`；
- 不提交开发 `.env`、秘密、凭据、token、私钥和临时过程文件；
- 不覆盖、清理或顺手提交无法确认归属的用户修改；
- 不为了让提交成功而修改代码、文档或配置；
- 不添加 `Co-Authored-By` 或其他协作者尾注。

用户要求 push、强制提交秘密、绕过 hook 或执行破坏性 Git 时，拒绝该部分并说明原因。

## 不负责的内容

本能力不实现功能、不修复 Bug、不审查业务正确性、不替代测试和真实验收、不创建或切换分支、不合并分支、不 push。发现功能不完整或质量问题时，返回给调用方或开发能力处理，而不是在提交过程中自行修改。
