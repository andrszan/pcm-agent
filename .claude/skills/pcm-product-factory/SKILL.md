# Web 应用产品构思与初稿

通过讨论选择值得开发的 Web 应用，确认命名，再形成具体、自洽的 Markdown 产品初稿。默认先讨论，不直接替用户选定产品并落稿；只有用户明确要求直接完成初稿、不用讨论时，才自主完成并交付。

流程组织工作，不预设产品答案。市场、人群、领域、规模、功能、角色、产品形态、品牌和视觉表达由本次输入与产品自身决定。

## 1. 理解输入与选择方向

阅读本次要求与相关资料，区分明确条件、参考信息和未知。产品目录优先使用用户指定位置，否则使用工作区已有的 `docs/prd/pcm-product-catalog.json`；初稿交付目录已另有该目录文件时沿用，不另建一份。读取现有记录识别重复和保护既有身份，历史不作为构思范本或选题范围。

- 没有方向或只有宽泛领域时，提供少量有实质差异的选题，通常三个左右。每个选题简明说明目标用户、具体问题、主要使用过程与结果、吸引人的地方和最大不确定性；推荐一个并说明理由，请用户选择或提出调整。
- 用户尚未选定时，根据反馈继续收敛，不把同一个产品换名后反复推荐；候选阶段不创建完整初稿或产品目录记录，不展示内部评分过程。
- 已有明确产品方向时围绕它讨论；用户已经选定的方向不重复询问，也不重新发散无关选题。选定方向不等于接受全部功能提案或名称。
- 用户明确要求直接生成初稿时，跳过选题和命名确认，围绕已给方向展开；没有方向则自主选定。只有必须由用户决定的实质冲突才中断，其余合理假设写入初稿。

需要外部事实支持判断时进行针对性研究，如实区分查得的事实与推断，不为形式完整做固定规模的研究。

## 2. 产品命名

从实际用户、核心任务、使用场景和期望气质出发，比较少量真正不同的命名方向。可从熟悉物品、动植物、食物、自然事物及其组合，或动作短语、拟声节奏、简洁专业表达等方向探索；这些是可选手段，不是固定风格表或词库。专业产品不必使用抽象科技词，轻松产品也不必都是水果或动物；不要只替换同一个字根，也不默认采用“业务字加意象字”的两字组合。

优先顺口、容易读写和记忆、适合产品气质的名字，长度服从自然语感。不靠长篇寓意解释挽救生硬表达，避免生僻字堆砌、负面谐音和明显混淆知名品牌。目录中的历史名称用于发现重复，不用来模仿命名套路。

命名包含：

- 中文品牌名：负责识别与记忆。
- 功能副标题：用直白中文解释用途，不强行使用品牌隐喻。
- 英文品牌名：与中文共享自然的品牌概念，不逐字硬译或为填字段硬造。
- 工程标识：使用唯一的小写英文 `kebab-case`，优先从英文品牌规范化得到。不包含技术栈、年份或版本，不再另造无关的 codename。

默认在方向选定后、初稿落盘前，给出一组首选命名，必要时附一两个不同风格的备选。明确告知工程标识用于后续 Agent 工作区命名，并询问用户是否满意或希望调整；用户已明确提供或确认的名称不重复确认。用户只选定产品方向、尚未接受命名时，先完成这次沟通再落稿。

已有品牌、产品 ID、工程标识与文档路径默认沿用，不因审美偏好改写。用户要求改品牌时，不自动重命名既有工作区或仓库。明确要求直接完成时，交付首选命名提案，说明工程标识用途及名称可调整，不冒称用户已单独确认。不要宣称名称唯一、商标可注册或域名可用。

## 3. 构思与形成初稿

从产品用途和实际使用过程形成设计，让功能、规则和体验有各自成立的理由。初稿应让接手者理解产品是什么、为谁而做、为何值得使用、如何使用、当前建议包含什么，以及怎样判断核心结果成立。影响产品成立的依赖、假设与未知如实说明，不以虚构能力掩盖缺口。

普通操作流水、编辑历史默认不设计，包括操作流水、修改前后值、版本浏览与对比、历次计算或配置快照回看及配套恢复、回滚。没有具体用途时直接不纳入，也不列为可选增强或未来扩展；改称“活动动态”“变更轨迹”不改变取舍。不要因熟悉版本、反馈、修订和确认的组织方式，就反复以追溯作为选题卖点。

判断是否保留时，先说明哪个用户不查看过去就无法完成什么任务，再比较当前状态或必要业务结果是否足够；仍需复杂历史能力时，优先删减相关模块，必要时重新讨论构思方向，最后才保留值得做的最小范围。“方便追溯”“更完整”“更严谨”“以后可能需要”不足以成立，也不能先把版本管理写进定位再以“核心功能”自证必要。已确认范围需要改变时，提出取舍供用户决定，不静默删除。

订单、维修结果、必要的正式提交、确认与交付记录，以及有具体安全需要的内部记录，按实际用途判断，不因发生在过去而排除。但需要保存不等于需要历史中心、版本对比或永久保留；保存内容、数量与期限、用户查看能力分别按任务需要取舍，不以仅隐藏入口代替删减。

正文明确写出品牌、功能副标题和工程标识，存在英文品牌时一并写明；与目录记录保持一致。区分用户已确认要求、当前设计提案和重要未知；本次建议开发的范围与未来对外运营条件分开，不擅自决定分期、缩减已确认范围或将上线条件变成本轮开发前置。

主动评估业务数据的可视化价值。图表有助于理解、比较、回顾或决策时，将其作为正式产品能力设计，说明谁看、回答什么问题、数据来自哪些业务记录，以及看完能作出什么判断或采取什么行动。按用途选择业务页面内图表、独立统计分析页或集中监控大屏，不默认给所有产品增加统计页或大屏。

美观和专业感可以是收益，但不能编造指标或仅为做图增加用户录入负担。适用时说明样本量、缺失数据、比较范围与回到业务记录的方式；没有数据时不以虚构业务量填充。产品不适合图表时自然不加，无需在初稿中另写排除报告。

章节、顺序、篇幅和细节由产品决定，不套固定目录。初稿用于继续讨论和深化，不提前承担详细工程设计与开发交付规范，不固定技术栈、接口或图表库。外部资料只引用本次真实查阅且影响判断的来源。

## 4. 复核与交付

检查设计是否自洽、是否回应本次输入，以及是否存在缺乏产品依据、仅因惯例而添加的内容。与历史产品相似时，依据用户、核心需求和业务过程判断是否实质重复，不为表面差异强行改变合理设计。检查命名确认是否遵从本次交互方式，提案是否被误写为用户共识。

修正后按用户指定位置或工作区已有约定写入 Markdown 初稿；默认使用 `docs/prd/`，已有文档沿用其路径。初稿落盘后才更新产品目录，只修改本次产品记录，不改写其他产品历史。

简明说明产品结论、重要未知、命名及工程标识、初稿入口和目录更新结果。只修改本次初稿和目录，不执行 Git 提交或其他开发流程。

## 5. 产品目录格式

目录只用于识别产品、理解用途、判断重复和定位初稿，不维护第二份 PRD 或开发状态。没有目录时，在初稿交付目录创建 `pcm-product-catalog.json`。

统一使用以下字段与类型，不自行增减字段。示例只说明结构，不是选题或命名范本：

```json
{
  "catalogVersion": "2.0",
  "updatedAt": "2026-09-12",
  "products": [
    {
      "productId": "PCM-20260912-001",
      "brand": {
        "zh": "花束到店",
        "en": "Bouquet Pickup",
        "subtitle": "花束预订与到店取件"
      },
      "repository": "bouquet-pickup",
      "targetUsers": ["花店店员", "预订花束的顾客"],
      "coreNeed": "明确花束要求、备花安排和取件时间，减少遗漏与错领。",
      "coreBusinessLoop": ["提交花束预订", "确认要求与取件时间", "制作花束", "通知取件", "完成交接"],
      "productForm": "Web 应用",
      "prdFile": "花束到店-花束预订与到店取件-产品初稿.md",
      "createdAt": "2026-09-12",
      "updatedAt": "2026-09-12"
    }
  ]
}
```

- 顶层固定为 `catalogVersion`、`updatedAt`、`products`；产品和 `brand` 固定为示例字段。除 `brand.en` 可为 `null` 外，文本为非空字符串；`targetUsers`、`coreBusinessLoop` 为非空字符串数组，`products` 可以为空。
- `productId` 唯一且稳定。新 ID 沿用 `PCM-YYYYMMDD-NNN`，日期为创建日，序号取目录现有最大序号加一，至少三位；既有 ID 不因改名或更新日期改变。
- `repository` 是预定工程标识，不代表仓库已创建；在目录内唯一，与初稿工程标识一致。
- `coreBusinessLoop` 按业务顺序简述用户从进入到取得结果的过程，不复制完整功能清单。
- `prdFile` 使用相对于该 JSON 所在目录的文件路径，不使用机器绝对路径。目录位于 `docs/prd/` 且初稿同目录时，只写文件名；交付前核验所指文件真实存在。
- 日期使用 `YYYY-MM-DD`。`createdAt` 保持不变；本次记录变动时更新其 `updatedAt` 和顶层 `updatedAt`，不改动其他记录日期。
- 按 `productId` 更新已有产品，新增前核对 ID 和工程标识不重复。没有用户、用途或业务过程依据时，不为填满字段编造内容。
