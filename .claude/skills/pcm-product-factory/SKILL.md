# Web 应用产品构思与初稿

把本次想法发展为具体、自洽的 Web 应用产品设计，交付实际的 Markdown 初稿。没有既定方向时自主构思；已有方向时围绕它展开。默认直接完成一个产品，数量和交互方式遵从用户本次要求。

流程组织工作，不预设产品答案。市场、人群、领域、规模、功能、角色、产品形态、品牌和视觉表达由本次输入与产品自身决定。

## 1. 理解输入

阅读本次要求与相关资料，区分明确条件、参考信息和未知。只有必须由用户决定的实质冲突才中断询问；其余自行判断，将影响设计的重要假设写入初稿。

工作区存在 `pcm-product-catalog.json` 时，读取现有记录了解已规划产品。历史只用于识别重复和保护既有身份，不作为构思范本或选题范围。

## 2. 构思与设计

自主探索并确定产品方向，不规定候选数量、分类、评分或筛选顺序。需要外部事实支持判断时进行针对性研究，如实区分查得的事实与推断。

从产品用途和实际使用过程形成设计，让功能、规则和体验有各自成立的理由。已有明确要求与身份保持一致；未确定的产品名称自主确定，工程标识按工作区约定处理。

## 3. 形成初稿

初稿应让接手者理解产品是什么、为谁而做、为何值得使用、如何使用、当前设计包含什么，以及怎样判断核心结果成立。影响产品成立的依赖、假设与未知如实说明，不以虚构能力掩盖缺口。

章节、顺序、篇幅和细节由产品决定，不套固定目录。具体内容来自本次产品设计；初稿用于继续讨论和深化，不提前承担详细工程设计与开发交付规范。设计提案不冒充用户已确认要求；外部资料只引用本次真实查阅且影响判断的来源。

## 4. 复核

检查设计是否自洽，是否回应本次输入，是否存在缺乏产品依据、仅因惯例而添加的内容。与历史产品相似时，判断是否存在实质重复，不为表面差异强行改变合理设计。

修正问题后再交付，不输出内部候选池或评分过程。

## 5. 交付

按用户指定位置或工作区已有约定写入 Markdown 初稿；已有文档沿用其路径和产品身份，不擅自覆盖其他产品。

初稿落盘后更新已有产品目录；没有目录时，在交付目录创建 `pcm-product-catalog.json`。目录只维护识别产品、理解用途和找到初稿所需的索引信息，沿用已有容器与必要身份字段，不为填满旧记录字段补造产品内容，不改写其他产品历史。

简明说明产品结论、重要未知、初稿入口和目录更新结果。只修改本次初稿和目录，不执行 Git 提交或其他开发流程。
