# requirement-breakdown — 大需求拆分与 Backlog 规划

## 定位

本 Skill 将用户提供的项目目标、产品场景、需求资料、现有系统信息或对话内容，整理并拆分为一组围绕用户任务或内聚业务能力、具有明确产品结果、范围、前置依赖和建议开发顺序的大需求，形成通俗易读、可用于后续设计和开发的 Backlog。

它回答：

- 目标用户或使用方在什么场景下需要解决什么问题；
- 当前项目或增量范围需要完成哪些大需求；
- 每个大需求解决什么问题，包含什么、不包含什么；
- 用户如何进入并完成核心任务，最终能够观察到什么结果；
- 哪些异常、空状态、权限或恢复路径会影响需求是否完整；
- 开始开发前必须完成哪些大需求；
- 完成后用户、系统或其他模块获得什么真实能力；
- 哪些端到端需求完成后，普通业务功能才真正可用；
- 应如何根据依赖关系安排推进顺序。

## 独立调用与职责边界

本 Skill 是独立调用的规划能力：

- 不知道自己位于工作流的什么位置；
- 不要求先调用任何其他能力，也不要求完成后调用什么；
- 不依赖固定文档名称、编号体系、仓库结构或技术栈；
- 不成为其他能力的强制前置；
- 编排顺序、输入转换和运行期调度由外部编排决定。

本 Skill 不负责：

- 详细数据库表结构和完整业务接口列表；
- 完整页面流程、线框图、视觉稿、组件层级和逐字段交互设计；
- 类、函数、目录、代码层和具体框架写法；
- 编写代码、启动服务和执行测试；
- 运行期状态流转、交付登记、执行记录和下一个需求调度；
- 自动启动任何后续设计或开发能力。

Backlog 可以保留简洁状态字段，但本 Skill 只在新建或重构文档时初始化、保留或建议状态，不持续维护开发过程。

## 输入适配

可以接收以下一种或多种输入：

- 用户自然语言描述和多轮对话；
- 项目说明、需求说明、产品功能说明；
- 技术方向、体验约束、验收要求；
- README、现有代码、已有功能、API 文档；
- 已有 Backlog；
- 用户指定的局部模块或新增范围。

缺少某一种标准文档、固定 ID 或固定章节时，不拒绝执行。先根据已有信息工作，只追问真正影响范围、边界、依赖、初始化、用户结果或真实闭环的问题。

## 多视角与事实边界

拆分时从需求相关的多个视角形成统一结论，而不是让虚拟角色分别输出意见：

- 用户与产品视角关注目标用户、使用场景、核心任务、业务价值和可见结果；
- 体验与交互视角关注入口、关键路径、状态反馈、容错、恢复和必要的可访问性；
- 客户端、服务端与数据视角关注各交付面如何共同兑现产品行为；
- 测试与质量视角关注如何从用户操作和真实系统状态共同证明完成；
- 安全、运维或外部协作等专项视角只在需求相关时使用。

产品与体验判断也必须区分：

- 已确认事实：来自用户说明、产品资料、现有系统或已验证行为；
- 现有惯例：当前产品、平台或设计系统已经稳定采用的做法；
- 合理默认：低风险、易调整且不改变产品范围的常规选择；
- 产品假设：缺少直接证据但拆分暂时依赖的判断；
- 待确认决策：会改变范围、用户结果、安全、兼容性或显著成本的选择。

产品视角用于发现遗漏、冲突和体验风险，不授权自行扩大范围。未经证据支持的新能力应作为建议、假设或待确认事项，不直接写入承诺范围。纯服务、CLI、数据处理或基础设施需求也要识别真实使用方和结果，但不强行填写 UI/UX 内容。

## 对话优先，文档后置

收到资料后，不直接静默生成最终文档。

先向用户说明：

- 当前理解的项目目标、目标用户、使用场景和范围；
- 已识别的业务模块、用户任务与共享能力；
- 已确认事实、现有惯例、合理默认、产品假设和待确认问题；
- 初步拆分方向和关键依赖；
- 可能遗漏的核心路径、状态反馈、首次可用或跨模块闭环。

需要澄清时，一次只询问一个会改变拆分结果的关键问题。不要在这里追问应由后续设计决定的 ORM、接口路径、表字段、类名或测试框架。

信息足够后，先在对话中给出简洁拆分草案，至少包含：

| 候选 ID | 大需求 | 类型 | 前置依赖 | 完成结果 |
|---|---|---|---|---|

同时解释：

- 为什么这样拆；
- 哪些内容被合并或拆开；
- 哪些涉及多个交付面的端到端需求承担真实联调；
- 哪项能力处理首次初始化；
- 哪些模块可以独立推进。

用户确认草案后再生成或更新正式 Backlog。用户明确要求依据充分资料直接生成时，可以减少讨论，但仍须说明重要假设并完成质量检查。

## 大需求定义

一个大需求是：

> 围绕一项内聚业务能力形成的、可独立进入设计、开发和验证的交付单元。

合适的大需求通常具备：

- 一个可以用通俗语言说明的主要目标；
- 明确的目标用户、使用场景或实际调用方；
- 一组围绕同一用户任务或业务能力的范围；
- 从任务入口到可观察结果的完整关键路径；
- 明确、可观察的产品和系统完成结果；
- 一组内聚的核心验证场景；
- 清楚的前置依赖；
- 一次设计和开发可以稳定掌握的上下文规模。

大需求不等于一个接口、一张表、一个页面组件、一个代码层、一个目录、一个仓库或一次固定开发运行。

## 拆分方法

### 明确当前边界

先确认 Backlog 覆盖整个项目还是局部增量，并识别：

- 本次需要实现的内容；
- 明确不在本次范围内的内容；
- 已经存在、可以直接使用的能力；
- 不属于当前 Backlog 的外部系统和运行条件。

只拆新增模块时，不重新生成整个项目计划。

### 按业务模块组织

使用用户能够理解的业务概念组织内容，例如身份认证、用户管理、内容管理、订单处理和统计分析。模块用于阅读和归类，不代表每个模块固定产生相同数量的大需求。

### 识别共享基础能力

识别被多个模块共同依赖的应用运行、持久化、身份、权限、文件、消息或外部服务连接能力。

共享基础大需求也必须有真实效果。不要把“创建目录”“安装依赖”“增加基础类”单独作为大需求。

### 按端到端业务能力形成候选项

针对每个模块判断：

- 目标用户或调用方是谁，在什么场景下产生操作意图；
- 用户最终需要完成什么，核心任务从哪里开始、在哪里结束；
- 用户完成任务后能够观察到什么，是否与真实系统状态一致；
- 入口、加载、空数据、校验失败、无权限、重复操作和恢复路径中，哪些会影响需求完整性；
- 系统需要对外提供什么业务能力；
- 哪些产品行为和业务规则必须一起成立才有意义；
- 哪些部分可以独立产生使用价值并被真实验证；
- 哪些部分具有不同的前置依赖、产品风险或验证方式；
- 哪些交互问题必须在后续设计中确定，哪些可遵循现有惯例自主决定。

默认围绕用户任务或端到端业务结果形成垂直大需求，不因为客户端、服务端、数据库、页面或接口属于不同代码层就机械拆开：

```text
用户目标与完成结果
    ├─ 用户流程与交互反馈
    ├─ 客户端呈现与状态处理
    ├─ 服务端业务规则
    ├─ 数据、权限与外部协作
    └─ 真实环境中的端到端验证
```

如果各交付面单独完成都不能产生有意义的产品结果，应合并为同一个大需求，并在后续设计和开发中明确协作边界。服务端或其它底层能力只有在能够独立服务真实调用方、被多个需求共享、需要提前稳定公共契约，或其本身就是产品交付面时，才适合单独拆分。

这里的用户端、客户端和服务端根据项目形态确定，不假设一定是 Web、REST 或前后端分仓。纯服务、API、CLI、移动端、桌面端、数据处理和外部集成项目使用适合自身的使用方、交付面和完成结果。

### 识别业务闭环

普通功能的真实联调直接属于对应端到端大需求的完成条件，不机械增加独立联调项，也不为了归属联调而拆出单独的用户端需求。

只有跨模块、跨角色、异步或多阶段流程具有独立验收价值时，才增加业务闭环大需求。即使存在跨模块闭环，前面的普通用户端功能也不能只通过 Mock 完成。

## 颗粒度判断

考虑拆开一个候选项，当它：

- 包含多个独立用户任务或业务目标；
- 各部分前置依赖明显不同；
- 一部分完成后已经能独立产生使用价值；
- 产品行为、业务规则和上下文过大；
- 验证方式明显不同；
- 包含具有独立价值的跨模块流程。

考虑合并多个候选项，当它们：

- 单独完成都不能让用户或真实调用方获得有意义结果；
- 只是客户端、服务端、数据库、目录、文件或代码层不同；
- 必须同时成立才构成完整用户任务或业务能力；
- 目标、依赖和验证方式基本相同；
- 只是为了制造并行度而被拆开。

不使用固定工期、接口数量、文件数量或“每个模块固定几项”的公式。复杂模块可以在同一交付面拆成多个大需求，但必须按业务能力拆分。

## 依赖关系

### 前置依赖

前置依赖只有一个严格语义：

> 当前大需求开始开发前，所有前置依赖必须已经完成。

要求：

- 指向明确存在的大需求 ID；
- 不允许自依赖、未知依赖和循环依赖；
- 不写成“数据库”“后端”“基础模块”“前面的任务”等模糊对象；
- 不为了顺序整齐而把互不依赖的模块强行串行化。

数据库、第三方服务和账号等不属于 Backlog 大需求的条件放入“外部依赖”。

### 关联需求

关联需求表示有助于理解的业务联系，不控制开发顺序，也不参与调度。

### 用户交付面的依赖与路径反查

对每个包含用户交付面的端到端大需求或确有独立价值的用户端大需求，反向检查真实开发和验收需要的：

- 用户从何处进入，是否存在必要的导航、前置页面或客户端基础能力；
- 身份如何获得，目标用户是否具有可建立的权限；
- 全部必要的服务端业务规则、数据和外部协作能力；
- 空系统能否产生首条业务数据，是否存在首次使用死锁；
- 操作结果能否被用户再次读取、确认，并与真实系统状态对应；
- 失败后是否存在继续、重试、返回或恢复路径。

只有当前需求开始开发前必须完成的能力才列为严格前置依赖，不把每个页面或交互步骤机械拆成依赖。不能使用静态数据或 Mock 绕过尚未真实可用的关键能力。

## 真实完成规则

以下规则按大需求实际包含的交付面应用，不要求为了套用规则把一个端到端大需求拆成服务端和用户端两项。

### 服务端能力

涉及业务数据或业务操作的服务端大需求，完成标准应要求：

- 正式运行路径使用真实业务实现；
- 需要持久化的数据连接项目配置的真实数据库；
- 实际启动服务或执行项目真实运行入口；
- 通过项目对外提供的真实入口验证核心成功和失败场景；
- 验证数据写入、读取、修改和必要约束；
- 服务重启后数据仍然存在；
- 空数据库能够通过项目约定方式准备到可运行状态。

只有代码、单元测试、接口文档、路由注册或测试方法说明，不足以证明服务端大需求完成。固定响应、内存数组、临时文件和假数据访问实现不能代替正式业务能力。

### 用户交付面

包含用户交付面的端到端大需求或确有独立价值的用户端大需求，其完成标准应根据需求风险要求：

- 所有严格前置依赖已经真实完成；
- 启动真实服务端和用户端应用；
- 用户端连接真实服务地址；
- 使用真实初始化身份或测试身份；
- 目标用户能够找到入口，并在浏览器或项目真实客户端环境中完成核心任务；
- 初始、加载、空数据、提交中、成功、失败、无权限和恢复等相关状态具有清楚且及时的反馈；
- 防止或正确处理重复操作，失败后不无故丢失仍可继续使用的输入；
- 验证页面或客户端结果与服务端、真实数据库状态一致；
- 适用时验证基本键盘操作、焦点、标签、错误关联以及不只依赖颜色表达状态；
- 必要时刷新页面、重新进入或重启服务，确认结果不是临时状态。

包含用户交付面的普通需求完成，即表示目标用户已经能够真实完成对应业务任务。不能把常规联调统一推迟到项目末尾，不能只证明页面存在、API 调通或浏览器能够点击，也不能把未执行的真实验证交给用户后仍标记完成。

### 无法真实验证

数据库、服务、第三方凭据或浏览器环境不可用时，保留原完成标准并记录未完成或阻塞原因。不得自动切换 Mock、删除验收场景或降低标准后宣称完成。

## Mock 与开发数据

Mock 可以用于：

- 单元测试和组件测试；
- 局部界面状态开发；
- 难以稳定制造的异常、超时和第三方故障场景；
- 不在当前范围内的外部系统替身。

Mock API、静态 JSON、内存数据访问、固定响应或假数据页面不能单独作为业务需求完成依据。

真实写入项目数据库、通过真实服务读写的初始化或测试数据属于合法开发数据；仅存在于 Mock、代码常量或临时文件中的数据属于假实现。项目保留 Mock 模式时，真实服务连接仍应是正常开发和验收路径，不能因默认配置意外进入 Mock。

## 初始化与首次可用

拆分项目时检查：

- 系统是否需要登录；
- 是否提供公开注册；
- 没有注册时首个身份如何产生；
- 空数据库是否可以启动和进入系统；
- 是否需要基础角色、权限、菜单、字典或示例业务数据；
- 初始化是否可以安全重复执行；
- 初始化后能否完成首个真实业务流程。

如果系统需要登录、没有公开注册且空数据库中没有身份，Backlog 必须包含确定的初始身份能力。根据复杂度，可以合并到身份能力、数据基础能力，或单独拆成初始化大需求。

初始化完成标准通常包括：

- 空数据库可以执行初始化；
- 初始身份可以真实登录；
- 必要基础数据关系正确；
- 重复执行不会创建重复数据；
- 已有业务数据不会被覆盖；
- 初始化后系统可以进入首个真实功能。

开发环境初始凭据可以来自 `.env`、开发配置或初始化命令参数。Agent 可以读取、创建和修改开发环境 `.env` 以完成真实功能验证，但真实秘密必须被 Git 忽略，不得写入文档、审查内容、提交记录或对外输出。

## 环境原则

- 默认使用用户已经准备好的数据库和中间件；
- Agent 不主动使用 Docker 或 Docker Compose 启动数据库、中间件或应用；
- 依赖不可用时先检查现有环境和配置，不擅自创建容器；
- 不因为真实依赖不可用而改用假数据完成验收；
- 最终是否提供容器化交付能力由用户在交付阶段单独决定。

开发期间不维护详细数据库设计文档作为事实源。数据结构以项目代码、实体、Schema、迁移或项目实际采用的机制为准；Backlog 只说明是否需要持久化、结构准备和初始化数据。

## Backlog 文档结构

默认建议输出到：

```text
docs/backlog/<项目或范围名称>-backlog.md
```

用户可以指定其他路径。推荐结构：

```markdown
# <项目或范围名称> Backlog

## 范围说明
## 拆分思路
## 全局完成原则
## 开发路线
## 大需求总览
## 大需求详情
### <业务模块>
#### BR-001 <大需求名称>
## 整体风险与待确认事项
```

小项目可以省略不必要章节，不保留空模板。开发路线可以使用自然语言和 Mermaid 辅助展示；详情卡中的前置依赖是主要依据，图、总览表和详情卡必须一致。

### 大需求总览表

| ID | 大需求 | 类型 | 业务模块 | 前置依赖 | 状态 | 完成结果 |
|---|---|---|---|---|---|---|

新文档使用中性、稳定 ID，例如 `BR-001`。ID 只负责唯一标识，不编码交付面、模块、优先级、状态或开发顺序；调整顺序时不重新编号。

新需求默认状态为“待开发”。重构已有文档时保留可靠状态；对尚未建立可靠归档、发生拆分、合并或真实完成证据不足的状态，建议使用“待核验”。

### 已归档历史与需求演进

- 正式验收并归档的已完成需求属于不可变历史。必须保留其 ID、标题、范围、验收标准、状态和历史 TRD 链接；这些历史字段不得修改，即使后续发生拆分、合并或发现新范围。
- 旧 Backlog 中导入的 `done` 状态，如果尚未建立为可靠历史，仍可在真实完成依据不足时标记为“待核验”。“待核验”只适用于可靠归档尚未建立的状态，不适用于已经正式验收并归档的完成历史。
- 新需求如果是对已归档需求的升级、重构、替代、补完或缺陷修复，必须创建新的 Backlog 项、使用新的稳定 ID，并为该演进创建新 TRD。历史需求和历史 TRD 不改写；新项应说明保留的行为、变化或替代的行为、兼容或迁移要求，以及新的完成结果。
- 可以在详情卡中增加以下可选内容：

  ```markdown
  ### 演进关系

  - 类型：升级 / 重构 / 替代 / 补完 / 缺陷修复
  - 演进自：BR-006
  ```

  `演进自`只记录历史谱系，不自动等同于“前置依赖”。只有当另一个尚未完成的需求确实必须先完成、当前需求才能开始时，才把它列为严格前置依赖。

### 大需求详情卡

必备内容：

```markdown
## BR-xxx 大需求名称

**类型：**
**业务模块：**
**状态：**

### 目标
### 完成后的效果
### 包含范围
### 不包含范围
### 前置依赖
### 关键业务规则
### 完成标准
### 验证场景
```

按需增加：

- 来源依据；
- 目标用户与使用场景；
- 核心用户路径；
- 产品行为与体验约束；
- 关联需求；
- 初始化与首次可用要求；
- 外部依赖；
- 风险与待确认事项；
- 后续设计重点。

用户可见或交互式需求通常应说明目标用户与使用场景、核心用户路径，以及影响范围和完成结果的产品行为与体验约束；纯内部能力不强行填写。核心路径只描述任务入口、关键步骤和可观察结果，不在 Backlog 中固定页面布局、组件、字段或接口。

不适用的可选章节直接省略，不为模板完整填写大量“无”“暂无”或“待定”。

详情卡使用通俗业务语言，不默认写详细表结构、完整接口列表、类名、函数名、目录、框架写法、测试命令、代码提交或运行记录。

## 重构已有 Backlog

收到已有 Backlog 时：

- 先说明当前拆分方式、主要问题和拟调整方向，不直接覆盖；
- 提出合并、拆分、重命名和依赖调整草案；
- 保留稳定业务范围、业务规则、有效验收结果和可靠状态；
- 移除技术实现清单、Mock 实现清单和开发流水；
- 用户确认后再修改正式文档。

旧 ID 已被其他资料引用时，不自动批量改号。确需迁移时先检查引用并提供旧新 ID 映射。

旧需求拆分或合并后，不机械继承“已完成”。如果旧完成依据只是 Mock、假数据、代码存在或测试说明，且该 `done` 尚未建立为可靠历史，应标记为“待核验”，明确需要补做的真实验证；正式验收并归档的完成历史不得改写。

## 质量检查

生成草案前和正式写入后，检查：

### 范围与业务价值

- 用户明确提出的功能都有归属；
- 非本次范围没有被误加；
- 已有能力没有被重复拆分；
- 每项完成后都有真实业务效果；
- 不自行扩展未要求的企业级能力。

### 颗粒度

- 不存在多个无关目标混在一个巨型需求中；
- 不存在只创建接口、表、文件或代码层的小项；
- 合并和拆分理由能够解释；
- 不以制造并行为拆分目标。

### 依赖

- 所有引用 ID 存在；
- 无自依赖和循环依赖；
- 每个需求都有合理启动路径；
- 用户端依赖完成核心任务所需的全部关键能力；
- 独立模块没有被错误串行化。

### 产品与体验完整性

- 每项用户可见需求都有明确的目标用户或使用方、使用场景和完成结果；
- 大需求围绕用户任务或端到端业务结果拆分，没有机械按客户端、服务端或数据库分层；
- 核心路径的入口、关键操作、状态反馈和可观察结果完整；
- 加载、空状态、失败、无权限、重复操作和恢复路径已按相关性与风险考虑；
- 用户看到的结果能够与真实服务端和数据状态相互验证；
- 未经确认的产品假设没有被写成确定事实或承诺范围；
- 没有为了“体验完整”擅自增加业务能力；
- 无交互需求没有被强行套用 UI/UX 模板。

### 真实可用

- 服务端要求真实运行入口和真实持久化；
- 用户端要求真实客户端或浏览器联调；
- Mock 不作为完成依据；
- 初始身份和首次可用没有遗漏；
- 普通联调没有被推迟到最终人工收尾。

### 可读性与一致性

- 非技术用户能够理解标题、目标和效果；
- 不以大段 YAML 为主要形式；
- 不机械重复全局规则；
- 不保留大量空章节；
- 总览表、详情卡、开发路线和依赖图一致；
- 没有混入应由后续设计维护的易变技术细节。

### 已归档历史与演进

- 正式验收并归档的需求未被重写，且 ID、标题、范围、验收标准、状态和历史 TRD 链接均被保留；
- 每项升级、重构、替代、补完或缺陷修复工作都创建了新项和新的稳定 ID，并指向或将产生新 TRD，而不是改写历史 TRD；
- `演进关系`只表示历史谱系，没有被误用为前置依赖；
- “待核验”只用于可靠历史仍在建立中的状态，而不是用于改写已归档的完成历史。

### 常见错误

- 错误：发现旧需求不完整就把已归档的 `done` 改成“待核验”。正确做法是保留已归档历史，新增一个完成、补完或纠正需求，并使用新的稳定 ID。

发现问题时先修正草案或文档，再向用户报告完成。

## 完成输出

完成后向用户说明：

- 生成或更新了哪个文件；
- 共拆分多少个大需求；
- 主要依赖链和建议推进方向；
- 哪些涉及多个交付面的端到端需求承担真实联调；
- 哪项能力处理初始化和首次可用；
- 是否存在待确认或待核验项。

不自动启动任何后续能力。
