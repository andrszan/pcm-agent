# requirement-breakdown — 大需求拆分与 Backlog 规划

## 定位

本 Skill 将项目或增量的最终范围拆分为一组围绕用户任务或内聚业务能力的正式大需求。每项大需求都应具有明确目标、完整范围、可观察结果、严格前置依赖和真实完成标准，最终形成可继续设计与开发的 Backlog。

Backlog 负责说明“要交付哪些完整能力、为什么这样拆、依赖什么、如何证明完成”，不提前固定详细页面、组件、字段、类、函数、表结构、完整接口或具体实现步骤，也不记录“待开发”“开发中”“已完成”“阻塞”等需求开发状态。

当前活动需求、完成情况和恢复位置由调用方使用外部结构化状态管理；本 Skill 不推断、迁移或更新这些运行期状态，也不根据状态删除、降级或改写需求内容。业务对象或业务流程自身的状态仍可作为需求范围和规则的一部分。

## 输入与事实边界

可以接收任意组合：

- 用户自然语言、多轮对话、项目或产品资料；
- 需求说明、体验约束、验收要求或总体技术方向；
- README、现有代码、可运行系统、接口契约和测试；
- 已有 Backlog，或用户指定的局部模块和新增范围；
- 与当前范围相关、可访问且可核验的工程架构资料。

有此类工程架构资料时，按需读取模块职责、稳定公开能力、依赖方向、目录职责、文件归属和 Current/Target 差异，并与当前代码、契约、测试和运行事实交叉核验；资料未提供、不相关、漂移或不足时，仍独立完成拆分，只暴露无法安全判断的高影响缺口，不索取固定文件、步骤或其它 Skill。缺少标准文档或固定 ID 时继续根据现有事实工作，只追问会改变最终范围、边界、依赖、首次可用、用户结果或真实闭环的问题。

拆分时区分：

- **已确认事实**：来自用户说明、产品资料、当前系统或已验证行为；
- **现有惯例**：项目或平台已经稳定采用的做法；
- **合理默认**：低风险、易调整且不改变产品范围的常规选择；
- **产品假设**：尚无直接证据但拆分暂时依赖的判断；
- **待确认决策**：会改变范围、用户结果、安全、兼容性或显著成本的选择。

产品和体验视角用于发现遗漏、冲突与不必要复杂度，不授权自行扩大或缩减范围。纯服务、CLI、数据处理或基础设施需求也要识别真实使用方和结果，但不机械补写 UI 内容。

## 对话与草案

收到资料后，先说明：

- 当前理解的目标用户、使用场景、最终范围和非目标；
- 已识别的用户任务、业务模块、共享能力和现有基础；
- 事实、假设、待确认问题和可能遗漏的闭环；
- 初步拆分方向、复杂度热点和关键依赖。

需要澄清时，一次询问一个会改变拆分结果的关键问题。信息足够后，先给简洁草案：

| 候选 ID | 大需求 | 类型 | 前置依赖 | 完成结果 |
|---|---|---|---|---|

同时解释合并与拆分理由、首次初始化归属、端到端真实联调归属、可并行模块和建议的首条验证切片。用户确认草案后再生成或更新正式 Backlog；用户明确要求依据充分资料直接生成时，可以减少讨论，但仍须公开重要假设并完成质量检查。

## 拆分方法

### 1. 建立最终范围覆盖表

先确认 Backlog 覆盖整个项目还是局部增量，并列出：

- 本次最终交付必须包含的用户能力、业务规则、异常与恢复；
- 明确非目标；
- 已存在且可直接复用的能力；
- 外部系统、账号、数据、环境和其它运行条件。

将每项已确认范围映射到一个大需求或全局完成原则。任何未归属、重复归属或被拆分过程遗漏的内容都必须在草案中暴露并修正。只拆局部增量时，不重建整个项目计划；但该增量的最终范围仍须完整覆盖。

### 2. 按用户任务和业务能力组织

一个大需求是：

> 围绕一项内聚业务能力形成、可独立进入设计和开发，并能通过真实系统验证完整结果的正式交付单元。

合适的大需求通常具有：

- 一个清楚的用户或调用方目标；
- 明确场景、入口、关键路径和完成结果；
- 围绕同一目标的业务规则、异常和恢复；
- 内聚的真实验证场景；
- 清楚的前置依赖；
- 一次设计和开发可以稳定掌握的上下文。

有可核验的工程架构资料时，按需关联需求所属业务模块、稳定公开能力和跨边界约束，但仍按用户任务和业务结果拆分；不得按目录或文件归属拆需求。工程依赖方向只说明实现协作，不自动等于 Backlog 的严格前置依赖。

默认形成端到端大需求，不按客户端、服务端、数据库、页面、接口、目录或仓库机械分层。各交付面单独完成都不能产生有意义结果时，应合并为同一大需求。底层能力只有能独立服务真实调用方、被多个需求共享、需提前稳定公共契约，或本身就是交付面时，才适合单独拆分。

普通功能的真实联调属于对应大需求的完成条件。只有跨模块、跨角色、异步或多阶段流程本身具有独立目标和验收价值时，才增加业务闭环大需求。性能优化、容量验证、基础设施调整或既有模块重构只有在自身具有已确认结果、独立风险与验收价值，且不能作为当前业务需求内的相称实现工作完成时，才单独形成需求；不得为使业务需求显得完整而把没有依据的工程专项夹带进去，也不得把已确认的必要专项隐去。

### 跨需求体验决定

可接收任意来源、与当前范围相关的已确认 Target 或有依据的默认 Target。只有已确认 Target 要求演进既有产品表面、迁移本身形成独立可观察的用户结果，且开始其它需求前确实必须完成时，才创建正式迁移 BR，并按该严格前置关系建立依赖。默认 Target 只作为相关业务需求的体验约束，保留依据和重新评估条件，不单独制造迁移 BR 或严格依赖；若某需求需要偏离默认 Target，或偏离会改变跨需求体验骨架，则暴露为待确认决定。任何情况下都不按页面、组件、CSS 或目录拆分，也不把框架文档或其它 Skill 写为依赖。

### 3. 检查不必要复杂度

逐项检查是否存在：

- 没有独立职责或权限差异的额外角色；
- 不能影响业务结果、恢复或审计的额外状态；
- 可合并、自动完成或移除的操作步骤和页面跳转；
- 系统已经知道却要求用户重复输入的信息；
- 同一信息在多个阶段重复填写且没有明确理由；
- 只为代码分层、组织结构、制造并行度或降低单项表面耗时而拆出的需求；
- 没有当前容量、延迟、合规或运行风险依据，却被附加为硬性完成门槛的性能、基础设施或全面验证专项；
- 名称不同但目标、规则、依赖和验证基本相同的重复能力。

可以主动建议合并或删除，并说明保留的产品结果、影响和风险。未经确认，不得因为实现困难、工期压力或现有代码限制静默裁剪最终范围。

### 4. 判断颗粒度

考虑拆开，当候选项包含多个独立目标、前置依赖明显不同、部分完成已产生独立价值、上下文过大、验证方式不同，或包含有独立价值的跨模块流程。

考虑合并，当候选项单独完成没有真实价值、必须同时成立才构成完整任务、目标与依赖基本相同，或只是交付面和代码层不同。

不使用固定工期、接口数、文件数或“每模块固定几项”的公式，也不为了让单项设计或开发时长看起来更短而拆成必须连续完成、分别没有用户价值的多个需求。颗粒度判断服务于完整结果、可掌握上下文和真实依赖；拆分后的总设计、交接、集成和回归成本同样需要考虑。

### 5. 建议首条验证切片

开发路线应建议一条最先验证关键价值和高风险假设的切片。它必须由**一个完整正式需求**，或**多个各自完整、共同形成首个真实闭环的正式需求**组成，并满足各自全部范围和完成标准。

首条验证切片只是开发与验证顺序建议，不是 MVP、半完成需求、Mock 演示或范围缩减；不能把选中需求拆成“先做页面”“先通接口”或“先用假数据展示”，也不能把未进入首条切片的最终范围降为可选项。

## 依赖与开发路线

### 前置依赖

前置依赖只有一个严格语义：

> 当前大需求开始开发前，所列大需求必须已经完成。

要求：

- 只指向 Backlog 中存在的稳定需求 ID；
- 不允许自依赖、未知依赖和循环依赖；
- 不写“数据库”“后端”“基础模块”或“前面的任务”等模糊对象；
- 不为顺序整齐把互不依赖的模块强行串行化；
- 数据库、第三方账号和运行环境等条件放入“外部依赖”。

关联需求只表达业务联系，不控制开发顺序。工程架构资料中的依赖方向、目录职责或文件归属也不自动构成严格前置依赖；只有符合“开始前必须完成”语义的 Backlog 大需求才可列入。

### 路径反查

对包含用户交付面的需求，反查：入口和导航是否存在、身份和权限如何获得、服务端与数据能力是否齐全、空系统能否产生首条业务数据、结果能否再次读取确认、失败后能否重试或恢复。

再从完成标准和验证场景反查实际需要的业务对象、入口和来源，不能只检查显式依赖列表无环：

- 公共能力通过已存在或本需求交付的首个真实调用方验证；后续业务的接入由各自需求负责验收。例如图片能力先验证物品图片，后续维修、返修需求分别验证自己的图片接入，不能反过来成为公共图片能力的完成条件。
- 调用方逐条完成需求时，声明的前置满足后，当前需求应能完整实现并验收，不再等待尚未开发的需求。发现缺口时调整前置关系、重新划分接入归属，或合并无法独立交付的能力；保留最终范围，不用 Mock、降低完成标准或提前实现后续需求绕过。
- 只有调用方确实支持多需求并行和后续收口时，才安排“可先开始、待其它需求完成后集成验收”，并明确承担集成的需求和完成条件。不假设调用方能挂起未完成需求，也不以“关联需求”或“最终验收时接入”掩盖实际等待关系和循环。

开发路线根据上述核验、依赖和首条验证切片给出建议顺序与适用的并行关系，不把建议顺序伪装成依赖，不把每个交互步骤拆成依赖，也不制定具体排期。

## 真实完成原则

完成必须由当前大需求涉及的真实交付面共同证明，而不是由代码存在、文档、Mock 或未执行的测试说明代替。

### 服务与数据能力

涉及业务操作或持久化时，应要求：

- 正式运行路径使用真实业务实现和项目配置的真实数据库；
- 实际启动服务或执行项目真实入口；
- 通过项目对外入口验证核心成功、失败和权限场景；
- 验证数据写入、读取、修改和关键约束；
- 刷新、重进或服务重启后结果仍正确；
- 空数据库可按项目约定准备到可运行状态。

### 用户交付面

包含界面或其它用户客户端时，应按风险要求：

- 真实客户端连接真实服务，使用适用角色的真实开发账号；
- 目标用户能找到入口并完成核心任务；
- 加载、空数据、提交、成功、失败、无权限、重复操作和恢复等相关状态反馈清楚；
- 失败后保留仍可继续使用的输入，用户能理解下一步；
- 客户端结果与服务端和真实数据库状态一致；
- 适用时验证键盘、焦点、标签、错误关联和不只依赖颜色表达状态；
- 必要时刷新、重新进入或重启，确认不是临时假象。

纯内部变化按其真实调用方、数据和系统行为验证，不强套浏览器或 UI 标准。

### Mock、阻塞与开发数据

Mock 可支持单元测试、组件状态和难以稳定制造的外部故障，但不能单独作为业务需求完成依据。固定响应、静态 JSON、内存数组和假数据页面不能代替正式能力。

真实依赖不可用时，保留原完成标准，记录阻塞原因和补验条件，不自动降低标准后宣称完成。通过真实服务写入项目数据库的初始化或开发验证数据属于真实开发数据。最终保留在交付开发数据中、交付后仍可登录目标产品的所有开发账号及密码均为受版本控制的产品交付信息；PCM 或目标产品用于访问其它系统或资源的凭据及真实个人认证信息仍属秘密，只放在 Git 忽略的受保护开发配置中，不写入 Backlog 或输出。

## 项目数据基线与首次交付

### 必须明确的最终效果

每次拆分都判断项目是否需要持久化开发／使用数据，并在 Backlog 中给出有事实依据的归属；不能只写“支持 Seed”“准备测试账号”或默认在末尾追加一个“初始化与全量验收”标题。

适用项目的交付承诺是：

> 客户或接手者拿到当前项目，按受跟踪说明完成依赖安装和真实服务配置后，执行一个项目级初始化命令或等价单一入口，即可获得完整、自然、可操作的初始现场；有登录能力时，可使用交付开发账号从正常入口登录并完成主要已交付任务。明确放弃当前数据时，可通过受保护的重置入口清空目标项目环境并重新获得同等完整的起点。全过程不依赖原开发者机器上的数据库现场、临时命令、未交付文件或口头说明。

这个结果是长期使用合同，不是一次验收活动。数据库有几条记录、管理员能登录、页面有内容或测试通过，都不能单独代替完整交付。

### 初始化与重置的最小合同

默认规划 `init` 与 `reset` 两种语义；名称和技术实现由项目决定，不在拆分阶段固定 CLI 框架、目录或表结构。

- **初始化**：从空的目标环境建立必要结构、参考数据、身份、角色、关联业务对象和所需持久化文件，不要求接手者再逐项执行 Seed、注册管理员或手工上传文件。已完成初始化时重复执行不新增重复对象，也不覆盖正常使用后的编辑、消耗、已读、权限变化或删除；已有来源不明的业务数据时不擅自混入、认领或清空。
- **重置**：在明确目标、归属和删除后果后，清除整个约定项目环境的数据并重新初始化；范围须说明是否包含使用者后来新增的账号、业务记录、会话、任务、上传文件和派生对象，不能用“清 Seed 数据”冒充“恢复完整起点”。环境外数据与共享资源必须保持不变，预检失败或取消不产生破坏性影响。
- **中断恢复**：初始化和重置失败后必须准确说明数据影响，并能重试已确认操作或给出清楚的受控恢复路径。跨数据库与对象存储不能假设原子回滚，不能仅数据库恢复就宣布完成。
- **避免多做第三种模式**：默认不要求向已经使用的现场自动合并新版基线、补齐用户删除内容或提供 `ensure`；只有用户明确需要并确认数据合并、删除和权限冲突语义时另行纳入。重试命令自身中断不等于新增保留式补齐能力。

### 数据内容与完整性

按产品真实任务识别并归属以下内容，不机械要求每个项目具备全部类型：

- 必要参考数据、基础角色、初始身份，以及主要角色可直接使用的关联业务对象和代表性状态；不能因产品支持公开注册就省略已承诺的可直接登录使用结果。
- 自然且符合产品领域的名称、数量、日期、内容和关系；数据要能解释来源、历史及下一步行动，不使用需求编号、fixture 标签、随机海量记录或极端状态堆砌。近期安排在首次初始化／重置时仍应合理，普通重入不平移已有历史。
- 所有最终保留且可登录的项目专用开发账号及密码，在项目既有受跟踪账号说明中记录环境、入口、角色、凭据、初始化／重置方式和主要已有数据；逐角色真实登录核验。临时测试后删除或回滚的短期账号无需记录，不冒用真实个人身份，不增加演示租户、隔离业务数据或生产禁用 Seed 等部署阶段限制。
- 数据库记录实际引用的对象存储文件、本地持久化文件及必要处理结果，必须与记录一起纳入恢复、关联和正常访问核验；源文件或生成输入可随项目可靠取得，不依赖临时第三方 URL。没有真实文件业务时不为了形式新增对象存储或图片。
- 实际环境使用稳定的产品级资源身份，开发与测试的写入／清理范围明确，不以某个需求编号作为长期数据库、账号或存储身份；账号交付信息与数据库、存储、SMTP 等基础设施秘密分开。
- 可操作开发基线与确定性自动化 fixture 分工明确。专项冲突、失败和权限测试不能要求客户日常使用的整套数据保持不可变；测试数据和对象由测试负责受控清理，不无界累积。

### 正式需求归属与开发顺序

当上述完整恢复涉及多角色、跨业务关系、持久化文件或多个零散入口时，必须创建或复用一个有独立客户交付结果的正式需求，写清本项目的数据范围、初始化／重置效果、删除边界、失败恢复、使用入口与验收场景。已有正式需求覆盖时不重复创建；简单项目可合并到一个内聚业务需求，但不能漏掉交付结果。

这不是“所有项目最后一条需求”的排版规则。首次身份和必要基础初始化应随最早依赖它们的业务能力交付；后续需求新增角色、主要任务、状态或文件时同步维护既有基线。跨模块完整恢复的收口需求按真实依赖和执行方式安排：逐条完成需求时，应在其最终验收所需的业务能力可用后进入，不能因基线需要从早期维护，就提前选择一个必须等全项目完成的需求；也不把无关需求机械设为前置。审计修复或后续增量改变数据合同后，同样要更新基线，不能永远停在最初版本。

无持久化业务数据或不依赖预置数据的产品，明确说明哪些内容不适用及原因；有登录或文件依赖的部分仍分别履行合同。单角色、数据量少、用户可以自己录入只影响是否单独拆需求，不自动免除已经承诺的初始化、恢复和接手使用结果。

### 必须进入完成标准的证据

需求详情应将下列适用结果具体化为本产品的真实场景，不能原样复制成无对象的口号。基线验收证明恢复入口、账号、数据与文件关系及接手者的代表性主要任务成立，不默认重做全部业务需求的并发、故障注入和权限负例；这些专项验证仍由各业务需求承担。初始化／重置自身的并发、权限、删除边界和失败恢复仍须验证，恢复影响业务不变量时补充针对性回归。

1. 新接手者依据 README 可发现的说明，从空目标环境执行单一入口，获得完整现场，无隐含补操作。
2. 每个交付角色从正常入口登录，能读取对应已有数据并完成代表性主要任务；有媒体时验证真实内容和权限，而不只是数据库引用存在。
3. 连续初始化，以及正常使用后误重跑初始化，都不会重复创建、覆盖使用成果或恢复已撤销权限。
4. 在目标内新增业务记录和文件后重置，再次得到完整基线；明确的范围外数据库、记录和对象前后不变。
5. 错误目标、取消、并发或在途写入、外部服务失败和中断重试均有准确结果，未完成不能宣称成功。
6. 账号说明、配置示例、源资产和恢复入口与当前项目版本一致；业务日期、数量、关系和内容在真实页面或调用路径中符合使用情境。

本 Skill 只负责把这些目标写入可实现、可验收的需求；不运行 Seed/reset、不创建资源、不声称已经完成真实恢复，也不调用开发或其它 Skill。具体技术协议在 TRD 中确定，实际证据由开发验证提供。

## Backlog 文档结构

默认建议路径：

```text
docs/backlog/backlog.md
```

推荐结构：

```markdown
# Backlog

## 范围说明
## 拆分思路
## 全局完成原则
## 开发路线
## 大需求总览
## 大需求详情
### <业务模块>
#### BR-001 <大需求名称>
## 整体风险与待确认事项
```

小项目可省略不必要章节，不保留空模板。开发路线可用自然语言或 Mermaid；总览、详情卡、路线和依赖图必须一致。

### 总览表与标识

| ID | 大需求 | 类型 | 业务模块 | 前置依赖 | 完成结果 |
|---|---|---|---|---|---|

新文档使用中性稳定 ID，例如 `BR-001`。ID 不编码模块、交付面、优先级或顺序，调整路线时不重新编号。Backlog 不设置或维护需求开发状态。

### 大需求详情卡

必须写清目标与可观察结果、范围边界、前置依赖、关键业务规则和真实完成标准；这些是信息要求，不要求逐项独立成章。默认示例：

```markdown
## BR-xxx 大需求名称

**类型：**
**业务模块：**

### 目标与完成效果
### 包含范围
### 不包含范围
### 前置依赖
### 关键业务规则
### 完成标准
```

完成标准写清必须成立的结果。验证场景按需补充能区分正确与错误行为的代表性操作、边界和预期结果；完成标准已包含这些信息时，不再另写同义场景。简单需求可合并章节，但不因精简丢掉范围、规则或验证方向。

按需增加来源依据、目标用户与场景、核心路径、体验约束、工程归属与边界关联、关联需求、初始化、外部依赖、风险与待确认事项、后续设计重点和演进关系。工程归属与边界关联只说明所属模块、稳定公开能力或跨边界约束，不写完整文件路径；不适用的章节直接省略。

适用于多个需求的完成原则集中说明，详情只补充本需求的特殊规则、场景和必要上下文；不在范围、规则、完成标准和验证场景中完整复述同一要求。已有技术或体验决定保留相关影响并引用权威说明，不复制整份协议或配置清单。

核心路径只描述入口、关键步骤和可观察结果；详情使用通俗业务语言，不固定页面布局、组件、逐字段交互、详细表结构、完整接口、类、函数、目录、测试命令或开发流水。开发中途的临时界面也不升级为永久产品承诺：例如要求“未交付能力不提供误导用户的可操作入口”，而不是反复规定过渡说明的具体位置，以及链接、按钮、route、表单、API 必须逐项不存在。

## 需求演进与既有历史

由外部状态记录确认已经正式验收并归档的需求，其 Backlog 内容是不可变历史：

- 保留其 ID、标题、范围、验收标准和历史 TRD 链接；
- 不因后续拆分、合并、缺陷或新范围而改写；
- 升级、重构、替代、补完或缺陷修复必须创建新 Backlog 项、新稳定 ID 和新 TRD；
- 新项说明保留行为、变化或替代关系、兼容或迁移要求和新的完成结果；
- `演进自`只表示历史谱系，不自动成为前置依赖。

既有 Backlog 若包含需求开发状态，调用方应在改写前将这些事实保存在外部结构化状态中。本 Skill 不迁移、推断或更新状态；正式 Backlog 不保留状态字段，也不依据状态改变需求范围、ID 或演进关系。

## 重构已有 Backlog

先说明当前拆分、主要问题和拟调整方向，再提出合并、拆分、重命名和依赖调整草案。保留稳定范围、业务规则、有效验收和历史链接，移除需求开发状态字段、易漂移的实现清单、Mock 完成声明和开发流水。

旧 ID 已被引用时不自动批量改号；确需迁移，先检查引用并提供旧新映射。用户确认后再修改正式文档。需求开发状态的保留或迁移由调用方在外部结构化状态中完成，不属于本 Skill 的修改范围。

## 质量检查

写入前后检查：

- 最终范围、规则、异常和非目标是否完整归属，没有静默遗漏或扩张；
- 是否识别并处理不必要角色、业务状态、步骤、重复输入和重复需求；
- 跨需求体验决定是否只在相关范围引用；默认 Target 是否保留依据和重议条件且未单独制造迁移 BR，已确认 Target 的迁移 BR 是否同时满足独立用户结果和严格前置条件；
- 每项需求都有真实使用方、内聚目标、完整路径和可观察结果；
- 没有按代码层机械拆分，也没有把无关目标塞入巨型需求；
- 有可核验工程架构资料时，需求的模块归属、稳定公开能力和跨边界约束不与代码、契约、测试或运行事实冲突；资料不足时不虚构这些关联；
- 前置依赖全部存在，且从完成标准反查后也没有隐藏等待或循环；路线符合调用方执行方式，外部条件、关联需求和工程依赖方向未混作严格前置；
- 首条验证切片只由完整正式需求组成，没有变成 MVP、半成品或 Mock 展示；
- 服务、客户端、数据、权限、初始化和恢复按实际范围形成真实完成证据；
- 每个项目都已明确数据基线适用性及需求归属；适用范围是否写清“接手者单入口初始化即可使用、明确重置可恢复完整起点”，以及实际角色、自然业务情境、所需文件、删除边界和失败重试，而不是只在末尾追加 Seed 标题；
- 首次可用、逐需求维护和完整恢复收口的职责是否连贯；是否避免默认引入保留式补齐／合并模式，以及以单角色、数据少或支持注册为由遗漏已承诺的交付结果；
- Mock 不作为完成依据，普通联调没有推迟到最终人工收尾；
- 总览、详情、路线和依赖图一致，且不包含需求开发状态；
- 由外部状态记录确认的既有历史未被改写，演进工作使用新项、新 ID 和新 TRD；
- 文档通俗、紧凑，不重复全局规则或保留大量空章节。

发现问题先修正文档，再报告结果。

## 完成输出

说明生成或更新的文件、大需求数量、最终范围覆盖情况、主要依赖链、首条验证切片和真实联调归属。明确数据基线的适用结论、承担需求、接手者初始化／重置后的具体结果、涉及的账号与持久化内容，以及首次可用和后续维护的归属；不适用时说明事实依据。报告仍待确认的范围、假设或外部事项，不输出或更新需求开发状态。
