# requirement-breakdown — 大需求拆分与 Backlog 规划

## 定位

本 Skill 将项目或增量的最终范围拆分为一组围绕用户任务或内聚业务能力的正式大需求。每项大需求都应具有明确目标、完整范围、可观察结果、严格前置依赖和真实完成标准，最终形成可继续设计与开发的 Backlog。

Backlog 负责说明“要交付哪些完整能力、为什么这样拆、依赖什么、如何证明完成”，不提前固定详细页面、组件、字段、类、函数、表结构、完整接口或具体实现步骤，也不记录“待开发”“开发中”“已完成”“阻塞”等需求开发状态。

当前活动需求、完成情况和恢复位置由调用方使用外部结构化状态管理；本 Skill 不推断、迁移或更新这些运行期状态，也不根据状态删除、降级或改写需求内容。业务对象或业务流程自身的状态仍可作为需求范围和规则的一部分。

## 输入与事实边界

可以接收任意组合：

- 用户自然语言、多轮对话、项目或产品资料；
- 需求说明、体验约束、验收要求或总体技术方向；
- README、现有代码、可运行系统、接口契约和测试；
- 已有 Backlog，或用户指定的局部模块和新增范围；
- 与当前范围相关、可访问且可核验的工程架构资料。

有此类工程架构资料时，按需读取模块职责、稳定公开能力、依赖方向、目录职责、文件归属和 Current/Target 差异，并与当前代码、契约、测试和运行事实交叉核验；资料未提供、不相关、漂移或不足时，仍独立完成拆分，只暴露无法安全判断的高影响缺口，不索取固定文件、步骤或其它 Skill。缺少标准文档或固定 ID 时继续根据现有事实工作，只追问会改变最终范围、边界、依赖、首次可用、用户结果或真实闭环的问题。

拆分时区分：

- **已确认事实**：来自用户说明、产品资料、当前系统或已验证行为；
- **现有惯例**：项目或平台已经稳定采用的做法；
- **合理默认**：低风险、易调整且不改变产品范围的常规选择；
- **产品假设**：尚无直接证据但拆分暂时依赖的判断；
- **待确认决策**：会改变范围、用户结果、安全、兼容性或显著成本的选择。

产品和体验视角用于发现遗漏、冲突与不必要复杂度，不授权自行扩大或缩减范围。纯服务、CLI、数据处理或基础设施需求也要识别真实使用方和结果，但不机械补写 UI 内容。

## 对话与草案

收到资料后，先说明：

- 当前理解的目标用户、使用场景、最终范围和非目标；
- 已识别的用户任务、业务模块、共享能力和现有基础；
- 事实、假设、待确认问题和可能遗漏的闭环；
- 初步拆分方向、复杂度热点和关键依赖。

需要澄清时，一次询问一个会改变拆分结果的关键问题。信息足够后，先给简洁草案：

| 候选 ID | 大需求 | 类型 | 前置依赖 | 完成结果 |
|---|---|---|---|---|

同时解释合并与拆分理由、首次初始化归属、开发验收数据基线的 owning BR 与全局完成原则、端到端真实联调归属、可并行模块和建议的首条验证切片。用户确认草案后再生成或更新正式 Backlog；用户明确要求依据充分资料直接生成时，可以减少讨论，但仍须公开重要假设并完成质量检查。

## 拆分方法

### 1. 建立最终范围覆盖表

先确认 Backlog 覆盖整个项目还是局部增量，并列出：

- 本次最终交付必须包含的用户能力、业务规则、异常与恢复；
- 明确非目标；
- 已存在且可直接复用的能力；
- 外部系统、外部账号、外部数据、环境和其它运行条件；
- 为自主体验主要已交付功能所需的开发验收数据基线内容，或已经确认的空态首个成功路径。

将每项已确认范围映射到一个大需求或全局完成原则。开发验收数据基线同时映射到全局完成原则和负责相关产品能力的 owning BR；任何未归属、重复归属或被拆分过程遗漏的内容都必须在草案中暴露并修正。只拆局部增量时，不重建整个项目计划；但该增量的最终范围及其基线变化仍须完整覆盖。

### 2. 按用户任务和业务能力组织

一个大需求是：

> 围绕一项内聚业务能力形成、可独立进入设计和开发，并能通过真实系统验证完整结果的正式交付单元。

合适的大需求通常具有：

- 一个清楚的用户或调用方目标；
- 明确场景、入口、关键路径和完成结果；
- 围绕同一目标的业务规则、异常和恢复；
- 内聚的真实验证场景；
- 清楚的前置依赖；
- 一次设计和开发可以稳定掌握的上下文。

有可核验的工程架构资料时，按需关联需求所属业务模块、稳定公开能力和跨边界约束，但仍按用户任务和业务结果拆分；不得按目录或文件归属拆需求。工程依赖方向只说明实现协作，不自动等于 Backlog 的严格前置依赖。

默认形成端到端大需求，不按客户端、服务端、数据库、页面、接口、目录或仓库机械分层。各交付面单独完成都不能产生有意义结果时，应合并为同一大需求。底层能力只有能独立服务真实调用方、被多个需求共享、需提前稳定公共契约，或本身就是交付面时，才适合单独拆分。

普通功能的真实联调属于对应大需求的完成条件。只有跨模块、跨角色、异步或多阶段流程本身具有独立目标和验收价值时，才增加业务闭环大需求。

### 跨需求体验决定

可接收任意来源、与当前范围相关的已确认 Target 或有依据的默认 Target。只有已确认 Target 要求演进既有产品表面、迁移本身形成独立可观察的用户结果，且开始其它需求前确实必须完成时，才创建正式迁移 BR，并按该严格前置关系建立依赖。默认 Target 只作为相关业务需求的体验约束，保留依据和重新评估条件，不单独制造迁移 BR 或严格依赖；若某需求需要偏离默认 Target，或偏离会改变跨需求体验骨架，则暴露为待确认决定。任何情况下都不按页面、组件、CSS 或目录拆分，也不把框架文档或其它 Skill 写为依赖。

### 3. 检查不必要复杂度

逐项检查是否存在：

- 没有独立职责或权限差异的额外角色；
- 不能影响业务结果、恢复或审计的额外状态；
- 可合并、自动完成或移除的操作步骤和页面跳转；
- 系统已经知道却要求用户重复输入的信息；
- 同一信息在多个阶段重复填写且没有明确理由；
- 只为代码分层、组织结构或制造并行度而拆出的需求；
- 名称不同但目标、规则、依赖和验证基本相同的重复能力。

可以主动建议合并或删除，并说明保留的产品结果、影响和风险。未经确认，不得因为实现困难、工期压力或现有代码限制静默裁剪最终范围。

### 4. 判断颗粒度

考虑拆开，当候选项包含多个独立目标、前置依赖明显不同、部分完成已产生独立价值、上下文过大、验证方式不同，或包含有独立价值的跨模块流程。

考虑合并，当候选项单独完成没有真实价值、必须同时成立才构成完整任务、目标与依赖基本相同，或只是交付面和代码层不同。

不使用固定工期、接口数、文件数或“每模块固定几项”的公式。

### 5. 建议首条验证切片

开发路线应建议一条最先验证关键价值和高风险假设的切片。它必须由**一个完整正式需求**，或**多个各自完整、共同形成首个真实闭环的正式需求**组成，并满足各自全部范围和完成标准。

首条验证切片只是开发与验证顺序建议，不是 MVP、半完成需求、Mock 演示或范围缩减；不能把选中需求拆成“先做页面”“先通接口”或“先用假数据展示”，也不能把未进入首条切片的最终范围降为可选项。

## 依赖与开发路线

### 前置依赖

前置依赖只有一个严格语义：

> 当前大需求开始开发前，所列大需求必须已经完成。

要求：

- 只指向 Backlog 中存在的稳定需求 ID；
- 不允许自依赖、未知依赖和循环依赖；
- 不写“数据库”“后端”“基础模块”或“前面的任务”等模糊对象；
- 不为顺序整齐把互不依赖的模块强行串行化；
- 数据库、第三方账号和运行环境等条件放入“外部依赖”。

关联需求只表达业务联系，不控制开发顺序。工程架构资料中的依赖方向、目录职责或文件归属也不自动构成严格前置依赖；只有符合“开始前必须完成”语义的 Backlog 大需求才可列入。

### 路径反查

对包含用户交付面的需求，反查：入口和导航是否存在、身份和权限如何获得、服务端与数据能力是否齐全、空系统能否产生首条业务数据、结果能否再次读取确认、失败后能否重试或恢复。

只把“开始前必须完成”的大需求列为严格依赖，不把每个交互步骤拆成依赖，也不使用 Mock 绕过关键能力。

开发路线根据依赖、首条验证切片和可并行性给出建议顺序，不把建议顺序伪装成依赖，也不制定具体排期。

## 真实完成原则

完成必须由当前大需求涉及的真实交付面共同证明，而不是由代码存在、文档、Mock 或未执行的测试说明代替。

### 服务与数据能力

涉及业务操作或持久化时，应要求：

- 正式运行路径使用真实业务实现和项目配置的真实数据库；
- 实际启动服务或执行项目真实入口；
- 通过项目对外入口验证核心成功、失败和权限场景；
- 验证数据写入、读取、修改和关键约束；
- 刷新、重进或服务重启后结果仍正确；
- 空的专用开发或验收环境可按项目约定恢复开发验收数据基线，或从已确认空态完成首个真实成功路径。

### 用户交付面

包含界面或其它用户客户端时，应按风险要求：

- 真实客户端连接真实服务，使用适用角色的真实开发账号；
- 目标用户能找到入口并完成核心任务；
- 加载、空数据、提交、成功、失败、无权限、重复操作和恢复等相关状态反馈清楚；
- 失败后保留仍可继续使用的输入，用户能理解下一步；
- 客户端结果与服务端和真实数据库状态一致；
- 适用时验证键盘、焦点、标签、错误关联和不只依赖颜色表达状态；
- 必要时刷新、重新进入或重启，确认不是临时假象。

纯内部变化按其真实调用方、数据和系统行为验证，不强套浏览器或 UI 标准。

### Mock、阻塞与开发数据

Mock 可支持单元测试、组件状态和难以稳定制造的外部故障，但不能单独作为业务需求完成依据。固定响应、静态 JSON、内存数组和假数据页面不能代替正式能力。

真实依赖不可用时，保留原完成标准，记录阻塞原因和补验条件，不自动降低标准后宣称完成。通过真实服务写入项目数据库的数据可以成为开发验收数据，但只有纳入下述 canonical 基线并受版本控制维护的内容才构成交付基线。任意测试临时数据、生产数据、真实个人数据，以及 PCM 或目标产品访问其它系统或资源的凭据均不属于该基线，也不得写入 Backlog 或输出。

## 开发验收数据基线归属

开发验收数据基线包括为自主体验主要已交付功能所需的产品内账号与角色、必要参考数据、代表性业务对象与状态、适用对象资源、恢复与验证方式和交付说明。Backlog 按以下方式安排责任：

- 在“全局完成原则”中要求项目维护一份受版本控制的 canonical 基线，并在项目 README 或既有受跟踪交付文档中提供适用环境、前置服务、恢复/核验入口、管理范围、数据影响、账号文档、对象资源范围和成功判断；
- 将账号与角色归入负责身份和权限能力的 owning BR，将参考数据、代表性业务对象、状态和对象资源归入首次引入或改变对应产品能力的 owning BR；
- 每个后续增量只维护自己引入或改变的基线内容、恢复行为、文档和验收，不把全量基线重复写进每张详情卡；
- 不得仅为 Seed、fixture、reset、验收数据准备或基线文档机械制造独立 BR。初始化、恢复或全量基线收口本身形成跨需求、可独立验收的交付结果，无法合理归属单一业务 BR，或确实是其它需求开始前必须完成的前置能力时，才按该结果拆分；
- `project-readiness` 所需的外部服务、外部账号、运行凭据、私有数据和设备属于外部依赖，不作为开发验收数据基线或 owning BR 的产品数据增量；`media-assets` 自带测试 fixture 也不承担该基线。

相关 owning BR 的完成标准按实际范围覆盖：canonical 定义和恢复/核验实现受版本控制；重复执行不产生重复数据或覆盖管理范围外内容；接手者可按文档恢复，并从正常入口使用目标角色完成代表性主要任务；对象资源与业务记录一致；账号、对象、状态或资源变化时同步交付文档。

## 初始化与首次可用

检查登录与注册、首个身份、基础角色和权限、必要字典或参考数据、空环境启动、安全重复初始化，以及恢复后能否完成首个真实业务流程。产品定义明确从空态开始时，则检查空态能否引导目标用户从正常入口取得首个真实成功结果，而不机械制造示例数据。

系统需要登录、没有公开注册且空环境无身份时，Backlog 必须包含明确的初始身份能力，可合并到身份、数据基础或其它 owning BR。完成标准至少覆盖：专用环境可建立初始身份、初始身份可真实登录、关系正确、重复执行不产生重复数据、不覆盖管理范围外的已有账号或数据，并能进入首个真实功能。

恢复方式按项目事实选择，可以是非破坏 initialize、独立 verify、重建专用环境后 Seed，或只对管理范围明确的专用环境执行严格受控的 destructive reset；Backlog 不强制统一命令、技术栈、Manifest 或原地 reset。破坏性方式必须要求明确适用环境、管理范围、数据影响和安全前置条件。

任何最终保留在开发验收数据基线中的普通用户、业务角色、产品管理员和产品超级管理员都应使用项目专用、不冒用真实个人身份、真实存在且可登录的产品内开发账号。相关 owning BR 的完成标准必须要求：在受跟踪账号文档中同步适用环境、登录入口、角色、账号、密码、恢复方式和必要已有数据说明，并在完成前逐个核验账号存在、密码可登录、角色一致、约定数据可见以及代表性允许行为。临时测试后删除或事务回滚、未保留在最终交付开发状态中的短期账号和数据无需记录；不得增加演示租户、隔离业务数据或生产禁用 Seed 等部署阶段限制。

## Backlog 文档结构

默认建议路径：

```text
docs/backlog/backlog.md
```

推荐结构：

```markdown
# Backlog

## 范围说明
## 拆分思路
## 全局完成原则
## 开发路线
## 大需求总览
## 大需求详情
### <业务模块>
#### BR-001 <大需求名称>
## 整体风险与待确认事项
```

小项目可省略不必要章节，不保留空模板。开发路线可用自然语言或 Mermaid；总览、详情卡、路线和依赖图必须一致。

### 总览表与标识

| ID | 大需求 | 类型 | 业务模块 | 前置依赖 | 完成结果 |
|---|---|---|---|---|---|

新文档使用中性稳定 ID，例如 `BR-001`。ID 不编码模块、交付面、优先级或顺序，调整路线时不重新编号。Backlog 不设置或维护需求开发状态。

### 大需求详情卡

必备内容：

```markdown
## BR-xxx 大需求名称

**类型：**
**业务模块：**

### 目标
### 完成后的效果
### 包含范围
### 不包含范围
### 前置依赖
### 关键业务规则
### 完成标准
### 验证场景
```

按需增加来源依据、目标用户与场景、核心路径、体验约束、工程归属与边界关联、关联需求、初始化、开发验收数据基线增量、外部依赖、风险与待确认事项、后续设计重点和演进关系。工程归属与边界关联只说明所属模块、稳定公开能力或跨边界约束，不写完整文件路径；不适用的章节直接省略。

核心路径只描述入口、关键步骤和可观察结果；详情使用通俗业务语言，不固定页面布局、组件、逐字段交互、详细表结构、完整接口、类、函数、目录、测试命令或开发流水。

## 需求演进与既有历史

由外部状态记录确认已经正式验收并归档的需求，其 Backlog 内容是不可变历史：

- 保留其 ID、标题、范围、验收标准和历史 TRD 链接；
- 不因后续拆分、合并、缺陷或新范围而改写；
- 升级、重构、替代、补完或缺陷修复必须创建新 Backlog 项、新稳定 ID 和新 TRD；
- 新项说明保留行为、变化或替代关系、兼容或迁移要求和新的完成结果；
- `演进自`只表示历史谱系，不自动成为前置依赖。

既有 Backlog 若包含需求开发状态，调用方应在改写前将这些事实保存在外部结构化状态中。本 Skill 不迁移、推断或更新状态；正式 Backlog 不保留状态字段，也不依据状态改变需求范围、ID 或演进关系。

## 重构已有 Backlog

先说明当前拆分、主要问题和拟调整方向，再提出合并、拆分、重命名和依赖调整草案。保留稳定范围、业务规则、有效验收和历史链接，移除需求开发状态字段、易漂移的实现清单、Mock 完成声明和开发流水。

旧 ID 已被引用时不自动批量改号；确需迁移，先检查引用并提供旧新映射。用户确认后再修改正式文档。需求开发状态的保留或迁移由调用方在外部结构化状态中完成，不属于本 Skill 的修改范围。

## 质量检查

写入前后检查：

- 最终范围、规则、异常和非目标是否完整归属，没有静默遗漏或扩张；
- 是否识别并处理不必要角色、业务状态、步骤、重复输入和重复需求；
- 跨需求体验决定是否只在相关范围引用；默认 Target 是否保留依据和重议条件且未单独制造迁移 BR，已确认 Target 的迁移 BR 是否同时满足独立用户结果和严格前置条件；
- 每项需求都有真实使用方、内聚目标、完整路径和可观察结果；
- 没有按代码层机械拆分，也没有把无关目标塞入巨型需求；
- 有可核验工程架构资料时，需求的模块归属、稳定公开能力和跨边界约束不与代码、契约、测试或运行事实冲突；资料不足时不虚构这些关联；
- 前置依赖全部存在、无循环，外部条件与关联需求没有混用，工程依赖方向没有被误写为严格前置依赖；
- 首条验证切片只由完整正式需求组成，没有变成 MVP、半成品或 Mock 展示；
- 服务、客户端、数据、权限、初始化和恢复按实际范围形成真实完成证据；
- 开发验收数据基线是否同时落实为全局完成原则和 owning BR 增量，没有机械制造纯 Seed/fixture/reset BR，也没有与外部资源准备或 `media-assets` 测试 fixture 混淆；
- 基线相关完成标准是否覆盖受跟踪 canonical 定义、文档、管理范围、恢复与核验、重复执行保护、正常入口体验及对象资源一致性；
- Mock 不作为完成依据，普通联调没有推迟到最终人工收尾；
- 总览、详情、路线和依赖图一致，且不包含需求开发状态；
- 由外部状态记录确认的既有历史未被改写，演进工作使用新项、新 ID 和新 TRD；
- 文档通俗、紧凑，不重复全局规则或保留大量空章节。

发现问题先修正文档，再报告结果。

## 完成输出

说明生成或更新的文件、大需求数量、最终范围覆盖情况、主要依赖链、首条验证切片、真实联调与初始化归属、开发验收数据基线的全局原则和 owning BR，以及仍待确认的范围、假设或外部事项。不输出或更新需求开发状态。
