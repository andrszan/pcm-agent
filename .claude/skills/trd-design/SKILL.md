# trd-design — 技术实现设计

## 目标与边界

将一个内聚需求、已有任务或技术问题转化为可指导实现与验证的活动 TRD：讲清用户或调用方要完成什么，复用什么、改变什么，以及必要的产品、技术和验收决定。不实现业务功能，不管理运行状态或执行 Git 写操作。

输入可以是自然语言、Backlog、Issue、活动 TRD、产品与体验资料、工程架构、代码、测试或可执行契约，不要求固定来源、目录或其它能力。输入包含可独立交付、独立验证或风险明显不同的变化时，先建议按用户结果拆分；不机械拆成前端、后端和数据库需求，也不为缩短单项耗时增加交接。

最小方案是在已确认范围内降低实现与验证成本，不是默认缩成 MVP。不得擅自删减产品能力、权限、数据语义或历史承诺。

## 工作路径

1. 明确本次使用方、核心任务、范围、非目标和可判定完成结果。
2. 读取当前需求、直接相关设计和实际实现入口，核验可复用能力及必要变化。出现具体冲突或关键缺口时才扩读历史与旁域；证据足以支持决定后停止调查，不反复全面扫描项目。
3. 在现有工程内选择满足需求的最简单方案。只提前固定影响用户结果、正确性、安全、数据、兼容性或跨端协作的决定，其余留给实现阶段。
4. 按需要交接的信息组织 TRD，写清方案、约束与相称的验证。重大取舍先交接问题，不为所有候选展开完整模型、接口与迁移。
5. 自审并原位修正；没有阻碍实现的实质未决事项后结束。补问只补该事项，修订只复核受影响内容，不重新设计整份文档。

## 事实与决策

区分已确认事实、现有惯例、合理默认、设计假设和待确认决策。不得虚构路径、实体、接口、字段、测试、用户研究或运行结果；无法核验时明确限制。

Current 优先依据已验证运行行为和实际契约，其次是代码与可执行测试，再次是说明文档和通用规则。工程与体验资料可以表达已确认 Target，不能冒充 Current；旧 TRD 不能替代相关现状核验。资料与代码冲突时说明冲突、影响及有效边界，不为无关需求强制迁移到过时规则，也不擅自忽略已确认的新目标。

在请求范围内自主收敛普通工程判断。只有实质改变产品范围、用户结果、权限与隐私、高影响操作、稳定架构、公共兼容性、重要数据语义，或引入显著成本和不可逆迁移时，先说明问题、事实与约束、可行选项、影响和推荐理由并取得确认。判断依据是实际影响，不是是否涉及安全、接口或数据库等主题；成熟安全措施、常规反馈、等价内部组织和已授权文档落盘不重复确认。高影响决定即使只有一个可行方案也应说明并确认。

未知生产规模、未来容量和后续观察不自动成为当前设计阻塞。没有明确承诺时，不为消除未知而自行制造精确容量、并发、延迟、硬件或部署门槛；已有明确承诺则保留，确需调整时交接决定。

## 选择相称的工程方案

- 默认复用已有模块、契约、组件、授权、事务和恢复能力；沿用项说明本次依赖及差异，不重新设计其全部状态与失败矩阵。
- 新增机制须服务已确认需求、具体缺陷或有依据的当前风险。仅因“方便追溯”“更严谨”“更完整”“以后可能需要”，不足以引入新状态、操作流水、编辑历史、版本浏览对比、历次计算配置回看、通用抽象、基础设施或相邻模块改造。
- 方案带来显著实现或验证成本时，先比较更简单的替代方式，说明为何仍需该投入；不要求为每个普通选择填写成本表。
- 区分业务口径一致与读取同一数据库快照。跨页面复用权威事实，不自动要求所有只读请求采用新的隔离级别、二次授权协议或锁序；仅在具体一致性或安全风险需要时设计，并保留必要授权与数据隔离。
- 列表按实际风险设计有界读取、数据库分页与批量查询。不凭空冻结 SQL 次数、索引数量、查询计划形状或唯一优化路径；精确限制须有可核验依据。已知 N+1、无界加载或越权查询不能以成本为由忽略。
- 新内部接口描述能力、调用关系与关键语义；复用项目真实契约，不复制全量 Schema。公共 API、第三方协议或高成本兼容场景按需要保留精确合同。
- 技术组织与重试方便不足以增加用户登录、确认或重复输入，先比较不增加操作的方案；已有正式安全政策仍须遵守。

普通操作流水、编辑历史、版本浏览对比、历次计算配置回看及配套恢复、回滚默认不设计，换成“动态”“轨迹”等名称也不例外。先依据已有事实明确它服务的具体用户任务，再判断当前状态或必要业务结果是否已经足够；足够时从数据、接口、后台任务和界面的设计中整体删去或并回现有结果，不只隐藏入口，也不列为可选项或未来扩展；仍需复杂历史能力时，先比较删除或简化依赖它的相关模块，涉及已确认范围则交接决定，模块确实值得保留时才设计最小记录对象、关键时点、保存范围与期限和读取能力。不得先把版本能力设为核心方案，再用该方案需要版本数据来证明必要。

正确性所需的当前快照、并发 `version`、事务日志或回滚按最小范围设计，不自动扩成全量编辑历史、可浏览对比或永久保存。订单处理、维修结果、正式提交、确认和交付等业务事实，以及有明确依据的安全记录，仍按实际语义保留，但不自动附加统一版本中心。若用户已确认上述历史能力，核验后发现其成本过重或简单结果已足够，应交接范围取舍、影响和推荐，不得擅自删减。

有适用工程架构时，只承接受影响交付单元的稳定 owner、目录/包/模块职责、公开/私有边界、依赖方向和改动归属。按事实区分无结构变化、既有边界内扩展、新增稳定边界或迁移替换；只有边界变化或偏离时说明架构 delta、理由、影响和最小迁移。边界内部文件名、数量与等价拆分留给实现，不冻结完整目录；跨 owner 合并、打平、绕过公开出口或引用私有路径不是普通文件调整，也不能用巨型入口、页面或通用收纳目录替代稳定边界。

## 用户行为与体验

用户可见需求不能只交接接口和数据。围绕核心任务说明入口、主要行动、结果，以及真正相关的状态与恢复：

- 检查步骤、字段、确认和跳转是否必要；消除可推导选择、重复输入和无意义往返，不删除业务或安全所需操作。
- 使用用户能理解的术语，明确内容主次、主要与次要行动、取消与退出。关键标签、规则、错误原因和恢复指引不能依靠 Tooltip 解释内部技术术语。
- 选择本次相关的加载、空数据、校验、提交、成功、失败、失权、数据过期或中断重入状态，说明输入保留、重试与返回；写操作按风险处理重复提交、未知结果和冲突，不给只读页面机械套用完整命令恢复模型。
- 保留适用的响应式、键盘、焦点、可见标签、字段错误关联、可读性和非纯颜色状态表达。颜色、间距、组件和像素布局通常由实现决定，已有明确合同或承载业务含义时例外。

关键行为须能对应到客户端或调用方、服务端规则、数据与权限职责及验证结果，按最清楚的方式组织，不强制另做映射表。纯内部变化省略 UI 章节，只说明需保持的调用方行为和系统约束。

跨需求体验决定仅承接本次适用的来源、具体要求、范围及重要前提或例外；沿用项不重填 Current/Target 或重议条件。存在实际差异、改变或重要假设时再说明依据、影响与必要迁移。不能复制整份体验框架，也不能静默改变产品表面、Shell 或导航骨架。

主动评估媒体对内容识别、场景、品牌与产品展示的收益。有收益时说明用途、来源类型、静态或动态落点、必要构图和无图/失败表现；特定构图可以直接选择定制图片，不必穷尽图库。无收益的表单与内部需求不机械配图，不另写媒体报告；测试 fixture 不充当产品资产，工作区工具凭据不进入产品运行配置。

高风险交互或信息密度仅靠文字无法判断时，使用最低成本的轻量原型或实际预览解决具体疑问，记录代表性状态、观察和结论。不固定工具、目录、格式或高保真产物；既有界面与事实足以判断时不额外制作。

## 验证设计

完成标准描述必须证明的用户结果与关键风险，不默认展开为完整测试工程规格。先覆盖核心成功路径、关键失败与边界、角色与对象权限、必要持久化及受影响回归，再选择合适证据：

- 局部规则使用针对性测试；查询、权限、持久化、必要并发与事务使用真实接口或数据库集成验证。
- UI 用真实浏览器验证核心任务、前后端接线、关键反馈和代表性视口的实际呈现，不在浏览器重跑全部后端矩阵。
- 按受影响仓库保留必要静态、类型、构建和回归检查；已有有效证据可复用，不要求每个参与者重复全套验证。
- 性能数据用于暴露具体查询风险，规模和分布由验证目的或已确认容量目标决定，不统一指定数据量。没有依据时不默认搭建专用 benchmark、硬件门禁、逐组合多轮 p95 与全量 EXPLAIN；小数据也不能用来掩盖已知规模风险。
- 高并发、复杂事务交错、容量、特殊迁移与混合版本部署验证，只在当前承诺或具体风险需要时增加。已有明确性能与安全要求不能改称可选观察。

真实服务、数据库和适用浏览器是集成证据，Mock 只支持局部测试。不能只写“页面存在”“接口成功”“单元测试通过”，也不能把未执行计划当结果。测试方法和可调整开发基线不自动升级为产品承诺；成本不相称时比较替代证据并校正设计，而非要求无限优化直到自设指标全部通过。

## 交付开发账号

仅当需求创建或调整最终保留的登录账号时，设计首个身份或等价初始化、权限建立与恢复，并固定以下约束；设计阶段不创建账号或执行 Seed/reset：

- 覆盖实际交付角色，包括适用管理员和超级管理员，使用项目专用、不冒用真实个人身份且能从正常入口登录的开发账号；不改称演示或假账号，不附加演示租户、隔离业务数据或生产禁用 Seed 等部署限制。
- 账号及密码随受跟踪 README 或账号文档交付，记录环境、入口、角色、账号、密码、Seed/reset 与必要已有数据说明，变更时同步。测试后删除或回滚、不保留的短期账号无需逐个交接。
- 初始化/恢复幂等且保护管理范围外数据；开发验收从正常入口逐账号确认存在、密码可登录、角色正确、已有数据可见。
- 外部系统、资源、工作区工具凭据与真实个人认证信息保持秘密，不随产品账号公开。

## 文档组织与维护

按实际交接需要组织：实现摘要、范围与完成结果、必要当前事实、关键行为、实现方案与约束、验证场景。可合并章节；历史、数据、接口、迁移和风险只有新增必要信息时才展开，不填写大量“无”。不固定字数或章节数量，不复制全量字段、端点、类/函数、文件或测试清单。

同一决定在最适合的位置完整说明，其它位置只补独有影响或引用。自审直接修正文档，不追加读取流水、逐项通过声明、重复设计调整清单或未执行测试列表；保留影响可信度的证据限制和真实未决事项。

活动 TRD 是可校正的设计基线。等价内部命名、文件和测试组织通常无需更新；用户行为、业务规则、职责、接口、数据、安全、迁移或验证目标发生稳定变化时，原位更新对应正文并删除失效说明。重大承诺变化先确认，不能保留原合同、少实现或少验证后宣布完成。只修改授权范围内文件，不在 TRD 冻结 `allowed_paths`。

归档需求与 TRD 保持不可变。升级、补完和缺陷修复使用新需求标识与新 TRD，说明来源、保留行为、变化和必要兼容；演进关系不自动成为严格前置依赖，不重新质疑已建立的可信历史完成状态。

默认命名为 `docs/trd/<YYYY-MM-DD>-<文档标识>-<简短名称>.md`。沿用可靠需求 ID，没有时用稳定语义短名；保留首次日期，不随编辑改名。写入前确认属于同一活动设计，不覆盖其它设计或归档资料；文件名不含状态、审批结果或 `v2`、`final` 等模糊后缀。

## 自审与结束

自审确认范围与关键行为明确、当前事实可靠、必要跨端与模块协作清楚、约束和验证相称，未遗漏权限、数据、兼容和关键失败，也未追加无依据的工程或验收承诺。检查是否还能通过复用减少机制、用户步骤和重复说明；普通历史能力是否有具体用户任务与最小保存范围，是否误把快照、并发版本或回滚扩成全量版本设计。

普通低成本可逆设计自审通常足够；有具体高风险或实质取舍时可增加独立审查，不因跨模块或涉及安全主题机械增加审查轮次。审查基于稳定正文，期间不并行改写同一范围；修订后只复核原发现与受影响内容。真实新缺陷仍需处理，但“还能更完善”、等价写法或更多验证方法不足以重新全面审查。

审查建议不是扩大范围的授权。新增状态、生命周期、协议或验收负担前核验当前依据与简单替代；已确认范围、关键行为、方案与必要验证足以指导实施，且没有实质阻碍时即可结束，不要求冻结所有普通实现细节或未知未来指标。

最终说明 TRD 路径、关键决定、必要差异和证据限制，不复述全文。有负责人待决事项时，在回复中直接讲清准确问题、事实与约束、可行选项、影响和推荐理由，文件引用不能代替决策交接。被要求补问时只补必要信息，不重写整份 TRD；没有待决事项时不为格式逐项声明“一切无问题”。
