# trd-design — 技术实现设计

## 定位

TRD 将一个内聚需求、已有任务或技术问题转化为可指导实现和验证的语义化 Markdown 设计。它先明确真实使用方如何完成任务、系统反馈什么、最终承诺什么结果，再说明客户端或调用方、服务端、数据、权限和外部协作如何共同兑现这些行为。

一份 TRD 通常对应一个内聚需求。输入包含多个可独立交付、独立验证或风险明显不同的变化时，先建议拆分；不要把它们塞进同一份设计，也不要把一个完整需求机械拆成客户端、服务端或数据库设计。

## 适用输入

可以接收任意组合：

- 自然语言需求、Backlog 项、Issue 或具体技术问题；
- 产品、体验、方案、契约和历史资料；
- 已有且仍处于活动状态的 TRD；
- 目标代码、测试、仓库路径或可运行项目；
- Swagger、OpenAPI 或项目实际采用的可执行契约；
- 与当前范围相关、可访问且可核验的工程架构资料。

有此类工程架构资料时，按需读取模块职责、公开能力、依赖方向、目录职责、文件归属和 Current/Target 差异，并与当前代码、契约、测试和运行事实交叉核验；资料未提供、不相关、漂移或不足时，仍独立完成设计，只暴露无法安全判断的高影响缺口，不索取固定文件、步骤或其它 Skill。

适用于新能力、缺陷修复、升级、重构、替换、补完、迁移和兼容性调整。纯内部变化同样可以设计，但只记录需要保留的调用方行为和系统约束，不机械套用界面章节。

## 事实边界与优先级

设计结论必须区分：

- **已确认事实**：来自用户说明、产品资料、可验证运行行为、当前代码或有效测试；
- **现有惯例**：项目稳定采用的产品模式、设计系统和工程约定；
- **合理默认**：低风险、易调整且不改变产品语义的常规选择；
- **设计假设**：缺少直接证据但当前方案暂时依赖的判断；
- **待确认决策**：会改变范围、用户结果、安全、兼容性或显著成本的事项。

描述 Current 时，事实优先级通常是：已验证运行行为和实际契约，其次是当前代码与可执行测试，再次是说明性文档和通用规则。工程架构资料可表达已确认的 Target 和稳定边界，不能替代对 Current 的上述核验；资料与代码、契约、测试或运行事实冲突时，显式记录冲突、影响和待确认边界。规则中的组件名称、属性或交互细节与真实代码和测试冲突时，以代码和测试事实为准，并记录规则已漂移；只有已确认的新需求明确要求改变现状时，才把差异设计为本次变化。

不得虚构路径、类、函数、实体、Schema、字段、端点、配置、测试、用户研究或现有交互。无法核验时明确标记“假设”“待确认”或“待核验”。

### 跨需求体验决定

仅引用本需求真正适用、任意来源的已确认 Target 或有依据的默认 Target。每项引用记录来源、适用范围、Current、Target，以及本需求是遵循还是改变该决定；默认 Target 还记录依据和重新评估条件，Current 仍以可核验事实为准。偏离默认 Target 时说明原因；偏离会改变跨需求体验骨架、用户结果或显著迁移成本时，按高影响决定确认。不复制整份体验框架，不固定文件、目录或资料路径，也不要求由上游 Skill 提供。

## 设计过程

围绕证据和决策推进，不套固定状态机：

1. 理解真实使用方、场景、核心任务、范围、非目标、完成结果和历史关系。
2. 检查相关产品行为、界面或调用入口、代码、数据、接口、权限、测试和项目惯例。
3. 说明当前理解、已验证事实、可复用基础、约束、假设和冲突。
4. 对用户可见需求先设计体验责任，再映射到技术职责。
5. 讨论会实质影响产品、架构、安全、兼容性、迁移或高影响交互的少量决策。
6. 形成实现方案、验证场景、风险和可调整边界。
7. 获得必要确认后写入活动 TRD，并完成自审。

发现需求、文档、代码和历史承诺不一致时，明确冲突、影响和建议边界。局部澄清可直接体现在当前 TRD；会改变产品范围、公共行为或不可逆结果的选择必须先取得用户确认。

## 用户确认与自主判断

需要明确确认的事项包括：

- 产品范围、目标用户、核心任务或完成结果的实质变化；
- 高影响操作的确认、失败、取消和恢复语义；
- 有意义的架构取舍或新增基础设施；
- 权限、安全、隐私、公共协议和兼容性边界；
- 不可逆迁移、重要数据语义或高成本回退；
- 需求与当前代码存在重大冲突时采用哪一边界。

类名、已确认稳定边界内部的文件组织、函数拆分、等价局部重构、常规状态反馈和不改变产品语义的布局，可按当前项目惯例自主决定。跨业务所有者、目录/包/模块稳定边界的合并或打平，绕过公开出口、引用私有路径或改变依赖方向，属于架构 delta，不得作为“文件组织调整”静默决定。用户确认应聚焦实质取舍，不变成固定签字流程。

## 单需求产品体验责任

对用户可见、交互式或具有外部调用方行为的需求，TRD 必须对这个需求本身的体验完整性负责，而不是只写接口和数据。

### 简化任务路径

从用户意图到确认完成逐步检查：

- 每个步骤是否服务目标、业务规则、安全或必要确认；
- 字段是否确实需要用户提供，系统已知信息是否被重复输入；
- 决策是否必须由用户作出，能否通过合理默认或已有事实消除；
- 页面、弹窗、标签页和跳转是否造成无意义往返；
- 同一信息或确认是否在多个位置重复出现。

逻辑完整不代表体验合格。流程即使能完成，只要步骤、字段、决策或跳转没有必要，也应在本次设计中提出删除或合并，并说明保留的业务结果和约束。简化不能擅自删除已确认能力、审计要求、安全边界或真实异常处理。

### 明确信息与行动

按需求风险记录：

- 用户使用的业务术语，以及需要避免暴露的内部模型、接口或工程术语；
- 内容主次：用户先理解什么、辅助信息放在哪里、什么信息只在需要时出现；
- 页面或步骤的主要行动、次要行动、取消与退出方式；
- 关键文案意图，包括标签要表达什么、确认为何必要、成功如何被感知、错误如何解释并引导恢复；
- 初始、加载、空数据、可操作、校验失败、提交中、成功、部分成功、业务失败、外部失败、无权限、数据过期和中断重入等相关状态；
- 失败后输入是否保留，如何重试、返回、撤销或恢复；
- 重复提交、危险操作、长任务和并发冲突如何避免误解或误操作；
- 适用的键盘、焦点、标签、错误关联、可读性和不只依赖颜色表达状态等约束。

面向用户的标签和主文案应使用用户理解的术语。不要把技术术语直接放进界面，再依赖 Tooltip 补救；Tooltip 只适合补充非关键解释，不能替代清楚标签、关键规则、错误原因和恢复指引。

只固定影响用户结果、业务正确性、安全、兼容性或跨端协作的内容。颜色、间距、动画、像素布局和具体组件通常留给实现，除非它们承载业务含义或已经被当前事实明确约束。

### 条件式体验证据

当高风险 UI 决策仅靠文字无法可靠判断，例如关键路径、复杂输入、信息密度、高影响确认或状态切换存在明显取舍时，可以使用最低成本的轻量原型或实际预览作为决策证据。

是否需要此证据由风险决定，不固定工具、文件格式、目录或产出数量，也不要求完整视觉稿。只记录要验证的问题、代表性状态、观察结果和最终设计结论；能够从现有界面、组件和运行事实安全判断时，不额外制作原型。

### 与技术方案对应

关键产品行为必须能追溯到调用方或客户端职责、服务端规则、数据和权限约束、错误语义及验证场景。可按需使用：

| 产品行为 | 客户端或调用方职责 | 服务端职责 | 数据、权限与异常约束 |
|---|---|---|---|
| <用户可见行为> | <输入、呈现与状态处理> | <业务规则与结果语义> | <一致性、权限和失败边界> |

纯内部重构、索引调整、依赖升级等不改变外部行为时，省略 UI 设计，只说明必须保持的调用方行为、性能或数据约束、失败边界和系统验证。

## 当前项目分析

有可访问代码时，正式 TRD 必须分析与需求相关的实现，但不做无边界全仓审计。至少确认：

- 当前入口、目标使用方、外部行为和真实系统行为；
- 可复用的产品模式、设计系统、组件、服务和项目惯例；
- 相关导航或调用路径、加载、空状态、错误、权限、反馈与恢复；
- 相关数据、接口、权限、异常、初始化、迁移和测试；
- 不同交付面对同一状态和错误的解释是否一致；
- 必须改变的行为、职责、协作关系和受影响区域；
- 需求、资料、代码、测试和历史承诺之间的差异。

有可核验工程架构资料时，按需说明相关模块所有权、稳定公开能力、禁止穿透的内部实现和跨模块编排。架构判断分类为“无结构变化”“既有边界内扩展”“新增稳定边界”或“迁移替换”；TRD 须记录本需求适用的稳定 owner、目录/包/模块边界、公开/私有边界、允许/禁止依赖和预期改动归属。边界内部的文件名、数量和等价拆分不必冻结；跨边界合并、打平、绕过公开出口、引用私有路径或用巨型入口/页面、通用收纳目录、同名平铺文件替代已确认边界时，必须记录影响、理由和最小迁移，不能静默降级。只有稳定边界发生变化或实现偏离已确认边界时才记录为架构 delta，不得为此冻结完整目录或文件清单。

无法访问代码时，只能形成暂定设计，并分开记录已知事实、假设、待确认和待核验内容。已有 TRD 只能作为上下文，不能替代对当前代码的重新核验。

## TRD 结构

推荐使用以下语义结构：

```markdown
# <需求名称>技术设计

## 文档信息
## 实现摘要
## 需求定位
## 历史基础与演进关系
## 当前项目分析
## 产品行为与用户体验
## 需求调整
## 实现方案
## 数据与持久化
## 接口与外部协作
## 权限、安全与异常处理
## 实现约束与可调整项
## 验证场景
## 风险与待确认事项
## 本次设计调整
## 设计审查
```

稳定核心语义是：`实现摘要`、`需求定位`、`当前项目分析`、`实现方案`、`实现约束与可调整项` 和 `验证场景`；用户可见需求还应包含 `产品行为与用户体验`。其它章节按需使用，无关内容直接省略，不填写大量“无”。正文使用可读 Markdown，不加入运行编排 YAML。

## TRD 应固定的内容

按需求相关性记录：

- 使用方、场景、核心任务、范围、非目标和可判定完成结果；
- 产品事实、代码事实、现有惯例、合理默认、假设和待确认决策；
- 当前外部行为、可复用基础、约束和必要变化；
- 单需求的关键路径、术语、内容主次、主要行动、状态、反馈和恢复；
- 模块职责、关键协作、业务流和有意义的状态变化；
- 主要技术决策、理由、替代方案和取舍；
- 数据完整性、一致性、生命周期、初始化、迁移和兼容性；
- 接口能力、调用方、权限、关键语义、错误、幂等和兼容性；
- 必须满足的约束、允许调整的细节和明确非目标；
- 覆盖真实系统状态、异常、边界和回归风险的验证场景。

通常不固定完整用户研究、Persona、全页面流程图、完整视觉稿、每个组件名称、像素样式、类与函数清单、完整文件列表、全量字段、全量端点或测试文件拆分。只有精确字段、协议、顺序或组件行为影响正确性、唯一性、安全、迁移、并发或外部兼容时，才把它写成约束。

## 数据、接口与外部协作

- 产品行为是客户端、服务端和数据设计的共同输入，不能先固定接口再让用户流程被动适配。
- 实际实体、Schema、迁移、数据库代码和可执行契约是实现后的事实源；TRD 记录关键语义与约束，不复制全量定义。
- 需要登录但没有公开注册入口时，设计首个身份或等价初始化机制，以及权限建立和恢复路径。
- 已有接口引用项目真实契约；新内部接口先描述能力、调用关系、关键行为和错误语义。
- 公共 API、第三方协议、Webhook、消息协议或高成本兼容场景才保留较详细的独立契约。
- 设计明确各交付面对状态、错误和协作的共同语义；实现阶段用真实服务、数据库和接口联调验证。
- Mock 只用于局部测试支持，不能替代真实集成证据。

这些规则不预设语言、框架、数据库、ORM、接口协议或测试工具，具体选择来自项目事实和已确认决策。

## 验证场景

验证优先从真实任务描述，再落到各层证据：

- **用户或调用方行为**：能够找到入口、理解状态、完成任务并识别成功或失败；
- **客户端或调用方表现**：正确处理输入、加载、空状态、权限、重复操作、反馈与恢复；
- **系统状态**：真实服务执行规则、持久化正确结果、拒绝非法操作，并在刷新、重进或必要重启后保持一致。

纯内部变化以调用方契约、数据正确性、性能或系统行为为主要证据。验证不能只写“页面存在”“接口成功”或“单元测试通过”，也不能用未执行计划冒充结果。

## 历史与演进

已正式归档的需求和 TRD 是可信历史，不改写标题、范围、验收、状态或历史链接。升级、重构、替换、补完和缺陷修复创建新的稳定需求标识和新 TRD，并在 `历史基础与演进关系` 中说明来源、保留行为、变化、兼容或替代关系。

演进关系只表示历史基础，不自动成为严格前置依赖。新设计必须重新分析当前代码，验证新行为和需要保留的历史行为；只有旧完成状态尚未建立为可靠历史时，才可标记“待核验”。

## 自审与按风险审查

正式写入前检查：

- 使用方、场景、范围、核心任务和完成结果是否清楚；
- 产品事实、代码事实、规则、默认、假设和决策是否分离；
- 当前实现是否基于相关代码、测试和实际契约核验；
- 跨需求体验决定是否确实适用，并记录来源、适用范围、Current、Target 与本需求的遵循或改变关系；默认 Target 是否保留依据和重议条件，偏离时是否按影响正确处理；
- 有可核验工程架构资料时，是否避免反向依赖、内部实现泄漏、无消费者的共享抽象和对已确认 Current/Target 的静默偏离；稳定 owner、目录/包/模块边界是否被保留，边界内部文件粒度是否仍可调整，跨边界变化是否已作为架构 delta 记录；
- 是否删除或合并了不必要步骤、字段、决策、重复输入和跳转；
- 用户术语、内容主次、主要行动、关键文案意图、状态与恢复是否充分；
- 产品行为与客户端、服务端、数据、权限、错误和验证是否对应；
- 安全、迁移、兼容性、初始化、异常和回归风险是否遗漏；
- 是否擅自扩大或缩减范围，或过早固定视觉和局部代码细节；
- 纯内部变化是否避免机械套用 UI；
- 已归档历史是否保持不变。

普通、低成本可逆设计完成自审通常足够；跨模块或存在明显取舍时可增加独立审查；安全、不可逆迁移、并发、公共协议、资金或大型架构变化通常值得独立审查。审查意见是决策输入，不是自动批准；只把采纳后的结论和仍需决定的事项写入正文。

## 开发期间的设计调整

活动 TRD 是设计基线，不是不可修改的法律：

- 等价类名、已确认稳定边界内部的文件组织、函数拆分和测试组织变化通常无需更新；跨 owner、目录/包/模块边界的合并、打平、出口绕过或依赖方向变化必须作为架构 delta 更新；
- 产品行为、用户路径、反馈与恢复、职责、数据语义、接口语义、迁移或验证方式发生稳定变化时，更新当前活动 TRD；
- 产品、安全、兼容性或数据层重大变化先与用户讨论；
- 只重新规划受影响部分，不丢弃仍有效的设计和实现；
- 路径安全由需求边界、Git diff、精确暂存和审查保证，不在 TRD 冻结 `allowed_paths`。

## 文件命名

默认建议：

```text
docs/trd/<YYYY-MM-DD>-<文档标识>-<简短名称>.md
```

- 有可靠需求 ID 时沿用；没有时使用稳定语义短名，不编造 Backlog ID；
- 文件保留首次创建日期，后续编辑不因日期变化改名；
- 写入前检查目标路径，只更新确认属于同一活动设计的文件；
- 不覆盖不同设计或已归档历史，冲突时创建语义可区分的新文件；
- 文件名不包含状态、审批结果或 `v2`、`final` 等模糊后缀。

## 完成输出

说明创建或更新的 TRD、关键产品与技术决定、与当前代码或规则的差异、使用的条件式体验证据、仍待确认事项和未核验范围。
