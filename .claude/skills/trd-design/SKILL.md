# trd-design — 技术实现设计

## 核心定位

TRD 是基于用户目标、产品行为、当前代码和项目约束形成的实现决策文档。它先明确目标用户或调用方如何完成任务、系统如何反馈及承诺什么结果，再说明客户端、服务端、数据和外部协作如何共同兑现这些行为。它需要让后续 AI 不必猜测关键产品与技术设计，同时保留视觉细节、类名、局部重构和低层实现的合理调整空间。

本 Skill 用于把一个内聚需求、已有任务或技术问题转化为可指导实现的语义化 Markdown 技术设计。它可以独立调用，不依赖固定上游产物、模块状态或能力执行顺序。

### 何时使用

- 需要为新能力、缺陷修复、升级、重构、替换或补完形成技术设计；
- 需要结合当前项目分析某个 Issue、Backlog 项、方案资料或自然语言需求；
- 需要检查已有但尚未归档的 TRD，并根据代码事实调整设计；
- 需要围绕一个具体技术问题比较方案、明确约束和验证方式。

一份 TRD 通常对应一个内聚需求。如果输入包含多个可独立交付、独立验证或风险明显不同的变化，应先建议拆分，而不是把它们机械塞进同一文档。

### 可独立接收的输入

以下输入可单独提供，也可任意组合：

- 自然语言描述、单个内聚需求、Backlog 项或 Issue；
- 项目、产品、方案、契约或其它相关资料；
- 已有且尚未作为完成历史归档的 TRD；
- 目标代码、代码片段、仓库路径或可访问的项目工作区；
- Swagger、OpenAPI 或项目实际采用的可执行接口契约；
- 一个需要落地的技术问题。

没有 Backlog、固定模块 ID、仓库字段或上游文档，不是拒绝设计的理由。缺少的仅是影响正确设计的必要上下文时，应在当前会话中补充询问。

### 责任边界

- 有现有代码且能够访问时，正式 TRD 必须分析相关代码；用户可以要求减少讨论，但不能要求跳过相关事实核验。
- 无法访问代码时，只能形成暂定设计，并明确区分已知事实、假设与待确认事项。
- 本 Skill 不负责运行期状态、Manifest、任务调度、开发执行、交付流水或下一能力选择。
- TRD 不是完整产品稿、视觉稿或代码规格，不输出完整页面线框、像素级样式、类、函数、文件、接口或表结构清单。
- 外部编排如需兼容旧格式，应在 Skill 之外转换；新 TRD 不为兼容目的重新加入运行 YAML。

## 多视角设计与事实边界

设计时从需求相关的多个视角形成一套一致方案，而不是让虚拟产品、设计、前端、后端和测试角色分别输出会议意见：

- 用户与产品视角明确目标用户、使用场景、核心任务、业务价值和可见结果；
- UX 与交互视角明确入口、关键路径、状态反馈、容错、恢复和必要的可访问性；
- 客户端、服务端与数据视角把产品行为映射为清楚的技术职责和协作关系；
- 测试与质量视角从用户操作、客户端表现和真实系统状态共同验证；
- 安全、运维、迁移或外部协议等专项视角只在需求相关时深入。

产品判断与代码判断一样必须有事实边界：

- 已确认事实来自用户说明、产品资料、现有界面、当前代码或已验证行为；
- 现有惯例来自项目已经稳定采用的产品模式、设计系统和平台行为；
- 合理默认是低风险、易调整且不改变产品语义的常规选择；
- 产品假设是缺少直接证据但设计暂时依赖的判断，必须明确标记；
- 会改变范围、用户结果、安全、兼容性或显著成本的事项属于待确认决策。

产品与体验视角用于把功能做对，不授权自行把功能做大。未经证据支持的新业务能力应作为建议、假设或待确认事项，不直接纳入承诺范围，也不得把 AI 推测包装成用户研究结论。

## 设计行为

以对话和证据推进设计，而不是套用固定状态机：

- 理解目标用户或调用方、使用场景、核心任务、范围、非目标、真实完成结果和历史关系；
- 对用户可见或交互式需求，先明确关键路径、用户可见状态、反馈、失败与恢复，再进入技术方案；
- 检查相关产品行为、界面或客户端、设计系统、代码、数据、接口、权限、安全、测试和项目惯例；
- 向用户反馈当前理解、已验证事实、可复用基础、合理默认、产品假设、约束和关键发现；
- 识别需求与现有产品行为、代码、文档或历史承诺之间的冲突，不静默迁就任一方；
- 讨论会实质影响产品结果、核心交互、架构、安全、兼容性或迁移成本的决策；
- 形成设计草案，明确产品行为如何映射到客户端、服务端、数据、权限、异常与验证；
- 获得必要确认后写入正式 TRD，并完成自审。

发现冲突时，先说明冲突及影响，再按影响等级在当前会话中澄清或修改尚未归档的相关文档。无需为了局部修正重新调用之前的 Skill，也不得假装冲突不存在。

## 用户确认与自主决策

| 决策类型 | 行为 |
|---|---|
| 产品范围、目标用户、核心流程或完成结果发生实质变化 | 说明选项、影响与建议，取得用户明确确认 |
| 高影响操作的确认、失败或恢复语义 | 说明用户影响和安全边界，取得用户确认 |
| 有意义的架构取舍 | 给出少量可行方案及取舍，取得用户确认 |
| 权限、安全或隐私边界 | 明确风险与约束，取得用户确认 |
| 兼容性破坏或公共行为改变 | 说明受影响对象、迁移方式和回退条件，取得用户确认 |
| 不可逆数据迁移 | 明确数据影响、验证与恢复策略，取得用户确认 |
| 引入新基础设施或中间件 | 说明必要性、运维成本和替代方案，取得用户确认 |
| 重大需求与代码冲突 | 暴露冲突并确认采用哪一边界 |
| 普通类名、文件组织、局部重构、等价工程选择 | 按现有项目惯例自主决定，不把低层细节升级为产品决策 |
| 复用现有组件和设计系统、常规状态反馈、不改变产品语义的布局与文案 | 按现有产品和平台惯例自主决定，并将有风险的假设明确标记 |

用户确认只针对实质性取舍，不应变成具名闸门、固定签字序列或阻塞普通工程判断的流程仪式。

## 代码分析与事实边界

现有代码是可用时的强制设计输入，但分析范围应与需求相关，不做无边界的全仓审计。

必须检查并记录：

- 已验证的当前实现、入口、目标用户可见行为和真实系统行为；
- 可复用的产品模式、设计系统、客户端组件、基础能力、项目惯例和约束；
- 与本需求相关的导航或调用入口、加载、空状态、错误、权限、反馈和恢复现状；
- 与本需求相关的数据、接口、权限、异常和测试现状；
- 当前各交付面对同一状态和错误的解释是否一致；
- 必须改变的产品行为、责任边界、协作关系和受影响区域；
- 代码事实与需求、产品资料、现有体验或历史承诺之间的不一致。

不得虚构或编造现有路径、类、函数、实体、Schema、字段、端点、配置或测试。无法核验时，使用“假设”“待确认”或“待核验”明确标记，不能用貌似精确的符号掩盖未知。

已有 TRD 可作为上下文，但只有尚未成为不可变完成历史时才能直接调整。即使参考旧 TRD，也必须重新分析当前代码，不能把旧设计当作当前实现事实。

### 设计分析红旗

- 收到资料后立即套模板，没有先建立用户目标、产品行为和项目理解；
- 只读需求，不检查可访问的相关产品行为和代码；
- 直接从功能描述跳到接口、数据库或模块设计，没有明确用户如何完成任务；
- 因用户催促而省略事实核验；
- 为显得详细而编造用户研究结论、交互依据、路径、类名、接口或字段；
- 把产品假设写成已确认事实，或为了“体验完整”自行扩大业务范围；
- 把所有视觉和代码细节提前固定，替后续设计与实现做完低层选择；
- 发现冲突就要求重跑前序能力，而不在当前会话处理受影响内容。

## TRD 的语义化 Markdown 结构

推荐结构如下：

```markdown
# <需求名称>技术设计

## 文档信息
## 实现摘要
## 需求定位
## 历史基础与演进关系
## 当前项目分析
## 产品行为与用户体验
## 需求调整
## 实现方案
## 数据与持久化
## 接口与外部协作
## 权限、安全与异常处理
## 实现约束与可调整项
## 验证场景
## 风险与待确认事项
## 本次设计调整
## 设计审查
```

以下标题是稳定的核心语义锚点：

- `## 实现摘要`
- `## 需求定位`
- `## 当前项目分析`
- `## 产品行为与用户体验`，适用于用户可见、交互式或具有外部调用方行为的需求
- `## 实现方案`
- `## 实现约束与可调整项`
- `## 验证场景`

其它章节按需使用；无关章节直接省略，不机械填写“无”。纯内部重构或不改变外部行为的技术需求可以省略或简化产品行为章节，但仍须说明需要保留的调用方行为。可以使用短表格、清单和稳定的场景编号，但不得把正文替换为新的 YAML Schema 或运行契约。

## 产品行为与用户体验

对用户可见、交互式或具有外部调用方行为的需求，应在技术方案之前明确实现需要兑现的产品行为。根据需求按需记录：

- 目标用户或调用方、使用上下文、进入条件、任务目标、身份和数据前提；
- 从产生意图到确认完成的核心路径，以及关键分支和退出方式；
- 初始、加载、空数据、可操作、校验失败、提交中、成功、部分成功、业务失败、外部失败、无权限、数据过期或中断重入等相关状态；
- 用户或调用方如何知道操作开始、成功或失败，失败后输入是否保留，如何重试、返回或恢复；
- 重复提交、危险操作、长时间任务和并发冲突如何避免误操作或错误理解；
- 适用的响应式、键盘操作、焦点、标签、错误关联、可读性和不只依赖颜色表达状态等基本约束；
- 应复用的现有产品行为、设计系统、平台模式和交互惯例。

不是每个需求都要机械覆盖所有状态。只固定会影响用户结果、业务正确性、安全、兼容性或实现协作的行为；颜色值、间距、动画、具体组件名和像素级布局通常留给实现阶段，除非它们承载业务含义或已有设计系统明确约束。

产品行为不能与技术方案各写各的。每项关键行为都应能追溯到相应的客户端或调用方职责、服务端规则、数据与权限约束、错误语义和验证场景。可以按需使用以下简表，不强制所有 TRD 套用：

| 产品行为 | 客户端或调用方职责 | 服务端职责 | 数据、权限与异常约束 |
|---|---|---|---|
| <用户可见行为> | <呈现、输入与状态处理> | <业务规则与结果语义> | <一致性、权限和失败边界> |

## 内容与细节边界

### TRD 应记录

所有需求都应记录：

- 真实使用方或受影响调用方、使用场景、核心任务、范围、非目标和可判定的完成结果；
- 已确认的产品事实、现有惯例、合理默认、产品假设和待确认决策；
- 已验证的当前外部行为与代码实现、可复用基础、约束和必要变化；
- 组件或模块的职责、关键协作关系、业务流和有意义的状态变化；
- 主要技术决策、选择理由、替代方案及其取舍；
- 数据完整性、一致性、生命周期、初始化、迁移和兼容性；
- 接口能力、调用方、权限、关键语义、错误、幂等和兼容性；
- 必须满足的约束、允许调整的实现细节和不在范围内的内容；
- 覆盖真实系统状态、异常、边界和回归风险的验证场景。

用户可见、交互式或具有外部调用方行为的需求还应按相关性记录：

- 关键路径、可见状态、反馈、失败与恢复，以及必要的可访问性约束；
- 产品行为在客户端或调用方、服务端、数据、权限与异常之间的责任映射；
- 覆盖用户或调用方行为、客户端表现和真实系统状态的验证场景。

纯内部技术变化只需说明必须保留的外部行为和适用的系统验证，不强行补写用户交互内容。

### TRD 通常不固定

- 完整用户研究、Persona、页面流程图、线框图或视觉稿；
- 像素级布局、颜色、间距、动画和每个组件名称；
- 每个类、函数及其完整签名；
- 完整文件列表或局部重构机械步骤；
- 全量数据库字段定义；
- 全量业务端点目录；
- 测试文件如何拆分；
- 运行命令、执行元数据或开发任务清单。

只有当精确字段、协议或顺序会影响业务正确性、唯一性、安全、迁移、生命周期、并发或外部兼容性时，才将其固定为设计约束。写得更长不等于更可实现：只固定关键决策，易变的局部代码细节留给实际实现。

## 数据、接口与真实联调

- 产品行为是客户端、服务端和数据设计的共同输入，不能先固定技术接口再让用户流程被动适配。
- 最终数据结构以实际实体、Schema、迁移和数据库代码为事实源；TRD 记录关键语义和约束，不复制全量定义。
- 需要登录但没有公开注册入口的系统，必须考虑首个账号或等价初始化机制，以及权限建立和恢复路径。
- 已有接口应引用 Swagger、OpenAPI 或项目实际采用的可执行契约，不在 TRD 中重定义一份可能漂移的完整接口。
- 新设计的内部接口可以先描述能力、调用关系、关键行为和错误语义；实际实现后的 Swagger、OpenAPI 或等价契约成为接口事实源。
- 只有公共 API、并行团队协作、第三方协议、Webhook、消息协议或高成本兼容场景，才需要在 TRD 中保留较详细的独立契约。
- 设计阶段由客户端或调用方、服务端和数据共同确定产品行为、状态、错误语义与协作契约；实现和联调阶段使用真实服务端能力验证，不能由任一交付面单方面重新定义。
- Mock 可用于隔离局部测试，但不能替代真实数据库、服务或 API 的集成验证与联调。

用户可见功能的验证应形成三层相互对应的证据：

- 用户行为：目标用户能够找到入口、理解状态、完成核心任务，并识别成功或失败；
- 客户端行为：正确处理相关加载、空状态、输入、反馈、权限、重复操作与恢复；
- 系统状态：真实服务执行规则、持久化正确结果、拒绝非法操作，并在刷新、重进或必要的重启后保持一致。

验证场景优先从用户任务描述，再落到客户端表现和系统状态；不能只写接口成功、页面存在或单元测试通过。

这些规则不预设编程语言、框架、数据库、ORM、接口协议或测试工具；具体技术必须来自用户约束、项目资料、现有代码或本次确认的决策。

## 跨文档调整与历史不可变

### 当前需求的调整等级

| 调整等级 | 处理方式 |
|---|---|
| 局部澄清，不改变范围或外部行为 | 可直接修正尚未归档的文档，并在 TRD 中简要说明 |
| 需求结构或依赖关系变化 | 先解释影响，获得同意后在当前会话更新相关未完成 Backlog、方案、TRD 或产品文档 |
| 产品、架构、安全、兼容性或不可逆变化 | 必须取得用户明确确认后再修改相关设计 |

当前会话可以同步修正受影响的未完成文档，不需要重新执行无关能力。`trd-design` 可以说明变化可能影响哪些状态或计划，但不负责维护运行期状态。

### 已完成历史不可变

一旦需求和 TRD 已正式归档为可信历史：

- 不得修改旧需求的标题、范围、验收、状态或 TRD 链接；
- 不得重写归档 TRD 的设计来表示后来的实现；
- 升级、重构、替换、补完或缺陷修复必须创建新的稳定需求 ID 和新 TRD；
- 新 TRD 可使用 `## 历史基础与演进关系` 说明来源、保留行为和替代关系；
- 演进关系表示历史基础，不自动等同于严格的前置依赖；
- 必须重新分析当前代码，不能复制旧 TRD 代替事实核验；
- 验证既覆盖新行为，也覆盖需要保留的历史行为。

只有旧 Backlog 的完成状态尚未建立为可信历史时，才可标为“待核验”；不能借“待核验”修改已经确认的归档历史。

## 自审与按风险审查

### 自审始终必需

正式 TRD 写入前，Leader 必须至少检查：

- 真实使用方或受影响调用方、场景、核心任务、范围和可观察完成结果是否明确；
- 产品事实、代码事实、现有惯例、合理默认、假设、决策和待确认事项是否分离；
- 设计是否建立在相关外部行为、代码与实际契约上；
- 是否遗漏安全、权限、迁移、兼容性、异常或回归风险；
- 关键决策是否有理由，验证是否覆盖适用的真实行为和系统状态；
- 是否擅自扩大产品范围或把产品假设写成事实；
- 是否过早固定视觉或局部实现细节，或混入运行编排职责；
- 是否破坏已完成历史。

对于用户可见、交互式或具有外部调用方行为的需求，还必须检查：

- 是否先明确产品行为，再映射技术实现；
- 关键路径是否按风险覆盖加载、空状态、失败、权限、重复操作、恢复和必要的可访问性；
- 客户端或调用方、服务端、数据、权限与异常职责是否共同覆盖产品行为；
- 用户或调用方可见状态与真实系统状态是否一致；
- 验证是否同时覆盖用户或调用方行为、客户端表现和系统状态。

纯内部技术变化不强套 UI/UX 检查，只检查需保留的外部行为和系统验证。

### 独立审查由风险决定

| 风险 | 审查策略 |
|---|---|
| 普通 CRUD、局部行为或低成本可逆变化 | 自审通常足够，独立审查可选 |
| 中等风险、跨模块协作或存在明显方案取舍 | 可以安排独立审查 |
| 安全、不可逆迁移、并发、公共协议、资金处理或大型架构变化 | 通常应安排独立审查 |

不固定依赖任何具名引擎或审查代理。独立审查意见只是建议，不是强制批准条件，也不因“第二引擎”而高于 Leader 对产品、代码和项目约束的判断。

Leader 必须逐项选择采纳、调整、拒绝，或在涉及实质取舍时询问用户。合理意见直接融入 TRD 正文；普通被拒绝意见无需记录。默认不创建单独的审查流水文件，也不保留完整审查对话。若确实进行独立审查，可在可选的 `## 设计审查` 中只记录有用的最终结论和仍需用户决定的事项。

## 开发期间的设计调整

TRD 是需求仍处于活动状态时的设计基线，不是不可修改的法律：

- 类名、文件组织、函数拆分、测试组织和等价局部重构变化，通常不需要更新 TRD；
- 产品行为、用户流程、反馈与恢复、职责、数据语义、接口语义、迁移或验证方式的稳定变化，应在当前开发会话更新活动 TRD；
- 产品、安全、兼容性或数据层面的重大变化，必须先与用户讨论；
- 不重新启动整套流程，也不丢弃仍然有效的代码；只重新规划受影响的剩余工作；
- `allowed_paths` 不在 TRD 中冻结。范围安全来自需求边界、Git diff、精确暂存和审查。

## 文件命名

默认建议路径：

```text
docs/trd/<YYYY-MM>/<YYYY-MM-DD>-<项目或范围>-<文档标识>-<简短名称>-技术设计.md
```

- 有可靠的上游需求 ID 时，以该 ID 作为文档标识；无需求 ID 时，不得编造 Backlog ID，也不要求用户先创建 Backlog，而应根据本次设计范围生成稳定、可复用的文档标识，例如规范化语义短名，并在同一会话或同一活动设计的后续更新中沿用；
- 新文件始终保留首次创建日期前缀，后续编辑不因日期变化改名；
- 写入前检查目标路径是否已存在。只有确认目标是同一份、尚未归档的活动 TRD 时，才允许在原路径更新；
- 如果目标属于不同设计、已完成或已归档历史，或者无法确认归属，必须生成不冲突且语义可区分的新文件名，禁止覆盖；
- 文件名不包含状态、流程顺序或审批结果；不使用 `v2`、`final` 等模糊版本后缀，必要时使用明确的范围短名或稳定区分标识，新建独立 TRD。

## 示例：从用户目标和事实到实现决策

以下是表达方式示例，不代表任何项目的既有符号：

```markdown
## 当前项目分析
- 产品事实：管理员需要在空数据库首次部署后进入系统，但当前没有公开注册入口。
- 代码事实：当前登录能力只支持已存在账号，尚无首账号建立路径。
- 现有惯例：登录失败使用页内错误提示并保留非敏感输入。
- 待确认：初始化凭据由部署系统注入，还是由一次性命令生成。

## 产品行为与用户体验
- 目标用户：首次部署系统的管理员。
- 核心路径：执行受控初始化 → 使用首账号登录 → 进入首个真实业务功能。
- 失败与恢复：已有账号时重复初始化应被明确拒绝，不覆盖现有账号；登录失败时不泄露账号是否存在。

## 实现方案
采用显式的一次性初始化能力；成功创建首账号后即失效，并记录审计信息。登录界面沿用现有反馈模式，初始化能力、认证服务和真实数据库共同保证上述产品行为。具体类名、文件位置和函数拆分按项目惯例在实现时决定。

## 验证场景
- AC-001：空数据库首次部署时，管理员可建立首账号并通过真实登录界面进入系统；客户端反馈、认证结果和数据库账号状态一致。
- AC-002：已有账号后再次执行初始化会被明确拒绝，现有账号和权限不变，且不会产生重复数据。
- AC-003：无效凭据登录时，用户得到可理解且不泄露账号存在性的反馈，系统不建立会话。
```

## 快速参考

| 常见情况 | 应采取的行为 |
|---|---|
| 没有 Backlog | 接受自然语言、Issue、资料或技术问题，补充必要上下文后设计 |
| 产品资料不足 | 区分事实、现有惯例、合理默认、产品假设与待确认决策，不编造用户研究 |
| 用户可见功能 | 先明确产品行为和状态，再映射客户端、服务端、数据与验证 |
| 纯内部技术变化 | 说明需保留的调用方行为，不强行套用 UI/UX 模板 |
| 无法访问代码 | 输出暂定设计，分开标注事实、假设、待确认和待核验内容 |
| 需求与代码冲突 | 说明冲突和影响，在当前会话按调整等级处理，不静默修改 |
| 普通局部实现选择 | 按项目惯例自主决定，不要求用户批准每个类名或文件 |
| 重大兼容性变化 | 说明影响、迁移与回退条件，取得用户明确确认 |
| 已完成历史的能力演进 | 新需求、新稳定 ID、新 TRD，并记录演进关系与回归验证 |
| 普通低风险设计 | 完成自审，独立审查可选 |
| 高风险设计 | 完成自审，并通常安排独立审查 |
| 下游要求旧 YAML | 由外部编排做兼容转换，不把运行字段写回新 TRD |

## 常见错误

- 把本 Skill 写成流程编号、固定前后顺序或生命周期状态机；
- 强制要求 Backlog、模块 ID、仓库字段或其它上游产物；
- 未理解用户目标、产品行为和项目就立即生成模板文档；
- 从功能描述直接跳到接口、数据库和模块，遗漏入口、状态、反馈和恢复；
- 猜测或编造用户研究、产品事实、代码符号、数据结构和接口；
- 为了“体验完整”擅自增加业务范围，或把多视角设计写成虚拟角色会议记录；
- 在 TRD 中复制完整视觉稿、Schema、表结构或 API 目录；
- 用 Mock-only 结果代替真实用户路径、数据库、服务和接口联调；
- 把独立审查或第二引擎批准设为强制条件；
- 保存完整审查流水，而不是把合理结论融入正文；
- 覆盖已归档的需求、状态或 TRD 来表达新变化；
- 为旧下游兼容重新加入运行 YAML、执行元数据或开发编排章节。
