# PCM 计时记录与字段说明

计时文件位于 `pcm-demo/runs/<run-id>/timings.json`，当前格式为 **v2**。以下字段由程序自动生成，不是启动参数，不需要手动填写。它只保存本地观测数据，不控制业务步骤、完成裁决、重试或恢复；业务状态仍以 `state.json` 和 `steps/` 结果为准。

## 先看哪几个字段

在 `steps` 中找到目标 `step` 和 `requirement_id`：

- **`agent_elapsed_seconds`**：Claude Code 各次已记录执行区间的累计耗时。
- **`wall_elapsed_seconds`**：整个步骤第一次开始到最终成功完成，跨越了多长时间。
- **`agent_executions`**：逐次查看 Claude Code 什么时候开始、结束、中断以及每次执行多久。
- **`note`**：仅在存在旧历史缺失、未知中断等需要解释的情况时出现。带提示的累计值可能只是已知部分，不能冒充完整用时。

所有时间戳均为北京时间，使用 ISO 8601 的 `+08:00` 偏移，例如 `2026-09-05T14:51:19.141561+08:00`。所有耗时数值均以**秒**为单位，可以带小数；终端会转换为时、分、秒。

## 1. 顶层字段

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `schema_version` | 整数 | 计时文件格式版本，当前为 `2`，与业务 state/result 的版本无关。 |
| `steps` | 数组 | 步骤级计时记录。第 0～12 步按项目区分，第 13～18 步按需求 ID 和步骤编号区分。 |

第 13 步在实际选择需求前失败时，可以留下 `requirement_id: null` 的未选定记录；后续新调用选出需求，不把之前无归属的记录猜测分配给它。同一需求后续恢复则继续累计对应步骤中的 Agent 区间。

## 2. 每个步骤的字段：`steps[]`

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `step` | 整数 | 步骤编号，当前为 0～18。 |
| `name` | 字符串 | 步骤名称，例如“形成活动 TRD”“实现与验证”。 |
| `requirement_id` | 字符串或 `null` | 所属需求。项目级步骤为空；需求选择尚未确定时也可以为空。 |
| `status` | 字符串或 `null` | 已记录的步骤业务结果：`success`、`failed`、`blocked`；尚未取得本次最终结果或被取消时为空。首次成功后保持成功，不因复用检查重置。 |
| `started_at` | 时间戳或 `null` | 该步骤已知的首次开始时间。恢复不会重新设为本次启动时间；历史起点无法确定时为空。 |
| `finished_at` | 时间戳或 `null` | 该步骤首次成功已持久化后观测到的完成时间，先于终端结果输出保存；随后收到退出信号不会撤销已观测成功。失败、阻塞或中断不填写此字段；历史成功缺少结束证据时也为空。 |
| `agent_elapsed_seconds` | 数值或 `null` | 当前已记录、已闭合的主 Claude Code 调用区间耗时之和。执行中的区间暂不计入；存在缺口时仅代表已知累计，见 `note`。 |
| `wall_elapsed_seconds` | 数值或 `null` | `finished_at - started_at`。只有步骤已成功且起止时刻均可信、时间差非负时才有数值。 |
| `agent_executions` | 数组 | 该步骤中每次主 Claude Code 调用的时间区间，按开始顺序保存。 |
| `note` | 字符串，可省略 | 数据缺失或时钟异常等解释。正常完整记录不写这个字段。 |

### 两个耗时为什么不同

`agent_elapsed_seconds` 只包住 PCM 对主 Claude Code 的实际调用，包含调用内的启动、模型交互、工具、测试和子代理等待；不包含调用外的 AI-compatible 负责人决策、Python 收口、步骤级 10/30 秒退避或进程退出后等待恢复的时间。

`wall_elapsed_seconds` 计算整个步骤的自然时间跨度，上述等待全部包含在内。不同进程间的停机间隔不需要也不会伪装成 Agent 执行区间。

每次正常 `continue`、完成核验后的修复、达到调用限制后的继续、通道失败后的自动重试、手工恢复，都只在**确实再次调用 Claude Code**时新增一个 Agent 区间。同一个 Claude session 可以对应多个区间；区间数量不是单纯的错误重试次数。

新执行的纯 Python 步骤或仅调用 AI-compatible 模型的步骤，没有主 Claude Code 调用时，`agent_executions` 为空、`agent_elapsed_seconds` 为 `0`。正在执行第一段 Agent 时，已闭合累计也可能暂为 `0`，应结合区间的空结束字段理解。旧历史只有命令耗时、没有 Agent 区间证据时则是 `null`，不能当成 `0` 或用旧命令耗时代替。

内部 Subagent 的工作时间包含在主调用区间里，不另行叠加，以免并行部分重复计时。本功能不拆分每个子代理、每个工具调用或每次 HTTP 请求，也不是纯模型推理耗时统计。

## 3. 每次 Claude Code 执行的字段：`agent_executions[]`

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `started_at` | 时间戳 | 这一次主 Claude Code 调用发起前的开始标记时间。先落盘，再进入 Agent 调用。 |
| `finished_at` | 时间戳或 `null` | 这一次调用返回或异常退出、完成相应清理后的观测时间。**不表示整个步骤已成功。** |
| `interrupted_at` | 时间戳或 `null` | 可观测的中断时刻：收到取消信号时的时间，或调用返回/抛出时识别到异常、限制的时间。正常返回为空；无法取得证据时也为空，须结合 `end_reason`。 |
| `elapsed_seconds` | 数值或 `null` | 单调时钟测出的主调用耗时，包含 SDK 自身退出清理，但排除计时文件读写和计时器自身的返回结果分类。系统日历时间调整不会改变此数值，未闭合区间不补算。 |
| `end_reason` | 字符串或 `null` | 结束原因，取值见下表。刚开始尚未结束时为空。 |

开始标记需要先落盘，而单调时钟累计从标记写完、紧邻实际调用的位置起算，并在调用返回或抛出时立即停止。因此开始标记落盘延迟和系统时钟变化可能使两个时间戳之差与 `elapsed_seconds` 略有不同；执行耗时以 `elapsed_seconds` 为准，不从日历时间戳反算。

### `end_reason` 的取值

| 取值 | 含义 |
| --- | --- |
| `returned` | SDK 主调用正常返回。Agent 可能是在请求决定，仍不代表步骤完成。 |
| `turn_limit` | 达到 Agent 调用轮数限制后返回，可按原合同恢复。 |
| `budget_limit` | SDK 返回历史兼容的预算限制终止；计时功能不新增预算配置。 |
| `api_error` | SDK 返回 API 错误状态或明确 API 错误终止。 |
| `error` | SDK 返回其它错误、异常信息或非正常终止原因。 |
| `exception` | 主调用直接抛出异常。计时不保存异常正文，不改变原异常传播。 |
| `cancelled` | 调用被取消，但没有捕获到更具体的 SIGINT/SIGTERM 接收信息。 |
| `sigint` | 在本次调用期间捕获默认 SIGINT，例如 Ctrl+C。 |
| `sigterm` | 在本次调用期间捕获默认 SIGTERM。 |
| `unknown` | 后续恢复时发现历史区间未闭合，无法确定真实结束原因与时刻。 |
| `null` | 尚未记录结束原因；既可能还在执行，也可能已经发生不可观测的退出。 |

### 中断与结束为什么可能有两个时间

收到 SIGTERM 后，SDK 可能还要取消任务、释放资源。因此 `interrupted_at` 可以早于 `finished_at`：前者表示首次收到信号，后者表示调用已退出清理范围。

API 错误、轮数限制等由返回结果才能识别的情况，记录的是程序**收到异常返回或捕获异常**的观测时间，通常等于该区间的 `finished_at`，不是服务端故障最早发生的时刻。

默认 SIGINT/SIGTERM 处理会保存观测时间并维持取消退出，不触发自动重试；已有自定义或忽略信号策略不会被计时功能覆盖。SIGKILL、断电或进程彻底崩溃无法靠自身保存中断时间，结束、中断和耗时字段保持为空。后续恢复只将结束原因标为 `unknown` 并添加步骤级提示，不使用恢复时刻或文件 mtime 补造旧区间。没有外部观察者时，不能承诺内核精确终止时间。

即使某个 Agent 区间缺少结束证据，只要步骤首次开始和最终成功时间已知，**步骤总历时仍然可以计算**；Agent 累计值则保留缺口提示。这是两个独立指标，不用一个“计时完整”布尔值混在一起控制。

## 4. 读取示例

下面只是字段示意，不是真实运行记录。第一次 Agent 调用执行 600 秒后因 SIGTERM 中断，恢复后的调用执行 900 秒；步骤从 14:00 到 15:00 完成：

```json
{
  "schema_version": 2,
  "steps": [
    {
      "step": 14,
      "name": "形成活动 TRD",
      "requirement_id": "REQ-EXAMPLE",
      "status": "success",
      "started_at": "2026-09-05T14:00:00+08:00",
      "finished_at": "2026-09-05T15:00:00+08:00",
      "agent_elapsed_seconds": 1500.0,
      "wall_elapsed_seconds": 3600.0,
      "agent_executions": [
        {
          "started_at": "2026-09-05T14:00:05+08:00",
          "finished_at": "2026-09-05T14:10:05+08:00",
          "interrupted_at": "2026-09-05T14:10:00+08:00",
          "elapsed_seconds": 600.0,
          "end_reason": "sigterm"
        },
        {
          "started_at": "2026-09-05T14:30:00+08:00",
          "finished_at": "2026-09-05T14:45:00+08:00",
          "interrupted_at": null,
          "elapsed_seconds": 900.0,
          "end_reason": "returned"
        }
      ]
    }
  ]
}
```

由此可见：Claude Code 累计执行 **25 分钟**，整个步骤跨越 **1 小时**。负责人决策、恢复等待等没有被塞进 Agent 区间。

## 5. 旧版记录与安全升级

v1 的顶层是 `executions`，每条记录代表一次步骤命令，而非一次 Claude Code 调用。新版本只读汇总时可以在内存中投影为 v2，不改原文件，也不创建归档。

在既有单机串行流程中，后续新启动的步骤或显式恢复首次需要写入时，才执行：

1. 先将 v1 文件的**原始字节**完整写入并关闭临时文件，再以原子、独占的方式发布为同一 run 目录的 `timings.v1.json`。写入中断不会发布半成品归档；已有不同内容的归档不覆盖，计时警告后停止本次持久化，业务继续按原合同执行。
2. 将可确认的步骤首次开始和首次成功结束转换为北京时间，原子写入新 `timings.json`。
3. 不把旧 `elapsed_seconds` 转成 `agent_elapsed_seconds`，不把旧步骤命令记录伪造成 Agent 区间。历史 Agent 时间为空，必要解释进入 `note`。

已有运行中的旧进程不会热加载代码；不为了计时重启它，也不在它执行期间手工编辑记录。后续新步骤自然加载新代码。已经启动的旧 `run_all.py` 主进程可能仍不能显示 v2 汇总，下次启动的新版本可以正常读取。当前流程不支持同一 run 的多个写入进程并行执行。

`timings.v1.json` 是原始历史归档，因此保留旧时区表示和旧字段；当前 `timings.json` 才是精简后的北京时间视图。

### 旧字段对照

| v1 字段 | 原含义与 v2 处理 |
| --- | --- |
| `schema_version` | 原为 `1`，当前格式为 `2`。 |
| `executions` | 一次步骤命令一条；新版改为 `steps` 聚合，真实 Agent 调用在 `agent_executions`。 |
| `step`、`name`、`requirement_id` | 步骤与需求归属，继续保留。 |
| `started_at` | 原为本次命令的开始；新版步骤层为可信的首次开始，区间层为每次 Agent 开始。 |
| `finished_at` | 原为本次命令的结束，可能成功、失败或阻塞；新版步骤层仅记录首次成功结束，区间层记录每次 Agent 调用的结束。 |
| `elapsed_seconds` | 原为整次命令耗时，包含决策、核验和自动重试等待；只保留于 v1 归档，不作为 Agent 时间。新版同名字段仅出现在真实 Agent 区间内。 |
| `attempt_count` | 原为本次命令内的步骤尝试数，不是 Agent 调用数；新版不再写入，真实调用次数可看区间数组长度。 |
| `status` | 业务结果语义保留，但 v2 按步骤聚合，不再对应每次命令记录。 |
| `applicable` | 是否适用，属于业务结果；计时不再复制。 |
| `reused_success` | 原用于排除成功后的复用检查；新版没有真实 Agent 调用就不新增区间，首次完成信息不重置，不再写该布尔值。 |
| `history_missing` | 原为历史缺失标记；新版使用空的未知时间与必要的步骤级 `note`，不反复展示 `false`。 |

## 6. 使用与边界

- 默认启用，无需新增参数或环境变量。`run_step.py` 显示当前步骤的两个指标，`run_all.py` 完成或停止时只读汇总。
- 输出提示使用 stderr，原有 stdout 结果路径不变；计时读写或展示失败只警告，不改变业务结果和退出码。
- 不直接调用或解析模型来判断耗时；不把步骤、需求或计时背景追加到模型 prompt。记录中不保存 prompt、模型回复、错误正文、API Key 或环境变量。
- 首次成功后的正常幂等复用不会新增 Agent 区间或改写原始起止时间。业务判断仍由步骤本身负责，计时文件不是成功证明。
- 本功能没有定时心跳、剩余时间预测、成本统计、子代理独立时间轴或外部监控服务。
