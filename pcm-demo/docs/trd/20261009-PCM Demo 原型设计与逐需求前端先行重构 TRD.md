# PCM Demo 原型设计与逐需求前端先行重构技术设计

> 设计日期：2026-10-09
> 状态：原型与前端先行初版已接入，其全量 969 项自动化测试及独立审查通过；当时版本的隔离代表性产品已完成真实第 1～18 步，含前端独立交付及后端同会话恢复。
> 范围：产品定义中的 HTML 原型、风格与框架继承，以及三类需求开发入口共用的前端先行执行。

## 一、目标与确定的路线

产品从一句话或初稿进入自动化开发。先通过产品文档和可操作 HTML 原型确定整体体验；每项需求完成活动 TRD 后，独立完成该需求的前端，再由另一个开发会话完成剩余实现、后端接入和真实集成。全局体验先统一，业务页面按需求实现。

第 1～18 步编号及现有阶段入口保持不变：第 2 步内部增加原型域，第 15 步内部增加前端域。产品质量迭代和人工反馈复用同一第 15 步，不另建开发路线或选择开关。纯后端需求不启动前端 Agent；纯前端需求的后续开发域完成必要集成与交付核验，不为形式增加后端代码。

执行 Agent 负责设计判断、实现、浏览器验证、独立体验评审和定向精修。AI-compatible 负责人处理流程语义、必要取舍和完成交接，不评判页面审美、不读取截图重做验收，也不要求真人确认原型。公共 `completed/continue/blocked`、外层三态、重试、锁、端口和远程同步规则保持原义。

本次依赖已实现的 [frontend-ui-ux](../../../.claude/skills/frontend-ui-ux/SKILL.md)。它及调用方须显式使用完整插件入口 `/ui-ux-pro-max:ui-ux-pro-max`，子 Agent 同样收到专业任务说明和实际调用要求。核心领域能力继续独立；具体调用顺序由 PCM 调度，不在通用开发 Skill 内建立固定插件调用链。

## 三、第 2 步：产品定义与 HTML 原型共同收敛

### 3.1 执行顺序与适用性

先由现有 `project_intake` 会话形成产品定义，再判断产品是否有需要表达的用户界面。判断使用既有 AI-compatible 结构化调用，输入为已经核验的两份产品文档正文；输出仅为严格布尔 `applicable` 和非空 `reason`。它只决定是否需要原型，不评价效果。结构错误按现有结构化请求处理，不能默认按 false 跳过。

在创建原型会话前，将判断及固定入口保存为 `state["project_intake"]["prototype"]`。恢复直接复用已保存事实；判定后原型域对文档的授权内细化不触发重新分类。实质改变产品交付形态属于范围变更，不作为普通原型修正。

适用时顺序运行 `product_prototype` 域，首行调用 `/frontend-ui-ux`，创建独立 Claude session、decision conversation 和 system snapshot。无用户界面的产品不创建该域的执行会话、不调用插件、不产生空 HTML 或占位目录。

原型域复用现有 `development` 模型与 effort 配置；产品定义域继续使用 `project_intake`。不新增 model-policy 必填项或环境变量。

### 3.2 原型任务合同

输入为两份产品定义、原始产品资料的必要引用、工作区规则、已有品牌约束、适用资源及运行配置。只传相关资料路径，Agent 按需读取，不内联全部附件。

首次设计且没有明确品牌／视觉方向时，由 `frontend-ui-ux` 简短比较少量实质不同且适合产品的方向（通常两个），依据产品任务选定一个再实施；已有明确方向直接继承，模板默认不自动成为产品品牌。方向差异涉及排版、密度、构图、表面或品牌色关系，不靠随机换色；不设禁用颜色、固定候选报告或额外真人审美审批。

原型覆盖主要页面、导航、核心任务和代表性状态，使整体产品理解与视觉方向可观察。采用原生 HTML/CSS/JavaScript，可拆分本地样式、脚本和必要资产；不初始化正式框架工程，不在 `frontend/` 或 `backend/` 写业务代码。

固定入口为 `docs/prototype/index.html`，其它原型页面与资源在同目录内组织。产品功能文档提供该入口及需要长期保留的交互决定；不增加第三份产品定义、原型 manifest 或全量逐页规格。代码与页面保留正式业务内容，不出现演示、模拟数据、待接接口等过程说明；实际模拟边界在开发交接中明确。

Agent 可修正两份产品文档中已经授权的行为澄清、术语和一致性问题，使文档与可操作结果一致。不得改写产品初稿或导入原始资料，不擅自扩大或缩减产品承诺。涉及实质范围变化时通过原有负责人对话决定，并同步有效正文；不回退外层步骤。

所有产品（含后台与平台）都要打磨组件质感和适当交互动效，主动使用合适的 SVG、图标与媒体；删除重复副标题、装饰眉题、口号和无用小字，保留必要业务信息、规则、风险与恢复说明。原型域自行完成浏览器操作、实际渲染检查、独立体验评审，并依据具体发现多轮定向精修。Python 只检查文件事实，负责人只根据有效交接推进，不建立视觉评分或截图审查器。

### 3.3 运行、完成与输出

静态预览按 `.pcm/runtime.json` 的 frontend host、port、endpoint 启动，可使用当前运行环境已有的静态服务能力，不为原型安装正式应用框架。只停止本任务启动且归属明确的服务，交接前释放自己使用的预览端口；未知占用按冲突处理，不换端口或停止未知进程。测试截图遵循产品工作区的忽略目录约定，不当作原型正式资产提交。

保持 `02.json.outputs` 精确为：

- `docs/requirements/项目需求说明.md`
- `docs/requirements/产品功能说明.md`

在结果顶层增加 `prototype`：

```json
{
  "applicable": true,
  "entry": "docs/prototype/index.html",
  "reason": "产品包含面向用户的页面与交互"
}
```

不适用时 `applicable:false`、`entry:null`，reason 说明实际产品形态。prototype 对象是新 success 的必需交接；判断未完成的失败结果只保存已知事实，不填 false 占位。成功复用核验该对象，不由 HTML 文件是否存在反推适用性。

两文档域完成且原型域完成／不适用后，才写第 2 步 success 并进入第 3 步。适用时核验两份最终文档和固定 HTML 入口均为工作区内可读、非空的普通文件，沿用当前路径及符号链接保护；文档一致性、资源引用和真实交互由 Agent 验证。缺入口在原型原会话修复，不能因两文档已齐全就成功。

本步骤不提交。第 4 步只组装工程目录，原型自然保留；第 8 步将两文档、原型及正式资源纳入根仓首次提交。

## 四、第 6、10 步：继承原型，不重新选择产品外观

### 4.1 项目化、风格和品牌

第 6 步保留 `project_bootstrap`、`tailwind_theme`、`brand_assets` 三个域及原有模型配置、适用性、Tailwind v4 CSS-first 检查和结果结构。三个域均得到第 2 步原型交接与入口引用。

- 项目化域继续调用 `/project-bootstrap`。原型及两份产品定义只读，不按模板残留清理；完成身份、配置、基础运行与 README。必要时在正常开发说明中提供原型入口，不开发业务页面。
- 主题域调用 `/tailwind-theme`，PCM 提示仍明确要求实际调用 `/ui-ux-pro-max:ui-ux-pro-max`；任务限定为从原型落实当前工程的主题、字体、间距和共享视觉基础。保留 `tailwind_theme` 领域 key 和 task，避免改动模型策略。保持已选方向，允许适配 preset，校准字体可用性、明暗模式、对比度与组件状态；原型只读，不以 preset 覆盖既定方向，不改业务布局。
- 品牌域由 `/frontend-ui-ux` 承接，实际调用 `/ui-ux-pro-max:ui-ux-pro-max`，按需使用插件品牌能力及工作区已有媒体工具，主动选择合适的 SVG、图标和媒体。优先复用原型品牌，补齐同一身份的页面标识和 favicon；不重做业务布局。生成服务不可用时遵循工具错误处理规则，可采用合格的本地 SVG 或文字标识；秘密边界及 Agent 自验合同保持。

主题工程与品牌设计各用对应专业入口，媒体能力按需使用。主题和品牌可复用仍有效证据，不重复检查整套原型。第 5 步已建立产品文档指纹基线，因此第 6 步不得为风格整理修改两份产品文档或回写原型；需要澄清时在当前工程和已有适用设计位置表达，不静默改变资源准备依据。

### 4.2 产品级体验框架

第 10 步继续由 `/ui-ux-framework` 只维护 `docs/ui-ux/framework.md`，不增加页面开发会话。输入增加原型入口及当前主题、品牌的真实实现。

原型表达已确定体验方向，工程中的主题与品牌表达当前实现；框架文档整理并补齐导航、Shell、页面模式、滚动、常驻关系、响应式和跨页面使用规则，不另起设计。真实冲突按原有对话处理，允许的写入范围仍只有框架文档，Git clean／提交边界保持。

第 11 步继续按完整业务结果拆分需求，包含原型未展开的必要能力与规则；不按页面、前端、后端拆成两份 Backlog。正式页面随需求落地后，代码成为当前实现事实，不要求双份维护 HTML 原型。

## 五、活动 TRD 与前端适用性

第 14 步仍独立设计自由格式活动 TRD，不增加机器必填章节或前端布尔字段。调用 Prompt 明确承接原型和已有界面，并在本需求范围内收敛会影响前端的用户路径、关键状态、数据展示／输入语义、权限呈现、同步或异步结果及主要失败恢复。普通组件拆分、后端内部组织等继续留给实现。

第 15 步消费现有需求、cycle、workspace、第 14 步 scoped success 与完整 TRD，复用 `parse_response` 作一次严格的 `applicable: bool`、`reason: str` 判断。判断仅回答本需求是否需要前端界面或用户可见交互工作，不重新设计 TRD；依据需求行为而非有无 frontend 目录或关键词。

将结果先保存至：

```text
state["development_<ID>"]["frontend_applicability"]
```

随后才启动开发 Agent。缺失可首次判断，合法记录恢复时直接复用；格式错误失败，不重置或默认为 false。产品有 frontend 但本需求纯后端时为 false；需要前端而当前权威工程没有对应交付单元时报告本地合同冲突，不以不适用掩盖。

这个事实表示当前需求开始时的任务分工，不是永久冻结产品界面。后续集成中出现必要的局部 UI 调整，由当前开发会话处理；实质范围改变仍走现有决定与活动 TRD 更新规则，不回退重新运行已完成的前端域。

## 六、第 15 步：独立前端与完整集成交付

### 6.1 会话、输入和模型

| 域 | key / state_key | 能力与责任 |
| --- | --- | --- |
| 前端 | `frontend_ui_ux_<ID>` | `/frontend-ui-ux`；当前需求的正式框架前端设计、实现和局部验证 |
| 完整开发 | `development_<ID>` | `/dev-workflow`；承接前端，完成剩余实现、后端、真实接入与需求收口 |

两域使用不同 session、conversation 和 system snapshot，均复用现有 `development` 模型策略。前端不适用时不创建前端 session；完整开发域仍执行。外层一直停在 `requirement:15_development`，前端完成不会推进第 16 步或修改需求完成状态。

两个域都得到当前需求、活动 TRD 路径，以及质量／反馈周期中与当前需求相关的原发现、原场景和采纳目标。Agent 按需读取原型、框架、工程架构和实际代码；不向前端上下文灌入全部后端文件，也不向后端灌入所有原型 HTML 源码。

负责人各域上下文继续采用第 15 步已有的完整活动 TRD 及必要非秘密路径事实，不增加截图、代码 diff 或完整产品文件作为审美验收材料。适用性判断复用同一 TRD 输入；进入完整开发域时重新读取当前活动 TRD，承接前端已授权的稳定修正。

领域 Prompt 只表达任务、输入、输出、约束和交接，不包含 PCM 步骤编号、运行目录或整套编排背景。前端委派显式传入完整插件入口；完整开发中的用户可见设计调整也明确使用该能力，纯接口地址或数据映射修改不重跑设计。

### 6.2 前端域

在最终选定技术栈的现有工程中实现当前需求，不创建第二套演示应用。首次需要共享基础时，在当前范围内建立 Shell、路由接线、主题与必要共享组件；后续复用已验证实现，不提前展开全部业务页面。

已有真实接口直接复用；缺失部分允许集中、可替换且语义连贯的模拟数据访问。完成当前用户任务、相关状态、宽窄屏与实际滚动验证，并按能力合同及上述体验质量要求完成独立体验评审，依据具体发现多轮定向精修。不得因为没有尚待开发的后端，要求前端域提前完成数据库或真实持久化验收。

只修改当前需求所需的正式前端代码、测试、资产和必要开发说明；早期 HTML 原型只读，不通过反向修改原型掩盖实现偏差。可以同步活动 TRD 的授权内稳定细化，不改后端业务、需求生命周期或 `.claude/rules/`。保持同一需求分支和待提交变更，不 stage、commit、建分支、merge 或 push。

正常交接说明实际入口、已实现行为、真实／模拟数据边界、实际验证及仍需接入的内容。交接保存在现有 conversation，不新增前端阶段报告。负责人按当前前端任务完成合同判断；不因真实后端尚未实现或未逐项复述证据反复继续，也不把该 completed 当作整个需求完成。

### 6.3 剩余实现与真实集成

前端完成后，PCM 从现有保存的对话取得有效交接，传给新的 development 会话；使用现有 `agent_conversation_report` 保留有序自然语言交接，不只取可能是局部补充的最后一句。实际代码与活动 TRD 仍为事实依据，不传工具日志或重新制造成果快照。

开发 Agent 主要完成后端规则、权限、数据、接口、前端接入和真实用户任务。前端是需要保留的设计成果，不是不可修改的成品：真实数据、失败恢复或权限状态要求调整时定向处理，不能为接线方便整页重做；涉及 UI/UX 实施时实际调用已指定前端能力及插件。

`dev-workflow` 保留完整需求交付责任及真实环境、数据、账号、审查和 README 合同。前端独立体验证据可在仍有效时复用，变化只使受影响部分失效。后端规则用相称接口／集成测试，浏览器覆盖真实接线、结果持久化与关键恢复，不重复整套前端设计和所有后端矩阵。

### 6.4 结果、Git 与后续复盘

第 15 步结果继续使用 `outputs: []` 及原有需求、TRD、开发 session 字段，新增 `frontend` 对象，保存适用性、理由和前端 session 引用；不适用时 session 为 null。frontend 对象是新 success 的必需交接；分类尚未完成的失败结果可不含该对象，不能填 false 冒充不适用。成功必须同时满足前端 completed／不适用与完整开发 completed；Python 不通过截图、DOM 或 Git diff 自行判断质量。

前端 session 留在公共 sessions/conversation 存储，不向 cycle 复制另一套状态。`requirement_cycle.development_session_id` 始终只指向后端与集成 session；前端先失败时允许它尚为空，不能错填前端 ID。失败／阻塞结果保留已知 frontend 交接与当前错误，CLI 的 scoped 保存逻辑同步处理前端域，不能硬编码所有错误都属于 development 域。

第 16 步仍恢复 development session，复盘其真实执行与已承接事实，不增加第二轮前端复盘。第 17、18 步继续统一提交、ff-only 合并和需求生命周期收口。只有第 18 步完成后，正式需求才成为 completed。

## 七、中断恢复与旧现场边界

复用公共循环，不增加 `frontend_ready`、专属恢复日志或第二套完成状态：

- 第 2 步原型失败时，已完成的产品定义域不重跑；恢复原型原 session 及其已保存对话。
- 第 15 步前端失败时不启动 development；前端完成后 development 失败，恢复时复用前端已完成记录，继续原 development session。
- `--resume-message-file` 的候选 key 增加第 2 步的 `product_prototype` 和第 15 步的 `frontend_ui_ux_<ID>`。沿用唯一未完成对话定位、歧义拒绝和一次消费规则，不向已完成前端误投消息。
- 各域完成后、步骤 result 写入前中断，复用已有 completed 对话；result 已写、state 未推进时只补推进。严格成功校验纳入新增交接，不重做已完成成果。
- 适用性判断保存后不重复调用分类模型；判断完成但尚未保存即中断，允许重试该无业务写入的判断。真实 Agent 执行恢复沿用现有通道重试。

新流程不原地接管语义已经改变的旧执行现场。第 2 步当前 success 缺少 prototype 合同；第 15 步已存在 development session／conversation 却缺少 frontend_applicability，或当前 success 缺少 frontend 结果合同时，均只读拒绝接管，不自动补写、重放或清理。只有适用性记录、尚无执行会话的新现场不属于旧运行，允许按记录继续。第 2 步尚未完成的旧产品定义域目标未变，可以沿用原会话完成定义，再创建新原型域。

旧现场识别必须在适用性分类、Agent 调用及通用 scoped 失败回写之前完成。拒绝通过入口的只读早退或等价保护返回明确错误，不修改原 `state.json`、步骤 result 或 conversation；不能仅在步骤中抛异常后，任由现有 CLI 把旧 success 覆盖为 failed 或重新锚定节点。新成功校验与历史结果保护分别处理，已经越过节点的记录不反向套用新字段要求。

发布前应先用原工具版本收口正在执行的旧需求／初始化；未收口现场保留，由原版本按原恢复合同处理。新程序只有本次路线，不增加旧执行分支或自动迁移工具。已经越过相关节点的历史完成记录只读，不反向套用新产物要求或追补原型。

既有已完成产品可以在能力就绪后创建新的质量／反馈周期，源 run 只读。没有早期 HTML 原型时，使用当前真实前端和已有设计作为该产品基线，不回退补跑初始化。新周期仍执行本次前端先行路线。

## 八、能力发布与实施接点

第 1 步从权威模板取得能力；SDK 只加载目标工作区的 `plugins-lock.json`。新模板需要包含完整 `frontend-ui-ux` 目录、可用插件及具备 Skill 工具的开发角色。扩展现有模板最低能力检查，避免昂贵运行开始后才发现缺失；不得借用用户级缓存来掩盖产品工作区缺能力。

旧产品的能力文件不会因 PCM 代码更新而升级。开始新周期前显式同步所需受控能力并使用新 session 验证，保留已有产品规则和配置；按既有 Git 规则提交受控更新、恢复各仓 clean main 后再附着新周期，不由领域 Agent 偷改只读能力模板。本项不建设通用升级器；缺少所需能力时准确失败并指出同步条件，不静默改回原开发路线。实际发布模板或修改既有产品需对应授权，本次设计不执行这些动作。

| 位置 | 必要改动 |
| --- | --- |
| `steps/step_01_create_workspace/workspace.py` 及模板测试 | 检查新增能力及配套资源可用，不改发布和秘密边界 |
| `steps/step_02_project_intake/step.py` 与对应 prompts/测试 | 一次原型适用性判断、原型独立 loop、文件核验及 prototype 结果交接 |
| `steps/step_06_project_bootstrap/step.py` 与 prompts/测试 | 原型只读输入，主题／品牌的专业实施入口；保留领域 key、模型 task、技术 gate 和结果结构 |
| `steps/step_10_ui_ux_framework/step.py` 与 prompts/测试 | 增加原型输入和继承约束，保持唯一文档写入范围 |
| `steps/step_14_trd_design/step.py` 的 Prompt 合同 | 当前需求行为达到前端可实现程度，不增加格式或机器字段 |
| `steps/step_15_development/step.py` 与 prompts/测试 | 适用性记录、双域顺序、交接、scoped 结果与恢复保护 |

| `quality/workflow.py`、`feedback/workflow.py` 及入口测试 | 核验两个域接收同一当前需求的必要原发现；沿用数值步骤入口 |

两处适用性判断使用同一小型结构化输出形状，但不为两个调用新建通用任务框架。领域模型策略、SDK、提供商、环境变量和基础设施保持；模型请求与耗时记录归属原数字步骤，沿用现有计时，不建立专用监控或额外过程文件。

## 九、验证与完成标准

### 9.1 自动化验证

| 场景 | 必须证明的结果 |
| --- | --- |
| UI 产品与无 UI 产品 | 前者两文档及 HTML 一致交付；后者零原型 Agent/插件调用、entry 为 null；分类错误不能默认为不适用 |
| 原型缺失与组装 | 两文档齐全但适用 HTML 缺失时不能成功；缺失在原型原 session 修复；第 4 步组装后原型仍在且正式工程占位未受污染 |
| 风格与框架继承 | 原型引用实际传入；第 6 步不写产品定义或原型；第 10 步仍只修改框架文档 |
| UI、纯后端、纯前端需求 | UI 先前端后完整开发且 session 不同；纯后端零前端调用；纯前端不强制增加后端实现 |
| 交接与三入口 | 活动 TRD 及完整有效前端交接传给开发；质量/反馈原场景不遗漏；同一需求、分支和完成生命周期不变 |
| 失败、阻塞与恢复 | 前端未完成不启动后端；后端恢复不重跑前端；两个域消息定位正确且只消费一次；失败 scope 不误填 session |
| 成功写入中断 | completed 对话、result→state 两个窗口均可续接；完整 success 复用不调用模型、不新增业务副作用 |
| 旧现场及能力缺失 | 拒绝发生在分类和通用失败回写之前；原 state/result/conversation 字节不变且无 Agent 调用，不将旧 success/session 当新合同完成；新周期缺新能力准确失败 |

复用现有第 2、6、15 步、公共 loop、`run_step.py`、质量与反馈入口测试。Prompt 测试检查资料和能力调用接线，不逐句锁死提示词。原型与前端先行初版的全量 969 项自动化测试、语法与 diff 检查及独立审查通过；当时版本的真实验证覆盖与限制见下文，不将未执行检查记为通过。

### 9.2 真实验证

在隔离且具备真实依赖的产品工作区完成一条代表性执行链：

1. 使用包含新能力的实际模板，确认新 session 加载插件，并观察实际 Skill 调用，不能以文件存在替代。
2. 第 2 步生成多页面或多状态 HTML，实际操作主要任务并读取渲染；两份产品文档与原型保持一致，静态预览使用分配端口。
3. 组装、项目化、主题与品牌、体验框架承接同一原型，检查原型保留、正式工程未提前实现业务页及主题继承。
4. 一个正式 UI 需求完成 TRD、独立前端、后端和真实集成；在后端尚未完成时验证前端体验，接入后以真实接口与数据验证完整任务和持久化。
5. 定向制造一次前端完成后的后端中断，恢复只进入原后端会话，前端成果保留；确认最终提交与合并仍统一收口。

纯后端与质量／反馈的路由、证据传递由自动化覆盖，并对受影响真实入口作相称补验。不为同一公共开发链重复建设三个完整产品。浏览器同时关注内容理解、导航滚动、宽窄与矮屏、关键状态及正式业务文案；复用仍有效证据，不用固定审美分数、截图数量或模型自评代替结果。

完成实现后分别报告程序回归、真实通道、代表性产品交付的实际覆盖与限制。独立 Skill 的现有测试不代表本次 PCM 编排已通过；隔离切片也不能冒充全产品从 0 到 1 已完成。

### 9.3 初版实际覆盖（2026-10-10）

2026-10-10，隔离单用户便签产品完成真实第 1～18 步。产品定义与可操作 HTML 原型独立完成，主题、品牌及体验框架继承原型；正式需求经过 TRD、独立前端和后端集成，最终统一提交并 ff-only 合并。原型与正式前端均观察到实际设计插件调用，原型、前端和完整开发使用不同 session；模型、effort、SDK 与提供商沿用当前配置。

在前端完成后的后端会话中注入一次受控中断，真实失败落盘后恢复原后端 session；恢复时前端 session、conversation 及文件哈希保持不变，后续未重新启动前端域。独立核对隔离产品的 root/frontend/backend 三仓均在 main、工作区干净且没有远程。普通模型流中断由既有重试机制恢复，不作为产品实现成功证据。

隔离产品完成后的独立复验通过后端 22 项测试、前端 47 项单元／集成测试、15 项 Chromium E2E，以及类型、Lint、构建和 Python 语法检查。其中 6 项 E2E 使用真实 HTTP／SQLite，另 9 项使用路由夹具检查界面，不能混作持久化证据。真实断言覆盖新增、筛选、完成／取消、刷新、后端进程重启及提交后回包丢失等恢复场景；便签没有用 localStorage 冒充真实存储。复验未重置日常开发库，前后数据与文件指纹一致；宽窄短屏截图已实际检查，测试进程及隔离副本已收尾。仍有约 571 KB 的前端单包构建提示；未验证 Firefox／WebKit、生产部署及真实断电恢复。

无 UI 产品与纯后端索引需求的两次真实适用性判断均为不适用。质量／反馈的双域路由、原发现传递、能力缺失和旧现场只读保护由自动化覆盖，未重复执行两个完整真实产品周期；本次本地链未验证 GitLab 建仓或远程推送。证据保存在根工作区忽略的 `.test-screenshots/pcm-frontend-flow/` 及其 `launch-info.json` 指向的隔离运行目录，不纳入产品交付文件。

### 9.4 设计能力补充验证

专业主题入口恢复及设计能力补充后，PCM 全量 969 项自动化、语法、文档链接与独立合同审查通过。单主题域真实切片使用生产 Prompt、公共循环与 SDK：`/tailwind-theme` 由 CLI 解析并加载正文，设计插件有实际 Skill 调用成功记录；已有合格主题保持不变，原型、产品定义与业务布局未改，构建和明暗／宽窄屏检查通过。这个切片验证专业能力接线及继承边界，不替代重新执行完整第 1～18 步。

设计评估采用高频调度、内容阅读和既有绿色品牌精修三类任务，以旧版 Skill 为基线。首轮独立盲评在前两项偏向新版，精修项旧版略优；新版过期成功反馈的问题已定向修正并独立复验，原盲评结论保留。首轮两个新设计仍偏绿，因此进一步明确首次比较需同时涵盖色彩关系与非色彩维度，再对前两项冷启动执行；既有明确品牌仍继承，不以禁用某种颜色或人为给成品换色作为通过方式。 第二轮独立检查确认调度采用暖白／墨蓝双栏、阅读采用暖纸／墨绿／赭色札记，实际选择同时覆盖色彩与非色彩维度。发现的调度筛选外详情说明和键盘焦点问题已定向修正并独立复验；保留原始发现，不把初稿包装为没有问题。

本轮证据保存在根工作区忽略的 `.test-screenshots/frontend-style-selection-workspace/`。样例与过程断言用于验证选择、实现和精修行为，不是通用审美分数，也不能证明所有产品的风格分布已改变；运行中新增要求及复用基线均单独记录，不据此推断时间或 Token 收益。此次未重跑真实生图服务，未自动更新既有产品的能力副本。
