# PCM Demo 产品质量迭代工作流技术设计

> 设计日期：2026-09-22
> 状态：已实现并通过隔离回归；实际产品完整质量周期尚未验收。
> 范围：为已由 PCM 完成开发的产品建立独立的质量迭代 run，保留原开发记录，复用现有需求开发能力。

## 一、目标与设计决定

阶段一证明已知正式需求完成；质量迭代证明这些能力组合后，主要用户任务能够完整、清楚地完成。它在完整开发流程中承担阶段二，但可以在阶段一结束后单独启动，不要求恢复或改写原 run。

采用以下边界：

- **独立运行记录**：新 run 保存审计、候选处置、新需求生命周期、会话、计时和恢复位置；来源 run 只读。
- **同一个产品**：复用工作区、当前产品定义、canonical Backlog、代码、资源绑定和端口，不复制环境，不创建第二份当前 Backlog。
- **同一套开发能力**：复用第 13～18 步的需求选择、TRD、开发验证、复盘、提交和合并，仅解开阶段及返回位置的硬绑定。
- **先证明修复，再完成需求**：原问题回归属于修复需求的开发完成条件，在提交合并前完成；批次结束后才独立执行完整复审。
- **克制的增量**：修复当前正式范围的真实障碍及边界清楚的改进，不以审计为由自动重定义产品，也不追求消灭全部优化建议。

本次不建设通用工作流引擎、全局需求数据库或同产品并行开发。人工流程提供质量目标；本工作流的运行隔离、注册表和回归时序以本文为实现合同。

现有程序接点：

- 目标产品 `.pcm/runtime.json` 仍绑定原 owner 和固定端口。新 run 不重新认领产品，不调用 release，也不重分配端口。

## 二、入口、执行权与历史隔离

### 2.1 CLI 合同

新增独立入口：

```bash
# 来源可以是已完成的阶段一 run，或已经完成的质量迭代 run
python run_quality.py --source-run rulefolio-20260914 \
  --run-id rulefolio-quality-20260922

# 恢复质量迭代自己的当前节点
python run_quality.py --resume rulefolio-quality-20260922

# 向可恢复的原 Agent 会话补充资料，沿用公共消息投递边界
python run_quality.py --resume rulefolio-quality-20260922 \
  --resume-message-file /path/to/message.txt
```

新运行要求明确 `source-run` 和新的 `run-id`；工作区、仓库清单和 Backlog 路径从来源读取，不接受另一个工作区覆盖参数。已有 run 目录不覆盖；恢复不重新导入来源，也不创建新会话冒充恢复。

`run_quality.py --resume <quality-run-id> --node <当前 quality 节点>` 只执行当前一个命名节点；完整质量编排通过这一模式启动节点子进程，并继承父进程的锁。节点必须与 state 一致，不提供任意跳转或回放历史节点的写入接口。需求节点继续调用 `run_step.py --step 13..18`；原数值步骤入口不增加质量节点分派。

现有 `run_all.py` 默认行为保持阶段一。新增显式 `--with-quality` 用于一键串联：阶段一成功结束后，驱动独立的 `<来源 run-id>-quality` run；该目录已存在且来源一致时恢复它，不新建重复周期。质量运行期间不得让阶段一父进程和质量子进程分别重复取得同一产品锁或消耗两个容量名额，按现有父子锁传递方式交接执行上下文。来源 run 的已完成 state、结果、会话及计时不再写入。再次质量迭代使用独立入口，以最近完成的质量 run 为来源。

### 2.2 产品身份与执行 run 分开

持久产品记录的 `owner_run_id` 继续表示原创建归属与端口租约，不在每次迭代时改写。产品 key、canonical workspace 路径、租约和 `.pcm/runtime.json` 保持不变。

新 run 的执行上下文记录自己的 `execution_run_id`，并关联既有产品 key 和持久 owner。附着时核验：来源确实对应同一产品、产品租约仍为 active、工作区路径与 runtime 一致。读取既有端口，不要求正在运行的已知产品服务端口空闲。已释放的租约或产品身份冲突属于 `failed`，不自动重新激活或迁移。

完整入口和直接单步都必须取得自己的 run 锁、容量名额及同一产品排他锁；父子进程继承锁协议与现有方式一致。不同 run 不能同时修改同一产品。产品 release 使用相同产品锁，因此质量工作流执行中也不能释放租约。诊断输出分别说明持久归属与当前执行 run，不把旧 owner 等同于正在运行的进程。

### 2.3 开始现场

新 run 的 prepare 要求来源已完成、没有活动需求。来源为阶段一时使用现有完成谓词；来源为质量 run 时要求终点为 `quality:completed` 且成功，不能只看某个节点的 `success`。

所有适用仓库应是当前工作区内的独立仓库，位于 clean local `main`，没有进行中的 Git 操作。允许当前 main 在来源完成后正常前进：读取当前 SHA 作为新周期基线，不要求等于来源末次提交。发现未跟踪文件、未提交变更、未知分支或操作中现场时，准确说明并 `failed`，不自动 stash、忽略、提交、删除或重置。Rulefolio 当前四张未跟踪截图须在实际启动前明确归属并按既有规范处理，本次设计不替它们作决定。

开始基线只核验一次；后续节点信任前序交接，各自负责自己的文件与 Git 动作，不逐节点重复审计来源历史。

## 三、事实来源与最小持久化

### 3.1 四类事实各有职责

| 事实 | 权威位置 |
| --- | --- |
| 当前承诺、需求范围和验收方向 | 产品定义、canonical Backlog、相关当前设计 |
| 文档与代码的变化历史 | 各仓 Git |
| 原开发执行及历史完成事实 | 只读来源 run |
| 当前周期的候选处置、新需求执行和恢复位置 | 当前质量 run |

不把生命周期写回 Backlog，也不将当前 run 的候选状态同步到旧 run。已归档需求与 TRD 不回写；有缺陷时建立关联的新需求。

### 3.2 接入时按 ID 承接完成事实

prepare 从来源读取已完成注册表，从当前 canonical Backlog 的同一份字节通过已有 Responses/Pydantic 路径提取正式需求静态字段。Python 保留现有 ID、顺序和依赖图校验，不解析 Markdown 表格、标题或状态措辞。

- 当前正式 ID 集合必须与来源已完成 ID 集合一致，忽略大小写后的身份仍须唯一；出现未知新增 ID、缺失 ID 或无法确定的身份变化时 `failed`，不猜测完成状态。
- 标题、文档顺序及显式依赖按当前 Backlog 读取；历史 `status/completion` 按稳定 ID 承接，不因标题变化重置为 pending。
- 来源本身的标题、指纹、顺序、完成记录均不修改。新注册表记录当前 Backlog 路径及当前哈希，并保留来源 run 和来源 ID 集合。
- 产品语义冲突由 prepare Agent 依据当前产品定义与设计决定核实；不以代码已经如此实现证明承诺已合法删减，也不因为旧标题仍在就恢复已经明确取消的功能。

哈希用于本次读取一致性与恢复，不证明语义或开发完成。来源静态信息与当前文档不同是允许的输入，不建设旧文档迁移机制。

### 3.3 state 与结果布局

新 run 增加 `workflow: product_quality`、`source_run_id`；全周期采用 `phase: product_quality_iteration`。保留现有 workspace、仓库清单、注册表、active requirement、cycle、session 与 conversation 引用。不要复制来源的完整 state、session 或 coordination 执行身份。

质量私有状态只维护当前轮次、轮次上限、当前批次正式 ID，以及开始时的历史 ID 集合和版本基线。节点结果从固定位置读取，不在 state 再复制整份审计与分流内容：

```text
runs/<quality-run-id>/
  state.json
  quality/prepare.json
  quality/rounds/0001/audit.json
  quality/rounds/0001/route.json
  quality/rounds/0001/pool.json
  quality/rounds/0001/register.json
  quality/complete.json
  steps/requirements/<new-ID>/13.json ... 18.json
  conversations/ ...
  timings.json
```

质量节点的 `step/current_step` 为 null，以命名 `current_node` 定位；需求节点继续使用 13～18 和既有 `requirement:*` 名称。需求 cycle 的返回点为 `quality:select_requirement`。旧 run 没有 `workflow` 字段时保持原阶段一行为，不迁移历史记录。

节点对外仍只有 `success/blocked/failed`。注册表仍只有 `pending/active/completed`，候选不是第四种需求状态。

### 3.4 候选和正式需求不是一一对应

完整审计原文及会话保留在当前 run。程序通过 Responses/Pydantic 忠实提取任务覆盖、经核验发现、重复项、覆盖缺口和高影响事项；只做结构与引用校验，不作用户价值裁决。提取失败按 `failed` 恢复，不回退到 Markdown 正则解析或重新执行已完成审计。

候选使用 Python 在本轮结果中分配的稳定局部标识，如 `Q001-C001`，不使用正式 BR ID。提取结果先保存，后续节点不重新提取和重新编号。每项交接保留用户任务、触发条件、当前事实、预期结果与依据、影响、证据引用和限制，不能只留标题或截图路径。

pool 结果中的 `plan.requirements` 保存正式 ID 到纳入候选的关联，`plan.regression_owners` 保存候选到完整原场景回归承接需求的关联。通过 `covered_by` 合并的候选保留在本轮分流结果中；交接开发时沿归属链扩展所有相关原发现、受阻任务和完整回归 owner，不因去重丢失不同场景。允许多个候选合成一项需求；一项候选拆成多个需求时，指定自然承接完整回归的最后一项，并建立对其余必要项的真实依赖。无法得到内聚、可验收的拆法时保持一个需求，不制造独立的通用验收需求。

## 四、节点与执行合同

### 4.1 主循环

```text
quality:prepare
  → quality:audit
  → quality:route
      无纳入项且满足结束条件 → quality:complete → quality:completed
      有纳入项 → quality:pool → quality:register
        → quality:select_requirement
        → 13 选择建分支 → 14 TRD → 15 开发及原发现回归
        → 16 原会话复盘 → 17 提交 → 18 合并完成
        → quality:select_requirement
            本批仍有 pending → 继续需求循环
            本批全部完成 → 新轮 quality:audit
```

一个节点内部能补证或修复的问题，在该节点使用原会话处理，不设计返回旧节点的回退链。无可选需求但仍有 pending 是依赖错误，不是批次完成。

### 4.2 prepare：接入与运行条件

Python 负责第二、三节的确定性交接。通用 Agent 在当前产品中核实审计所需的实际入口、主要角色、数据、运行状态和操作边界，按现有规则使用已提供资源及服务启动方式。补齐的是本轮所需现场，不重新执行项目初始化或整个资源准备流程。

该节点可以在授权范围内启动已知产品服务、准备非敏感可复位测试数据、使用项目已有开发账号；不自动执行全库 reset、真实外发、真实资金操作或高影响删除。必要依赖缺失时按实际原因处理，不能让审计 Skill 越过自身安装或写入边界。需要产品代码或受跟踪配置修复才能继续的事项，准确报告当前失败及所需处理，不在准备任务中绕过正式开发流程。

prepare 输出足够的任务范围、角色与运行条件说明。动态范围由 Agent 根据当前产品建立，Python 不枚举路由或从页面数量推导覆盖率。桌面产品不会因为有窄窗口检查而自动变成移动端交付。无用户交互表面的产品按实际调用方与交付面判断适用性，不强制浏览器或多个页面；确实没有适用体验任务时保留明确依据，由收口判断对应工程结果，不制造候选。

### 4.3 audit：完整审计

每轮使用独立 session 显式调用 `product-experience-audit`。输入当前各仓 main SHA、prepare 的范围与运行条件、当前产品资料，以及以前各轮候选处置和本批改动的必要摘要。首轮和复审同样覆盖全部主要任务，不仅检查修复页面。

Agent 负责真实任务执行、适用角色与状态、浏览器交互、实际读取截图及动态证据。Python 不给截图打分，不检查报告是否逐句复述 Skill 条款；负责人通过公共循环处理 Agent 提出的真实未完成事项，不重复验收。

主要任务的环境、身份或证据能力缺口应在当前审计会话内补齐；无法取得的不可替代外部条件为 blocked，本地错误为 failed。确无证据的问题保持观察或缺口，不能转成经核验候选。

产品缺陷与运行条件缺失分开处理：已实际复现的缺陷如果阻断后续任务，审计记录该候选、被阻断的任务及二者关系，在完成其余可执行覆盖后可以 success 交接分流，不能因尚未修复而把流程困在审计节点。这些未覆盖任务随候选进入本批，修复后在原场景回归及完整复审补齐；带有此类缺口的审计绝不能用于最终收口。审计成功表示本轮调查与交接完成，不等于产品通过。

本轮开始保存版本指纹，恢复沿用原 session 与已保存结果。审计过程不修改业务代码、Backlog、设计或 Git；使用项目规则约定的临时截图位置。运行代码须与本轮版本事实相符，不能拿仍运行的旧服务冒充当前版本。版本在审计中发生无法解释的变化时失败并保留现场，不静默换一轮吞掉冲突。

### 4.4 route：候选处置

通用 Agent 可读取完整审计原文、结构化候选、当前产品文档、代码及历史处置；它负责事实与价值判断，AI 负责人只处理其自包含交接的具体取舍。结果经 Responses/Pydantic 提取后，Python 校验每个候选有且只有一个最终处置，引用合法，无正式 ID 偷渡：

- `include`：真实、有用户影响、当前值得处理，结果和验收方向明确。
- `covered`：同轮其它候选或尚未完成的正式修复项已经承接，必须指明归属。
- `exclude`：误判、偏好、收益不足、当前时机不合适或范围外机会，记录具体理由与适用条件。

补证是当前节点内部工作，不是可绕过的第四种最终处置。重要疑点无法补证时保留非成功状态；非阻断设计机会可以明确 exclude，但不能因此掩盖主要任务覆盖缺口。

历史已完成需求曾经描述过预期行为，不构成 covered；当前仍复现则建立关联的新修复需求。同一候选的表述变化也不能绕过既有排除决定，只有新证据或前提变化才重新评估。

优先删除、合并、调整默认值或复用既有模式；不把审计建议的具体方案当成唯一实现。高影响取舍按现有 AI 负责人合同在事实与授权内决定，不新增人工逐项审批，也不能据此取得未提供的外部授权。确需新增产品目标或全新正式能力的机会保留为后续产品工作，不在质量循环中自动启动重新定义产品；当前范围内必要的体验、架构或行为修正可纳入，并交接具体影响。

### 4.5 pool：正式需求入池

没有 include 项时不建立分支、不调用需求拆分或提交。否则 Python 从当前根 main 记录 base 和稳定分支 intent，例如 `quality/<run-id>/r001-pool`，再创建根仓短期分支；子仓保持原 main，不建立代码分支。

外层显式调用 `requirement-breakdown` 的充分资料直接生成路径，只规划本批增量。Agent 读取当前 Backlog、候选、注册表 ID 和已确认处置，确定内聚需求、正式 ID、顺序、依赖与验收方向。ID 沿用产品惯例，并在现有与本批 ID 中忽略大小写唯一；不能回收历史 ID。小修复仍是正式需求，但不要求把它写成大功能或凑齐固定篇幅。

默认只新增 Backlog 条目，保留已完成条目与历史 TRD。确实需要校正当前跨需求设计或产品行为说明时，route 先明确文件范围与决定，由外层单独交给对应领域任务；不让需求拆分 Skill 顺手越权。不得以修正文档消除仍应兑现的承诺。所有本批文档变更在同一入池分支精确提交，不创建第二份平行产品范围。

调用 `commit-changes` 提交根仓本批文档；Python 显式 ff-only 合并保存 tip，核验并安全删除入池分支。结果保存 base/tip、实际文档范围、新正式 ID、候选映射与回归归属。入池不创建活动 TRD、代码分支或完成状态；入池合并成功后才允许注册。

### 4.6 register：增量登记

复用现有静态提取与校验能力，但不调用会重置全部状态的第 12 步初始化入口。为使不合法的拆分依赖能在原会话修正，入池任务的完成核验先读取 Backlog 的同一份字节，提取完整静态 catalog、计算哈希并完成以下检查；通过后与入池计划一起保存。登记时确认合并后的 Backlog 指纹一致，复用这份已核验 catalog，不重复调用模型：

1. 所有既有 ID 必须保留；本次新增集合必须精确等于 pool 保存的正式 ID。
2. 既有需求的静态字段保持本周期接入后的值；入池节点不得借本批规划重命名、删除或重新排序历史项。新增项追加在既有顺序后，必要依赖可指向历史 completed 项或本批合法 ID。
3. 对全部项校验顺序、ID、依赖存在性和无环，对候选映射与回归 owner 校验归属及必要依赖。
4. 按 ID 保留全部既有动态状态，只把新项置为 pending/completion null，原子更新当前 run 的注册表及来源哈希。

结果先写 register.json，再推进 state。恢复读取已保存 catalog 完成同一次更新，不重新生成需求、不重置已完成项。Backlog 是外层本批合法入池产生的变化；其它无法解释的漂移失败，不将其静默吸收。

### 4.7 需求开发：复用而不伪装成阶段一

第 13～18 步接受两种受控执行上下文：旧阶段一与新的产品质量迭代。阶段、选择节点与完成返回点由工作流类型决定，不开放任意可配置状态图。缺少 workflow 字段的旧 run 沿用原值；质量 run 不临时伪装成 phase_1 来绕过检查。

选择仍由 Python 从 pending 项中按依赖与 order 确定，不允许调用方跳过依赖直接指定开发 ID。准备时所有历史项已完成，故可选项自然只有本周期正式新增项。

第 14 步把候选的用户障碍、复现条件和预期结果作为本需求必要输入，活动 TRD 写清对应验收方向；不注入整个审计历史。第 15 步按 TRD 完成实现与原发现回归，并把可理解的结果留在活动 TRD及正常回复中。

- 先重现原障碍，再验证修复后原任务、相关状态和相邻路径。
- 原场景需要真实浏览器、服务、权限或持久化时，不能用单元测试或截图单独替代。
- 对一候选拆分的多个需求，各项验证自己的结果，regression owner 在必要前置项完成后验证完整原场景。
- 独立验证按当前开发任务风险安排，由执行 Agent 调度合适能力；不新增全项目审计调用或强制额外完整审查。
- 失败仍在当前开发任务处理，需求保持 active；可修复时继续原 development session，不先标 completed 再回退历史。
- Python 不新增“逐条复述证据”门禁，也不代替负责人重新检查产品。当前候选不能仅因代码提交或模型宣称已修复就脱离真实验收职责。

第 16～18 步仍按原职责完成复盘、精确提交和 ff-only 合并；第 18 步只在真实合并完成后标 completed，返回 `quality:select_requirement`。同一验证版本经 ff-only 合并不因分支名变化重复整套局部测试；若提交准备造成影响行为的变化，必须先回到当前未完成任务的必要验证，不能由纯提交职责放行。

本批全部需求完成后才能建立下一审计轮。完整复审发现修复复发时，在新轮形成新的正式修复项并关联原发现，不回写已完成需求。

### 4.8 complete：收口

只有最新一轮完整审计及分流满足以下条件，才写入 `quality/complete.json`，将节点置为 `quality:completed`：

- 当前主要任务已获适用动态覆盖，必要角色、数据、状态与目标视口缺口关闭；不以页面数量、平均分或没有反馈代替。
- 所有候选都有准确处置，没有未处理的高信心阻断或高优先级问题，也没有本轮仍应入池的 include 项。
- 本周期已入池需求全部完成，原场景回归已有承接结果；没有活动 cycle 或 pending 项。
- 最新审计是在本批修复后的集成版本执行，不使用修复前的审计给修复后的产品背书。
- 当前数据初始化与重置合同及适用文件随业务变化维护，已有仍有效证据直接复用；README 的稳定入口和交接仍准确。
- 适用仓库均在预期 main 且没有意外未提交变更，最终版本与审计、交付结果一致。

允许首轮审计无纳入项时直接完成，无需制造空需求或再审一次。结果列明覆盖范围、完成工作、保留机会和真实限制，不承诺以后不会发现问题。阶段一成功与质量周期成功分别报告，不修改旧完成记录来宣称它曾经做过本轮审计。

## 五、恢复、有限迭代与可观测性

### 5.1 当前节点恢复

继续使用现有原子 JSON、session、conversation、公共三态和重试规则。负责人不读取工程或重复开发验收；Python 只核验本节点必要输入、输出与自身 Git 边界。所有人工恢复消息只投递当前节点唯一合法的原会话。

| 中断位置 | 恢复动作 |
| --- | --- |
| 新 run 已建立但 prepare 未完成 | 保留当前 run，续接准备；不写来源，不重新认领产品 |
| 审计会话已产生结果，结构提取失败 | 读取原结果重试提取，不重新运行审计或重新编号已保存候选 |
| 分流待补证或待裁决 | 继续本轮原会话，保留已核验事实和既有处置 |
| 入池分支存在、部分文档已写 | 按本轮 base/branch、原 session 和当前文件补完；不另建分支或重复分配 ID |
| 入池已提交或已合并，result/state 未推进 | 依据保存 tip 和当前 Git 完成未完成动作；部分结果不重复提交或合并 |
| 注册 result 已写、state 未推进 | 以同一保存 catalog 幂等更新当前注册表 |
| 需求开发、提交、合并中断 | 复用现有 requirement-scoped 恢复，返回质量选择节点 |
| 最终结果已写、终点未推进 | 只完成本节点必要核验与状态推进，不重跑全项目审计 |

入池在 Git 写入前持久化 branch/base intent，提交完成后保存 tip 再合并；这些是本节点所需恢复锚点，不引入跨工作流事务日志或补偿系统。引用冲突、分叉、未知修改等保留现场并 failed，不自动回滚已经成功的 Git 动作。

### 5.2 有限迭代

新增 `--max-rounds`，首次运行默认 3，表示最多启动三轮完整审计，含首轮。它是成本与运行边界，不是质量评分或通过阈值；同轮原会话补证与恢复不增加轮次。

当前批次完成后需要新完整审计而轮次预算不足时，在 `quality:audit` 保存下一轮位置并返回 failed，错误为 `iteration_limit`，准确说明已完成修复和尚缺复审。不得把预算耗尽记为 success，也不能把剩余真实问题自动 exclude。操作人员可在该失败位置恢复并显式提高 `--max-rounds`；只允许增加，保存新上限，不重跑已有轮次。其它恢复不改变原运行参数。

### 5.3 模型、计时与日志

沿用 `model-policy.toml` 的集中模型策略，为 prepare、audit、route、pool 的实际领域调用增加命名任务分配；需求开发继续使用现有任务策略。一次运行或恢复进程加载一次，不热更新，不把模型策略写入领域 prompt。

新增质量调用继续使用公共 runner 与决策循环；不增加步骤外无限重试。审计、分流的结构提取复用现有 Responses/Pydantic 封装及错误语义。

计时沿用当前 timings v2：质量命名节点按 node 与 round 区分，需求步骤仍按 requirement ID 与 step 区分；复用结果不生成虚假调用记录。为现有记录增加命名节点定位所需的最小可选字段，旧数值步骤与读取方式兼容，不迁移旧文件。计时失败只警告，不改变业务结果。

证据保留脱敏事实、版本、观察条件和允许的引用；临时截图遵循根工作区 `.test-screenshots/` 约定，不能只靠可能清理的图片路径传递候选。目标产品账号按已有交付文档使用，外部凭据不进入审计输出、state、日志或本 TRD。

## 六、Skill 与 Prompt 调整范围

实现时只做服务上述合同的局部调整：

- `product-experience-audit`：区分当前承诺与历史资料；修正历史需求“已覆盖”不等于当前缺陷已解决；接收以前处置与本轮变化作为背景，独立复核实际行为。仍只完整审计，不修复、不写 Backlog、不管理生命周期。
- `requirement-breakdown`：复用充分资料直接生成与局部增量路径，明确本批保留旧 ID/正文、新需求与来源及回归归属；需要补足的合同只限增量输入，不增设“阶段二专用 Skill”。
- TRD 与开发调用：由外层交接与本需求相关的原发现和完整回归归属；先使用现有设计与验证能力，不因工作流节点名称新增 Skill，不对阶段一全部需求增加质量周期专属验证。
- 分流与准备：先采用有明确边界的普通 Agent 任务，不创建新的自定义 Skill；负责人仍只依据自包含问题作决定，不接管工程调查或验收。

领域 prompt 只描述任务、输入、输出和授权，不包含 PCM 步骤编号，也不在 Skill 正文中点名其它自定义 Skill。模板工作区中的能力不会因本仓修改自动更新；真实集成前核实目标产品实际可用能力，必要更新必须有明确文件范围，不自动覆盖整份 `.claude/` 或产品已有规则。

## 七、实现边界与验证

### 7.1 最小代码落点

- 新 `run_quality.py` 负责附着、当前节点循环及独立完成条件；`run_all.py` 只增加显式串联，不更改阶段一默认入口及完成语义。
- `run_quality.py` 同时提供命名节点单步模式；只将现有有限重试、恢复消息和锁传递中实际共用的部分提取复用，不复制 `run_step.py` 的整套数值步骤错误矩阵。`run_step.py` 仅调整附着产品的锁校验和质量需求的受控执行上下文。
- `common/coordination.py` 增加只读附着校验，区分持久 owner 与执行 run；阶段一 `claim_product()` 和 owner 校验保持原语义，不为质量运行放宽原产品认领规则。
- 复用 `common/state.py` 与 `common/files.py` 的状态读写及原子替换；质量命名路径、节点推进集中在 `quality/workflow.py`，结构模型在 `quality/models.py`，入池 Git 操作在 `quality/git.py`，不把候选模型散入各需求步骤。
- 第 12 步的静态提取校验按需要提取为可复用函数，原初始化语义不变；第 13～18 步只接受受控工作流上下文，质量原发现通过既有任务输入传递。
- 复用公共 Agent 决策循环、Git 操作模式、模型策略、计时和诊断。只抽取真实被两处调用的共用逻辑，不先建设可插拔工作流框架。

### 7.2 自动化验收

使用隔离临时 run 和真实临时 Git 仓验证确定性行为；模型响应可在编排单测中替身，但不作为真实产品体验验收证据。

1. 阶段一现有测试通过，旧 run 无需增加 workflow 字段；默认入口和循环结果不变。
2. 质量 new/resume/单步/串联入口均使用新记录，不改变来源 state、result、conversation、timing 的字节；来源未完成或有 active cycle 时拒绝。
3. 同一产品不同 run 互斥，旧 run 恢复与新 run 互斥，直接单步不能绕过；产品 owner/runtime/端口在新 run 及恢复后不变，release 不能绕过产品锁。
4. 当前 main 合理前进、旧标题或 Backlog 哈希不同但 ID 集合相同可以接入；未知新增或缺失 ID 拒绝，不重置完成状态；dirty 现场不清理。
5. 审计原文保存后提取失败可恢复，已保存候选不重新编号；分流遗漏、非法引用或 covered 指向已完成历史条目不能冒充有效归属。
6. pool 的分支创建、文档生成、提交、合并、清理各位置中断后无重复 ID、提交或合并；未知工作树与分叉保留失败现场。
7. register 保留历史动态状态，仅追加本批 pending；新增集合不匹配、ID 大小写冲突、依赖环、回归归属缺失均拒绝；result→state 中断可恢复。
8. 一个需求承接多个候选，以及候选拆分后由最后需求完整回归的输入、映射和依赖正确；回归未完成时不进入提交合并，需求保持 active。
9. 需求完成返回质量选择节点；批次结束进入新的独立审计 session；无候选可首轮完成，复审新缺陷建立新需求，不改历史。
10. 达到轮次上限仍未收口时 failed，不触发通道自动重试；增加预算后仅启动尚未执行的新轮。最终成功结果和失败、阻塞结果明确区分。
11. 质量模型配置、命名节点计时、失败诊断和恢复消息生效，旧记录仍可读；计时缺失不影响业务三态。

### 7.3 Rulefolio 真实验收边界

实施完成后，先明确当前未跟踪截图的归属、确认产品执行权与实际能力版本，再使用独立质量 run。现有文件、数据库、对象存储和原 run 不因测试而重置或复制。

真实审计至少覆盖产品当前承诺的“当前材料—试玩—证据—问题—调整—复测—回顾”主任务，并按实际角色验证最小参与授权、跨任务衔接及受影响失败恢复。使用固定产品端点，适用文件与数据同时验证；不从旧文件名恢复版本发布范围，也不把桌面窄窗口检查扩张为移动端产品交付。

验收包括真实 Agent、负责人、审计输出、结构提取与恢复。实际发现有合格候选时验证入池、开发回归及完整复审；若首轮没有合格候选，可真实证明无修改完成分支，修复分支由隔离测试覆盖，明确保留尚未真实覆盖的范围，不人为制造产品缺陷以宣称整链已验证。

当前实现已通过 PCM Demo 全量 **649 项 unittest**、Python 编译、差异格式、文档链接与评估 JSON 检查。独立审查发现的 covered 候选原场景遗漏和入池依赖错误无法在原会话修复，均已修复并通过专项复核；真实通道发现的校验错误序列化故障也已复现、修复并补测。

`probes/probe_quality.py` 已在隔离 CLI fixture 上通过真实准备、审计、结构提取和候选分流，包含超时后的原会话恢复及正式恢复消息。审计覆盖 13 个任务、输出 2 个候选，分流后准确停在待入池位置；未执行真实 Agent 修复和修复后的完整复审。证据在 Git 忽略的 `runs/quality-channel-20260922T142254Z/probe-result.json` 及同 run 的节点结果中。探针来源完成状态是明确构造的测试输入，不是实际阶段一交付证据。纯 CLI 不需要桌面截图，实际执行中已经通过恢复消息纠正调用方不必要的截图要求，后续新调用按真实交付面选择证据。

Rulefolio 的原 run、产品代码、数据和未知截图未被本次实现修改；该实际产品的完整质量周期尚未执行。Skill 的新增评估用例已纳入并完成结构检查，未将其宣称为独立的大规模模型对比评估。
