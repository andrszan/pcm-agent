# PCM Demo GitLab 远程仓库与推送技术设计

> 设计日期：2026-10-05
> 状态：代码、本地整合验证与独立审查已完成；真实 GitLab 建仓与 SSH 推送验收因 API 凭据及测试对象授权缺失而未执行。
> 范围：为后续新产品建立 GitLab 远程仓库，提供独立显式推送能力，并接入初始化与三个阶段的收尾。

## 一、目标与方案

新产品无需人工逐个创建、绑定远程仓库；初始化和阶段成果能按固定时机同步到指定 GitLab group，负责人也能在完成临时修改的提交后，通过一条命令推送当前产品。提交、建仓、推送分别承担明确职责，网络或权限失败不能导致重新开发已经完成的需求。

采用以下方案：

1. 新增独立 `push-changes` Skill，仅响应显式调用；提供随 Skill 分发、可独立运行的确定性 Git 推送脚本。
2. PCM 在第 8 步本地首次提交完成后，通过程序创建产品 subgroup 和适用远程仓库、绑定 `origin`，并首次推送 `main`。
3. 阶段一、阶段二以及阶段三每批结束前，程序直接复用同一推送实现，不启动 Agent 或负责人决策会话。
4. 提供按产品工作区执行的独立手动推送命令；它不启动开发流程，不改变 run 的业务完成状态。
5. 已有产品和旧 run 保持原恢复合同，不自动补建远程、不回退重跑初始化。负责人手工绑定远程后，可以显式使用推送入口。

本次推送是 Git 提交成果同步，不是开发环境完整备份。未提交文件、被忽略的实际配置、数据库及外部文件不随 Git 自动保存。自动同步以初始化和阶段收尾为界，不增加后台定时器或逐需求推送。

## 三、能力边界与用户入口

### 独立推送能力

`push-changes` 设置 `disable-model-invocation: true`，用户通过 `/push-changes` 显式调用。Skill 接收明确的仓库路径、目标分支与 remote，缺省分支为 `main`、remote 为 `origin`；功能分支必须由调用者明确指定。它不依赖其它自定义 Skill，不包含 PCM 步骤、run 状态或固定 GitLab group。

随 Skill 提供 `scripts/push.py` 作为唯一通用 Git 推送实现，使用 Python 标准库与 Git，不依赖 `pcm-demo`、模型配置或新增 CLI。可按显式仓库列表运行，既服务 Skill，也供 PCM 调用。PCM 负责提供产品仓库清单、预期地址、阶段目标版本和锁；脚本负责 Git 边界检查、执行及逐仓结果。普通内部函数与文件拆分留给实现，但不在 PCM 再复制一套 push 逻辑。

该能力只推送已有提交：不暂存、提交、切换分支、合并、变基、修改远程或改写历史，也不创建远程项目。发现工作区 dirty、历史冲突或 remote 缺失时，返回具体问题，不通过隐式准备动作消除它。

### 手动产品推送

命令入口如下：

```bash
# 在 pcm-demo 目录执行；不创建新 run，也不启动 Agent。
uv run python push_project.py --workspace /absolute/path/to/product

# 在具备该 Skill 的工作区中，显式推送某个仓库的功能分支。
python3 .claude/skills/push-changes/scripts/push.py \
  --repo /absolute/path/to/repository --branch req/example
```

产品入口一次推送根仓和所有适用代码仓的 `main`。仓库清单读取产品已有归属与创建 run 的权威记录，不递归扫描目录猜测仓库，也不把子目录所属的父仓误判成独立仓库。归属或清单无法确认时停止；通用脚本仍可接受调用者直接指定的仓库。

手动产品推送取得现有 Product Lock，避免与自动开发、合并及其它推送并发；有持有者时说明产品正被使用，不抢锁、不停止其它进程。该操作不分配端口、不新认领产品、不占用模型执行名额。自动阶段收尾使用外层已经持有的锁，不重复取得同一非重入锁。未受 PCM 管理的仓库通过通用脚本使用，调用者负责避免外部并发写入，脚本仍须复核目标分支未漂移。

输出逐仓说明目标地址、分支、目标提交和结果，区分“已推送”“远程已一致”“失败”“尚未执行”。有任何未同步仓库，整体返回非零退出码。dirty 时明确指出尚有未提交内容，不只推旧提交后显示整个任务成功。手动成功不会直接修改已失败 run；恢复原 run 后由其自身核验推送事实并完成收尾。

## 四、GitLab 建仓与初始化

### 固定命名与可见性

父 group 固定为 `https://gitlab.com/baiyiyu/andrszan/pcm-projects`，不由 AI、产品初稿或单次 CLI 参数更换。产品名复用第 1 步已确定的稳定 `project_directory_name`，不另做品牌翻译，也不使用 run ID 命名产品。

以 `mealflow` 为例：

```text
baiyiyu/andrszan/pcm-projects/
└── mealflow/                    产品 subgroup
    ├── mealflow                根仓
    ├── mealflow-backend        后端仓，适用时创建
    └── mealflow-frontend       前端仓，适用时创建
```

根仓绑定 `git@gitlab.com:baiyiyu/andrszan/pcm-projects/mealflow/mealflow.git`，代码仓分别绑定同 subgroup 下的 `mealflow-backend.git`、`mealflow-frontend.git`。API 返回的 namespace、项目路径和 SSH 地址必须与预期一致。不存在的交付端不创建空远程仓。

产品 subgroup 和项目显式创建为 private；根仓包含内部能力与产品开发账号文档，不能默认为 public。创建空仓库，不生成 README、许可证模板或服务器端初始提交；首次推送后核验默认分支为 `main`，必要时通过 API 设置。不削弱既有分支保护来绕过推送拒绝。

### 配置与授权

PCM 使用 GitLab REST API 创建 subgroup 和 project，Git 数据传输使用 SSH。复用当前 Python 运行环境和标准库，不引入 GitLab SDK 或要求安装 `glab`。API 权限和 SSH 推送权限分别核验，能够读取模板不能证明具备其中任一写权限。

新增工具配置键 `PCM_GITLAB_TOKEN`，从 PCM 现有受保护配置链或进程环境读取；服务地址与父 group 固定在本项实现中。令牌身份须具备指定父 group 下创建 subgroup、项目及必要项目设置的权限；SSH 身份须能写入这些项目的 `main`。配置缺失时不伪造值，不把个人身份或管理令牌写入目标产品。

实现时同步实际 `pcm-demo/.env` 与 `.env.example`：前者仅在取得真实可用值后补齐，后者只保留配置键与安全占位说明。令牌不进入产品根或前后端 `.env`、工作区工具配置副本、项目资源准备清单、Git URL、命令参数、模型上下文或运行结果；不继承给无关子进程。日志和异常沿用已有精确脱敏能力，SSH 私钥也不复制到产品。

启用本合同的新运行，应在昂贵的 Agent 开发前做轻量配置与认证准备核验；远程写入仍固定在第 8 步。具体创建权限及新仓 push 能力以第 8 步真实执行为准，不用本地配置存在或只读 API 成功冒充写权限证明。

### 第 8 步的执行顺序

1. 继续完成原有仓库边界、适用身份、本地首次提交和 clean main 核验。已完成提交的恢复不再次创建提交或提交会话。
2. 确认全部待绑定仓库的 `origin` 未配置，或与本次已登记的预期绑定一致；不同地址或不明配置立即停止，不先创建一批远程对象再覆盖冲突。
3. 根据固定完整路径取得父 group ID，在其下创建 private 产品 subgroup，再创建权威清单对应的 private 空项目。每个成功返回的对象及时保存无秘密的 ID、完整路径及绑定地址到本步骤现有结果／恢复记录。
4. 为已核实的本地仓库配置 `origin`，已有同一绑定则复用。调用通用推送实现，将代码仓先、根仓最后首次推送到远程 `main`，并建立 `main` 的对应 upstream。
5. 核验各项目可见性、默认分支和远程分支目标 SHA，再发布第 8 步 success，进入原第 9 步。

有此合同的新 run，现场全仓 clean 只代表本地部分完成，不能继续沿用旧的“clean 直接 success”路径跳过建仓与首推。新增远程结果不改变原有 `outputs: []` 和 `applicable_repositories` 交接语义；后续工程设计步骤不承担 GitLab 核验。

### 重入与未知创建结果

已保存对象 ID 且完整路径、所属父级和 private 属性匹配时，可以续接创建或绑定；已创建的成功对象不删除重建。首次遇到没有本次归属证据的同名 subgroup 或项目，不因它为空、地址相似或可访问就自动接管。已有 `origin` 也不能单独证明远程对象是本 run 创建的。

若 API 已完成创建，但网络断开或进程退出导致对象 ID 未保存，重复运行可能遇到同名对象。此时报告“创建结果／归属未确认”并保留现场，由维护者核实后在明确授权范围内修复该次绑定与恢复事实，再恢复原步骤；普通 `--resume` 不猜测接管，也不盲目再次 POST。不为此增加远程标记、补偿删除、自动认领或通用迁移入口。

## 五、推送安全与部分成功

所有路径先确认是真实目标仓库自身的 Git top-level。推送前对整批仓库进行预检，再按代码仓先、根仓最后执行：

- 自动和产品手动入口均要求各仓位于 `main`、HEAD 存在、工作区与 index 干净，且没有 merge、rebase、cherry-pick 或 revert 进行中；通用脚本使用显式目标分支，要求现场与其一致。
- 核对实际 push 地址，而不只读取 fetch URL。拒绝多 push 目标、与预期不符的地址或隐含镜像配置；不能因 remote 名叫 `origin` 就视为可信。PCM 的新产品绑定必须匹配初始化约定；手动接入旧产品则按负责人已经配置的唯一地址显式执行，不替其建仓或改地址。
- 使用明确的源提交和目标分支引用，不依赖 `push.default`、隐式标签跟随或调用环境的默认 refspec。不使用 force、`--all`、`--mirror`，不删除远程分支，不附带标签推送。
- 远程目标不存在时创建对应分支；已经等于本次目标 SHA 时成功复用；可以正常快进时推送。远程领先、分叉或服务端拒绝时保留现场并停止，不自动拉取、合并或变基来消除差异。
- 不使用会隐式扩展上传范围的递归子仓操作，不跳过现有 Git hook 或 SSH 主机身份校验。网络操作非交互且有有限超时，缺少凭据、主机信任或权限时准确返回，不能无限等待输入。
- 每仓完成后读取远程分支 SHA，必须等于本次目标；同时复核本地目标引用没有变化。请求发出后响应丢失时，恢复首先查询远程事实，而不是依据上次退出码认定必然失败。

提交层既有秘密检查继续负责实际变更准入；本次不以“已加入 `.gitignore`”证明历史安全。已知待推送历史含真实外部秘密时必须停止，不能为了推送成功自动删除、改写历史或降低检查。产品交付开发账号继续遵循现有受跟踪文档合同，不与 GitLab 工具凭据混淆。

三仓不承诺原子同步。某仓失败即停止后续推送，保存每仓的目标提交、已核验远程提交和具体失败；已成功的仓库不回滚。恢复时重新核对远程事实，跳过已经一致的仓库，只继续未完成项。远程出现新变化时按普通冲突处理，不用 force 恢复旧现场。根仓最后只是收尾顺序，不代表跨仓事务。

## 六、自动推送时机与完成状态

| 时机 | 前置事实 | 同步与完成边界 |
| --- | --- | --- |
| 第 8 步 | 本地首次提交完成、适用仓库 clean main | 建仓、绑定、首推及核验全部成功后，才发布初始化步骤 success。 |
| 阶段一结束 | 全部正式需求完成第 18 步，无活动或待开发需求，各仓 clean main | 进入独立可恢复的阶段收尾，推送成功后才允许声明阶段一完成或串联阶段二。 |
| 阶段二每次收尾 | 原质量完成条件满足，最终版本已经核对 | 在 `quality:complete` 内推送，全部成功后进入 `quality:completed`。无修复批次也核对同步，已一致则无写入。 |
| 阶段三每批收尾 | 反馈文档和纳入需求完成原有提交、合并及必要验证 | 在 `feedback:complete` 内推送，全部成功后进入 `feedback:completed`；无纳入需求也包含真实反馈文档提交。 |

阶段三未启动时不创建推送任务。第 17、18 步不增加远程依赖，需求完成仍表示本地实现、验证、提交与合并完成；阶段收尾失败不把 completed 需求重置为 pending 或 active。

### 阶段一的新增收尾

新增命名节点 `phase_1:complete`，由 `run_all.py` 在原需求循环全部结束后进入；本节点负责最终仓库核验与远程同步，成功后记录 `phase_1:completed`。复用现有 state、结果写入及锁，不增加数字第 19 步，也不改变单需求循环的步骤号。

本地需求全部完成与整个阶段已完成必须分开判断。启用远程合同的 run，`phase_one_completed()`、`--with-quality` 串联及质量来源准入都必须要求阶段收尾成功，不能仍只检查注册表。通过单步执行最后一个第 18 步，仅表示最后一条需求完成；随后使用 `run_all.py --resume <run-id>` 完成阶段收尾，不能直接作为已完成来源。

普通 `run_all.py --resume` 能识别并进入该命名节点，不尝试再选择需求；阶段收尾无需加载或调用模型。推送成功但最终状态写入中断时，根据已保存的目标和当前远程 SHA 补齐成功，不重开需求。既有阶段二、三命名节点入口与完整入口必须走同一收尾函数，不能只有完整 CLI 会推送。

### 状态与跨 run 继承

为后续新建阶段一 run 登记最小远程同步启用事实；稳定产品名沿用首次确认值。独立质量和反馈 run 显式承接该事实、同一产品身份与适用仓库清单，不能因 `new_state()` 只复制旧字段而丢失同步要求。未启用的历史来源继续保持原行为，不能仅因本机新增了 GitLab token 或产品有 `origin` 就推断已授权自动接入。

本地仓库的 `.git/config` 保存实际 remote 绑定，初始化步骤记录保存创建对象和预期地址；当前收尾结果只记录本次要同步的逐仓 SHA 与结果。复用既有 run 结果位置，不增加产品内的第二份远程 Manifest、同步数据库或长期推送台账。具体内部字段名不构成用户接口，但缺失启用事实必须明确表示旧合同，不能默认升级。

每次自动收尾在开始推送前保存已经完成本地核验的目标 SHA。恢复复用该目标，不把失败期间出现的新提交偷偷纳入原阶段，也不重跑已成功的审计、反馈核验或开发会话。本地或远程不再符合该目标时返回冲突，保留现场；已经真正完成的历史 run 不持续监控远程，也不因日后正常前进失效。

## 七、失败、恢复与兼容

沿用 `success`、`blocked`、`failed` 三态，GitLab API 和 Git 失败不进入仅服务 Agent SDK 的 6 小时重试窗口。

| 情况 | 行为 |
| --- | --- |
| 缺少当前环境无法取得的有效 GitLab 授权、SSH 身份或必要写权限 | `blocked`，说明缺少的配置键／权限、目标及解除条件，不展示秘密。 |
| 网络失败、超时、API 服务错误、命令失败 | `failed`，保留部分成功与现场，普通 resume 重新核对后继续。 |
| dirty、分支不符、远程绑定冲突、未知同名对象、目标漂移、非快进或不合法状态 | `failed`，说明具体仓库和冲突；不清理、接管或强推。 |
| 响应丢失但远程分支已达到目标 | 当前重入核验后接受成功，不制造重复提交。 |
| 业务已完成但远程仍未同步 | 明确报告两者区别，阶段停在收尾；已完成需求和已有有效验证保持不变。 |

第 8 步失败使用原单步或完整运行恢复；阶段一收尾使用 `run_all.py --resume`；质量／反馈收尾使用各自已有 `--resume`，也支持当前命名节点入口。输出必须提供适用恢复命令和失败仓库，不要求负责人重新执行开发验收。

旧 run、已完成产品、历史 success、会话和旧模板副本不回写或补迁移。新建质量／反馈 run 若来源未启用远程合同，也不自动接入；旧产品绑定远程后的按需手动推送与自动流程升级是两件不同的事。新产品使用的模板必须实际包含新增 Skill 与脚本；只修改当前工作区不等于远程模板已发布，模板推送仍需独立授权。

## 八、实现归属与文档同步

实现按稳定职责组织：

- `.claude/skills/push-changes/`：独立显式能力、标准库推送脚本及必要行为验证，可随能力目录复制使用。
- PCM 的 GitLab 初始化辅助代码与第 8 步：固定 namespace、API 配置、远程对象创建与归属恢复、origin 绑定和首推。
- `run_all.py` 与相关完成判定：阶段一命名收尾、恢复、串联与来源完成判定。
- `quality/`、`feedback/` 的状态构造与完成节点：启用事实继承、原业务完成结果复用和推送成功门槛。
- `push_project.py`：薄产品入口，只负责定位、现有产品锁、调用共用脚本和展示结果。

开发时同步两份流程主文档中“默认只本地、不自动 push”的当前合同：领域能力仍不越界，但流程的明确收尾可执行远程同步。`.claude/README.md` 补能力与 Git 分工，`pcm-demo/README.md` 补配置、手动入口和恢复方式，`.env.example` 与实际受保护配置按规则同步；不向其它文档重复追加执行流水。

## 九、验证与完成标准

### 必须覆盖的行为

1. **初始化成功与适用性：** 在固定父 group 下创建 private 产品 subgroup 和适用仓库；不适用端不建空仓，SSH 绑定正确，空远程首次获得本地 main，默认分支及远程 SHA 正确。
2. **初始化重入：** 本地提交已完成、仅部分对象创建、部分 remote 绑定、部分首推以及 result／state 写入中断均能保留成功事实续接；未知同名对象、错误 origin 和未知创建结果安全停止。
3. **Git 推送边界：** 已一致、首次分支、正常快进成功；dirty、非目标分支、多 push 地址、错误绑定、无 HEAD、进行中 Git 操作、分叉与远程领先不会被强行处理。实际仅推指定分支，不上传其它分支或标签。
4. **部分成功：** 代码仓成功而另一仓失败时，根仓尚未推送，整体准确失败；恢复只补未完成部分；响应丢失后可通过真实远程 SHA 判定结果。并发改变目标时不误报成功。
5. **三个阶段：** 阶段一全部需求 completed 但 push 失败时，完整入口、单步后的完成判定和质量来源准入都不能绕过；阶段二有／无修复及阶段三有／无纳入需求均经同一收尾。恢复不重复审计、开发或反馈文档提交。
6. **跨 run 与兼容：** 新来源的质量、反馈及再次反馈都继承同步要求；旧 run 与旧来源保持原行为；手动配置 origin 不自动触发迁移。第 8 步原有 outputs 与后续交接仍兼容。
7. **手动与并发：** 产品命令一次处理权威适用仓库，持有产品锁时不能并发执行；自动调用不重复取锁。手动成功不伪造 run 成功，显式功能分支调用不会切换分支或自动提交。
8. **凭据与触发：** Skill 不被模型自主选择；自动推送零模型调用；API token 不进入产品、Git URL、日志、命令参数、Agent 或无关子进程。缺权限和主机信任时准确停止，不绕过保护。

### 验证方式

复用现有 `unittest`、步骤恢复和 CLI 测试。用临时本地 bare 仓库实际执行 Git，覆盖成功、分叉、部分推送和重入；GitLab API 的结构与错误分支可用受控响应做程序测试，但不能用它代替真实建仓、可见性和权限证据。测试规模服务上述行为，不另建通用评估平台。

真实集成使用明确获准的隔离测试产品，在同一固定父 group 下验证 subgroup／project 创建、SSH 首推、再次同步和中断续接；不能操作现有业务产品来代替隔离验证。测试对象创建范围须在执行前明确授权，创建许可不等于删除许可；测试结束后准确交接保留对象，需要删除时另按精确目标确认。可复用隔离构造的已完成需求现场验证阶段收尾，但须标明这是编排验证，不宣称重新完成了真实产品开发。

实现完成要求：相关程序检查通过，真实 GitLab 建仓与推送证据成立，三个阶段和手动入口的完成／恢复边界正确，旧 run 不回归，文档与配置合同一致。未取得外部授权或未执行真实链路时保留具体缺口，不能仅以 TRD、Mock 或本地 bare 仓通过宣布功能已交付。
