# PCM Demo 阶段二前端体验质量强化技术设计

> 设计日期：2026-10-05
> 状态：代码、自动化、真实语义小样本及图形审计／分流已验证；真实入池收尾因裁决服务连续 HTTP 503 尚未完成。
> 范围：在现有阶段二中强化前端审查、候选处置和改善结果交接，不新增工作流。

## 一、目标与保留边界

阶段二既要发现业务错误和任务障碍，也要稳定发现有依据的前端质量问题：功能能够操作，但内容难懂、主次不清、导航不连贯、布局不合理，或视觉表达仍停留在通用模板和技术演示层面。是否阻断操作不是体验改善的唯一准入条件。

本项保留[流程主文档第七章](../../../docs/pcm/PCM版AI%20Agent自动化流程设计.md#七阶段二独立产品质量迭代工作流)的一次完整审计、一批分流和修复、相关回归后结束。审计仍覆盖完整集成产品的全部主要用户任务，前端重点不替代功能、权限、数据与恢复检查。仅补强审查内容及语义交接，不改变步骤结果协议、完成条件、模型策略、重试、轮次、运行参数、Git 和恢复机制。

本项在能力模板与 PCM 质量流程中实施。阶段一设计能力、阶段三反馈机制和第三方 Skills 不在本次改造范围，不对三个反馈来源产品再次启动审计或开发。

### 来源与实现前基线

依据尾屿、跃动俱乐部、Mealflow 三份人工审查材料及代表性截图，共性是信息层次、产品语言、导航连续性、查看与编辑的组织、操作反馈，以及视觉与空间利用。材料同时包含相反方向的合理诉求：工作台应减少冗余说明，新手入口又需要补足用途介绍。因此目标不是统一减字，而是让必要信息在适合的位置出现。

实现前，`product-experience-audit` 已要求真实任务、实际读取截图，以及内容、视觉、组件、适配等检查；候选规则也明确允许非阻断质量改善。`quality/workflow.py` 的分流措辞使用“真实障碍”“非阻断偏好”，需要明确区分有依据的质量改善与无依据的风格偏好，使分流与审计合同一致。

跃动俱乐部既有质量批次的16个候选集中于业务正确性、任务入口、草稿及来源保持和反馈误导，没有整体布局、密度或视觉改善候选。这只能证明这些改善没有进入候选集，不能据此认定当时完全未检查视觉，也不能把当前提示当作旧批次当时使用的版本。本项解决当前合同的可执行性和衔接，不回写旧审计结论。

## 二、前端审查重点

以下内容是审查视角，不是每个项目都必须添加的页面、组件或功能清单。按产品定位、正式交付面、主要角色和真实内容选择适用项。

| 方向 | 必须关注的用户结果 |
| --- | --- |
| 导航与上下文 | 用户知道所在模块、层级和当前对象；能返回上级或原任务；筛选、分页、家庭／项目等适用上下文不会因无关跳转丢失；路由或普通复核不会无故闪屏、清空草稿。 |
| 产品语言与信息层次 | 标题、对象、状态和主要行动清楚；技术字段、JSON、脚手架说明不代替面向实际使用者的内容；减少重复说明，同时补足用途、示例与必要引导。 |
| 查看与操作组织 | 默认内容服务当前任务；编辑、配置及低频操作在需要时进入；不把所有表单铺满详情，也不为简单动作制造无意义页面往返。 |
| 等待、结果与恢复 | 用户发起的操作有可辨认的等待、成功、明确失败或未确认结果；状态及时反映实际结果；安全允许的输入保留，失败后知道如何继续。 |
| 视觉、品牌与布局 | 首眼主次、分组、密度、留白、对齐、阅读顺序和操作层级符合内容；颜色、图标、图片、图表及适量动效有表达价值，而非所有业务套同一种大卡片。 |
| 引导、适配与一致性 | 新用户知道主要用途和下一步；目标桌面宽度利用合理，必要窄窗口下不挤压或丢操作；共享模式、键盘与焦点、主题和减少动效等适用表现一致。 |

### 常见方案的判断边界

- **层级定位不等于只加面包屑。** 对具有明确嵌套层级的管理型 Web 页面，默认检查面包屑或等价层级入口；已有方案充分时不机械补组件。层级返回与返回原筛选结果分别判断，业务上下文不能仅靠浏览器返回维持。
- **精简不是隐藏必要内容。** 低频解释可按需展示；用途、关键标签、字段要求、后果、限制、错误与恢复指引应在需要时直接可见。Placeholder 或悬停提示不能成为必要信息的唯一来源；新手引导不足时应增加清晰内容。
- **浮层按任务选择。** 短操作可使用合适的 Dialog、Popover 或抽屉；复杂编辑、长流程及需要独立定位的任务可保留页面。判断打开、关闭、取消、输入保留与焦点，不统一将所有表单改为弹框。
- **反馈按业务结果组织。** 不对后台读取和所有 API 响应统一弹 Toast；普通成功可轻量反馈，资金、部分完成和结果未知等必要事实应持续可核对。真实失败不能用动画或装饰遮掩。
- **视觉价值不要求功能不可替代。** 图片、图标、SVG、图表和动效可以改善识别、场景感、品牌及吸引力，不必先证明操作被阻断。审查其适合程度、内容组织和实际效果，不以“没有图片”直接判缺陷，也不设资源数量指标。
- **方案应服从产品及技术栈。** 已有适用设计、组件和工具能力应有针对性地使用；审计本身仍只读，不安装库或获取资产来替代调查。核心能力不互相点名依赖，也不把某个第三方 Skill 设成前置；调用过能力不等于界面质量合格。

## 三、调查与候选形成

### 代表性覆盖

继续以全部主要用户任务组织审计，在这些任务中选取各实际模块的代表性表面与状态。适用时覆盖公开／登录入口、首页或工作台、列表、详情、表单或操作浮层，以及加载、空态、失败和成功。无需为不存在的表面建页面，也不展开所有角色、页面和尺寸的组合矩阵。

实际操作浏览器并读取截图；DOM、截图文件存在、页面没有溢出或测试通过，都不能单独代表视觉审查。长内容应查看相关区域，不能用首屏替代完整任务。截图判断文案、布局和层次，状态保持、结果更新、返回和持久化等行为须结合动态证据，不混淆两种证据能力。

发现共享导航、卡片、帮助或反馈模式的问题时，检查直接关联的实际消费者，合并共同问题并保留影响范围；不能只修最先截图的一页，也不扩为再次全产品审计。利用已有有效交接，不要求 Agent 对每一维度逐项声明“没有问题”，不因缺少这种声明反复继续。

### 可进入候选的事实

非阻断质量改善与业务缺陷使用同一现有候选链。候选应让后续负责人理解：谁在什么任务和表面上遇到什么、实际观察是什么、为什么值得改善、目标结果如何观察，以及相关状态和证据限制。

例如，业务正常的工作台仍可提出“多个重要事项以同权重长卡片呈现，重复元信息占据主要空间，难以扫描事项和下一步”的候选。改善目标是提高事项与行动的可辨认性、保留必要事实，不是预先锁死卡片数量、颜色或组件。

视觉与内容问题可以依据实际渲染和产品用途说明理解、扫描、识别、一致性、信任或品牌表达的改善价值，不需要虚构用户研究或精确效率数字。“不好看”“应该多放图”“我更喜欢另一种颜色”本身仍不足以成为经核验候选。

已有功能能用、符合旧文档、曾经验收、优先级较低，都不能单独证明当前质量问题不存在。反过来，没有问题的页面不必制造候选，不能用候选数量、截图数量、字数、弹框数或视觉评分判断审计成功。

## 四、分流、入池与开发交接

### 分流

AI 负责人继续依据完整审计材料、正式范围、历史处置和可观察收益作一次候选处置，使用原有结果与引用校验，不新增审批节点。

- 当前范围内、有证据、有质量价值且成本相称的非阻断前端改善可以纳入；不能仅以“功能正常”“未阻断任务”“旧设计如此”排除。
- 不纳入时说明具体依据，例如证据不足、已有体验已满足目标、方案收益不足以支持代价、确属无产品依据的风格偏好，或实质引入新能力。不得把所有非阻断项统称为偏好，也不强制所有 UI 候选纳入。
- 区分问题与建议方案：全响应弹框、全部说明移入 Tooltip 或所有编辑改浮层不合适时，仍应保留有证据的反馈、理解或操作成本问题，允许更合适的实现。
- 既有功能、数据和权限缺陷保持原优先保护。未知内容不能在分流中补造；确需补充调查时沿用现有合同，不增加另一套工程调查循环。

宠物图片上传、全新存储服务、注册能力等是否纳入，取决于是否属于当前正式承诺；不能仅因改善界面就自动新增。已承诺能力的必要关联修复不因涉及后端而被禁止。端口、基础设施及主题选项的个人偏好不提升为所有产品的通用要求。既有历史处置重议、新产品目标和高影响授权边界继续适用。

### 入池与验收

入池保留原候选的用户目标、现状、改善价值、受影响表面和可观察结果，避免将其压缩成“美化前端”。同根因可以形成一个内聚需求，不同结果或风险按现有原则拆分；保留候选关联、完整回归 owner 与必要依赖，不创建第二份体验 Backlog。

设计与开发复用已有原发现交接。非阻断改善不要求伪造错误复现，但须核对改善前的问题与改善后的实际呈现和行为。视觉目标用同一或可比内容及目标视口核对，交互目标重走原任务，共享变化检查相关消费者；无需统一建立像素快照基线或专门对照报告。

修复后必要任务与相邻路径仍由当前开发阶段验证；视觉改善不能以隐藏关键数据、删除状态、减少实际业务记录或放宽权限制造简洁。失败留在当前需求处理，后续复盘、提交、合并及批次完成沿用原流程，不加新的完成声明或 Python 审美门禁。

## 五、实现接点与兼容

实现优先使用现有文本合同和交接，不新增节点、命令、任务模型、候选类型枚举、状态字段、评分或报告文件。`quality/models.py` 的 `Finding` 已有任务、触发、事实、预期、依据、影响和证据；可观察改善目标及观察条件由现有 `expected`、`basis`、`evidence` 等字段承载，结合完整审计原文保留受影响表面，不新增平行数据模型。

现有结构允许任务已覆盖、没有阻断候选引用，同时仍保留非阻断质量发现。不得为了让视觉项进入分流，伪造任务未完成或设置阻断。`requirement_evidence` 已向需求设计和开发提供原发现及回归归属，优先验证并复用，不另造前端专属上下文。

| 现有位置 | 本项预期调整 |
| --- | --- |
| `.claude/skills/product-experience-audit/SKILL.md` | 原位强化代表性前端检查、方案判断和非阻断质量证据，保持全项目只读审计职责与独立性。 |
| `.claude/skills/product-experience-audit/evals/evals.json` | 加入有问题与无问题的对照案例，以及避免机械加组件、隐藏必要信息或扩大产品范围的判断。 |

| `pcm-demo/quality/` 已有测试与适用验证入口 | 证明质量事实未在提取、筛选、入池和开发交接中丢失，并保留既有兼容与停止行为。 |
| 流程主文档第七章 | 开发时同步阶段二质量目标和处置原则；其它说明仅在确有不一致时最小更新，不重复新增总说明。 |

上述是职责落点，不冻结内部文件拆分。归档 TRD、旧 run、历史会话及既有候选处置不改；本设计是对原质量迭代设计的增量，不用更新旧报告来证明新能力。

需要区分 PCM 编排提示与目标产品实际加载的 Skill。阶段一从配置模板仓库克隆产品，阶段二继承产品工作区，不重新复制或刷新 Skill；新产品也以实际模板来源版本为准。因此，本地模板修改不代表已有产品或远程模板已更新。隔离验证须使用明确包含本次变更的工作区，并核对实际 cwd、Skill 及 session。既有产品升级仅在明确目标与写入范围内处理，不批量覆盖产品规则和定制内容，不自动推送模板。

旧 run 恢复沿用原 session 和已保存的初始提示；成功节点直接复用结果。新提取提示可能处理旧会话，必须继续兼容旧成果和完整多轮报告。不能为采用新规则重置旧会话、改写已有结果，或把普通 resume 描述为已经启用新版完整审计。

## 六、验证与完成依据

### 行为案例

| 输入事实 | 预期结果 |
| --- | --- |
| 功能正常，但实际界面存在同权重长卡片、重复说明及主要行动不突出；改善在当前范围且代价相称 | 形成有事实和可观察目标的候选，分流可纳入，不以未阻断操作排除；入池和开发保留具体目标。 |
| 有清晰层级、恰当密度、必要引导和一致状态的界面 | 不因缺图片、特定动画库、面包屑组件或固定弹框数量制造问题。 |
| 用户无法定位层级，或普通跨模块跳转丢失当前业务上下文 | 区分导航呈现与动态状态问题，按实际证据提出结果；不只增加面包屑就宣布两类问题解决。 |
| 低频说明占主页面，同时必需说明或新手用途不清 | 减少冗余并补足必要信息；不统一删字、藏入 Tooltip 或用 Placeholder 替代标签。 |
| 有依据的反馈问题被建议统一改成每个 API 都弹 Toast | 保留反馈目标，拒绝机械方案，不连同真实问题一起排除。 |
| 新增上传、存储服务或业务能力并非当前承诺 | 不因视觉优化自动入池；按原范围边界给出具体处置理由。 |
| 同一个展示问题出现在多个共享消费者，另有业务阻断项 | 去重后保留全部实际影响和回归归属；不遗漏或降级原有业务阻断处理。 |
| CLI 或其它没有图形界面的完整产品 | 按实际交付面审计，不因前端增强强制创建页面、截图或视觉缺口。 |

### 验证层次

1. **自动化回归：** 复用现有质量模块、CLI 和需求交接测试，检查提示接线、已有字段承载、候选引用与归属，以及无候选、有纳入项、必要缺口、历史处置和恢复分支。不得仅靠提示含有某个关键词就宣称模型行为已通过；不改已有成功、失败、阻塞或重试断言来迁就新方案。
2. **真实模型语义小样本：** 用脱敏的正反案例验证有依据的非阻断改善不会仅因功能正常而被排除，纯偏好和范围扩张不会自动纳入，原问题和预期结果能经过提取、分流和入池保持。记录实际输出及偏差，静态构造响应只算程序测试。
3. **真实浏览器审计样本：** 使用隔离且可完整运行的图形界面产品样本，明确当前正式任务、实际版本及操作边界，实际执行任务并读取代表性渲染；必须覆盖有依据的前端质量发现及不机械改造的判断。既有 CLI 探针可复用调用方式，但其通过不代表视觉审计通过；少数静态页面也不能冒充全项目审计。
4. **修复与交接验证：** 对纳入的内聚改善验证原场景及相关共享表面，确认最终渲染和任务均符合目标，必要事实和业务能力保留。区分真实执行链与构造的测试来源，不把历史项目截图、已完成的阶段三或未执行计划算作本项验证。

隔离样本只验证本次增强，不授权重跑或修改三个现有产品。真实验证中的资源、截图、运行端口、Git 和进程管理沿用项目现有约定，不新建通用评估平台。验证成本与行为变化相称，复用已有有效证据，不逐修复全产品重审。

本项实现完成须同时具备：合同与提示已对齐、相关自动化通过、真实语义和图形界面样本有可核验结果，以及既有质量流程未回归。不能用文档和静态测试通过替代实际视觉行为；未能执行的范围准确保留为验证缺口，不宣称增强已完成。
