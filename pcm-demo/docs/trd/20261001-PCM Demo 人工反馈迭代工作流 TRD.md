# PCM Demo 人工反馈迭代工作流技术设计

> 设计日期：2026-10-01
> 状态：实现、自动化回归及隔离 CLI 真实通道验证已完成；未对已有客户产品执行反馈变更。
> 范围：将已确认的阶段三接入 PCM Demo；产品行为以[流程主文档第八章](../../../docs/pcm/PCM版AI%20Agent自动化流程设计.md#八阶段三人工反馈驱动迭代可选)为准，本文只说明实现接点、输入交接、恢复和验证。

## 1. 实现边界

新增独立 `run_feedback.py` 与 `feedback/` 模块。来源只接受成功完成的质量 run 或反馈 run，附着原产品，复用 owner、端口、执行锁、公共 Agent 决策循环及第 13～18 步。原阶段一、阶段二入口、完成条件、重试参数与历史结果保持不变。

现有质量模块的 Git 边界、Backlog 提取、增量需求关联及依赖校验可复用；反馈取舍不采用全产品审计的覆盖门槛。反馈支持已授权的新目标，无纳入项也可能需要提交反馈文档。只扩展实际接点，不建立通用工作流引擎或第二份正式 Backlog。

## 2. 入口与输入

```bash
# 新建一批反馈；材料中的附件也可通过 --attachment 显式交接
uv run python run_feedback.py --source-run <completed-quality-or-feedback-run> \
  --run-id <feedback-run> --feedback-file /absolute/path/to/feedback.md \
  --attachment /absolute/path/to/screenshot.png \
  --intent-file /absolute/path/to/batch-intent.md

# 恢复自己的当前节点，不重新导入来源或原始材料
uv run python run_feedback.py --resume <feedback-run>

# 只执行当前命名节点；数值需求步骤沿用 run_step.py
uv run python run_feedback.py --resume <feedback-run> --node feedback:triage
uv run python run_step.py --step <13-18> --run-id <feedback-run>

# 向唯一未完成的原 Agent 对话补充澄清或外部解除条件
uv run python run_feedback.py --resume <feedback-run> \
  --resume-message-file /absolute/path/to/message.md
```

新建必须给出来源、唯一 run ID 与非空 UTF-8 普通反馈文件。`--attachment` 可重复，`--intent-file` 可省略；正文与意图只通过文件交接，不打印到命令输出。创建 run 前检查文件可读及来源完成，已有目录不覆盖。初始输入成功持久化后才发布可恢复的 state；发布前失败保留临时目录，可换新 run ID 重建，不占据产品的未完成批次身份。`--resume` 不接受新建参数；`--node` 和恢复消息只适用于当前节点，沿用公共消息准入合同。

新建时把原反馈正文、原来源路径、附件绝对路径、意图正文及可选意图来源路径保存到当前 run 的 `feedback/input.json`。原始文件和附件不改动、不移动，附件不复制。恢复使用已保存的本批正文，不因原文件后来编辑而静默改变范围；附件保持可访问，缺失时说明具体输入问题。原反馈、附件与意图原件的路径均受写入边界保护。来源 run 的状态、结果、会话与计时均只读。

输入与恢复消息会进入模型上下文及受保护运行记录。凭据继续存放在现有受保护配置中，材料只引用配置路径或键，不提供凭据隔离承诺；受跟踪反馈文档只保留脱敏事实。

## 3. 节点与产物

`workflow` 为 `product_feedback`，`phase` 为 `product_feedback_iteration`。命名节点使用 `feedback:` 前缀，不引入轮次；一次运行只处理一批。节点结果保存在 `feedback/<节点名>.json`，通用会话与计时仍使用既有位置。

| 节点 | 职责与交接 |
| --- | --- |
| `prepare` | 核验当前 clean main，按稳定 ID 承接历史完成事实和当前 Backlog 静态字段，准备本批实际需要的运行条件。 |
| `triage` | 先保存并建立根仓短期文档分支；在独立会话显式调用反馈分诊，生成唯一反馈文档及完整候选处置。代码仓保持 main。 |
| `route` | 在可恢复的独立会话中，依据本批目标、授权和完整分诊材料确定纳入范围、明确延期条件与必要文档调整；不重做全产品调查。外部授权缺失时保留原对话，补齐后通过恢复消息继续。 |
| `pool` | 必要时先局部调整产品定义或设计，再形成增量 Backlog；精确提交文档并 ff-only 合并。无纳入项只收尾实际反馈文档。 |
| `register` | 复用入池时核验的 catalog，登记新增 pending 需求，保留历史动态状态。 |
| `select_requirement` | 选择尚未完成的本批需求，复用第 13～18 步；无剩余项进入收尾。 |
| `complete` | 核对本批需求、合并版本与反馈处置，形成完成结果并推进 `feedback:completed`。 |

state 只新增必要的反馈私有上下文：开始版本、来源需求 ID 集合、本批正式需求 ID、反馈文档位置及当前节点恢复所需事实。正文、候选与完整对话不重复塞进 state。

反馈文档默认位于产品 `docs/feedback/YYYY-MM-DD-<run-id>-核验反馈.md`。文档路径与根仓分支在首次写入前确定并持久化；恢复沿用。分诊能力只写该文档，产品定义、设计、Backlog 和 Git 分别由后续显式任务负责。

## 4. 负责人、入池与开发交接

执行 Agent 负责核验、设计、实现和验证，AI 负责人依既有授权作语义决定；程序只检查当前节点必要结构、归属与确定性事实。使用既有公共决策循环保存完整对话，语义提取通过 Responses/Pydantic 完成，不解析 Markdown 标题或表格。

普通建议、已明确产品决定与外部授权需要区分。缺陷验证实际行为；改进和新增目标依据用户结果与本批意图判断，不要求先证明旧代码错误。独立的待补证、待决项可以有依据地暂不纳入；本批明确必达事项不能被静默延期后成功结束。能在原会话补齐的问题先继续处理，真正缺少不可替代外部条件时 blocked，本地错误 failed。

入池仅承接已收敛目标。需要改变权威产品定义时显式使用 `project-intake` 局部调整；其它设计工作仅覆盖真实影响。文档修改限定为当前产品相关路径，历史 TRD 和私密资源资料不进入该文档提交。完成必要设计后才调用 `requirement-breakdown`，保留既有 ID、标题、顺序、依赖和正文，新增需求追加。

候选与需求允许多对多对应，每个纳入目标有完整原场景或目标结果的承接需求。拆分需求时，最终完整回归项依赖其它必要承接项。入池时提取并校验新增 catalog，合并后登记复用同一份结果，不重跑初始化或重置历史完成状态。

第 14、15 步按活动需求交接原反馈、核验事实、采纳目标、必要决定及完整回归归属。缺陷重走原场景；改进验证采纳后的可观察结果与受影响路径。第 18 步完成后返回 `feedback:select_requirement`，数字步骤位置清空，由外层决定继续或结束。不改变现有开发验收、复盘、提交和合并职责。

## 5. Git、恢复与完成

开始现场必须清楚；未知修改不自动清理或提交。新建取得产品排他锁后，使用已有 run 的状态确认同产品没有未完成反馈批次；存在时给出原批次恢复入口，不新建运行。准备仅使用当前工程和已授权运行资源，不以核验为由修改受跟踪业务代码或配置。反馈文档、已授权设计调整和增量 Backlog 使用同一根仓短期分支，代码仓此时保持原 main。

有纳入项时，根文档收尾成功后才进入新增需求开发。无纳入项时提交实际产生的反馈处置文档，根 main 可以前进到文档合并版本，代码仓保持核验版本；不创建空需求、代码分支或空提交。

节点先写成功结果再推进状态。结果落盘后中断只补状态，已完成会话和入池不重做；分支建立、提交、快进合并或分支清理中断后根据本节点 intent 与实际 Git 事实继续。需求恢复继续使用原 session 和现有 requirement cycle，不另建独立恢复机制。

正常完成要求：全部原始反馈有归属，本批纳入目标已由正式需求实现并通过必要回归、提交和合并，无 active/pending 需求，适用仓库 clean main，最终版本匹配本批合并，未纳入项有真实处置且没有被掩盖的必达事项。完成结果区分已解决、未纳入、待补证和待决，不等待人再次确认满意。新反馈另启批次，未完成批次恢复原运行。

## 6. 公共接线与选模

- `common/requirement_context.py` 增加反馈 phase 和返回节点。
- `run_step.py` 的数字需求步骤按反馈执行身份附着产品，不走阶段一认领。
- 第 14、15 步按工作流读取相关证据；第 18 步按工作流返回选择节点。
- 模型策略新增 `feedback_prepare`、`feedback_triage`、`feedback_route`、`feedback_pool`，沿用各配置现有适用 profile，不改变既有任务的模型或 effort。提交继续使用 `requirement_commit`，领域设计复用现有任务。
- 保留阶段一、质量工作流和已启动历史模型策略快照的兼容行为；新增反馈运行必须具备所需任务配置。

## 7. 验证范围

自动化覆盖真实行为而非提示词句式：

- 新建输入、附件、来源和恢复参数错误在副作用前拒绝；恢复不重读已修改的原正文。
- 来源与产品 runtime/owner 不改写，产品锁和数字步骤附着正确。
- 无纳入但有文档、有纳入并增量登记，两条路径都能完成根仓收尾。
- 多对多关联、依赖、完整回归归属、历史 ID 保留及非法引用拒绝。
- 未授权范围外写入、文档路径冲突、代码仓漂移保留现场。
- 分支、提交、合并、成功结果到状态等中断恢复不重复入池，不覆盖外部变更。
- 必达事项缺口、真实外部阻塞与执行失败不会变成成功。
- 原反馈与采纳目标传入设计和开发，完成后返回反馈批次；阶段一和阶段二相关回归保持通过。

隔离真实通道使用明确标记的 CLI 产品 fixture，验证真实分诊、负责人决策、文档提交及一项修复经原开发链完成；来源完成状态是测试输入，不代表某个真实客户产品已通过质量审计。另验证无纳入项的文档收尾。真实结果与自动化结果分别报告，失败或未覆盖范围不以 Mock 结果替代。
